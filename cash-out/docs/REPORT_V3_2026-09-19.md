## Главное ограничение — сразу и прямо

Официальная документация Yandex Fleet API **по-прежнему недоступна из этой
сессии**: `yandex.ru`, `yandex.com` и `fleet.taxi.yandex.ru` заблокированы
egress-политикой (проверил все три ещё раз; поиск и npm-пакеты сторонних
клиентов v3 не содержат). Я не мог «изучить актуальную документацию
самостоятельно» в буквальном смысле.

Поэтому контракт v3 реализован **по вашей сводке независимой проверки**
(`park_id`, `contractor_profile_id`, `amount`, `description`, `version`,
`condition.balance_min`, `data.kind`, статусы `in_progress/success/fail`,
`X-Idempotency-Token` 16–64 printable ASCII), и в документации каждый элемент
помечен: **CONFIRMED** — подтверждено официальным текстом (через вашу сводку),
**LIVE-UNVERIFIED** — задокументировано, но не проверено на реальном парке,
**UNKNOWN** — документация ответа не даёт. «Низкого доверия» больше нет: либо
подтверждено, либо честно UNKNOWN.

## A. Что именно изменено

### 1. Yandex Fleet API — v2 → v3

- `POST /v3/parks/driver-profiles/transactions` вместо deprecated v2. Тело:
  `park_id`, `contractor_profile_id`, `amount`, `description`, `version`,
  `condition.balance_min`, `data.kind`.
- `GET /v3/parks/driver-profiles/transactions/status` — статус транзакции по
  id; `in_progress` / `success` / `fail` маппятся в `IN_PROGRESS` / `SUCCESS` /
  `FAIL`; 404 → `NOT_FOUND`; 429 / 5xx / обрыв → `UNKNOWN`.
- `category_id` **не переносится** — это поле v2; из env убран
  `YANDEX_PAYOUT_CATEGORY_ID`, добавлены `YANDEX_TRANSACTION_VERSION`,
  `YANDEX_PAYOUT_KIND` (=`payout`), `YANDEX_REVERSAL_KIND`.
- Ответ 2xx без распознаваемого id → `UNKNOWN`, никогда не «успех» и не
  «ошибка». 2xx с id, но без финального статуса → `PENDING`.
- 4xx классифицируется по ключевым словам в `condition_failed` /
  `insufficient_funds`, иначе код API пробрасывается как есть (точные коды
  ошибок v3 — UNKNOWN).

### 2. Атомарная защита баланса

- Каждое списание уходит с `condition.balance_min = gross`: Yandex сам
  атомарно откажет, если баланс к моменту POST ниже суммы списания. Сценарий
  «водитель видел 100 000, баланс изменился, а мы списали в минус» закрыт на
  стороне Yandex.
- Собственная свежая перепроверка баланса при подтверждении (`BALANCE_CHANGED`)
  сохранена как вторая линия.
- Почему `balance_min = gross`, а не «баланс на момент котировки»: инвариант,
  который стоит денег, — овердрафт; при retry после `UNKNOWN` повторная оценка
  условия против уже списанного баланса дала бы ложный отказ. Обе трактовки
  безопасны при выбранной обработке (см. п. 3).

### 3. Статус транзакции и неопределённость

- **Новое состояние `RESERVE_PENDING`**: транзакция есть, id есть, исход ещё
  нет. Выход только через status endpoint. Добавлено в контракты, Prisma-enum
  (миграция `20260920090000_reserve_pending_state`), воркер, расчёт
  зарезервированного баланса, очередь «Needs attention», чип в админке.
- Правило: **`FAILED` ставится только если** Yandex отказал на самом первом
  POST **или** вернул `fail` по id, который сам выдал. Всё остальное, что не
  `success`, ждёт или уходит человеку.
- Отказ после попытки с исходом `UNKNOWN` → `MANUAL_REVIEW` с пометкой «a
  rejected replay does not prove the original was not applied».
- `NOT_FOUND` по id, который Yandex сам выдал, → `MANUAL_REVIEW`
  (противоречие, не «не применено»).
- Восстановление, если POST оборвался до получения id (`RESERVE_UNCERTAIN`):
  1. список транзакций парка по референсу — попадание даёт id → `RESERVE_PENDING`;
     промах ничего не доказывает; 2) повтор POST с **тем же** токеном —
     по контракту возвращает исходную транзакцию; 3) после 5 попыток — человек.
- Компенсирующий кредит — своя v3-транзакция со своим id (`yandexReversalTransactionId`,
  новая колонка); `in_progress` кредита отслеживается по id, а не
  переотправляется; кредит **никогда не бросается** — только `REVERSED` или
  `MANUAL_REVIEW`.
- SLA для `in_progress` считается от `slaDeadline`, поставленного внедрёнными
  часами, а не от `updatedAt` БД (та же ошибка двух источников времени, что
  раньше была в OTP; поймал тест).

### 4. Идемпотентность

- `assertIdempotencyToken`: 16–64 printable ASCII (`/^[\x20-\x7E]{16,64}$/`),
  проверяется в адаптере **до** отправки — запрос с невалидным токеном
  невозможно повторить, и это превратило бы каждый retry в новую транзакцию.
- Наши токены: списание — 32 hex-символа, кредит — те же + `-rev` (36).
  Есть тест, что реально сгенерированные токены соответствуют правилу.
- Mock v3 моделирует контракт: повтор токена возвращает исходную транзакцию
  в её текущем состоянии и **не** переоценивает `condition`; `balance_min`
  атомарен; режимы `in_progress`, `in_progress_then_fail`, `pending_but_timeout`,
  `applied_but_timeout`, `status_unavailable`, `unavailable`, `reject`.

## E. Что нельзя проверить без реального парка Yandex

1. Что повтор `X-Idempotency-Token` возвращает исходную транзакцию, а не
   создаёт вторую. **На этом держится восстановление после timeout.**
2. Что повтор не переоценивает `condition.balance_min` (обработано так, что
   любой ответ безопасен, но поведение должно быть подтверждено).
3. Точные имена полей ответа POST (`id` / `transaction_id` / `transaction.id`,
   есть ли `status`, есть ли `balance_after`).
4. Имя query-параметра и поля статуса у `GET …/transactions/status`.
5. Значение `version`, которое требует текущая схема.
6. Правильный `data.kind` для списания стороннего сервиса выплат и для его
   отмены; несёт ли направление знак `amount` или `kind`.
7. Коды ошибок: невыполненное `condition`, недостаточный баланс, неизвестный /
   заблокированный исполнитель, превышение лимита частоты.
8. Лимиты частоты запросов.
9. Что `X-Park-ID` нужен/принимается на v3.
10. Работоспособность чтения профиля/баланса (`/v1/parks/driver-profiles/list`)
    и списка транзакций (`/v2/…/transactions/list`) — они не входили в сводку.

## F. Что не является production-ready

- **Yandex live-адаптер** — написан по сводке контракта, ни разу не говорил с
  реальным парком. `YANDEX_MODE=live` запрещён в production конфиг-валидатором
  до проверки по списку E.
- **Yandex mock** — заглушка. Зелёные тесты на mock доказывают логику
  оркестратора, а не интеграцию.
- **Платёжный провайдер** — только порт и mock; живого адаптера нет,
  `PROVIDER_MODE=live` падает при старте.
- **SMS** — консольный шлюз.
- **Ввод карты, push-уведомления, юридические документы** — не реализованы.
- **Лимитер частоты** — in-memory, один инстанс.
- **Ротация ключей** — формат готов, задание на перешифровку не написано.

Ни один из этих пунктов не выдаётся за рабочий: плитки интеграций в админке
показывают `MOCK`, API предупреждает при старте, production-конфиг с
заглушками не стартует.
