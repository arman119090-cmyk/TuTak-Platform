# Code-level threat review — 20 September 2026

A reading of the code against a list of threats, not a penetration test:
nobody attacked a running system, no tooling was pointed at it, and nothing
here is a certificate. Each row says what the code does, whether that holds
up, and what changed as a result. Findings that could be fixed in code were
fixed in this pass (SR-1, SR-2) with regression tests in
`apps/api/test/integration/security-review.spec.ts`.

| Threat                       | What the code does                                                                                                                                                                                                                                                                            | Verdict                                                                                                |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Stolen (unlocked) device     | Access token 15 min, session checked on every request, refresh rotates with family revocation; every payout needs the PIN or a biometric-released device secret; "sign out everywhere" revokes all sessions at once.                                                                          | Holds. Money needs the PIN.                                                                            |
| Rooted / jailbroken device   | Tokens and the biometric secret live in the platform keystore. On a compromised OS the keystore can be read: biometrics then degrade to "possession of the secret", not "the face matched". PIN still required otherwise.                                                                     | **Assumption, documented.** No root detection; a hardware-attested signature is the fix (SECURITY.md). |
| Replay of a confirm          | Idempotency key per driver bound to a request hash; the quote is single-use (`consumedAt` set in the same transaction); the authorization token is single-use and bound to the quote; one live withdrawal per driver at the database level.                                                   | Holds.                                                                                                 |
| OTP brute force              | Six digits from a CSPRNG, scrypt-hashed; five attempts per challenge, then consumed; challenge bound to the requesting device; per-phone and per-IP send limits; cooldown between sends. Limits now live in Redis across instances.                                                           | Holds.                                                                                                 |
| PIN brute force              | scrypt hash; server-side lockout after five failures with a growing duration; 20 authorizations per driver per 10 min; failures audited and counted for the `pin_failure_rate_high` alert.                                                                                                    | Holds.                                                                                                 |
| Session theft                | Bearer JWT over TLS only (CORS restricted, no cookies for drivers); session row consulted on every request so revocation is immediate; admin sessions are opaque, hashed, TTL-bound, revoked on status change.                                                                                | Holds. TLS termination is the deployment's job.                                                        |
| Refresh-token reuse          | A rotated token presented again revokes the whole family and logs it; a token from another device id revokes the family too. Device id is client-supplied and stored beside the token, so a thief with both still has one refresh until detection.                                            | Holds, with the noted limit.                                                                           |
| IDOR                         | Every driver-facing read and write scopes by the token's `driverId`: withdrawals, timeline, history, payout methods, iDram account, auto-payout rule, Driver ID requests, park activation (membership must belong to the driver), notification preferences. Admin reads are role-gated.       | Holds (reviewed each service).                                                                         |
| Admin privilege escalation   | Fail-closed guard: no permission declared → refused; roles map to fixed permissions; there is **no API to create admins or change roles** — only the seed script with `ADMIN_BOOTSTRAP_*`. TOTP mandatory for every role that can act.                                                        | Holds. Escalation needs database access.                                                               |
| TOTP replay                  | **Was:** any code within ±1 step accepted any number of times for ~90 s — a code seen over the shoulder opened a second session. **Now:** the accepted step is stored (`lastTotpStep`) and a code for that step or earlier is refused and counted as a failure.                               | **SR-2, fixed.**                                                                                       |
| Webhook replay               | HMAC over the raw body, freshness window (`WEBHOOK_MAX_SKEW_SECONDS`), `(provider, externalId)` unique so a redelivery is a recorded no-op, state-aware application. Live iDram scheme still to map.                                                                                          | Holds for the mock scheme.                                                                             |
| Payout duplication           | Partial unique index: one non-terminal withdrawal per driver; advisory lock per driver; stable idempotency keys towards Yandex and the rail across retries; auto-payout slot key.                                                                                                             | Holds.                                                                                                 |
| Race conditions              | Serialisable transactions, optimistic version guard on every state change, lease per withdrawal, conditional updates in the key-rotation job.                                                                                                                                                 | Holds.                                                                                                 |
| Manipulated mobile client    | The server never trusts the client for money: amount and fees come from the signed quote; balance re-read fresh at confirm; eligibility, park and driver status re-checked at confirm; limits and risk evaluated server-side.                                                                 | Holds.                                                                                                 |
| Modified amount              | Quote HMAC covers id, driver, method, currency, gross, fees, net, balance, fee schedule, expiry — and now the park. Any change → `QUOTE_MISMATCH`.                                                                                                                                            | Holds.                                                                                                 |
| Modified park id             | **Was:** a quote did not record its park; a driver could quote under park A (its balance, its fee schedule) and confirm after switching to park B. **Now:** the quote stores and signs `parkId`; confirm refuses a quote from another park.                                                   | **SR-1, fixed.**                                                                                       |
| Modified Driver ID           | The driver can only _request_ a change; the Fleet API is consulted; an operator decides; approval refused while a payout is in flight; the roster row, not the client, carries the id used for money.                                                                                         | Holds.                                                                                                 |
| Compromised operator account | TOTP mandatory; sessions expire and are revoked on deactivation; every action audited with actor, reason, before/after; manual review needs a reason, completion needs provider evidence; adjustments are balanced ledger entries. **No four-eyes rule** on adjustments or manual resolution. | Holds; four-eyes recommended (below).                                                                  |

## Changes made in this review

- **SR-1** `Quote.parkId` (migration `20260920181000_quote_park`), signed in
  the canonical form, checked at confirm.
- **SR-2** `AdminUser.lastTotpStep` (migration `20260920180000_admin_totp_single_use`),
  `matchTotpStep` returns the step, sign-in refuses a reused step.

## Recommended, not done

- Four-eyes approval for ledger adjustments and manual-review completion
  above a threshold.
- Root / jailbreak signal from the app (e.g. `expo-device` + a
  server-side flag), used to require the PIN even when biometrics are on.
- Hardware-attested biometric signature (native key pair) — the honest fix for
  the rooted-device assumption.
- An admin-management API with its own audit trail, instead of the seed
  script, once there is more than one operator.
- A penetration test by a third party before real money moves.
