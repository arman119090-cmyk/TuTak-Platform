# ЗАДАЧА 1 — правка закреплена

## 1.1 Что изменено

`collapsable={false}` на внутренней обёртке `TextField` (та коробка, что рисует
рамку и кольцо фокуса) — **постоянно**, без условий: не зависит ни от
диагностической сборки, ни от какого-либо переключателя.

```tsx
<View
  ref={field}
  collapsable={false}
  style={[styles.field, …]}
>
```

Сохранено без изменений: подсветка фокуса (цвет рамки, фон, кольцо),
`onFocus`/`onBlur` экрана, ввод, разметка, префикс, текст ошибки и подсказки.

**Не добавлено ничего из запрещённого:** ни повторного `focus`, ни таймеров, ни
принудительного открытия IME. Это закреплено тестом (см. 1.3).

## 1.2 Ветвь CF убрана

Кнопки `CF` в панели больше нет, и арм удалён из `experiment.ts`. Причина: раз
свойство постоянное, переключатель ничего не переключает — а мёртвый тумблер
хуже отсутствующего, потому что следующий, кто его нажмёт, прочитает «ничего не
изменилось» как результат опыта.

Заголовок панели теперь: `SCF=off RR=on`.

**Инструментация сохранена** — именно она и нужна для проверки на телефонах:

- `tags <поле> w=… f=… i=…` — фактические нативные теги внешней обёртки,
  коробки поля и самого ввода;
- `shape <поле> #… ReactViewGroup parent=… kids=2` — сколько детей у коробки
  **в нативном дереве**. При работающей правке должно быть `kids=2`
  (для поля без префикса — `kids=1`). `kids=0` означало бы, что свойство
  перестало доезжать.

Также сохранены: журнал, нативная трассировка фокуса (`nfocus`/`ndetach` с
`ev/lag/u/w`), экспорт `TXT`/`TAIL50`/`TEXT` с маркером `END records=`,
и ветви `SCF` (off) и `RR` (on) — их значения по умолчанию не тронуты.

## 1.3 Что закреплено тестами

Добавлено 5 проверок (`TextField.focus.test.tsx`), из них новые:

| проверка | что ломается, если её нет |
| --- | --- |
| `collapsable === false` **в обычной сборке**, где `extra: {}` и диагностики нет | правка, работающая только там, где за ней наблюдают, — не правка |
| `collapsable === false` на поле с префиксом, с ошибкой и с `secureTextEntry` | правка, теряющаяся на одной из форм поля |
| рамка меняет цвет по фокусу **и** `onChangeText` вызывается | подсветка или ввод, потерянные при рефакторинге |
| `onFocus` и `onBlur` экрана вызываются ровно по разу | обработчики, потерянные при рефакторинге |
| `focus()` на вводе не вызывается **ни разу**, и таймеров не больше одного | повторный focus / таймер / принудительный IME — то есть запрещённые «починки», которые скрыли бы следующий сбой |

Последняя проверка написана как фиксация **отсутствия**: она падает, если
кто-нибудь когда-нибудь добавит повторный вызов фокуса или таймер.

## 1.5 Что это доказывает — и чего не доказывает

**Доказано механизмом и устройством.** В сборке 41 (`d3537af`, прогоны `SS06VF`
и `0HX8CM`) при `CF=on` отсоединений при смене фокуса нет, ввод телефона и
пароля работает; при `CF=off` отсоединения и переброс фокуса возвращаются;
повторное `CF=on` снова устраняет сбой. Применение подтверждено нативными
`shape`-записями, а не тем, что «сбой не воспроизвёлся».

**Не доказано: что виноват именно `shadowColor`.** `collapsable={false}`
закрепляет весь признак `FormsStackingContext`, а в него входят также
`elevation`, `opacity`, `transform`, `zIndex` и флаги обработчиков событий.
Установлено, **что** ломало — переход узла между «плоским» и «стековым»
состоянием, из-за которого Fabric переносил сфокусированный `ReactEditText`
между родителями. **Какое именно свойство** этот переход вызывало — не
установлено, и для ответа нужен ещё один опыт, от которого сейчас ничего не
зависит. Это записано в комментарии прямо в коде, в том месте, где иначе сделали
бы более сильный вывод.

## 1.6 Что нужно до закрытия дефекта

Проверить **постоянную** правку на обоих аппаратах — Samsung и Xiaomi, — по трём
экранам:

1. вход по паролю (Login: телефон и Password);
2. вход по коду (OtpLogin: телефон, затем шестизначный код);
3. регистрация (OtpRegister).

На каждом экране: коснуться поля, набрать значение целиком, убедиться, что
клавиатура не закрывается и фокус не перескакивает.

Дополнительно, по журналу (кнопка `TXT` → отправить файл):

- в строках `shape` должно стоять `kids=1` или `kids=2`, но **не** `kids=0`;
- между `focus <поле>` и следующим `blur <поле>` **не должно быть**
  `ndetach ReactEditText#<тот же тег>`;
- вверху журнала — `trace native-focus armed focus=1`, иначе проверка
  недействительна;
- внизу — `END records=<число>`, иначе текст обрезан при пересылке.

Дефект закрывается только после этого. Диагностика в сборке специально
оставлена ради этой проверки.

# ЗАДАЧА 2 — недоставка SMS: точка отказа

Разбор выполнен и отдан отдельным отчётом:
**`docs/STAGING_SMS_FAILURE_POINT_2026-09-09_RU.md`**. Перепроверено повторно
на 15:10 UTC 9 сентября: с 14:30:46 UTC ничего не изменилось, конфигурацию не
правили, новых деплоев нет. Ниже — суть.

## 2.1 Точка отказа

**Вызова отправки не было вообще.** На staging активен `UnavailableSmsProvider`
— класс, который отклоняет каждую отправку. Отказ происходит **в приложении, до
всякой сети**.

## 2.2 По пунктам задания

| вопрос | ответ | доказательство |
| --- | --- | --- |
| Дошёл ли запрос до API | **да** | `POST /v1/auth/register/request-otp`, requestId `64d58fb7…`, 14:30:46 UTC; сегодня всего четыре такие попытки |
| Вызван ли SMS-провайдер | **нет** | `[SMS] Refusing to send SMS: no carrier is configured for this deployment` — это `UnavailableSmsProvider` |
| Заглушка ли это | **нет** | `ConsoleSmsProvider`, который пишет код в журнал, недостижим на публичном развёртывании ни при каком значении `DEMO_MODE` |
| Вызван ли Viva, ответ, message id | **не вызывался** | ни одной строки от `VivaSmsProvider` за 8–9 сентября; ответа и `providerMessageId` не существует |
| Почему вызова не было | **конфигурация** | `SMS_ENDPOINT` пуст и `SMS_DRIVER` ≠ `viva` — единственные условия, при которых `selectSmsTransport` возвращает этот провайдер |
| Состояние аккаунта Viva | исключено | до Viva дело не дошло |
| Ограничение запросов | исключено | нет ни `Too many codes requested`, ни исчерпания глобального бюджета |
| VPN/шлюз Viva | **не установлено, и не могло быть** | обращения не было; проверять нужно **с исходящего адреса Render**, а не отсюда — порядок из трёх шагов в отдельном отчёте, раздел 5 |

## 2.3 Почему экран OTP не является подтверждением отправки

По коду `AuthOtpService.requestCode` ошибка отправки **проглатывается**
(`.catch(err => this.logger.error(…))`), и метод возвращает `success: true`
в любом случае. Приложение получает успех и переключает экран. Код при этом уже
записан в базу — то есть там лежат живые, никем не полученные коды.

## 2.4 Побочно: журнал сейчас вводит в заблуждение

При каждом старте печатается баннер `SMS codes are written to this log, not
delivered.` Для текущего кода это **неправда** — код в журнал не пишется. Тот,
кто пойдёт искать код в журнале по этой подсказке, потратит время впустую.
Правка на одну строку; в этой задаче я её не делал, потому что задание было на
установление точки отказа, а не на изменение поведения.
