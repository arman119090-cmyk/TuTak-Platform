## 1. Что доказано этим логом

### 1.1. JavaScript фокус не двигает — доказано отсутствием `REQ`

Каждый `REQ focus …` в логе стоит **после** `touch` того же поля, с задержкой
120–170 мс — это штатная задержка `Pressability` в React Native:

```
 8283ms  touch phone
 8404ms  REQ focus phone      ← +121 мс, обычный тап
10173ms  touch password
10318ms  REQ focus password   ← +145 мс, обычный тап
```

Все семь `REQ` в логе — такие. **Ни одного запроса фокуса без касания.**

А вот сами аномальные переходы `REQ`-строк не имеют вообще:

```
10319ms  blur  phone t=14914
10319ms  focus password kbd=default t=14924   ← запрошен (REQ выше)
10343ms  blur  password t=14924
10343ms  focus phone kbd=number-pad t=14914   ← НИКТО не запрашивал
10365ms  blur  phone t=14914
10365ms  focus password kbd=default t=14924   ← НИКТО не запрашивал
10365ms  blur  password t=14924
10365ms  focus phone kbd=number-pad t=14914   ← НИКТО не запрашивал
```

Это **вариант B** из постановки: фокус переводит native-сторона, а React
Native только сообщает о результате.

Инструмент устроен так, что это утверждение имеет вес: перехвачены **только
команды** (`focusTextInput`/`blurTextInput`, через которые проходит любой
`ref.focus()`), а не учёт (`focusInput`, вызываемый из `onFocus`). Молчание
`REQ` — это молчание команд, а не пробел в записи.

### 1.2. Ничего не пересоздаётся — доказано постоянством native-тегов

Через весь лог: `phone t=14914`, `password t=14924`. **Оба тега неизменны.**
Значит native-view не заменялись. Плюс за всё время сбоя нет ни одной строки
`mount`, `unmount`, `win`, `scr`, `appState`.

Отпадает: remount React-компонента, пересоздание Activity, перезапуск RN
surface, замена native-view, изменение размеров окна.

### 1.3. Рисунок сбоя строго детерминирован

Каждый эпизод — **ровно четыре чередующихся перехода, всегда заканчивающихся
на `phone`**, и только потом открывается клавиатура:

```
focus password → focus phone → focus password → focus phone → kbShow on=phone
```

И это не зависит от того, куда нажали. Тапнули по `phone` — тот же рисунок.
Тапнули по `password` — тот же рисунок, и он всё равно завершается на `phone`.

Регулярность важна: случайная гонка или петля layout так себя не ведут. Это
похоже на детерминированный обход фокусируемых элементов.

### 1.4. Настоящий симптом хуже, чем «клавиатура закрывается»

**В поле «Пароль» невозможно попасть.** Нажатие по нему заканчивается фокусом
на «Номер телефона» и цифровой клавиатурой. Форма входа неработоспособна.

Двойной `kbShow` с разной высотой подтверждает, что IME успевает
переключиться:

```
10377ms  kbShow h=332 on=phone   ← клавиатура одной раскладки
10388ms  kbShow h=303 on=phone   ← и сразу другой
```

## 3b. Механизм «почему всегда возвращается в первое поле»

Это половина ответа, и она найдена в исходниках, а не предположена.

Форма лежит в `ScrollView`. У Android `ScrollView` есть
`onRequestFocusInDescendants`:

```java
protected boolean onRequestFocusInDescendants(int direction, Rect previouslyFocusedRect) {
    ...
    final View nextFocus = previouslyFocusedRect == null
        ? FocusFinder.getInstance().findNextFocus(this, null, direction)   // ← первый подходящий
        : FocusFinder.getInstance().findNextFocusFromRect(this, previouslyFocusedRect, direction);
    ...
    return nextFocus.requestFocus(direction, previouslyFocusedRect);
}
```

С `previouslyFocusedRect == null` это отдаёт фокус **первому фокусируемому
потомку сверху** — то есть полю «Номер телефона». Ровно то, что в журнале:
чем бы ни начали, заканчивается на `phone`.

React Native про это знает. В `ReactEditText.clearFocusAndMaybeRefocus`
(RN 0.86.2) стоит комментарий: *«preventing `requestFocus()` on the rootView
from moving focus to any child»* — и защита включается только на Android 9 и
ниже:

```kotlin
internal fun clearFocusAndMaybeRefocus() {
    if (Build.VERSION.SDK_INT > Build.VERSION_CODES.P || !isInTouchMode) {
      super.clearFocus()          // Android 10+: защиты нет
    } else { /* блокируем потомков */ }
    hideSoftKeyboard()
}
```

Значит на Android 10+ любое снятие фокуса с поля позволяет корню назначить
фокус заново, и назначает он его первому полю. Это не про вендора и не про
складной экран — это про Android и `ScrollView`, одинаково на Xiaomi и на
Samsung.

**Чего всё ещё нет:** что именно снимает фокус в первый раз. Команд из JS
нет (доказано отсутствием `REQ`), значит снимает native.

## 3c. Исправление-кандидат: `elevation` убран из фокусной рамки

Из всего, что `TextField` менял при получении фокуса, **`elevation` —
единственное, что не является просто рисованием**. На Android это Z-координата
view; при её изменении родительский `ViewGroup` перестраивает упорядоченный
список детей, и фокусируемый ребёнок пересматривается в ходе этого. Остальное
в рамке — цвет границы и фон — только рисуется.

Ритм в журнале это поддерживает: между переходами 20–25 мс, то есть один-два
кадра, а не мгновенный native-поиск.

```diff
   ring: {
     shadowOpacity: 0.25,
     shadowRadius: 12,
     shadowOffset: { width: 0, height: 0 },
-    elevation: 6,
   },
```

**Что теряется:** тень под сфокусированным полем на Android. Граница и заливка
по-прежнему меняются, поле по-прежнему читается как активное. На iOS
`shadow*` работают без `elevation`, там ничего не меняется — и там сбой ни
разу не воспроизводился.

**Это кандидат, а не доказанная причина.** Наименьшее изменение, способное
дать наблюдаемое поведение. Проверяется только на двух телефонах, которые
воспроизводят сбой, — здесь проверить нечем.

Regression-тесты: `TextField.focus.test.tsx` — сфокусированное поле не несёт
`elevation` (в том числе с ошибкой), и при этом граница всё ещё меняется,
чтобы «исправление» не убрало саму индикацию фокуса. Проверено мутацией:
с возвращённым `elevation: 6` два теста падают.
