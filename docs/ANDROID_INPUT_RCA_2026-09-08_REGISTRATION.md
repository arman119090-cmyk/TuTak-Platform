Что из этого следует и что не следует:

* **Смена типа клавиатуры не доказывает переход native focus.** На этом

  фокуса на `phone`, но так же совместима с тем, что тому же самому полю
  переприменили props, и с тем, что клавиатура сама сменила раскладку.
* **Закрытие клавиатуры не доказывает blur.** Система закрывает IME и при
  сохранённом фокусе.
* **Рамка у поля** — это состояние React (`focused` в `TextField`), а не
  доказательство native focus: `onFocus` от RN приходит и в случаях, которые
  native-фокусом не заканчиваются.

Ни одно из трёх не различается по видео в принципе. Различается по журналу —
для этого и сделана сборка.

## 3. Что из расследования Login применимо к регистрации

Экран на видео — `OtpRegisterScreen.tsx` (подтверждено:
`AuthNavigator.tsx:27` монтирует именно его; `RegisterScreen.tsx` в
навигаторе отсутствует и ссылок на него нет).

| Вывод сентябрьского RCA | Применим ли к регистрации | Почему |
|---|---|---|
| **A** — касание не доходит до поля: исключён | Да | Тот же довод: клавиатура появляется, а Android открывает её только для получившего фокус native-поля |
| **H** — касание перехватывает родитель: исключён | Да | То же наблюдение. Оговорка прежнего отчёта в силе: это не исключает влияния **после** получения фокуса |
| **B** — JS снимает фокус | Да, перепроверено на сегодняшнем коде | `Keyboard.dismiss`, `.blur()`, `.focus()`, `autoFocus`, `blurOnSubmit` — ноль совпадений во всём `apps/mobile/src` |
| **G** — навигация меняет экран | Да, перепроверено | `navigation.reset`, `addListener('focus')`, `useFocusEffect`, `useIsFocused` — ноль совпадений |
| **C/D** — remount по смене `key` | Да, перепроверено | `key={` в `screens/auth/` и `app/navigation/` — ноль совпадений |
| `TextField`, `KeyboardAwareScroll`, `useCompactLayout` разобраны и признаны безопасными | Да | Это те же самые файлы; регистрация использует их без изменений |
| **E/F** — пересоздание Activity / система закрывает IME | Да, остаются открытыми | Ничем не закрыты |

**Что на регистрации есть, а на Login не было** — и потому требует отдельной
проверки:

1. **Два поля с разными клавиатурами.** `phone` — `number-pad`, `referral` —
   алфавитная. На Login такой пары нет, и вопрос «какому полю принадлежит
   клавиатура» там не возникал.
2. **Условная ветка `codeSent`.** До отправки кода рендерятся `phone` +
   `referral`, после — поле `otp`. React согласует первый `TextField` одной
   ветки с первым `TextField` другой. На видео этот переход не происходит (кода
   никто не отправлял), но в журнале это будет видно однозначно — по
   идентификатору экземпляра.
3. **`error` привязан только к `referral`.** Появление ошибки меняет стили и
   добавляет строку под полем; ремаунта `TextInput` это не даёт (позиция в
   дереве та же), но это отличие от Login, и оно тоже теперь попадает в
   журнал через инстансы.

| Событие | Строка в журнале | Что различает |
|---|---|---|
| Запуск JS-контекста | `run ABC123` в заголовке панели и экспорта | новый id = новый JS-runtime (перезапуск процесса, перезагрузка бандла) |
| Монтирование корня | `mount App #n @id` | `#2` при том же `run` = перезапуск RN surface (кандидат на пересоздание Activity) |

| Экземпляры полей | `mount field:phone #n @id`, `unmount field:phone @id` | замена поля отличается от его повторного рендера: у нового экземпляра другой `@id` |
| Фокус/блюр по полям | `focus phone kbd=number-pad`, `blur  phone`, `focus referral kbd=default` | какое именно поле и какую клавиатуру оно просит — независимо от языка интерфейса |
| Клавиатура | `kbShow h=… on=phone kbd=number-pad`, `kbHide on=…` | было ли `blur` перед закрытием — и **какому полю принадлежала клавиатура** |
| Фокус по версии RN | часть строк `kbShow`/`kbHide`: `on=<поле> kbd=<тип>`, `on=none of=2`, `on=phone+referral kbd=multiple` | какой input считает себя сфокусированным в момент появления и исчезновения клавиатуры |
| Окно и экран | `win WxH scr WxH` | уменьшается ли окно под IME |
| Состояние приложения | `appState active/inactive/background` | пересоздаваемая Activity не остаётся `active` всё это время |

### Как определяется «сфокусированное поле» — и чем это не является

Строки `kbShow`/`kbHide` несут ответ на вопрос «какому полю принадлежит эта
клавиатура». Ответ берётся так: каждое поле регистрирует свой живой handle
`TextInput`, и в момент события клавиатуры у каждого спрашивается
`isFocused()` — **собственный учёт React Native**, который ведётся по
native-колбэкам focus/blur.

Три вещи, которые надо держать раздельно:

1. **Рамка на экране — не доказательство фокуса.** Она рисуется из состояния
   React в `TextField`, то есть из мнения приложения о полученном событии.
   По видео и по фотографии читается именно она, и именно её читать нельзя.
2. **`isFocused()` — не запрос к Android.** Ни один публичный API React
   Native не отвечает на вопрос «какая native-view держит фокус сейчас». Это
   запись RN о тех событиях фокуса, о которых ему сообщили. Если Android
   переводит фокус, не уведомляя мост, здесь будет устаревший ответ.
3. **Именно поэтому расхождение и есть улика.** `kbShow … on=none of=2` —
   клавиатура на экране, а ни один input не считает себя сфокусированным —
   это находка, а не пробел в данных. `on=phone+referral kbd=multiple` —
   тоже.

Спрашиваются все зарегистрированные поля, а не первое ответившее: два поля,
одновременно считающие себя сфокусированными, стоят больше, чем любой из двух
ответов по отдельности.

### Что показали независимые тесты Симона и что они не показывают

Симон на базе `f63b34f`, не меняя код приложения, показал двумя
React-тестами: экземпляры обоих полей и их `keyboardType` **не меняются** при
focus/blur, вводе, очистке и изменении высоты клавиатуры.

Это закрывает JS-сторону вопроса «не подменяется ли поле само собой» и
согласуется с тем, что видно отсюда при чтении кода. Это **не** проверяет
native-фокус Android и **не** закрывает сценарии E (пересоздание
Activity / перезапуск RN surface) и F (система закрывает IME при сохранённом
фокусе) — у Jest нет IME и нет окна.

Практический вывод для этого раунда: раз JS-сторона устойчива, ценность
журнала смещается ровно туда, куда Симон и указал — на то, что говорит RN о
фокусе в моменты появления и исчезновения клавиатуры, и на счётчики
mount/run. Обе части в сборке есть.

### Поправка к прошлому раунду

Прошлый отчёт читал второй `mount Login` как пересоздание Activity. **Это
чтение сильнее данных.** Повторную строку `mount` дают три разные вещи:
remount React-компонента, перезапуск RN surface при сохранившемся JS-контексте
и новый JS-контекст. Раньше журнал их не различал; теперь различает — тремя
счётчиками, описанными выше. Формально: `mount X #2` сам по себе **не**
является доказательством перезапуска Activity.

### Чего диагностика не делает

* не меняет фокус, `keyboardType`, `softwareKeyboardLayoutMode`, ориентацию,
  `configChanges` и манифест — этот раунд про доказательство, и правка
  поведения сейчас сделала бы журнал описанием чего-то другого;
* не мешает касаниям: панель прозрачна для касаний вне себя
  (`pointerEvents="box-none"`), стоит внизу и не перекрывает поля;
* не очищается при переходе между экранами — только кнопкой CLEAR (есть тест);
* не записывает ничего введённого: только идентификаторы полей, размеры,
  счётчики и факт монтирования (есть тест, проверяющий, что номер и
  referral-код в журнал не попадают).

Диагностика включается только профилем `diagnostic`
(`extra.diagnostics === true`); `app.config.js` отказывается собрать
`DIAGNOSTICS=1` вместе с `APP_ENV=production`.

### Как проверено, что диагностика в сборке включена

Не «профиль называется diagnostic», а прочитанный конфиг — тем же способом,
которым его читает сборщик:

```
$ DIAGNOSTICS=1 APP_ENV=preview API_BASE_URL=… npx expo config --type public --json
name         TuTak (preview)
diagnostics  True          ← это и включает оверлей (isDiagnosticBuild)
appEnv       preview
package      am.tutak.app
orientation  portrait
softKbdMode  None          ← не задан; этой задачей не трогался
```

Ворота проверены в обе стороны:

* обычный `preview` **без** `DIAGNOSTICS` → `diagnostics: False` (оверлея нет
  ни в одной обычной сборке);
* `DIAGNOSTICS=1` вместе с `APP_ENV=production` → сборка **падает** с
  «DIAGNOSTICS=1 with APP_ENV=production» и APK не производит.

На устройстве APK не проверялся: он собран, но ни на телефоне, ни на
эмуляторе здесь не запускался. Первое, что подтвердит корректность сборки, —
чёрная панель с коротким SHA и run id внизу экрана.

## 7. Что нужно с телефона

### Установка

APK ставится **поверх существующего приложения** — package id `am.tutak.app`
во всех окружениях, подпись одна и та же (ключ хранится в EAS). Обновление,
не переустановка: данные приложения сохраняются.

Удалять приложение или чистить его данные **не нужно**. Если это всё же
понадобится — учтите последствия: удаление стирает сохранённую сессию, и
вход придётся выполнять заново, то есть снова через SMS-код.

Приложение будет называться **TuTak (preview)** и говорит с
`https://tutak-staging-api.onrender.com/v1` (staging, не production).

### Сбор журнала — четыре шага

1. Открыть приложение → «Создать аккаунт» (экран **Create your account**,
   поля Phone number и Referral code).
2. Нажать **CLEAR** в чёрной панели внизу — чтобы в журнале осталось одно
   взаимодействие.
3. Воспроизвести сбой ровно так, как на видео: нажать на поле, дождаться
   мигания клавиатуры. Повторить 2–3 раза, **не нажимая CLEAR между
   попытками** — три одинаковые последовательности подряд стоят больше, чем
   одна.
4. Нажать **EXPORT** и отправить журнал любым способом (Telegram, почта,
   заметки — открывается системное меню «Поделиться»).

Полезно, если несложно: сделать то же самое дважды — сначала нажав на
**Phone number**, потом на **Referral code**. Какое из двух полей ведёт себя
иначе — это уже половина ответа.

Если EXPORT почему-то не срабатывает — сфотографируйте панель; в её заголовке
есть и commit, и run id.

### Сведения о телефоне (без них журнал читается наполовину)

* модель (точно: Galaxy Z Fold какого поколения);
* версия Android и One UI;
* название клавиатуры (Samsung Keyboard, Gboard, другая);
* **сложен или раскрыт** в момент сбоя;
* ориентация (портрет/ландшафт);
* включён ли режим совместимости для приложения и в каком положении окна;
* тот же ли это телефон и то же ли состояние, что на прошлом видео.

Отдельно ценно: **повторить то же самое на сложенном телефоне**. Если журнал
там выглядит иначе, это само по себе указывает на режим совместимости
раскрытого экрана.

```
focus referral kbd=default
kbShow h=… on=referral kbd=default
kbHide     on=referral kbd=default     без blur, без mount, win не менялся
                                       → IME закрыла система, фокус остался (F)

focus referral kbd=default
kbShow h=… on=referral kbd=default
kbShow h=… on=phone    kbd=number-pad  → клавиатура сменила тип потому, что
                                         фокус ушёл на phone; смотреть, что
                                         произошло между этими строками

kbShow h=… on=none of=2                → клавиатура на экране, RN не знает ни
                                         одного сфокусированного поля;
                                         фокусом распоряжается не приложение

focus referral / kbShow / mount App #2 при том же run id
                                       → перезапуск RN surface (E)

unmount field:referral @2 / mount field:referral #2 @7
                                       → поле заменено; причина в JS, и она
                                         видна по тому, что произошло рядом

другой run id между двумя попытками    → JS-контекст перезапускался
```
