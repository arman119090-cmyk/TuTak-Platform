## 1. Главное: формулировка дефекта была неверной, и её исправили

Журнал со сборки 32 на экране «Вход по коду» (`run Z2NGK5`, `OtpLogin`,
**одно поле**):

```
kbHide on=none of=1          ← of=1: зарегистрировано ровно одно поле
…
17131ms  REQ focus Номер телефона
17131ms  focus Номер телефона
17163ms  blur  Номер телефона t=2328     ← через 32 мс, без REQ blur
```

Мигрировать было **некуда**. Значит дефект не «фокус мигрирует между двумя
полями», а:

> **Сфокусированное поле теряет фокус примерно через 30 мс после того, как
> его получило. Команды из JS при этом нет.**

| Было | Стало |
|---|---|
| «Фокус мигрирует между двумя полями и садится на первое» | **«Сфокусированное поле теряет фокус через ~30 мс»** |

Миграция — **следствие**:

* одно поле → фокус снят, возвращать некому → клавиатура закрывается;
* два поля → фокус снят, `ViewRootImpl` отдаёт его следующему фокусируемому,
  тот теряет так же, и так до затухания — это и выглядело как «пинг-понг,
  заканчивающийся на первом поле».

Одна причина, два внешних проявления. Прежние наблюдения этому не
противоречат — они описывали двухпольный случай.

## 2. Что это значит для кандидата `scrollsChildToFocus={false}`

**Не отменяется.** Путь `ReactScrollView.requestChildFocus` →
`scrollToChild(focused)` привязан к получению фокуса, а не к числу полей, и
срабатывает при одном поле точно так же.

Более того, экран «Вход по коду» теперь — **лучшее место для проверки любого
кандидата**: одно поле, нет второго, которое мутит картину.

## 3. Решающий сигнал в сборке 35

Записывается каждая прокрутка:

```
scroll y=<смещение>
```

| Что в журнале | Что из этого следует |
|---|---|
| `focus` → **`scroll y=…`** → `blur` | прокрутка попала в окно между получением и потерей фокуса. **Корреляция, не причина** |
| `focus` → `blur` **без** `scroll` | **не исключает ничего** — см. ниже |

**Поправка к прежней формулировке этого отчёта.** Я писал, что отсутствие
`scroll` убивает кандидата. Это неверно. `ReactScrollView.java`:

```java
int scrollDelta = computeScrollDeltaToGetChildRectOnScreen(tempRect);
if (scrollDelta != 0) {
  scrollBy(0, scrollDelta);
}
```

`scrollToChild` выполняется на **каждом** фокусе, а прокручивает только при
ненулевой дельте. Поле, которое уже видно целиком, даёт дельту 0: вызов был,
события нет. Поэтому `scroll y=` — сигнал для сопоставления, и только.

Запись пассивная: `onScroll` наблюдает и передаёт дальше,
`scrollEventThrottle={16}`.

**Ни подтвердить, ни опровергнуть `scrollsChildToFocus` по одному `onScroll`
нельзя.** Для причинного вывода нужен контролируемый эксперимент — он
подготовлен, см. `docs/ANDROID_FOCUS_LOG_ANALYSIS_2026-09-08_RU.md` §Р5.

## 4. Экран «Вход по коду» получил имена полей

У `OtpLoginScreen` не было `traceId` — поэтому в журнале поле называлось
по-русски, «Номер телефона». Теперь `phone` и `otp`, как на остальных
экранах, плюс `useMountTrace` и `useDimensionsTrace`. Журналы с разных
телефонов и с разными языками интерфейса стали сравнимы.

## 5. Обязательная проверка — три экрана, не два

На **обоих** телефонах (Samsung и Xiaomi), после установки 35:

1. **Вход по паролю** — два поля.
2. **Регистрация** — два поля (Phone number + Referral code).
3. **Вход по коду** — **одно поле.** Раньше в проверку не входил, и напрасно:
   именно он опроверг прежнюю формулировку.

На каждом экране:

* **CLEAR**;
* нажать на поле, дождаться поведения клавиатуры;
* повторить 2–3 раза;
* **EXPORT** — **независимо от результата**.

Отдельно, на экране входа: нажать на поле, дождаться клавиатуры, затем
нажать на пустое место экрана. Клавиатура **не должна** закрываться — эта
часть подтверждена ещё на сборке 33.

**Общий дефект не закрывается, пока не проверены все три экрана.**
