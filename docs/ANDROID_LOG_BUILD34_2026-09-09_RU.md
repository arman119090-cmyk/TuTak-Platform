## 2. Новое и важное: успешная попытка в том же журнале

```

1400ms  REQ focus phone src=anonymous
```

Разница с неудачными попытками — одна, и она видна прямо в журнале:
**здесь нет строки `focus phone`.** Запрос фокуса был, а события фокуса не
последовало — поле уже держало фокус, менять было нечего.

Сопоставление по всем попыткам этого журнала:

| Попытка | Событие `focus` | Исход |
|---|---|---|
| 1400 phone | **нет** (уже в фокусе) | клавиатура открылась и осталась |
| 5004 password | есть | фокус потерян через 25 мс |
| 6309 password | есть | фокус потерян через 29 мс |
| 13436 «Номер телефона» | есть | фокус потерян через 33 мс |

**Триггер — само событие смены фокуса.** Если фокус не менялся, ничего
плохого не происходит.

## 3. Что из этого следует для поиска

Единственное, что приложение выполняет в ответ на событие фокуса, — это
`setFocused` в `TextField`, и весь его эффект — перерисовка компонента:

```jsx
onFocus={(event) => {
  logEvent(...);
  setFocused(true);          // ← перерисовка
  ensureVisible(...);        // пустышка, NO_SCROLLING
  onFocus?.(event);
}}
```

Интервал 25–33 мс — это полтора-два кадра, то есть цикл «состояние →
перерисовка → обновление native-view». Совпадает.

**Это гипотеза, а не вывод.** Прямой связи «перерисовка → снятие фокуса» из
журнала не следует: перерисовка и потеря фокуса могут иметь общую причину, а
25–33 мс — это ещё и время появления окна IME.

## 4. Вторая ветвь эксперимента: `RR`

Добавлен второй переключатель — **RR** (re-render). При `RR=off` `TextField`
не вызывает `setFocused` вообще: перерисовки на фокус нет, и рамки фокуса в
этой ветви тоже нет. Видимая цена, приемлемая для опыта и непригодная для
релиза.

Обе ветви теперь в заголовке панели и в экспорте: `SCF=off RR=on`.

**Переключать по одной.** Заголовок показывает обе, поэтому опыт, в котором
случайно сдвинулись обе, виден как испорченный.

### Что будет считать выводом

| Результат | Вывод |
|---|---|
| При `RR=off` сбой устойчиво исчезает | Перерисовка на фокус вовлечена **в проверенных условиях**. Native-механизм этим по-прежнему не доказан, и `RR=off` не является исправлением — дальше надо сужать, что именно в перерисовке |
| Сбой одинаков при `RR=on` и `RR=off` | Перерисовка не при чём. Тогда фокус снимает Android сам, в ответ на своё же событие фокуса, и дальше нужен native trace (`adb logcat`) |

## 6. Границы, которые остаются в силе

* Отсутствие `REQ` исключает только команды, которые оборачивает инструмент;
  косвенное влияние JS через пропсы или вёрстку — нет.
* Постоянные `t=` исключают замену view, но не отсоединение и возврат той же.
* `scroll y=` — корреляция; его отсутствие ничего не исключает, потому что
  `scrollToChild` прокручивает только при ненулевой дельте.

# Приложение: журнал `run M2096X` (сборка 36, `7ad72ba`, `SCF=on`)

## П.1. Опыт не состоялся — из-за дефекта моего инструмента

Журнал почти целиком состоит из строк `scroll y=…`, и в заголовке стоит
`events 400 (older ones dropped)`. Запись обрывается ровно на
`120283ms REQ focus phone` — то есть **на самом первом интересном событии**.

Причина в том, как я сделал запись прокрутки. При `scrollEventThrottle={16}`
палец, ведущий по экрану, выдаёт около шестидесяти отсчётов в секунду, и ни
один из них текстово не совпадает с предыдущим — счётчик повторов в
`logEvent` срабатывает только на буквально одинаковых строках. Девяносто
строк подряд вытеснили из кольцевого буфера всё, ради чего журнал снимался.

**Это моя ошибка, а не ваша.** Опыт `SCF=on` придётся повторить.

## П.2. Исправлено

Добавлено сворачивание серии: `logEventCoalesced`. Серия прокруток теперь —
**одна строка**, датированная **началом** серии, с итоговым значением и
числом отсчётов:

```
scroll y=938 ×57
```

Начало серии выбрано намеренно: именно этот момент нужно сопоставлять с
`focus`. При этом одиночная прокрутка внутри обработки фокуса — то, ради чего
всё и делалось, — остаётся отдельной, полностью читаемой строкой:

```
focus phone
scroll y=12
blur  phone
```

Четыре теста закрепляют оба свойства, включая тот случай, который и произошёл:
пятьсот отсчётов подряд дают две строки, а не вытесняют журнал.

## П.2a. Защита журнала — сворачивания было мало

Вы правы: одно сворачивание не гарантия. Сделано два уровня.

**Уровень 1 — свёртка с сохранением времени и диапазона.** Серия прокруток —
одна строка, датированная **началом** серии, с обоими смещениями:

```
scroll y=120→938 ×57
```

Начало серии — то, что сопоставляется с `focus`. Диапазон — то, насколько
далеко ушло. Одиночная прокрутка внутри обработки фокуса печатается как
`scroll y=120` и остаётся полностью читаемой.

**Уровень 2 — отдельный бюджет вытеснения.** При переполнении буфера теперь
расходуются **только строки прокрутки**, и лишь когда их не осталось —
что-либо ещё. `focus`, `blur`, `REQ`, `mount`, `kbShow`/`kbHide`, `exp`,
`appState`, `layout`, `touch`, `press` вытеснить прокруткой **невозможно**.

Порядок при этом сохраняется: строка удаляется с того места, где стоит, а не
переносится. Последовательность — это и есть доказательство; переставленный
журнал был бы хуже обрезанного.

Семь тестов закрепляют оба уровня, включая ровно тот случай, который
произошёл: пятьсот отсчётов подряд не вытесняют ни `focus`, ни `REQ`.

## П.3. Что в этом журнале всё-таки видно

**Разметка полей работает:**

```
118401ms  mount field:phone #1 @4
118401ms  mount field:password #1 @5
118401ms  mount Login #1 @3
118415ms  layout phone h=86
118415ms  layout password h=86
```

**Впервые виден `mount App #2` — и он объясним:**

```
 91942ms  appState background
 92968ms  unmount App @1
 98183ms  mount App #2 @2
 98184ms  appState active
```

Приложение ушло в фон на шесть минут, React-корень был размонтирован, при
возвращении смонтирован заново. Это обычное поведение Android при
длительном фоне, а **не** та потеря фокуса, которую мы ищем: между ними шесть
минут и явные `appState`-переходы.

### Что `mount App` означает в этой реализации — проверено по коду

`useMountTrace('App')` стоит в компоненте `Root` (`App.tsx:63`), который
вложен в `ErrorBoundary → SafeAreaProvider → I18nextProvider →
QueryClientProvider → ThemeProvider`.

Следовательно, `mount App #n` фиксирует **монтирование этого React-компонента**
и ничего сверх того.

`unmount App @1` + `mount App #2 @2` при **том же** run id означает ровно
одно: **дерево React ниже `Root` было разобрано и собрано заново, а
JS-контекст при этом уцелел.**

| Что это | Вердикт |
|---|---|
| Перезапуск RN surface | **Совместимо**, но не доказано |
| Пересоздание Activity | **Совместимо**, но **не доказано** |
| Что-либо выше `Root`, сменившее идентичность | Дало бы те же две строки |

Различить их из JavaScript нечем. Нужен native trace жизненного цикла
Activity (`adb logcat`). **До него эти строки говорят «React-корень был
заменён» — и всё.** Ни пересоздание Activity, ни причина клавиатурного сбоя
по ним не объявляются.

Формулировка исправлена и в коде — в комментарии у самого вызова и в
`instanceTrace.ts`, чтобы следующий читатель не прочёл больше, чем там есть.

Отдельно: к искомой потере фокуса эти строки в любом случае не относятся —
между `background` и `active` шесть минут, и оба перехода явно записаны.
