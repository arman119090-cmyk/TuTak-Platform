**Это сборка 34, не 35 и не 36.** Переключателя SCF в ней нет:
`scrollsChildToFocus` жёстко `false`. То есть журнал снят целиком в ветви

## 1. Ваш критерий 3.3 сработал: при `off` сбой воспроизводится

Зафиксировано первым, как и договаривались.

```
5004ms  REQ focus password
5004ms  blur phone / focus password
5029ms  blur password / focus phone
5051ms  blur phone / focus password
5054ms  blur password / focus phone
5071ms  kbShow h=332 on=phone
```

И на однопольном экране:

```
13436ms  REQ focus Номер телефона
13436ms  focus Номер телефона kbd=number-pad t=3700
13469ms  blur  Номер телефона t=3700     ← 33 мс, без REQ blur
```

**Вывод: `scrollsChildToFocus={false}` дефект не устраняет.**

По вашей же формулировке 3.2 это **не полное исключение `ScrollView`** —
отключён один проп, а не компонент: `requestChildFocus` продолжает
вызываться, отключается только прокрутка внутри него. `ScrollView` остаётся
в кандидатах, но перестаёт быть первым.

## 2. Новое и важное: успешная попытка в том же журнале

```
1295ms  pressIn phone / touch phone
1399ms  press phone
1400ms  REQ focus phone src=anonymous
1477ms  kbShow h=303 on=phone kbd=number-pad
```

**Клавиатура открылась и осталась. Никакого сбоя.**

Разница с неудачными попытками — одна, и она видна прямо в журнале:
**здесь нет строки `focus phone`.** Запрос фокуса был, а события фокуса не
последовало — поле уже держало фокус, менять было нечего.

Сопоставление по всем попыткам этого журнала:

| Попытка | Событие `focus` | Исход |
|---|---|---|
| 1400 phone | **нет** (уже в фокусе) | клавиатура открылась и осталась |
| 5004 password | есть | фокус потерян через 25 мс |
| 6309 password | есть | фокус потерян через 29 мс |
| 13436 «Номер телефона» | есть | фокус потерян через 33 мс |

**Триггер — само событие смены фокуса.** Если фокус не менялся, ничего
плохого не происходит.

## 3. Что из этого следует для поиска

Единственное, что приложение выполняет в ответ на событие фокуса, — это
`setFocused` в `TextField`, и весь его эффект — перерисовка компонента:

```jsx
onFocus={(event) => {
  logEvent(...);
  setFocused(true);          // ← перерисовка
  ensureVisible(...);        // пустышка, NO_SCROLLING
  onFocus?.(event);
}}
```

Интервал 25–33 мс — это полтора-два кадра, то есть цикл «состояние →
перерисовка → обновление native-view». Совпадает.

**Это гипотеза, а не вывод.** Прямой связи «перерисовка → снятие фокуса» из
журнала не следует: перерисовка и потеря фокуса могут иметь общую причину, а
25–33 мс — это ещё и время появления окна IME.

## 4. Вторая ветвь эксперимента: `RR`

Добавлен второй переключатель — **RR** (re-render). При `RR=off` `TextField`
не вызывает `setFocused` вообще: перерисовки на фокус нет, и рамки фокуса в
этой ветви тоже нет. Видимая цена, приемлемая для опыта и непригодная для
релиза.

Обе ветви теперь в заголовке панели и в экспорте: `SCF=off RR=on`.

**Переключать по одной.** Заголовок показывает обе, поэтому опыт, в котором
случайно сдвинулись обе, виден как испорченный.

### Что будет считать выводом

| Результат | Вывод |
|---|---|
| При `RR=off` сбой устойчиво исчезает | Перерисовка на фокус вовлечена **в проверенных условиях**. Native-механизм этим по-прежнему не доказан, и `RR=off` не является исправлением — дальше надо сужать, что именно в перерисовке |
| Сбой одинаков при `RR=on` и `RR=off` | Перерисовка не при чём. Тогда фокус снимает Android сам, в ответ на своё же событие фокуса, и дальше нужен native trace (`adb logcat`) |

## 5. Побочное наблюдение: поля прошлого экрана остаются зарегистрированными

```
10825ms  mount field:Номер телефона #1 @5
10912ms  kbHide on=none of=3 ×2
```

`of=3` — в реестре три поля: два с экрана входа плюс одно с «Входа по коду».
Навигация в native-stack не размонтировала предыдущий экран.

На чтение журнала это не влияет — поля различаются по `traceId` и по `t=`, —
но при рассуждениях про «первый фокусируемый потомок» это надо учитывать:
в иерархии в этот момент больше полей, чем видно на экране.

(Русское имя поля — потому что это сборка 34; `traceId` для «Входа по коду»
добавлены в 35.)

## 6. Границы, которые остаются в силе

* Отсутствие `REQ` исключает только команды, которые оборачивает инструмент;
  косвенное влияние JS через пропсы или вёрстку — нет.
* Постоянные `t=` исключают замену view, но не отсоединение и возврат той же.
* `scroll y=` — корреляция; его отсутствие ничего не исключает, потому что
  `scrollToChild` прокручивает только при ненулевой дельте.
