# Эксперимент SCF: результат, и что он оставляет открытым

**Сборка 36, commit `7ad72ba`, run `BJA2G8`. Один телефон, экран «Вход по
коду», одно поле.**

## 1. Результат

| Ветвь | Попыток | Сбой |
|---|---|---|
| OFF-1 | 5 | 5 |
| ON | 2 | 2 |
| OFF-2 | 1 | 1 |
| **Всего** | **8** | **8** |

Задержки `focus` → `blur`: OFF-1 — 47, 41, 57, 58, 53 мс; ON — 59, 39 мс;
OFF-2 — 36 мс.

**Вывод: `scrollsChildToFocus=false` не устраняет дефект в проверенных
условиях.**

Числа попыток в ветвях разные, поэтому **никаких статистических выводов** о
частоте или скорости между ON и OFF не делается. Достаточный вывод один: сбой
воспроизведён в обеих настройках и при возврате к OFF.

Это **не устанавливает первопричину** и **не исключает `ScrollView`
целиком** — отключён один проп, `requestChildFocus` продолжает вызываться.

**Этот эксперимент не повторяется** без новой конкретной причины.

## 2. Новое, чего не было в прежних журналах

Клавиатура открывается **уже после того, как фокус потерян**, и открывается
впустую:

```
4623ms  focus phone t=4178
4670ms  blur  phone t=4178            ← +47 мс
4903ms  kbShow h=310 on=none of=1     ← +233 мс: IME пришла, фокуса уже нет
4953ms  kbHide on=none of=1           ← +50 мс: и сразу ушла
```

`on=none of=1` — зарегистрировано одно поле, и оно не считает себя
сфокусированным.

Это согласуется с тем, что `requestFocusProgrammatically` в React Native
делает два действия подряд: `super.requestFocus(...)`, затем
`showSoftKeyboard()`. Фокус снимается раньше, чем окно IME успевает
появиться, и клавиатуре не к чему прикрепиться.

**Граница этого наблюдения:** `kbShow` — это событие `keyboardDidShow`, то
есть поздняя точка. Порядок записанных JS-событий **не равен** доказанной
последовательности всех внутренних действий Android и IME: работа IME
начинается раньше, чем приходит это событие. Наблюдение сужает картину, но не
исключает участия IME.

Отдельно: в третьей попытке OFF-1 (16604 мс) `kbShow`/`kbHide` **нет вообще**
— фокус потерян, клавиатура не появилась. То есть появление клавиатуры не
является обязательным звеном.

## 3. Проверка семантики `CLEAR` и заголовка — по вашему запросу

Один `run BJA2G8` с тремя разными `started` — **это не перезапуск процесса.**
Проверено в коде:

```ts
const RUN_ID = Math.random().toString(36).slice(2, 8).toUpperCase();  // один раз на JS-контекст

export function resetEvents(): void {   // это и есть CLEAR
  started = Date.now();
  startedAt = new Date();               // ← заголовок «started» переписывается
  events = [];
}
```

`RUN_ID` вычисляется один раз при загрузке модуля, то есть один раз на
JS-контекст. `CLEAR` обнуляет отсчёт времени и переписывает `startedAt`.

Значит **один run id + три разных `started` = один JS-контекст, между
экспортами нажимали CLEAR.** Подтверждается и строкой `instances 6`,
одинаковой во всех трёх экспортах: счётчик экземпляров тоже не сбрасывался.

## 4. Границы доказательств — в силе, все

| Наблюдение | Что из него следует | Чего НЕ следует |
|---|---|---|
| Между `focus` и `blur` нет `REQ blur` | Команды, которые оборачивает инструмент, не вызывались | Что JS не при чём: косвенное влияние через пропсы или вёрстку не исключено |
| `t=4178` постоянен | View не заменялась другой | Что её не отсоединяли и не присоединяли обратно |
| `blur` записан раньше `kbShow` | Таков порядок **записанных JS-событий** | Что такова доказанная последовательность действий Android и IME |
| `appState background` в OFF-2 | Произошло на 25 секунд позже сбоя | Никакой связи с ним |
| `window 384x856` | Размер окна в этом прогоне | Модель телефона и версия Android — **не указаны и не выводятся** |
| Один run id, три `started` | CLEAR между экспортами (см. §3) | Перезапуск процесса |

## 6. Следующий шаг: ветвь `RR` — новая сборка не нужна

Ветвь `RR` уже в **сборке 39** (`612d202`), которая у вас есть. Это другой
параметр, а не повтор SCF.

Основание — журнал сборки 34: единственная удачная попытка там та, где
`REQ focus` **не породил события фокуса** (поле уже было в фокусе), и
клавиатура осталась. Все попытки с настоящим событием фокуса теряли его. При
`RR=off` `TextField` не вызывает `setFocused` вообще: перерисовки на фокус
нет.

**Порядок:** тот же, что и для SCF, но трогать только **RR**, оставив
`SCF=off`. В заголовке должно читаться `SCF=off RR=off` в опытной ветви и
`SCF=off RR=on` в контрольной.

| Результат | Вывод |
|---|---|
| При `RR=off` сбой устойчиво исчезает | Перерисовка вовлечена **в проверенных условиях**. Первопричина этим не доказана, и `RR=off` — не исправление: рамка фокуса пропадает |
| Сбой одинаков | Перерисовка не при чём. Дальше — только native-инструментация |

Этот шаг стоит вам одного короткого захода и не требует ни новой сборки, ни
компьютера.

## 7. Native-инструментация: выполнимость изучена

### Почему `adb logcat` сам по себе не поможет

Штатный logcat **не печатает стеки снятия фокуса**. Их там просто нет: Android
не логирует, кто вызвал `clearFocus` или перевёл фокус. Инструментация нужна в
любом случае — вопрос только в том, куда она отдаёт результат.

### Что технически возможно в этом проекте — проверено

Каталога `android/` в репозитории нет, его генерирует EAS при сборке. Значит
native-код должен попадать туда воспроизводимо. Проверено по установленным
пакетам:

* `@expo/config-plugins@57.0.6` экспортирует **`withMainActivity`** — плагин
  может дописать Kotlin в `MainActivity` на этапе prebuild, а prebuild
  выполняется внутри EAS-сборки. Значит правка воспроизводима и не требует
  коммитить `android/`.
* `ReactApplication.reactHost` присутствует в RN 0.86.2 — есть штатный путь
  добраться до React-контекста из активности.

### Предлагаемая конструкция

`ViewTreeObserver.OnGlobalFocusChangeListener` на `window.decorView`. Он
срабатывает на **каждую** смену фокуса в окне и получает обе view — прежнюю и
новую. Внутри обработчика доступен Java-стек **в момент снятия фокуса** — то
самое, чего из JavaScript получить нельзя.

Записывается: время, идентификатор и класс прежней view, то же для новой, и
отфильтрованный стек вызовов. Оттуда — в ту же диагностическую панель через
штатный эмиттер событий, то есть **экспорт остаётся на телефоне, компьютер не
нужен**.

Это покрывает named вами точки: `onFocusChanged`, `onAttachedToWindow` /
`onDetachedFromWindow`, смену window focus, обновление `inputType` /
`keyListener` / `focusable`, связь с обновлением пропсов и проходом вёрстки,
вызовы родительского `ScrollView` — все они, если участвуют, окажутся в стеке.

**Ничего из перечисленного не объявляется причиной.** Это точки наблюдения.

**Что не логируется:** введённый текст, номера, пароли, OTP, токены. Стек
вызовов и класс view их не содержат, а `describe(view)` печатает класс и
идентификатор, но не содержимое.

**Изоляция от production:** установка слушателя гасится тем же признаком, что
и панель, — диагностическим профилем сборки. В обычный профиль он не
включается.

### Почему я это ещё не собрал

Ветвь `RR` уже в ваших руках и стоит одного короткого захода. Native-правка —
это цикл сборки на каждую попытку компиляции и заметно больший риск сломать
сборку. Разумный порядок: сначала `RR`, и только если он ничего не даст —
native-инструмент, у которого к тому моменту не останется конкурентов.

Если предпочитаете сразу native — скажите, соберу.
