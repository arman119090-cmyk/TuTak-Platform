# TuTak — independent adversarial re-audit, August 2026

Second, independent pass over the whole repository. Nothing from
`docs/AUDIT_2026-08.md` or `docs/HARDENING_2026-08.md` was assumed correct;
every finding below was derived from reading the source.

**Headline:** the hardening pass fixed the arithmetic of the bonus engine and
made it genuinely solid. It did not fix *who is allowed to assert how much
money moved*. That is where the platform is still broken, and one of the holes
mints unlimited bonus points with three ordinary API calls.

---

## 1. CRITICAL

### C1 — Any customer can mint unlimited bonus points through EV charging

**File:** `apps/api/src/modules/ev-charging/ev-charging.controller.ts:88`,
`apps/api/src/modules/ev-charging/ev-sessions.service.ts:86,105`

**Reason.** `POST /ev/sessions/:id/meter-value` has no ownership check, no role
requirement, and no plausibility check. The energy delivered — the sole input
to the bill — is supplied by the client. `stop()` then computes
`cost = energyKwh × pricePerKwh` and accrues
`bonusEarned = cost × bonusAccrualRateBps / 10000`. Nothing verifies that the
energy was actually delivered, that the caller owns the session, or that the
figure is physically possible for the connector's power rating and the session's
duration.

**Exploit (3 calls, any registered customer):**
```
POST /v1/ev/sessions/start        { connectorId: <any AVAILABLE connector> }
POST /v1/ev/sessions/:id/meter-value  { energyKwh: "9999999" }
POST /v1/ev/sessions/:id/stop     {}
```
`energyKwh` is capped only by `Decimal(10,3)` (9 999 999.999) and `parseMoney`.
At a typical 100 AMD/kWh connector and a 5 % partner rate that is
**49 999 995 bonus points per session**, repeatable without limit. The missing
ownership check additionally lets an attacker inflate *another* customer's bill
to the same ceiling.

**Impact.** Total loss of control over bonus liability; the loyalty currency is
worthless the day this is discovered. Also a billing-fraud vector against
individual customers.

**Fix.** Meter values must come from the charge point, not the app: restrict the
endpoint to an authenticated CPO/OCPP identity (or remove it and ingest energy
only via `OcpiAdapter.fetchCdr`). Until then, at minimum require session
ownership, and bound each reading by
`connector.powerKw × elapsedHours × tolerance`.

### C2 — Seeded super-admin ships with a publicly known password

**File:** `apps/api/prisma/seed.ts:67-81`

**Reason.** `argon2.hash('ChangeMe123!')` for phone `+37400000000`, granted
`SUPER_ADMIN` (which holds every permission). The credential is committed to
the repository and `README.md` instructs operators to run `pnpm prisma:seed`.
`upsert({ update: {} })` means re-seeding never rotates it, and there is no
forced-rotation flag and no password-change endpoint (see C3) to rotate it with.

**Impact.** Anyone who reads the repo owns production: arbitrary bonus credits
via `POST /wallet/admin/adjust`, full user and audit-log access.

**Fix.** Generate a random password at seed time and print it once, or require
`SEED_ADMIN_PASSWORD` and refuse to seed without it. Add a `mustChangePassword`
flag enforced on login.

### C3 — No password reset, no password change, no account recovery

**File:** `apps/api/src/modules/auth/auth.controller.ts` (whole file),
`apps/api/src/modules/users/users.controller.ts` (whole file)

**Reason.** The only auth routes are register, login, refresh, logout. There is
no change-password, no forgot-password, no OTP delivery. `generateNumericCode`
exists in `apps/api/src/common/utils/crypto.ts:7` but is never called from
anywhere — the OTP flow was never built.

**Impact.** A customer who forgets their password is permanently locked out of
their bonus balance, with no support path that does not involve direct database
edits. Combined with C2, the seeded admin password can never be rotated through
the product. This alone blocks launch.

**Fix.** Add change-password (re-authenticating with the current password) and a
reset flow over SMS OTP, revoking all refresh tokens on success.

### C4 — Referral reward is farmable: no phone verification, self-service qualifying transaction

**File:** `apps/api/src/modules/referral/referral.service.ts:39-81`,
`apps/api/src/modules/qr-payments/qr-payments.service.ts:32-66`,
`apps/api/src/modules/auth/auth.service.ts:46`

**Reason.** Three gaps compose:
1. Registration is public and unverified. `isPhoneVerified` defaults to `false`
   and is **never set to true and never checked** anywhere in the codebase —
   the field is decorative. Any `+374XXXXXXXX` string creates an account.
2. Any customer can self-issue a payable QR code: `issue()` permits
   `type: USER_PAY_TOKEN` with no `partnerId` and an arbitrary `amount`, and
   `redeem()` never checks that the payer is not the issuer.
3. `handleQualifyingTransaction` rewards the referrer on *any* first
   `COMPLETED` transaction, of any type, for any amount, including one with no
   partner.

**Exploit.** Register account B with attacker A's referral code → B issues a
`USER_PAY_TOKEN` for `amount: "1"` → B redeems it → A receives
`REFERRAL_REWARD_AMOUNT` (default 1000 points). Repeat per throwaway number.
Rate-limited to 5 registrations/minute/IP, which is not a control.

**Impact.** Unbounded bonus liability; the `REFERRAL_RING_DETECTED` fraud signal
type exists in the schema but no rule ever raises it.

**Fix.** Require SMS verification before a wallet can earn. Qualify referrals
only on a transaction with a real `partnerId` above a minimum amount. Reject
`redeem()` when `qr.issuedByUserId === payerUserId`. Add device/IP clustering to
raise `REFERRAL_RING_DETECTED`.

### C5 — Referral reward can be paid twice (race) or paid repeatedly (failed status write)

**File:** `apps/api/src/modules/referral/referral.service.ts:39-81`

**Reason.** Read invite → check `status === PENDING` → count transactions →
`accrue` → `update` status. None of it is in a transaction and the status update
is unconditional rather than `updateMany({ where: { id, status: PENDING } })`.
Two concurrent `transaction.completed` events both observe `PENDING` and both
accrue. Separately, if `accrue` succeeds and the subsequent `update` throws, the
listener at `referral.listener.ts:16` swallows the error and the invite stays
`PENDING` — every later transaction pays the referrer again.

**Impact.** Duplicate and repeated payouts, invisible because the failure is
logged and discarded.

**Fix.** Wrap in one transaction; claim the invite with a conditional
`updateMany` on `status: PENDING` and only accrue if `count === 1`.

### C6 — Privilege escalation: an ADMIN can promote itself to SUPER_ADMIN

**File:** `apps/api/src/modules/admin/admin.controller.ts:15,27`,
`apps/api/src/modules/admin/admin.service.ts:36-51`

**Reason.** `AdminController` is gated by `USER_MANAGE`, which the `ADMIN` role
holds. `assignRole` accepts any `RoleName` for any `userId` — including the
caller's own — with no check that the granted role is at or below the actor's
level, and no self-grant guard. `SUPER_ADMIN` is seeded with
`Object.values(PermissionName)`.

**Impact.** Any compromised or malicious ADMIN account escalates to full
platform control, including `WALLET_WRITE` for unlimited manual credits. The
audit entry is written *after* the grant and by the same actor.

**Fix.** Restrict `SUPER_ADMIN` grants to `SUPER_ADMIN`; forbid self-grants;
require a second approver for role changes at admin level.

## 2. HIGH

### H1 — Refresh-token rotation is not atomic; no reuse detection

**File:** `apps/api/src/modules/auth/auth.service.ts:170-202`

**Reason.** `findUnique` then `update({ where: { id } })` — two concurrent
requests with the same refresh token both pass the `revokedAt` check and both
receive a valid new pair. There is also no token-family tracking: a stolen token
replayed after the victim rotates simply fails, and nothing detects the theft.
`replacedByTokenId` exists in the schema but is never written.

**Impact.** A leaked refresh token (30-day lifetime, stored in `localStorage` on
web — see H2) can be duplicated into a parallel session, and the compromise is
never surfaced.

**Fix.** `updateMany({ where: { id, revokedAt: null }, ... })` and abort if
`count === 0`. Populate `replacedByTokenId`; on presentation of an
already-revoked token, revoke the whole family and raise a fraud signal.

### H2 — Web apps persist access *and* refresh tokens in `localStorage`

**File:** `apps/admin/src/lib/stores/authStore.ts:26-40`,
`apps/partner/src/lib/stores/authStore.ts:26-40`

**Reason.** `zustand/persist` with the default `localStorage` backend. Any XSS —
including one in a future dependency — exfiltrates a 30-day refresh token.

**Impact.** Full, long-lived account takeover of admin and partner operators
from a single script injection.

**Fix.** Keep the access token in memory only; move the refresh token to an
httpOnly, `Secure`, `SameSite=Strict` cookie issued by the API.

### H3 — `partner.isActive` is written but never read

**File:** `apps/api/src/modules/partners/partners.service.ts:59-61`; no reader
anywhere (`grep isActive` across `qr-payments`, `ev-charging`, `partners`
returns only the writer)

**Reason.** `PATCH /partners/:id/active` flips the flag; `findByIdOrThrow`,
`redeem()` and the EV pricing path never consult it.

**Impact.** Deactivating a fraudulent or terminated partner has no effect: their
QR codes keep redeeming and keep accruing bonus at the platform's expense. The
admin control is inert while appearing to work.

**Fix.** Reject redemption, accrual and session start for an inactive partner.

### H4 — Internal error messages are returned to the client

**File:** `apps/api/src/common/filters/all-exceptions.filter.ts:45-47`

**Reason.** Any non-`HttpException`, non-`PrismaClientKnownRequestError` error
sets `message = exception.message` while the status stays 500.
`PrismaClientValidationError` messages embed the full query and its arguments;
`PrismaClientInitializationError` embeds the database host; the CHECK-constraint
violations added by the hardening migration surface as
`PrismaClientUnknownRequestError` and leak table and constraint names.

**Impact.** Schema, query and infrastructure disclosure to any caller who can
provoke an error.

**Fix.** Log the detail, return a generic message and a correlation id for
status ≥ 500.

### H5 — Partner-scoped roles are never enforced for EV asset management

**File:** `apps/api/src/modules/ev-charging/ev-charging.controller.ts:56-66`,
`apps/api/src/modules/ev-charging/ev-stations.service.ts:10-16`

**Reason.** `POST /ev/stations` and `POST /ev/connectors` require only
`EV_STATION_MANAGE` (held by `PARTNER_OWNER`). `CreateStationDto.partnerId` and
`CreateConnectorDto.stationId` are taken from the body without checking them
against `user.partnerScopes`. `RolesGuard` and `PermissionsGuard` never look at
`partnerScopes` at all — only `AnalyticsController` and `PartnersController` do
it by hand.

**Impact.** Partner A creates stations and connectors under partner B, sets
`pricePerKwh`, and can therefore drive bonus accrual and revenue attribution
against a competitor's account.

**Fix.** A scope guard that resolves the partner from the payload and checks it
against `partnerScopes`, applied to every partner-scoped route.

### H6 — Mobile defeats idempotency and mis-sends the bonus amount

**File:** `apps/mobile/src/presentation/screens/qr/ScanQrScreen.tsx:52-56`

**Reason.** Two defects in four lines:
- `idempotencyKey: \`${token}-${Date.now()}\`` — a fresh key per attempt, so the
  per-user idempotency the backend now enforces can never match. A double-tap or
  a client retry on a `STATIC_MERCHANT` code charges twice.
- `bonusAmountToApply: String(Number(wallet.availableBonus))` — sends the entire
  balance regardless of the invoice, so the backend rejects with "Bonus applied
  cannot exceed the payment amount" for every customer whose balance exceeds the
  bill. The `Number()` round-trip also loses precision and can emit exponential
  notation (`1e+21`), which `IsMoneyString` rejects.

**Impact.** Double charges on retry; the "apply bonus" feature is broken for the
majority of customers.

**Fix.** Derive the key from the payment intent (`token` + a UUID minted once
per confirm screen, held across retries). Cap the applied amount at
`min(availableBonus, invoiceAmount)` using string/decimal arithmetic.

### H7 — Fraud detection raises signals that nothing acts on

**File:** `apps/api/src/modules/security/fraud-detection.service.ts:21-38`,
`apps/api/src/modules/qr-payments/qr-payments.service.ts:133-135`,
`apps/api/src/modules/transactions/transactions.service.ts:103` (dead)

**Reason.** `checkVelocity` returns a boolean that the caller discards
(`.catch(...)` only). `markFlagged` — the mechanism to hold a suspicious
transaction — is never called from anywhere. The EV path performs no fraud check
at all.

**Impact.** The fraud subsystem is decorative; velocity abuse completes normally
and is only visible in a table nobody is paged on.

**Fix.** Act on the signal — flag or hold the transaction, and cover the EV path.

### H8 — `platformOverview` is readable by every partner owner

**File:** `apps/api/src/modules/analytics/analytics.controller.ts:31-35`

**Reason.** `GET /analytics/platform` requires `ANALYTICS_READ`, which
`PARTNER_OWNER` holds (`prisma/seed.ts:12-20`). Unlike the per-partner route
immediately above it, there is no admin check.

**Impact.** Any partner reads platform-wide transaction volumes and the total
outstanding bonus liability — competitive intelligence and a balance-sheet leak.

**Fix.** Require ADMIN/SUPER_ADMIN, or introduce a distinct
`PLATFORM_ANALYTICS_READ` permission.

### H9 — `partnerAnalytics` loads every transaction into memory and sums with floats

**File:** `apps/api/src/modules/analytics/analytics.service.ts:9-36`

**Reason.** `findMany` with no `take`, then `reduce` with `Number(t.amount)`.

**Impact.** Two problems at once: the endpoint OOMs the API process once a
partner has a large history (a trivially reachable DoS), and money is summed in
IEEE 754 after the entire codebase was carefully built on `Decimal`. Revenue
figures shown to partners will drift.

**Fix.** `prisma.transaction.aggregate` / `groupBy` with `_sum`, and a distinct
count for `uniqueCustomers`.

### H10 — Account lockout is a denial-of-service against any known phone number

**File:** `apps/api/src/modules/users/users.service.ts:136-149`,
`apps/api/src/modules/auth/auth.service.ts:114-124`

**Reason.** Five failed attempts lock the account for 15 minutes; the lock check
runs *before* password verification and returns the exact unlock timestamp.
`registerFailedLogin` never resets `failedLoginCount` when it locks, so after the
lock expires the counter is still ≥ 5 and a single further mistake re-locks
immediately. The 8/min throttle is per-IP.

**Impact.** An attacker who knows a phone number can keep that customer locked
out indefinitely from a handful of IPs; the distinct error also confirms which
numbers are registered (enumeration).

**Fix.** Reset the counter when applying the lock; use an identical generic
error for locked, unknown and wrong-password; apply exponential backoff keyed on
the account rather than a hard lock.

### H11 — No settlement, payout or refund path exists

**File:** `apps/api/src/modules/transactions/transactions.service.ts:31-52`;
`TransactionType.REFUND` in `prisma/schema.prisma:353` is never produced

**Reason.** `create()` writes a row; no payment provider, no partner ledger, no
payout run, no refund handler. `Currency` has `AMD` and `BONUS_POINT` but no
conversion logic exists.

**Impact.** The platform records commercial events it cannot reconcile against
money, cannot pay partners, and cannot reverse a customer charge. A refunded
purchase leaves its accrued bonus permanently granted.

**Fix.** Out of scope for a fix here, but this is the largest missing subsystem
and must be designed before launch.

### H12 — Redis client has no error handler

**File:** `apps/api/src/infrastructure/redis/redis.module.ts:15-18`

**Reason.** `new Redis(...)` with no `.on('error', ...)`. ioredis emits `error`;
an `EventEmitter` `error` event with no listener throws and terminates the
process.

**Impact.** A Redis blip crashes the API. Note also that the injected client is
never used by any module — see M14.

**Fix.** Attach an error listener that logs and lets the retry strategy work.

## 3. MEDIUM

### M1 — Referral codes collide and abort registration

**File:** `apps/api/src/modules/auth/auth.service.ts:275-277`

`TT-${userId.slice(0,8).toUpperCase()}` over `ReferralCode.code @unique`. Eight
hex characters is a 32-bit space; by the birthday bound a collision is likely
around ~77 000 users, and each collision makes that user's registration fail
with an opaque 409. Fix: random base32 with a retry loop, or derive from a
sequence.

### M2 — `GET /referral/me/code` 500s for any user without a code

**File:** `apps/api/src/modules/referral/referral.service.ts:20-22`

`findUniqueOrThrow`. Codes are created only in `register()`, so the seeded
super-admin and any user created by other means have none. Fix: create on demand
or return `null`.

### M3 — Boolean body parameters bypass validation

**File:** `apps/api/src/modules/admin/admin.controller.ts:44`,
`apps/api/src/modules/partners/partners.controller.ts:65`

`@Body('isActive') isActive: boolean` extracts a raw value; `ValidationPipe`
skips primitive metatypes. `{"isActive":"false"}` reaches Prisma as a string
(500) and `{}` reaches it as `undefined`. A security-relevant toggle with no
schema. Fix: a DTO with `@IsBoolean()`.

### M4 — Cursor pagination can skip or repeat rows

**File:** `apps/api/src/modules/wallet/wallet.service.ts:22-34`,
`apps/api/src/modules/transactions/transactions.service.ts:111-134`,
`apps/api/src/modules/admin/admin.service.ts:10-34`,
`apps/api/src/modules/audit/audit.controller.ts:15-27`

Every list orders by `createdAt` but paginates on an `id` cursor. Ledger entries
written inside one transaction share a timestamp, so ordering among them is
undefined and pages drift. Fix: order by `[createdAt desc, id desc]`.

### M5 — CORS falls back to reflecting any origin with credentials

**File:** `apps/api/src/main.ts:18-23`

`origin: config.get('cors.origins').length ? ... : true` with
`credentials: true`. `CORS_ORIGINS` is not validated in `env.validation.ts`, so
a production deploy that forgets it silently becomes fully permissive. Fix:
require a non-empty allow-list when `NODE_ENV === 'production'`.

### M6 — No `trust proxy`, so rate limiting and audit IPs are wrong behind a load balancer

**File:** `apps/api/src/main.ts:11-25`, `apps/api/src/modules/auth/auth.controller.ts:14`

`req.ip` is the socket peer. Behind any ingress every request shares one IP:
the global throttler becomes a platform-wide bucket (trivial DoS) and every
`AuditLog.ipAddress` records the proxy. Fix: `app.set('trust proxy', 1)`.

### M7 — EV reservation cancel/expiry can free a connector that is charging

**File:** `apps/api/src/modules/ev-charging/ev-reservations.service.ts:43-52,64-82`

Both paths set the connector to `AVAILABLE` unconditionally, without checking
for an active session. A cancel racing a `start()` leaves a `CHARGING` session
on a connector advertised as free, and a second customer can start on it. Fix:
conditional `updateMany` guarded on the connector not being `CHARGING`.

### M8 — Reservations have no per-user limit

**File:** `apps/api/src/modules/ev-charging/ev-reservations.service.ts:10-32`

One customer can hold every connector in the network for up to 120 minutes.
`startAt` is accepted unvalidated (past dates allowed) and is not used for the
hold window. Fix: cap concurrent reservations per user; validate `startAt`.

### M9 — Registration is check-then-insert

**File:** `apps/api/src/modules/auth/auth.service.ts:47-50`

`findByPhone` outside the transaction, then create. Concurrent signups race to a
P2002. Separately, the distinct `ForbiddenException` message confirms whether a
number is registered (enumeration), and `email` is validated only as `@IsString`
despite being `@unique` — a duplicate or malformed email yields a confusing 409.
Fix: rely on the unique constraint, return a generic message, add `@IsEmail`.

### M10 — `refresh()` ignores lockout and soft-deletion

**File:** `apps/api/src/modules/auth/auth.service.ts:178-181`

Checks only `isActive`, while `buildRequestUserClaims` (the per-request gate)
also rejects `deletedAt` and `lockedUntil`. A locked account can still mint
fresh token pairs. Fix: reuse `buildRequestUserClaims` here.

### M11 — `UserRole` uniqueness is not enforced for global roles

**File:** `apps/api/prisma/schema.prisma:88`

`@@unique([userId, roleId, partnerId])` with nullable `partnerId`: Postgres
treats NULLs as distinct, so duplicate global roles are insertable. Only
`assignRole`'s hand-written `findFirst` prevents it. Fix: a partial unique index
on `(userId, roleId) WHERE partnerId IS NULL`.

### M12 — The audit log is called immutable but nothing enforces it

**File:** `apps/api/prisma/schema.prisma:732-749`

No revoked grants, no trigger, no hash chain. The application role can update or
delete rows. Fix: `REVOKE UPDATE, DELETE`, or chain each row's hash.

### M13 — `EvCdr.totalEnergy` is narrower than the value that reaches it

**File:** `apps/api/prisma/schema.prisma:661-670` vs
`apps/api/src/modules/ev-charging/ev-sessions.service.ts:166-175`

`Decimal(10,3)` on the CDR while `parseMoney` admits far larger readings;
`evCdr.create` overflows and aborts `stop()` inside its transaction. Fix: align
the precision and validate the reading at ingestion (see C1).

### M14 — Redis is provisioned but unused

**File:** `apps/api/src/infrastructure/redis/redis.module.ts`, `docker-compose.yml`

`REDIS_CLIENT` is injected nowhere. Throttling is in-memory, so rate limits are
per-process and reset on deploy; nothing is cached. Fix: back the throttler with
Redis, or drop the dependency.

### M15 — Per-request RBAC hits the database with a three-level join

**File:** `apps/api/src/modules/auth/strategies/jwt.strategy.ts:28-31`,
`apps/api/src/modules/users/users.service.ts:70-112`

Every authenticated request runs `user → roles → role → permissions → permission`
with no caching. Correct for revocation, expensive at volume. Fix: cache claims
in Redis with a short TTL, invalidated on role change and deactivation.

### M16 — Unbounded list endpoints

**File:** `apps/api/src/modules/ev-charging/ev-stations.service.ts:50-52`,
`apps/api/src/modules/wallet/wallet.service.ts:36-42`,
`apps/api/src/modules/security/fraud-detection.service.ts:59-64`,
`apps/api/src/modules/partners/partners.service.ts:48-50`,
`apps/api/src/modules/ev-charging/ev-reservations.service.ts:55-61`,
`apps/api/src/modules/referral/referral.service.ts:24-32`

`findMany` with no `take`. Response size and memory grow with the table. Fix:
paginate.

### M17 — Missing indexes on the sweeper queries

**File:** `apps/api/prisma/schema.prisma:275,656`

`BonusReservation` is indexed `[walletId, status]` but swept by
`status + expiresAt`; `EvReservation` is indexed `[connectorId, status]` and
swept the same way. Both scans run every minute to five minutes and degrade
linearly. Fix: add `[status, expiresAt]` indexes.

### M18 — Analytics date range is unvalidated

**File:** `apps/api/src/modules/analytics/analytics.service.ts:14-18`,
`apps/api/src/modules/analytics/analytics.controller.ts:20-21`

Raw `@Query('from')` strings go to `new Date()`; garbage yields `Invalid Date`
and a 500. Fix: a DTO with `@IsDateString()`.

### M19 — Web session gate can bounce an authenticated user to `/login`

**File:** `apps/admin/src/components/AuthGate.tsx:12-22`,
`apps/partner/src/components/AuthGate.tsx`

The effect redirects whenever `accessToken` is falsy, with no
`persist` hydration gate (`skipHydration`/`onRehydrateStorage` are not used) and
no SSR guard — `getOrCreateDeviceId()` even returns the literal `'ssr'` on the
server, so store state differs between render passes. Deep links and hard
refreshes can land on `/login` for a signed-in operator. Fix: gate on a
`hasHydrated` flag before deciding.

### M20 — Mobile ships pointing at `http://localhost:4000`

**File:** `apps/mobile/app.json:38-40`

`extra.apiBaseUrl` is hardcoded plaintext localhost with no per-environment
config. iOS ATS and Android cleartext policy also block plain HTTP by default.
Fix: environment-specific config and HTTPS.

### M21 — Device platform is always recorded as `WEB`

**File:** `apps/api/src/modules/auth/auth.service.ts:87,152`

`DevicePlatform.WEB` is hardcoded in both register and login; the DTOs carry no
platform field. `IOS` and `ANDROID` are unreachable. Fix: accept the platform
from the client.

### M22 — Manual wallet adjustment has no ceiling and no second approver

**File:** `apps/api/src/modules/wallet/wallet.controller.ts:41-60`

`WALLET_WRITE` alone permits a credit up to `MONEY_MAX` in one call. The audit
row is written after the fact by the same actor. Line 46 also throws a bare
`new Error('Target user not found')` — a 500 with a leaked message rather than a
404. Fix: cap the amount, require dual control above a threshold, use
`NotFoundException`.

## 4. LOW

- **L1** — Dead code: `markFlagged` (`transactions.service.ts:103`),
  `generateNumericCode` (`common/utils/crypto.ts:7`), `isPositive`
  (`common/utils/money.ts:13`), `OcpiAdapter.fetchCdr` (never called),
  `evApi.startSession` / `evApi.stopSession` in the mobile client (no screen
  calls them — the EV charging journey stops at browsing stations).
- **L2** — `USER_PAY_TOKEN` is semantically inverted: `redeem()` charges the
  caller, so a "user pay token" can only ever be redeemed by its own issuer.
  The type is unusable as designed (and is the vehicle for C4).
- **L3** — `generateNumericCode` uses `% 10**6` on a 32-bit value: modulo bias.
  Irrelevant while unused, a real weakness the moment OTP is built on it.
- **L4** — `parseDurationMs` (`common/utils/duration.ts:9`) accepts only
  `\d+[smhd]`; a conventional `JWT_ACCESS_EXPIRES_IN=900` throws at first login.
- **L5** — Registration audit uses `AuditAction.USER_LOGIN` with
  `metadata.via = 'register'`; the enum has no registration action.
- **L6** — `SecurityController.resolve` (`security.controller.ts:21-25`) gates a
  write behind `ADMIN_AUDIT_READ`.
- **L7** — `FraudSignal.resolvedByUserId` (`schema.prisma:770`) has no relation;
  dangling reference.
- **L8** — `listNearby` (`ev-stations.service.ts:37-48`) divides by
  `cos(latitude)`; at ±90° the longitude delta explodes and the bounding box
  matches everything.
