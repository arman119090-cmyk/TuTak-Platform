# TuTak — adversarial audit, August 2026 (round C)

Method: attack the **running** platform. Every claim below is a request that
either got in or did not, made against a live API with a freshly seeded
database. Nothing here was concluded by reading code alone — the two rounds
before this one did that, and all three defects found today had survived them.

State audited: commit `3f8bb60`, 389 integration tests + 77 unit tests passing.

---

## What was found

### C-1 — Every signed-in user could read every partner's commercial terms

`GET /partners` returned `prisma.partner.findMany()` — the whole row — to any
authenticated caller. A customer account, which anyone can create in a minute,
therefore received for every partner on the platform:

| Field | Why it matters |
| --- | --- |
| `taxId` | Tax registration number of a real business |
| `paymentCommissionRateBps` | The commission negotiated with that partner **individually** |
| `bonusAccrualRateBps` | Fine to expose — it is the advertised cashback |
| `payoutsBlockedAt` / `payoutsBlockedReason` | That a business is in a financial dispute, **and why** |

*Exploit:* register as a customer, `GET /partners`, receive the commercial
terms of every merchant on the platform. A competing loyalty platform learns
exactly what to undercut; a partner learns their rival negotiated a better
rate than they did.

*Fix:* a public projection (id, display name, category, cashback rate, active)
for everyone; the full record only for a platform administrator or the
partner's own people.

### C-2 — The fix for C-1 still leaked, to the audience with the clearest motive

Gating the full record on "holds `PARTNER_MANAGE`" is wrong, and looked right.
`PARTNER_OWNER` holds that permission too — owners manage *their own* partner.
A permission name carries no scope, so every partner owner could still read
every competitor's terms.

This is the same mistake as §H5 in `AUDIT_2026-08-B.md`, which is the reason
`common/auth/partner-scope.ts` exists. It was reintroduced roughly two hours
after that helper was used correctly elsewhere in the same session.

*Fix:* the test is `isPlatformAdmin` — a role — and `hasPartnerScope` for the
single-record route. The regression test builds a `PARTNER_OWNER` carrying the
real permission list, and was confirmed to fail against the old check.

### C-3 — An administrator could mint an unbounded number of points

`manualAdjustment` is the only path where a caller-supplied number becomes
loyalty points with nothing bounding it. A payment's accrual is bounded by
what the acquirer captured; an EV session by a meter's physical limits; a
referral by a configured constant. Points are a liability the business owes.

*Exploit:* one extra keystroke in a goodwill credit, or one compromised admin
session, and the balance sheet has a hole in it that nothing detects — the
ledger stays perfectly balanced, because the liability is real.

*Fix:* `BONUS_MANUAL_ADJUSTMENT_MAX` (default 1,000,000 points) refuses a
single adjustment above the ceiling. Configurable rather than constant, so a
legitimate large correction is still possible, just deliberate.

The same probe surfaced that an adjustment large enough to overflow
`Decimal(18,4)` reached Postgres and came back as a 500: `parseMoney` checked
the requested amount against the column's maximum, but nothing checked the
*resulting balance*. Now refused before the write. The first version of that
guard sat in `writeLedger`, which runs after the wallet update — the overflow
still happened first, and the test caught it.

## What was probed and held

Recorded so the next audit does not repeat it.

| Area | Result |
| --- | --- |
| Cross-tenant reads (payouts, balance, settlements, analytics, transactions) | 403 in every case |
| A partner minting a QR for another partner | Refused |
| Customer reading another customer's profile, transactions, notifications | Refused or scoped |
| Customer or partner issuing refunds | 403 |
| Partner declaring the acquirer paid us | 403 |
| Requester confirming their own payout | 403, and nothing moved |
| Two simultaneous confirmations | Exactly one settles |
| A resolved payout being confirmed again | 400 |
| One customer's idempotency key replayed onto another | Distinct payments |
| Unknown fields, negative amounts, scientific notation | 400 |
| Malformed ids | 404, no internals disclosed |
| Passwords, phone numbers or tokens in logs | None — grepped the log after pushing all three through |
| Account enumeration on login and password reset | Uniform responses either way |
| OTP and reset brute force | Per-account attempt counters in the database, plus tight per-route throttles (3/5min on reset request) |
| Security headers | Present |

## Two probe results that were my error, not the platform's

- **`/metrics` is not rate limited** — false. My burst was 40 requests against
  a limit of 120/minute. Repeated with 130: 120 served, 10 got 429.
- **An access token still works after logout** — true, and not a defect. It is
  a 15-minute bearer token; logout revokes the refresh token. Revoking access
  tokens on demand means a lookup per request, which is a real cost for a
  fifteen-minute window.

## What this audit cannot tell you

It was performed by the code's own author, which is worth less than an
independent one — and this round is the second time that has been demonstrated
rather than asserted: C-2 was a hole I introduced *while fixing* C-1, and I
found it only because I ran the probe again afterwards instead of trusting the
fix.

Three findings in areas that had already passed two reading-based audits and
389 tests is the useful signal here. It is evidence that the remaining unknown
defects are the ones neither reading nor these particular attacks reach —
which is an argument for an external review before real money, not a
certificate that none exist.

**Not covered by this round:** the mobile and dashboard clients as attack
surface, dependency and supply-chain review, infrastructure and network
posture, timing side channels beyond the metrics token, and anything requiring
sustained traffic to observe.
