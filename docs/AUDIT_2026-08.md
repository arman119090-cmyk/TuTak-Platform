## B. Критические ошибки

### 🔴 B1. Печать бонусов через отрицательный `bonusAmountToApply`

**Где:** `apps/api/src/modules/qr-payments/qr-payments.service.ts` (метод `redeem`), `apps/api/src/modules/ev-charging/ev-sessions.service.ts` (метод `stop`), DTO `redeem-qr.dto.ts`, `start-session.dto.ts` · endpoint `POST /v1/qr/redeem`, `POST /v1/ev/sessions/:id/stop` · таблицы `bonus_lots`, `wallets`, `transactions`

**Доказательство (живой запуск):**

```
Счёт 1000 AMD, партнёр 5% → легитимно 50 баллов
POST /qr/redeem  bonusAmountToApply: "-1000000"  → HTTP 201
  {"bonusApplied":"-1000000","bonusEarned":"50050"}
lifetimeEarned: 21101.15 → 71151.15   (+50 050 вместо +50)
```

**Почему это реальная проблема.** `IsNumberString` пропускает отрицательные числа. Проверяется только верхняя граница (`bonusToApply.greaterThan(amount)`), нижней нет. Ветка резервирования `if (bonusToApply.greaterThan(0))` для отрицательного значения пропускается, а затем `paidPortion = amount.minus(bonusToApply)` превращает вычитание в **сложение** — база начисления раздувается на любую сумму, задаваемую клиентом.

**Как проявляется.** Любой зарегистрированный пользователь печатает себе неограниченное количество баллов одним HTTP-запросом и тратит их у реальных партнёров. Партнёр получает списание, TuTak несёт обязательство. Финансово: неограниченный убыток.

**Варианты решения.**

| Вариант | Плюсы | Минусы |
|---|---|---|
| 1. `@Min(0)` через `@IsNumber` + трансформер на DTO | Точечно, быстро | Правится в 2 DTO; легко забыть третий вызов |
| 2. Guard-clause в доменном сервисе (`if (bonusToApply.isNegative()) throw`) | Защищает независимо от транспорта | Не мешает мусору дойти до сервиса |
| 3. Value-object `BonusAmount` с инвариантом «≥ 0» на конструкторе | Инвариант нельзя обойти нигде | Рефакторинг ~10 мест |
| 4. CHECK-констрейнт в БД (`bonusAppliedAmount >= 0`) | Последняя линия обороны | Ошибка вылезет как 500, а не 400 |

**Рекомендую: 1 + 2 + 4 одновременно.** DTO даёт корректный 400 пользователю, guard в сервисе закрывает любой будущий вызывающий код, CHECK в БД делает состояние непредставимым. Вариант 3 избыточен для текущего размера кодовой базы — правило пока одно.

**Риск внедрения:** низкий, чистое ужесточение. **Сложность: Low.**

**Что менять:** `redeem-qr.dto.ts` и `start-session.dto.ts` — заменить `@IsNumberString()` на `@IsNumberString()` + кастомный `@IsNonNegativeDecimal()`; в `QrPaymentsService.redeem` и `EvSessionsService.stop` добавить явный throw до расчётов; миграция с `ALTER TABLE transactions ADD CONSTRAINT ... CHECK ("bonusAppliedAmount" >= 0 AND "bonusEarnedAmount" >= 0)`.

**Тесты:** unit на `redeem` с `-1`, `"-0.0001"`, `"0"`, `"1e-10"`, `NaN`, `"Infinity"`; e2e — баланс не меняется, HTTP 400; property-тест «bonusEarned ≤ amount × rate».

**Документы:** `docs/ARCHITECTURE.md` (раздел QR-саги), `scripts/smoke-test.sh` (+2 проверки).
**Библия TuTak:** раздел *Bonus Engine → Инварианты начисления*.

### 🔴 B2. Леджер не позволяет восстановить баланс (двойной DEBIT + разная семантика `balanceAfter`)

**Где:** `apps/api/src/modules/wallet/bonus-engine.service.ts` — методы `reserve` (строка ~172) и `settleReservation` (~226) · таблица `bonus_ledger_entries`

**Доказательство:**

```
sum(CREDIT)=71151.15  sum(DEBIT)=16200.00  → разница = 54 951.15
wallet.available + pending                              = 63 051.15
расхождение 8 100 (= в точности lifetimeSpent)
redemption entries by phase: {"reserved":3, "settled":3}   ← 3 списания = 6 записей
```

**Почему это реальная проблема.** На одно списание пишутся **две** DEBIT-записи одного типа и суммы (`phase: reserved` и `phase: settled`). Различие спрятано в JSON-поле `metadata`, а не в типе или направлении. Любая агрегация «CREDIT − DEBIT» даёт неверный баланс. Дополнительно `balanceAfter` считается по-разному: в `accrue` это `available + pending`, в `reserve` — только `available`, в `settle`/`release`/`expiry` — тоже `available`. Из-за этого поле немонотонно и непригодно для сверки (в выводе: 63051.15 → 13001.15 → 12001.15 подряд).

**Как проявляется.** Бухгалтерия не может сверить обязательства по баллам. Финансовая отчётность по программе лояльности не сойдётся. При споре с партнёром или регулятором восстановить историю невозможно. `docs/ARCHITECTURE.md` утверждает «ledger is the source of truth… audit-grade» — **это утверждение сейчас фактически неверно**.

**Варианты решения.**

| Вариант | Плюсы | Минусы |
|---|---|---|
| 1. Убрать DEBIT на фазе reserve, писать только на settle | Минимальная правка, баланс сходится | Теряется след «резерв поставлен» |
| 2. Ввести отдельные типы `RESERVE_HOLD` / `RESERVE_RELEASE`, исключить их из балансовых сумм | Полная история + корректная сумма | Нужен явный контракт «какие типы балансовые» |
| 3. Полноценная двойная запись (debit/credit-счета: Available/Pending/Reserved/Spent) | Каноническая бухгалтерия, сверка тривиальна | Существенный рефакторинг + миграция |
| 4. Оставить как есть, считать баланс только из `wallets` | Ноль работы | Леджер бесполезен как источник истины — противоречит заявленной архитектуре |

**Рекомендую: 2, с фиксацией семантики `balanceAfter` как «available после операции».** Вариант 1 теряет ценную информацию о жизненном цикле резерва. Вариант 3 — правильная цель, но для MVP это переписывание ядра ради свойства, которое вариант 2 даёт на 80%; переход 2→3 позже не блокируется. Ключевое: добавить перечень балансовых типов в код **и** тест-инвариант «сумма балансовых записей = wallet.available + pending».

**Риск внедрения:** средний — меняется смысл существующих строк, нужна миграция или явная отсечка «данные до даты X считать по старым правилам». **Сложность: Medium.**

**Что менять:** `bonus-engine.service.ts` (5 мест записи в леджер), enum `BonusEntryType` (+`RESERVE_HOLD`, `RESERVE_RELEASE`), `packages/shared-types/src/enums/bonus.ts`, миграция Prisma.

**Тесты:** инвариант-тест «Σ балансовых CREDIT − Σ балансовых DEBIT = available + pending» после каждой операции; сценарии accrue→reserve→settle, accrue→reserve→release, accrue→expiry.

**Документы:** `docs/ARCHITECTURE.md` — переписать раздел про леджер честно.
**Библия TuTak:** раздел *Ledger → Модель записей и правила сверки*.

### 🔴 B3. Раскрытие чужой транзакции через `idempotencyKey`

**Где:** `apps/api/src/modules/qr-payments/qr-payments.service.ts` (начало `redeem`), `transactions.service.ts` → `findByIdempotencyKey` · таблица `transactions` (`idempotencyKey` — глобальный `@unique`)

**Доказательство:**

```
Атакующий (другой аккаунт) отправил чужой idempotencyKey:
  → {"transactionId":"f10e5abe…","amountCharged":"1000","bonusApplied":"-1000000","bonusEarned":"50050"}
*** вернулась транзакция, не принадлежащая атакующему ***
```

**Почему это реальная проблема.** Ключ уникален глобально, а не в разрезе пользователя, и при совпадении возвращается транзакция **без проверки владельца**. Ключи в мобильном клиенте предсказуемы: `${token}-${Date.now()}` (`ScanQrScreen`).

**Как проявляется.** Утечка сумм и ID чужих платежей; кроме того, злоумышленник может «занять» ключ и превратить будущий легитимный платёж жертвы в молчаливый no-op (отказ в обслуживании на уровне платежа).

**Решение.** Сделать ключ уникальным в паре с пользователем (`@@unique([userId, idempotencyKey])`) и сверять `existing.userId === payerUserId`, иначе 409. Альтернатива — хранить хеш `userId+key`; эквивалентно, но менее читаемо.

**Риск:** низкий. **Сложность: Low.**
**Тесты:** e2e — чужой ключ даёт 409, свой возвращает ту же транзакцию.
**Библия:** *QR Architecture → Идемпотентность*.

### 🔴 B4. Деактивированный пользователь сохраняет доступ

**Где:** `apps/api/src/modules/auth/strategies/jwt.strategy.ts` → `buildRequestUserClaims` (`users.service.ts`) · `PATCH /v1/admin/users/:id/active`

**Доказательство:** `before=200 after=200` — после деактивации существующий access-token продолжает работать.

**Почему проблема.** `buildRequestUserClaims` не проверяет `isActive` и не смотрит на блокировку. Refresh-путь проверяет, поэтому окно ограничено TTL access-токена (15 мин) — но при инциденте (украденный аккаунт, фрод) администратор нажимает «Deactivate» и **ничего не происходит немедленно**, а активные refresh-токены не отзываются.

**Решение (рекомендуемое).** В `buildRequestUserClaims` добавить проверку `isActive` и `lockedUntil` → `UnauthorizedException`; в `AdminService.setActive(false)` — массовый отзыв refresh-токенов пользователя. Более строгий вариант (денежный blacklist в Redis) избыточен, пока TTL 15 минут и Redis всё равно не задействован.

**Риск:** низкий. **Сложность: Low.**
**Тесты:** деактивация → следующий запрос 401; refresh после деактивации → 401.
**Библия:** *Security → Отзыв сессий*.

### 🔴 B5. Отрицательный `DEBIT` в админской корректировке пополняет кошелёк

**Где:** `apps/api/src/modules/wallet/bonus-engine.service.ts` → `manualAdjustment` · `POST /v1/wallet/admin/adjust`

**Доказательство:** `DEBIT -5000` → HTTP 201, `available: 0 → 5000`.

**Почему проблема.** `Decimal.min(remaining, lot.remainingAmount)` при отрицательном `remaining` даёт отрицательную аллокацию, а `{ decrement: negative }` = инкремент. Проверка `totalAvailable.lessThan(target)` для отрицательного `target` всегда ложна.

**Как проявляется.** Администратор (или скомпрометированный админ-аккаунт) обходит контроль «нельзя списать больше доступного» и выпускает баллы под видом списания. В аудит-логе это выглядит как обычный DEBIT — то есть **фрод маскируется под легитимную операцию**.

**Решение.** Тот же guard, что в B1 (`amount > 0` на DTO + в сервисе). Плюс — денежный CHECK в БД. **Риск: низкий. Сложность: Low.**
**Библия:** *Bonus Engine → Ручные корректировки*.

### 🔴 B6. Ноль тестов и отсутствие CI

**Где:** весь репозиторий. `find -name "*.spec.ts"` → **0 файлов**; `.github/workflows` → отсутствует.

**Почему проблема.** Всё выше найдено вручную. Jest сконфигурирован в `apps/api/package.json`, но не написано ни одного теста. `smoke-test.sh` (39 проверок) — единственная защита, и он **не поймал ни один** из B1–B5, потому что проверяет happy path. Ничто не мешает регрессии.

**Решение.** Не «покрытие ради покрытия», а целевой набор: unit на инварианты Bonus Engine (границы, конкурентность, истечение в момент удержания), e2e на саги QR/EV, негативные тесты на все найденные уязвимости. Плюс GitHub Actions с гейтами typecheck/lint/test/build.

**Риск: низкий. Сложность: Medium** (2–3 дня на осмысленный набор).
**Библия:** *Testing → Обязательный набор перед релизом*.

| Telegram-бот | Нулевой код. Отдельный продукт со своей auth-моделью — не ранее стабилизации ядра |
| Dark mode | Бонусные цвета настроены под белый; перенастройка — реальная работа без спроса |
| Реальный OCPI-клиент | Нет партнёра и креденшлов. Адаптер-шов готов, это верное состояние |
| Разделение профиля и настроек | Данных не хватает на два экрана |
| Замена «заглушки» QR ради красоты | Нужен настоящий энкодер (см. Топ-10 №10), а не другой узор |

## F. Технический долг

1. **`ARCHITECTURE.md` расходится с реальностью** — «ledger is the source of truth… audit-grade» опровергнуто B2. Документация, вводящая в заблуждение, хуже отсутствующей.
2. **Redis поднят, оплачен, не используется** — мёртвая зависимость в compose, конфиге и Dockerfile.
3. **Мёртвая модель:** `PartnerBranch`, `EvReservation` (UI отсутствует), `Device.pushToken` (push не отправляется), `FraudSignal.resolvedByUserId` частично.
4. **`NotificationChannel` PUSH/SMS/EMAIL** — только строка в БД, доставки нет.
5. **`replacedByTokenId`** — колонка без кода.
6. **«Библия TuTak» не существует** в репозитории. Разделы указаны для будущего документа, но сам он не создан.

## G. Риски запуска

| Риск | Вероятность | Ущерб | Митигация |
|---|---|---|---|
| **Печать бонусов (B1)** | Высокая — тривиально воспроизводится | Неограниченный финансовый | Блокер релиза |

| **Утечка чужих транзакций (B3)** | Средняя | Приватность, репутация | Блокер релиза |
| Фрод не останавливается деактивацией (B4) | Средняя | Продолжение атаки до 15 мин + refresh жив | Блокер релиза |

**Вывод: в текущем состоянии запускать на реальные деньги нельзя.** Не из-за незрелости архитектуры — она как раз здоровая, — а из-за пяти конкретных дефектов валидации и учёта.

## H. План по этапам

**Этап 0 — Стоп-кран (1–2 дня).** B1, B5 (валидация сумм), B3 (скоуп идемпотентности), B4 (isActive + отзыв). Негативные тесты на каждый. → *деньги перестают утекать*.

**Этап 1 — Целостность учёта (3–5 дней).** B2 (типы резерва + семантика `balanceAfter` + инвариант-тест), C1, C2 (зависшие резервы и коннекторы). → *отчётность сходится*.

**Этап 2 — Тесты и CI (2–3 дня, частично параллельно).** B6: unit Bonus Engine, e2e саг, GitHub Actions. → *регрессии ловятся автоматически*.

**Этап 3 — Прод-готовность (3–5 дней).** C3, C4, C7, D1, D4; фикс трёх мобильных багов; hydration-guard.

**Этап 4 — Функциональные пробелы (1–2 недели).** Экран активной зарядной сессии; решение по `STATIC_MERCHANT`; настоящий QR-энкодер; страница партнёра; push-доставка.
