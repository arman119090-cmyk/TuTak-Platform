# Находки

## F-1. Глобальный лимитер схлопывается в одно ведро на всех — HIGH

**Любой аноним может заблокировать вход всем пользователям сразу.**

`ThrottlerGuard` подключён глобально (`app.module.ts:117`) и ключуется по
`req.ip`. Кастомного трекера нет — проверено поиском по `getTracker`,
`extends ThrottlerGuard`, `ThrottlerStorage`: ноль совпадений.

`TRUST_PROXY` не задан намеренно (и правильно — это защита от подделки
`X-Forwarded-For`). Следствие: Express отдаёт в `req.ip` **адрес TCP-пира**, а
за балансировщиком Render это сам балансировщик. Один и тот же адрес для всех
запросов в мире.

Значит лимиты в `auth.controller.ts` не «на пользователя», а **на весь мир**:

| Эндпоинт | Лимит | Что достаточно сделать, чтобы лечь всем |
|---|---|---|
| `POST /auth/login` | 8 / мин | 8 запросов в минуту |
| `POST /auth/password-reset/request` | 3 / 5 мин | 3 запроса |
| `POST /auth/register` | 5 / мин | 5 запросов |
| `POST /auth/demo-session` | 8 / мин | 8 запросов |

Ни инструментов, ни аккаунта, ни авторизации не нужно. `curl` в цикле.

**Почему это пропустили.** В коде есть ровно эта защита — но только для OTP.
`OtpIpRateLimitService` вызывает `clientIpIsPerCaller()` и **отключает себя**,
когда IP не пер-клиентский. Предупреждение на старте прямо обещает: *«Per-IP
OTP limits are disabled in that state rather than collapsing into one shared
bucket»*. Обещание верно для OTP-лимитера и **неверно** для глобального
throttler'а, который именно схлопывается. Двух механизмов две, защита одна.

Отдельно: storage у throttler'а in-memory, не Redis. На нескольких инстансах
лимит умножается на число инстансов, а после рестарта обнуляется.

**Где сейчас:** на staging — прямо сейчас. В production — с первого дня,
если `CLIENT_IP_*` не задать.

**Что делать:** измерить хопы и задать `CLIENT_IP_STRATEGY=xff-depth` +
`CLIENT_IP_TRUSTED_HOPS` (процедура в `docs/RAILWAY_PRODUCTION_RUNBOOK_RU.md`
§9.3–9.4). Это уже числилось в списке как «включить лимиты OTP». Аудит
показывает, что цена бездействия выше заявленной: это не отключённая защита,
а работающий вектор отказа в обслуживании.

Дополнительно стоит перевести throttler на Redis-storage — иначе на
нескольких инстансах лимиты остаются приблизительными.

## F-2. `DEMO_MODE=true` снова открыл регистрацию по паролю — MEDIUM

**Причина — моё изменение в этой сессии.** Я включил `DEMO_MODE` на staging,
чтобы дать вход одним нажатием, пока не работает клавиатура.

`auth.service.ts:85`:

```ts
const isProduction = isPublicDeployment(appEnv);   // staging — публичный
if (isProduction && !demoMode) throw new ForbiddenException(...)
```

`isPublicDeployment` возвращает `true` для staging. До моего изменения
`demoMode` был `false` → регистрация закрыта. После — условие не срабатывает,
и `POST /v1/auth/register` открыт.

Что это создаёт, по описанию в самом коде: *«a fully normal, spend-capable
CUSTOMER account with zero proof of phone ownership at any point»*. Это тот
самый legacy-путь, который закрывали намеренно.

**Смягчающие обстоятельства:** staging, выдуманные данные, sandbox-эквайер,
реальных денег нет. И — по иронии — F-1 ограничивает это до 5 регистраций в
минуту на весь мир.

**Решение за вами:**
* оставить, пока идёт тестирование, — вход одним нажатием зависит от того же
  флага;
* или выключить `DEMO_MODE` и вернуться ко входу по паролю
  (`77100001` / пароль), когда клавиатура починится.

**В production `DEMO_MODE` не должен появиться никогда.**

## F-3. `fast-uri` — 4 High, исправимо — MEDIUM → LOW

`fast-uri@3.1.5`, патч в `>=3.1.6`. SSRF, host confusion, обход IDN-канонизации.

**Серьёзность снижена по факту:** тянется через `ajv` из **сборочного**
тулинга — `@angular-devkit/core` (CLI NestJS) и `schema-utils` (webpack). В
рантайм API не попадает, разбором внешних URL не занимается.

В отличие от `image-size` (2 High, `patched: <0.0.0` — исправления не
существует, dev-зависимость бандлера Expo) это чинится одной строкой в
`pnpm.overrides`. Раньше в отчётах фигурировал только неисправимый
`image-size`; `fast-uri` — новое.

Итого по аудиту зависимостей: **6 high, 5 moderate, 0 critical**.

## F-5. Утечка OTP осталась закрытой — проверено, ПОДТВЕРЖДЕНО

Это негативная находка, и она важна: включив `DEMO_MODE`, я мог открыть ту
самую дыру, которую закрывали в августе — консольный SMS-транспорт, который
пишет код подтверждения в лог.

Не открыл. Порядок проверок в `sms-transport.ts` таков, что публичное
развёртывание получает `UnavailableSmsProvider` **раньше**, чем дело дойдёт до
консольного, и `DEMO_MODE` на это не влияет:

```ts
if (isProductionDeployment(appEnv) && !demoMode) throw ...   // 124
if (isPublicDeployment(appEnv)) return new UnavailableSmsProvider();
return new ConsoleSmsProvider();   // только dev и тесты
```

Код подтверждения в логи staging не попадает ни при какой конфигурации.
