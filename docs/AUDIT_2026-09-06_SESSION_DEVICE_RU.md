Проход по тем же классам дефектов, где находки Astra подтвердились
(`docs/CLIENT_SESSION_BOUNDARY_2026-09-05_RU.md`). Логика такая: если в

## Находка A-1 (высокая) — push-токен переживает logout

**Файлы:** `apps/api/src/modules/auth/auth.service.ts:500-514`,
`apps/api/src/modules/notifications/notifications.service.ts:68-90`,
`apps/api/src/modules/notifications/push-dispatch.service.ts:37-60`,
`apps/api/prisma/schema.prisma:227-240`.

`logout()` отзывает refresh-токены (`refreshToken.updateMany` по
`userId + deviceId`) и **не трогает `Device.pushToken`**. Эндпоинта для снятия
регистрации не существует вовсе: в `NotificationsController` есть только
`POST /notifications/push-token`. Единственное место, где токен обнуляется, —
`push-dispatch.service.ts:83`, и то лишь когда Expo сам ответил
`DeviceNotRegistered`.

Что из этого следует, по шагам:

1. Пользователь A выходит из аккаунта. Строка `Device(userId=A,
   deviceId=D, pushToken=X)` остаётся жива.
2. `dispatch()` выбирает **все** устройства пользователя с непустым токеном
   (`where: { userId, pushToken: { not: null } }`) — значит A продолжает
   получать пуши на этот телефон после выхода.
3. Пользователь B входит на том же телефоне. `registerPushToken` делает
   upsert по ключу `(userId, deviceId)` — то есть создаёт **вторую** строку
   `Device(userId=B, deviceId=D, pushToken=X)` с тем же самым токеном.
4. Теперь один физический телефон подписан на уведомления **двух** аккаунтов.

Содержимое пушей — не абстрактное. `notifications.listener.ts:38`:
`push: { title: 'Payment complete', body: '${event.amount} AMD paid.' }` —
суммы платежей A попадают на экран блокировки телефона, которым пользуется B.

Это ровно тот же класс, что и утечка кэша, только серверная: клиентское
исправление от 2026-09-05 её не закрывает — там чистится кэш и токены доступа,
а строка `Device` живёт в базе.

**Как чинить (предлагаемая форма, решение за исполнителем):** обнулять
`pushToken` в `logout()` для пары `(userId, deviceId)`, тем же местом, где
отзываются refresh-токены. Удалять строку целиком не нужно — `lastSeenAt` и
`deviceName` остаются полезной историей устройства; обнулить нужно именно
адрес доставки.

## Находка A-2 (низкая) — язык интерфейса не следует за аккаунтом

**Файлы:** `apps/mobile/src/presentation/screens/settings/SettingsScreen.tsx:98-105`.

Язык переключается через `i18n.changeLanguage(locale)` и остаётся настройкой
устройства. При этом у пользователя есть серверное поле `locale`
(`AuthenticatedUserDto.locale`), и оно при входе не применяется. Итог: B
входит после A и видит интерфейс на языке, который выбрал A, хотя в его
профиле указан другой.

Это не безопасность, а согласованность: продукт заявляет три языка с первого
дня и хранит выбор пользователя на сервере — значит выбор должен ехать за
человеком, а не за телефоном.

## Задачи для ChatGPT Astra

Ниже — то, что можно передавать как есть. Задачи независимы, порядок
соответствует приоритету.

### Задача 1 — закрыть A-1: push-токен должен умирать вместе с сессией

Репозиторий: `github.com/arman119090-cmyk/TuTak-Platform`, ветку создать от
`claude/tutak-loyalty-mvp-e485jm`.

1. Прочитай `docs/AUDIT_2026-09-06_SESSION_DEVICE_RU.md` (этот файл) и
   `docs/CLIENT_SESSION_BOUNDARY_2026-09-05_RU.md` — второй показывает
   принятый в проекте стиль исправления и тестирования.
2. **Сначала напиши падающие тесты**, воспроизводящие проблему:
   - интеграционный: A регистрирует push-токен → A выходит → `dispatch` для A
     **не** должен найти ни одного адреса доставки;
   - интеграционный: A регистрирует токен X → A выходит → B входит на том же
     `deviceId` и регистрирует тот же токен X → уведомление для A **не**
     уходит на X;
   - регрессия: выход на одном устройстве не должен снимать push-регистрацию
     **других** устройств того же пользователя;
   - регрессия: обычная работа push-доставки внутри живой сессии не сломана.
3. Затем исправь причину в `auth.service.ts:logout()` — обнули `pushToken`
   для пары `(userId, deviceId)` в той же операции, где отзываются
   refresh-токены. Строку `Device` не удаляй.
4. Проверь, нужно ли то же самое на пути удаления аккаунта — там каскад
   `onDelete: Cascade` уже удаляет `Device`, так что скорее всего не нужно;
   подтверди это тестом или чтением, не догадкой.
5. Прогони: `pnpm --filter @tutak/api test`, интеграционные тесты API,
   `pnpm typecheck`, `pnpm lint`.

**Критерий приёмки:** после `POST /auth/logout` ни один пуш пользователя не
доходит до этого устройства, при этом его другие устройства продолжают
получать уведомления, и все существующие тесты API зелёные.

### Задача 2 — закрыть A-2: язык следует за аккаунтом

1. При входе (все пути: пароль, OTP-вход, OTP-регистрация, регистрация) и при
   восстановлении сессии применять `user.locale` через `i18n.changeLanguage`.
2. Ручной выбор языка в настройках должен по-прежнему работать и сохраняться
   на сервере для этого пользователя — иначе выбор будет откатываться при
   следующем входе. Проверь, есть ли уже эндпоинт обновления локали; если
   нет — **не выдумывай его молча**, опиши в отчёте, что его нет.
3. Тесты: вход A (hy) → выход → вход B (ru) → интерфейс на ru.
4. Прогони mobile-тесты и `scripts/build-demo-app.sh` (иначе упадёт проверка
   дрейфа `demo/` в CI).

### Задача 3 — независимая проверка того, что уже исправлено

Не переделывать, а **попробовать сломать**. Коммит `b24e6ed` ввёл
`sessionEpoch` в трёх клиентах. Найди сценарий, при котором закрытая сессия
всё-таки оживает или данные одного пользователя попадают другому: гонки при
холодном старте (`hydrate`), два одновременных входа, отказ SecureStore
на запись, повторный вход в тот же аккаунт, восстановление сессии по cookie
в веб-кабинетах. Если найдёшь — тест плюс исправление; если нет — так и
напиши, отрицательный результат тоже результат.

### Общие правила для всех трёх задач

- Ничего не выдумывать: домены, `SMS_ENDPOINT`, секреты, сроки хранения
  данных — это решения владельца, а не инженера. При нехватке данных —
  явный отказ с понятным сообщением, а не тихий fallback.
- Не трогать бизнес-логику и production-инфраструктуру, не относящуюся к
  задаче. Решения из `docs/NEXT_CLAUDE_TASK.md` не пересматривать.
- Не пушить в `claude/tutak-loyalty-mvp-e485jm` напрямую и не трогать
  открытый PR #29 (`design/tutak-mobile-v2-handoff`).
- Отчёт — отдельным файлом в `docs/` в стиле остальных отчётов репозитория:
  дата в названии, находки со ссылками `файл:строка`, что исправлено, какие
  тесты прогнаны и с каким результатом.
