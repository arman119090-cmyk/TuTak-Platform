## Что блокирует запуск на реальных пользователях

Семь пунктов. Первые три — блокеры в строгом смысле.

1. **Репозиторий разошёлся на четыре истории, ни одна не является «TuTak сегодня».**

6. **Бэкапы Railway не проверены восстановлением.**
7. **Боевого эквайринга нет** — если нужны платежи картой.

# ЧАСТЬ II. АУДИТ ПО НАПРАВЛЕНИЯМ

## 1. Безопасность

### 1.1 Что уже сделано — и сделано хорошо

**Валидация входа — образцовая.** `apps/api/src/main.ts:163`:

```ts
new ValidationPipe({
  whitelist: true,
  forbidNonWhitelisted: true,
  transform: true,
  transformOptions: { enableImplicitConversion: true },
})
```

`forbidNonWhitelisted` — это то, что многие забывают: неизвестное поле в теле
не «отбрасывается тихо», а отклоняет запрос. Массовое присвоение закрыто.

**SQL-инъекции.** Prisma параметризует всё. Сырых запросов в доменном коде
нет — единственные `$executeRawUnsafe` находятся в тестовой подготовке базы
(`apps/api/test/setup/global-setup.ts`) и там подставляется имя базы из
конфигурации, а не из запроса.

**XSS.** Дашборды на Next.js, дизайн-пакет проверяет заголовки
(`packages/design/security-headers.test.mjs`), CSP собирается на сборке.
`dangerouslySetInnerHTML` в коде нет.

**Rate limiting — три уровня, не один.**

* глобальный `ThrottlerModule` (`apps/api/src/app.module.ts:69`);
* поэндпоинтные лимиты — 20 штук, например `auth.controller.ts:69`
  «5 запросов в минуту» на запрос OTP, `:239` «3 в 5 минут» на смену пароля;
* отдельный сервис `otp-ip-rate-limit.service.ts` плюс глобальный бюджет СМС
  (`SmsBudgetService`), который **отказывает при недоступности Redis**, а не
  открывается — «неоплаченный счёт оператору не является приемлемой
  деградацией».

Ключ лимита выбирается осознанно: `ClientIpThrottlerGuard`
(`apps/api/src/common/guards/client-ip-throttler.guard.ts`), а вопрос «кто
такой клиент» решается явной настройкой `TRUST_PROXY` или
`CLIENT_IP_STRATEGY`. По умолчанию не доверяется ничего — заголовок
`X-Forwarded-For` подделать нельзя. Это уже результат пентеста 19.08.2026,
комментарий в `main.ts:96` описывает найденный обход.

**CORS.** Allow-list обязателен: без `CORS_ORIGINS` публичный деплой **не
стартует** (`main.ts:75`). Есть отдельная проверка `assertProductionCorsOrigins`
— список с localhost в проде тоже отклоняется. Ранее был fallback на домены
Render, его убрали намеренно.

**CSRF.** Refresh-токен в `httpOnly` cookie, доступ — Bearer-токен в
заголовке. Классический CSRF на Bearer не работает. Отдельный CSRF-токен для
cookie-эндпоинта `/auth/refresh` не помешал бы, но при `SameSite` он не
блокер.

**Аудит-лог.** 40+ типов событий в `AuditAction`
(`apps/api/prisma/schema.prisma:2684`), и это не только «вход/выход»:
`BONUS_ACCRUED`, `BONUS_RESERVED`, `BONUS_SETTLED`, `PAYOUT_RESOLVED`,
`ACQUIRER_SETTLEMENT_RECORDED`, `PARTNER_COLLECTION_CONFIRMED`,
`ACCOUNT_ANONYMIZED`. Записи о деньгах пишутся **внутри той же транзакции
базы**, что и само движение — то есть проводки без следа не бывает.

**Fraud detection.** `apps/api/src/modules/security/fraud-detection.service.ts`
— проверка аномальной скорости операций и `AuditAction.FRAUD_FLAGGED`. Плюс
доменные правила: нельзя погасить собственный QR, транзакция без партнёра не
двигает реферальный прогресс, лимит слотов, заработок только с подтверждённым
номером.

**Секреты.** В git не лежат — проверено: в репозитории есть только
`.env.example`. Всё живое — в панели Railway. Логи структурированные, и
Sentry-события чистятся allow-list'ом (`sentry-sanitize.ts:58`), то есть в
трекер уезжает только явно разрешённое, а не «всё кроме запрещённого».

### 1.2 Что не сделано

**SSL pinning — отсутствует, и в коде это честно записано** (`app.config.js:122`):

> «…whoever presented a certificate the device trusts. It is not certificate
> pinning, and this app has none».

**Нужен ли он вам?** На вашем уровне — **нет, и я бы не делал его сейчас.**
Пиннинг защищает от одного сценария: телефон с установленным чужим корневым
сертификатом (корпоративный MITM, вредонос). Против этого он работает. Но у
него есть цена: при плановой смене сертификата на сервере **все установленные
приложения перестают работать одновременно**, и починить это можно только
новой сборкой в сторе. Для платформы без штатного мобильного релиз-процесса
это риск больше того, который он снимает. Возвращаться к нему стоит, когда
будут карточные платежи и налаженный релизный цикл.

**Ротации секретов нет.** Ни расписания, ни процедуры, ни двух ключей
одновременно (JWT не поддерживает второй ключ на время перекрытия — значит
ротация `JWT_ACCESS_SECRET` разлогинит всех). Это надо описать, а для JWT —
доработать код.

**Уязвимости в зависимостях — 37, из них важны четыре.**

Прогон `pnpm audit --prod` сегодня:

| пакет | уровень | где | реально ли опасно |
|---|---|---|---|
| `next` 16.3.0 → **16.3.3** | **critical** | `apps/admin`, `apps/partner` | **Да.** Это сервер, который смотрит наружу |
| `multer` 2.2.0 → 2.3.0 | high | `apps/api` через `@nestjs/platform-express` | **Да.** Обход лимита размера файла; загрузки у вас есть |
| `sharp` 0.35.3 → 0.35.4 | high | `apps/api` | **Да.** Обрабатывает присланные картинки |
| `qs` 6.15.3 → 6.16.0 | moderate | `apps/api` через express | Умеренно |
| `@xmldom/xmldom`, `image-size`, `js-yaml` (23 шт.) | high/moderate | инструменты сборки Expo | **Нет.** На телефон и на сервер не попадают |

CI намеренно не валит сборку на аудите (`ci.yml`, шаг «Dependency audit
(advisory only)») — и в комментарии там написано, что все находки на тот
момент были сборочными. **Это перестало быть правдой:** сегодня три из них
сидят в рантайме. Комментарий сам предсказал этот момент: «if one ever lands
in an API production dependency, this is where it shows up first and the gate
becomes worth arguing about». Момент настал.

**Пентест.** Один уже был — 19.08.2026, его следы видны в коде
(`docs/AUDIT_PENTEST_FULL_2026-09-03.md`, `HARDENING_AUDIT_2026-08-19-P0-P3.md`).
Перед боевым запуском нужен повторный, потому что с тех пор появились две
панели, шлюз Viva и OTP-регистрация.

| переменная | задана? | следствие |

## 3. Производительность и масштабирование

**Нагрузочное тестирование — инструмент есть, цифр нет.**
`apps/api/src/scripts/load-test.ts` — грамотный: гоняет не HTTP (упрётся в
throttler), а сами движки, и в конце **проверяет, что реестр сошёлся**.
Запускался ли он на Railway — свидетельств нет. Цифр по одновременным
пользователям у меня нет, и придумывать их я не буду.

**Пул соединений — управляется.** `apps/api/src/infrastructure/prisma/database-url.ts`
дописывает `connection_limit` и `pool_timeout` в URL, уважая уже заданные.
Но на Railway `DATABASE_URL` их не содержит и переменных-настроек нет →
работает умолчание Prisma (`num_cpus × 2 + 1`). При нескольких инстансах это
переполнит Postgres. Считать надо так:
`connection_limit × число инстансов + запас < max_connections`.

**Индексы — 98 объявлений** `@@index`/`@@unique` на 57 моделей. Явных N+1 в
горячих путях я не нашёл: чтения идут через `include`.

**PostGIS — не нужен сейчас.** Поиск «рядом» сделан двухступенчато: SQL
сужает по прямоугольнику (`ev-stations.service.ts:94`), затем гаверсинус в JS
(`common/utils/geo.ts`) точно считает и сортирует. До нескольких тысяч точек
это быстрее PostGIS. Возвращаться — когда точек станут десятки тысяч или
понадобится поиск по полигонам.

**Кэша нет.** Redis используется под лимиты, блокировки, очереди — но не как
кэш ответов. Пока партнёров единицы, это правильно: инвалидация кэша дороже
самой выборки. Понадобится, когда «партнёры рядом» станет самым частым
запросом.

**CDN не нужен**, пока файлы отдаёт API. Понадобится вместе с S3.

**Горизонтальное масштабирование — код готов, конфигурация нет.**
Готов: outbox разгребается через `FOR UPDATE SKIP LOCKED` (несколько
воркеров безопасны), есть распределённая блокировка
(`distributed-lock.int-spec.ts`), сессии в Redis, а не в памяти.
Не готов: пул соединений не задан; `SWEEPS_ENABLED` включён на всех
инстансах — фоновые задачи будут запускаться в каждом (безопасно, но
расточительно); правильная схема — веб-инстансы со `SWEEPS_ENABLED=false` и
один воркер.

## 4. Данные и бэкапы

**Инструменты — на удивление зрелые.** В `scripts/`:
`backup.sh`, `restore.sh`, `pitr-archive.sh`, `pitr-basebackup.sh`,
`pitr-restore.sh`, **`pitr-rehearse.sh`**, `chaos-postgres.sh`. И в CI есть
шаг **«Backup and restore rehearsal»**, который сегодня прошёл.

**Но:** всё это про самостоятельно поднятый Postgres. На Railway база
управляемая, и её бэкапы — отдельный механизм, **который я из своей среды
проверить не могу**. Нужно открыть панель и убедиться, что они включены,
посмотреть частоту и срок хранения, и **один раз восстановить в отдельную
базу**. Бэкап, из которого никто не восстанавливался, — это надежда, а не
бэкап.

**Retention есть** — `apps/api/src/modules/retention/retention.service.ts`
чистит уведомления, сессии, истёкшие QR, записи идемпотентности,
обработанные события outbox, по настраиваемым срокам.

**Удаление аккаунта есть** — `account-deletion.service.ts`, с отсрочкой и
последующей анонимизацией; в аудите остаются `ACCOUNT_DELETION_REQUESTED` и
`ACCOUNT_ANONYMIZED` — «достаточно, чтобы ответить „удалили ли и когда“, и
ничего сверх этого». Это ровно то, чего требует GDPR.

**Персональные данные:** телефон, имя, фамилия, e-mail, локаль в `User`;
координаты не хранятся (передаются в запросе). Пароли — argon2. **Отдельного
шифрования полей нет.** Шифрование дисков — на стороне Railway, отдельно не
настраивается.

## 6. CI/CD и DevOps

### 6.1 CI — сильный, но сегодня **красный** на боевой ветке

`.github/workflows/ci.yml` делает всё правильное: lint, typecheck, сверка
двух копий Sentry-очистителя, юнит-тесты, интеграционные **на настоящем
Postgres**, **проверка расхождения миграций и schema.prisma**, тесты
мобильного, обеих панелей, сборка всех приложений, сборка трёх Docker-образов,
подъём всего стека, e2e Playwright и репетиция бэкапа.

**Проблема:** прогон **#533** на `fix/viva-gateway-path-signing` — той самой
ветке, из которой собран прод — **упал**. Шаг «Integration tests» шёл
с 14:09:40 до 14:24:53 при `timeout-minutes: 15`. Это не падение теста, это
**упор в потолок времени**. Локально тот же набор идёт 250 секунд, на раннере
GitHub — на грани.

То есть: **ветка, из которой работает прод, сейчас красная.**

### 6.2 CD

Railway деплоит автоматически при пуше в ветку сервиса. Разделения
staging/production **нет**: одно окружение `production`, помеченное
`APP_ENV=staging`. Отката одной командой нет — Railway умеет
«redeploy предыдущего», но процедуры не записано.

### 6.3 Работа с репозиторием — **самое слабое место всего проекта**

Проверено сегодня:

```
ветка по умолчанию: claude/tutak-loyalty-mvp-e485jm   ← фиче-ветка!
защищённых веток:   0 из 20
```

**Ни `main`, ни `master` не существует.** Веткой по умолчанию назначена
фиче-ветка недельной давности.

Хуже: **четыре истории разошлись и ни разу не сводились.**

| ветка | чем является | коммитов, которых нет в остальных |
|---|---|---|
| `claude/tutak-loyalty-mvp-e485jm` | «ветка по умолчанию» | отстаёт на 24 |
| `fix/viva-gateway-path-signing` | **что работает в проде** | 10 |
| `fix/mobile-api-base-url-railway` | **из чего собран APK №44** | 44 |
| `claude/railway-connector-check-wy0ffq` | отчёты и новые тесты | 24 |

**Ни одна ревизия в этом репозитории не является «TuTak сегодня».**
Исправление подписи Viva, благодаря которому доходят СМС, есть только в
одной ветке. Тест, закрывающий цепочку до реферальной награды, — только в
другой. Правка клавиатуры — в третьей.

Это не косметика. Это означает, что:
* нельзя откатиться на «предыдущую хорошую версию» — её не существует;
* CI зелёный на одной ветке ничего не говорит о другой;
