## 0. Где лежит код и почему не в отдельном репозитории

Вы просили отдельный репозиторий. Создать его не удалось: GitHub App,
подключённый к этой сессии, возвращает `403 Resource not accessible by
integration` на `POST /user/repos` — у него нет права «Administration: write»,
то есть создавать репозитории от вашего имени он не может.

Поэтому проект собран как **самостоятельный монорепозиторий внутри папки
`cash-out/`**: у него свои `package.json`, `pnpm-workspace.yaml`, `.gitignore`,
`README.md`, `.github/workflows/`. Он не подключён к workspace TuTak
(`pnpm-workspace.yaml` TuTak охватывает только `apps/*` и `packages/*`) и не
имеет с ним ни одной общей зависимости.

**Перенос в отдельный репозиторий — одна команда**, история сохраняется:

```bash
# 1. Создайте пустой приватный репозиторий cash-out на github.com/new
# 2. Затем:
git subtree split --prefix=cash-out -b cash-out-main
git push git@github.com:<вы>/cash-out.git cash-out-main:main
```

Либо просто скопировать папку в новый репозиторий, если история не нужна.

## 1. Краткая фактическая архитектура

### Главное архитектурное решение

Cash Out находится между двумя системами, которыми мы не управляем:

- **A. Баланс водителя внутри парка Yandex** — читается и изменяется через
  Fleet API.
- **B. Реальный банковский перевод** — выполняет лицензированный банк/PSP.

Ни одна из них не участвует в нашей транзакции. Значит, у каждой выплаты есть
окно, в котором одна сторона применена, а вторая — нет. Вся архитектура следует
из одного вопроса: **какую из двух операций мы можем отменить?**

- Состоявшийся банковский перевод отменить нельзя.
- Списание баланса в Yandex — это бухгалтерская запись, её всегда можно
  компенсировать обратной проводкой.

**Поэтому сначала списание в Yandex, и только после подтверждённого списания —
поручение банку.** В обратном порядке сбой Yandex после успешного перевода
означал бы безвозвратную потерю денег на каждой такой выплате.

Я **не принял предложенный в задании state machine как есть** — в нём
`YANDEX_RECONCILED` стоит после `PAYOUT_CONFIRMED`, то есть деньги уходят в банк
до фиксации в Yandex. Это как раз опасный порядок. Обоснование замены — в
заголовке файла `packages/contracts/src/withdrawal-state.ts`.

### Конечный автомат выплаты (18 состояний)

```
CREATED → RISK_CHECK → RESERVING → RESERVED → PAYOUT_SUBMITTING
        → PAYOUT_SUBMITTED → PAYOUT_CONFIRMED → COMPLETED

Ветки:  RISK_REVIEW (решает человек) → REJECTED
        RESERVE_UNCERTAIN / PAYOUT_UNCERTAIN (исход неизвестен → зонд)
        PAYOUT_FAILED / PAYOUT_RETURNED → COMPENSATING → REVERSED
        FAILED (ничего не двигалось)   MANUAL_REVIEW (нужен оператор)
```

Ключевое отличие от «обычного» автомата: **неопределённость — это состояние, а
не исключение.** У любого внешнего вызова три исхода, а не два: применено, не
применено и *неизвестно*. Схлопывание «неизвестно» в «ошибку» — это ровно то,
как водителю платят дважды. Поэтому у каждого внешнего вызова есть отдельное
состояние `*_UNCERTAIN`, выйти из которого можно только зондированием удалённой
системы по нашему собственному ключу идемпотентности.

Инварианты автомата проверяются тестами, в том числе: «никогда не переходит в
FAILED из состояния, где водитель уже списан», «в COMPLETED только из
PAYOUT_CONFIRMED или по решению оператора», «в REVERSED только через
COMPENSATING».

### Принцип «сначала записать намерение, потом действовать»

Каждому внешнему вызову предшествует переход в состояние `*_ING`. Процесс,
умерший посреди вызова, оставляет строку «мы, возможно, вызвали Yandex», и
восстановление — это зонд, а не догадка. Обратный порядок (сначала вызов, потом
запись) теряет именно ту информацию, которая нужна при сбое между ними.

Внутри транзакции БД внешние вызовы не делаются никогда: медленный банк не
должен держать открытой транзакцию.

### Деньги

Суммы — целые минорные единицы на `bigint`: в `packages/money`, в колонках
`BigInt`, и на проводе как `{ minor: "123456", currency: "AMD" }`. Ни float, ни
JSON-number рядом с суммой нет нигде: `double` теряет минорные единицы AMD выше
2^53, а активный парк такие суммы набирает.

Комиссии — точные рациональные дроби (`числитель/знаменатель`, обычно базисные
пункты) с явным режимом округления на каждый компонент. Инвариант
`gross = net + платформенная + банковская` проверяется трижды: в движке
комиссий, `CHECK`-ограничением в БД и перед записью в леджер.

### Леджер

Полноценный двойной учёт, только добавление. Ни один денежный факт не
утверждается иначе как сбалансированной проводкой; ошибка исправляется обратной
проводкой, а не правкой.

```
WITHDRAWAL_RESERVE   Дт PARK_RECEIVABLE   gross    Кт DRIVER_PAYABLE   gross
FEE_CAPTURE          Дт DRIVER_PAYABLE    комиссии Кт *_FEE_REVENUE    комиссии
PAYOUT_SETTLEMENT    Дт DRIVER_PAYABLE    net      Кт PSP_SETTLEMENT   net
COMPENSATION         Дт DRIVER_PAYABLE    net      Кт PARK_RECEIVABLE  gross
                     Дт *_FEE_REVENUE     комиссии
```

Три независимых механизма должны согласиться, прежде чем проводка появится:
проверка в коде, уникальный индекс по ключу идемпотентности записи и
**отложенный constraint-триггер**, пересчитывающий сумму проводок в момент
commit. `UPDATE` и `DELETE` по `journal_entries`, `ledger_postings`,
`withdrawal_events` и `audit_logs` отклоняются триггером на уровне БД.

Проверено вживую:

```
ERROR:  Journal entry ... does not balance in AMD: debits 100000 <> credits 99999
ERROR:  Table ledger_postings is append-only: UPDATE is not permitted.
ERROR:  Table journal_entries is append-only: DELETE is not permitted.
```

### Конкурентность

- **Одна живая выплата на водителя** — частичный уникальный индекс. Проверка
  есть и в коде (ради внятной ошибки), но два запроса на двух серверах в одну
  миллисекунду прошли бы её оба.
- Создание выплаты — `SERIALIZABLE` под advisory-lock по водителю, повтор только
  при serialization failure.
- Каждая смена состояния — условный `UPDATE ... WHERE version = ?`, так что два
  воркера не перезапишут решение друг друга.
- Воркеры берут аренду (lease) на выплату; аренда мёртвого процесса истекает.

### Восстановление и сверка

Ничто не зависит от промиса в памяти: воркер подметает все строки, готовые к
действию, повторяет с экспоненциальной задержкой и эскалирует человеку по
истечении SLA, а не даёт выплате тихо стареть.

Сверка — три независимых прогона: `LEDGER` (книги сами с собой), `YANDEX`
(каждое списание против транзакций парка), `PROVIDER` (каждый перевод против
записи банка, включая критический случай «мы отменили, а банк заплатил»).

## 2. Внешние интеграции и неизвестные данные

### Yandex Fleet API

**Самый важный факт: Fleet API никому не платит.** Он даёт доступ к внутреннему
учёту парка — прочитать баланс водителя и провести транзакцию, меняющую его.
Попадание денег на карту водителя — отдельное действие лицензированного банка
или PSP за счёт денег парка (или Cash Out). Так устроены все коммерческие
сервисы моментальных выплат для парков.

**Официальная документация была недоступна.** Домен `yandex.ru` (включая
`fleet.taxi.yandex.ru`) заблокирован egress-политикой этой сессии — я ничего
оттуда не копировал и ничего не выдумывал.

То, что закодировано в живом адаптере, подтверждено двумя независимыми
open-source клиентами и поисковым индексом официального справочника, которые
согласуются между собой:

| Деталь | Источник | Доверие |
| --- | --- | --- |
| Базовый URL `https://fleet-api.taxi.yandex.net` | оба клиента | высокое |
| Заголовки `X-Client-ID`, `X-API-Key` | оба клиента + индекс справочника | высокое |
| Заголовок `X-Idempotency-Token` | оба клиента | высокое |
| Заголовок `X-Park-ID` на v2 | индекс справочника | среднее |
| `POST /v1/parks/driver-profiles/list` | оба клиента + индекс | высокое |
| `POST /v2/parks/driver-profiles/transactions` | оба клиента | высокое |
| `POST /v2/parks/driver-profiles/transactions/list` | оба клиента | высокое |
| `accounts[].balance`, `.currency`, `.balance_limit` | индекс справочника | среднее |
| Имена полей запроса (`park_id`, `driver_profile_id`, `category_id`, `amount`, `description`) | один клиент | среднее |
| Имена полей ответа | выведены по аналогии | **низкое** |
| Коды ошибок и их значения | неизвестны | **нет** |
| Лимиты частоты запросов | неизвестны | **нет** |
| Дедуплицирует ли `X-Idempotency-Token` создание транзакции | **неизвестно** | **нет** |

Адаптер написан оборонительно именно из-за последней группы: ответ 2xx, который
он не смог разобрать, возвращается как `UNKNOWN`, а не как успех и не как
ошибка — оркестратор зондирует, а не угадывает.

**Адаптер обязан быть проверен на реальном песочном парке до того, как
`YANDEX_MODE=live` будет разрешён где бы то ни было.** Полный список из семи
вопросов — в `cash-out/docs/YANDEX_INTEGRATION.md`.

### Банк / PSP

Провайдер не выбран, поэтому живого адаптера **нет вообще**. Есть порт
`PaymentProviderPort`, mock и проверка вебхуков по той же схеме, которую должен
будет использовать живой адаптер. `PROVIDER_MODE=live` падает при старте с
внятным сообщением, а не притворяется.

Написать «живой» адаптер против воображаемого API — значит получить код, который
выглядит готовым и таковым не является.

## 3. Реальные блокеры

| Блокер | Почему это блокер |
| --- | --- |
| **Лицензированный платёжный партнёр** | Перевод денег на чужую карту — регулируемая деятельность. Нужен договор, а в большинстве юрисдикций — лицензия или партнёр, у которого она есть. |
| **Разрешение Яндекса** | У Яндекса есть собственный продукт моментальных выплат (через Яндекс Банк в РФ). Может ли независимый сервис использовать Fleet API таким образом на вашем рынке — вопрос коммерческий, не технический. |
| **Доступы парка** | API-ключ принадлежит парку, не нам. Как и решение позволить третьей стороне списывать балансы своих водителей. |
| **AML/KYC** | Кто проверяет личность водителя, что скринится, что и кому репортится — это дизайн комплаенса вместе с партнёром. |
| **Категория транзакции Yandex** | Списание нельзя провести без существующего `category_id`; его выдаёт владелец парка. |
| **SMS-шлюз** | Без реального провайдера в продакшене никто не сможет войти. |
| **Юридические документы** | Условия, политика конфиденциальности, политика хранения данных — работа юриста, а не разработчика. |

## 5. Дизайн-система

Токены (`packages/design-tokens`) — единственный источник: семантические роли
цвета (не «jade 600», а «фон основного действия»), шкала отступов по 4pt,
типографическая шкала, радиусы, тени, длительности анимаций, брейкпойнты,
минимальные размеры касания.

Решения, которые стоит знать:

- **Основная кнопка — 60pt в высоту**, не 44pt (это платформенный минимум, а не
  цель). Главный сценарий используется одной рукой, в машине, иногда в
  перчатках.
- **Баланс и итоговая сумма — 48pt, моноширинные цифры**, чтобы число не дрожало
  при обновлении и читалось на расстоянии вытянутой руки.
- **Статус несёт слово и знак, а не только цвет** — примерно один мужчина из
  двенадцати не различает красный и зелёный.
- **Контрастность проверяется тестами**: математика WCAG вынесена в код, и
  изменение палитры, уронившее подпись кнопки ниже 4.5:1, роняет CI, а не
  доезжает до водителя, щурящегося на солнце.

Компоненты: Text, Button, Card, Input, Screen, Skeleton, EmptyState, ErrorState,
Sheet (bottom sheet), Dialog, ListRow, AmountRow, WithdrawalRow, StatusChip,
BalanceHero, AmountField.

## 6. Мобильное приложение

19 экранов на expo-router: Splash, Onboarding, Phone, OTP, Driver linking,
Home/Balance, Withdraw amount, Payout method, Review, Confirmation (bottom
sheet), Processing, Success, Failure, History, Withdrawal details, Profile,
Devices, Support, Legal.

Главный сценарий: **открыть → увидеть баланс → «Вывести» → сумма → комиссии и
итог → подтвердить → понятный статус.**

Две детали, которые важнее, чем выглядят:

- **Ключ идемпотентности создаётся один раз** при открытии экрана проверки и
  переиспользуется при каждом повторе подтверждения. Он идентифицирует
  *намерение* водителя, а не HTTP-попытку: нажатие «повторить» после таймаута
  сервер распознаёт как ту же выплату, а не как вторую.
- **Экран «Отправляем деньги» говорит, что приложение можно закрыть** — и это
  правда: выплату двигает серверный воркер по строке в БД, а не открытый экран.
  Сказать это прямо — значит снять тревогу, которая заставляет людей нажимать
  «Вывести» второй раз.

Языки: армянский (по умолчанию), русский, английский. Переводы типизированы по
английскому дереву — ключ, добавленный без перевода, роняет компиляцию, а не
выводит английскую строку на армянский экран.

## 7. Админка

13 маршрутов: dashboard, withdrawals, needs attention, withdrawal details,
drivers, driver details, reconciliation, fees, limits, integrations, audit log,
sign-in.

- **Дашборд начинается с вопроса «у кого сейчас застряли деньги»**, а не с
  выручки. Платёжная операция, которая начинает с графика выручки, узнаёт о
  застрявшей выплате от водителя.
- Сессия оператора — в httpOnly-куке, прикрепляется на сервере; XSS в графике не
  унесёт её.
- Навигация фильтруется по правам оператора, но сервер проверяет права в любом
  случае — скрытая ссылка это вежливость, а не контроль.
- Разрешение ручной проверки требует письменной причины; отметка «деньги дошли»
  дополнительно требует ID транзакции провайдера как доказательства.
- Плитка интеграции показывает `MOCK`, а не `OK`, если процесс работает против
  заглушки. Зелёный mock хуже отсутствия плитки.

## 8. Безопасность

Реализовано: OTP (scrypt-хэш кода, три независимых лимита — на номер, на IP,
кулдаун; привязка к устройству; 5 попыток), ротация refresh-токенов с отзывом
всей «семьи» при повторном предъявлении, немедленный отзыв сессии, шифрование
колонок AES-256-GCM с идентификатором ключа (готовность к ротации), peppered
HMAC-отпечатки, подписанные котировки, идемпотентность с привязкой к хэшу
запроса, лимиты и velocity, объяснимый риск-скоринг, RBAC с fail-closed
(эндпойнт без объявленного права отклоняется), обязательный TOTP для всех ролей,
способных действовать, блокировка аккаунта после 5 неудач, подпись вебхуков по
сырому телу + окно свежести + дедупликация, редактирование секретов в логах,
хранение токенов в Keychain/EncryptedSharedPreferences.

Данные карт до Cash Out не доходят: их собирает SDK провайдера, к нам приходит
одноразовый токен. В базе — ссылка провайдера, маска и отпечаток.

Не сделано: автоматическая ротация ключей (формат готов, задание на
перешифровку не написано), Redis-лимитер для нескольких инстансов, пентест,
формальная модель угроз, привязка устройств для операторов.

| `@cashout/design-tokens` | 16 | контраст WCAG AA для светлой и тёмной темы, шкалы, CSS-экспорт |
| `@cashout/i18n` | 16 | полнота локалей, совпадение плейсхолдеров, формат денег без float |
| API unit | 29 | криптография (шифрование, хэши, отпечатки, подписи, CSPRNG), TOTP против векторов RFC 6238 |
| API integration | 80 | **против настоящего PostgreSQL** |

Интеграционные тесты идут против реального PostgreSQL намеренно: половина того,
что не даёт заплатить водителю дважды, живёт в базе — serializable-изоляция,
частичные уникальные индексы, отложенные constraint-триггеры, advisory locks.
Заглушка не проверила бы ничего из этого.

Что именно проверяется в форме, которую принимает реальный мир:

- списание в Yandex, дошедшее после того, как мы перестали ждать ответа;
- два телефона, подтверждающие выплату в одну миллисекунду;
- банк, который провёл перевод и затем вернул его;
- вебхук, доставленный дважды;
- переигранный вебхук с валидной подписью;
- котировка, отредактированная прямо в базе;
- refresh-токен, предъявленный после ротации;
- оператор, отмечающий выплату завершённой без доказательства;
- попытка отредактировать леджер и журнал аудита.

**Тесты нашли три настоящих бага** в уже написанном коде:

1. Postgres суммирует `bigint` в `numeric`, драйвер отдавал его строкой — и
   баланс леджера шёл через IEEE double. Исправлено явными приведениями
   `::bigint`.
2. Кулдаун OTP сравнивал внедрённые часы с меткой времени базы; два источника
   времени могли разойтись, и кулдаун тихо переставал работать.
3. Ограничитель частоты читал настенные часы, когда всё остальное читало часы
   как зависимость.

## 10. Проверено вживую

- Миграции применяются на чистой БД; триггеры и частичные индексы созданы.
- Инварианты БД действительно срабатывают (вывод выше).
- API поднимается, `/healthz` и `/readyz` отвечают, `readyz` сообщает
  `yandexMode: mock`, `providerMode: mock` и `ledger: balanced`.

- Вход администратора без второго фактора → `FORBIDDEN` («two-factor must be

  несуществующего аккаунта.

- Вебхук без подписи → `FORBIDDEN: missing_signature`.
- Некорректное тело → `VALIDATION_FAILED` с разбором по полям.
- Админка собирается (`next build`), все 13 маршрутов на месте.
- `pnpm -r typecheck` — чисто во всех шести пакетах.
- `pnpm format:check` — чисто.

## A. ЧТО УЖЕ РАБОТАЕТ

- Арифметика денег: целые минорные единицы, точные комиссии, инвариант
  `gross = net + комиссии`, проверяемый трижды.
- Конечный автомат выплаты со всеми ветвями отказа и компенсации.
- Двойной леджер: только добавление, баланс проверяется БД на commit, правка и
  удаление запрещены триггером.
- Котировки: свежий баланс, HMAC-подпись, одноразовость, TTL 2 минуты.
- Оркестрация выплаты: резерв → выплата → закрытие, зонды при неопределённости,
  компенсация при отказе, аренды, backoff, эскалация по SLA.
- Идемпотентность на всех трёх уровнях (клиент, Yandex, провайдер).
- Конкурентность: serializable + advisory lock + версионирование + частичные
  уникальные индексы.
- Лимиты (сумма, день, неделя, месяц, velocity) и объяснимый риск-скоринг.
- Авторизация водителя: OTP, устройства, сессии, ротация токенов.
- Привязка водителя к профилю Yandex с защитой от неоднозначного совпадения.
- Админка: вход с TOTP, RBAC, разрешение ручных проверок, управление
  комиссиями и лимитами, сверка, журнал аудита.
- Сверка: три прогона, очередь расхождений.
- Вебхуки: подпись, окно свежести, дедупликация, учёт состояния.
- Мобильное приложение: 19 экранов, 3 языка, дизайн-система с проверяемым
  контрастом.
- CI: типы, тесты, формат, миграции против PostgreSQL.
