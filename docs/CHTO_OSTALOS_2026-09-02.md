# Часть 1. Про логин и пароль Viva

## Коротко: не присылайте их мне

Не потому что «нельзя по правилам», а потому что это **не разблокирует
задачу** и создаёт реальный риск:

1. Всё, что вы напишете в чат, попадает в переписку. Пароль от Business App —
   это доступ к отправке SMS с вашего счёта. Учётные данные не должны жить в
   переписке, из которой их нельзя надёжно стереть.
2. **Из моей среды я всё равно не смогу ими воспользоваться так, как вы
   ожидаете.** Чтобы SMS реально ушла, запрос должен прийти к Viva **изнутри
   IPsec-туннеля** — Viva работает через site-to-site VPN, а не с открытого
   интернета. Туннеля пока нет (см. часть 2). Пароль без туннеля не даст
   ничего.
3. Секреты в TuTak вводятся **напрямую в Railway Variables**, минуя git и
   минуя меня. Так спроектировано специально. Я никогда не должен видеть
   значение — я работаю с именем переменной.

## Что мне нужно вместо пароля

Ровно шесть значений. Четыре из них — секретные, их вы вводите в Railway
сами. Мне нужно только **подтверждение, что вы их получили**, и два
несекретных ответа.

| Переменная | Что это | Где взять | Кому |
|---|---|---|---|
| `SMS_USERNAME` | логин Business App (e-mail) | у вас уже есть | **только в Railway** |
| `SMS_TOKEN` | пароль Business App | у вас уже есть | **только в Railway** |
| `SMS_VIVA_CLIENT_ID` | **API client_id** — это НЕ Partner ID 10064 | запросить у Viva | **только в Railway** |
| `SMS_VIVA_CLIENT_SECRET` | API client_secret | запросить у Viva | **только в Railway** |
| `SMS_VIVA_TEMPLATE_NAME` | имя шаблона из Templates/Text | создать в кабинете | можно прислать мне |
| `SMS_VIVA_NUMBER_FORMAT` | `national` / `msisdn` / `e164` | спросить у Viva | можно прислать мне |

Вызов `token/get` требует **все четыре** первых значения одновременно. Логин и
пароль — только половина; `client_id`/`client_secret` Viva выдаёт отдельно,
и это ровно то, чего у вас, судя по всему, ещё нет. **Именно поэтому
подключение не получается.**

## Почему `10064` нельзя подставить как client_id

`10064` — это **Partner ID** в кабинете, а не API client_id. Это разные
идентификаторы. Подставить его наугад — значит получить 401 и потратить день
на диагностику не той причины. В коде он не захардкожен нигде (проверено).

## Что нужно сделать в кабинете Viva Business App

Кабинет я не видел и выдумывать пункты меню не буду. По документу Viva нужно
три вещи, спросите у их поддержки, где именно они находятся:

1. **Sender name** — раздел Templates/Sender name. Значение должно совпадать
   с `SMS_SENDER` (сейчас `TuTak`).
2. **Шаблон текста** — раздел Templates/Text. Шаблон должен содержать **ровно
   один тег**, в который подставляется шестизначный код. Viva **не принимает
   произвольный текст**: мы передаём имя шаблона и значение тега, сам текст
   живёт у них. Без зарегистрированного шаблона отправка невозможна в
   принципе.
3. **API-доступ** — client_id и client_secret. Если в кабинете такого раздела
   нет, это выдаётся по запросу в поддержку.

## Что я могу сделать без ваших паролей

Всё остальное уже сделано: провайдер, кэш токена, refresh, обработка 401,
нормализация номера, изоляция всех неподтверждённых предположений в

# Часть 2. Почему Viva не подключается — полная цепочка

Подключение упирается не в один блокер, а в четыре последовательных. Каждый
следующий бессмысленно решать раньше предыдущего.

```
[1] API credentials Viva        ← нет client_id/client_secret
        ↓
[2] VPN-туннель до Viva         ← нет ни одного крипто-параметра
        ↓
[3] Gateway на Contabo          ← нет доступа к VPS
        ↓
[4] Первая живая SMS
```

## Блокер 1 — API credentials

См. часть 1. Решается письмом в Viva.

## Блокер 2 — IPsec-туннель

Viva даёт доступ к Business Hub только через site-to-site VPN. Из формы Viva
подтверждено 7 параметров (IKEv2, Main Mode, PSK, IKE SA 86400 s, ESP, PFS,
IPsec SA 3600 s). **Ещё ~10 параметров не известны и угадывать их нельзя** —
туннель либо не поднимется, либо поднимется не туда.

Список из 7 вопросов к Viva готов: `docs/VIVA_VPN_FORM_RU.md`. Форму я не
отправлял и не отправлю сам.

## Блокер 3 — доступ к Contabo VPS

VPS оплачен, но на машину никто не заходил. Три независимые причины:

| Причина | Проверка | Результат |
|---|---|---|
| Нет письма Contabo с доступом | вложения сессии | не приложено |
| В моей среде нет ssh-клиента | `command -v ssh sshpass` | пусто |
| Порт 22 закрыт egress-политикой | `/dev/tcp/…/22`, 15 с | timeout (443 проходит) |

**Даже с root-паролем я не смогу зайти на VPS из этой среды.** Поэтому
скрипты написаны так, чтобы их выполняли вы: `infra/viva-gateway/bootstrap/`,
7 штук, по порядку, первый — только чтение. Runbook:
`infra/viva-gateway/README.md`.

## Блокер 4 — два открытых вопроса протокола

Оба изолированы в переменные окружения, менять код не придётся:

* формат номера получателя (`SMS_VIVA_NUMBER_FORMAT`) — в документе Viva
  один пример и ни одного правила;
* как предъявляется access token (`SMS_VIVA_TOKEN_PLACEMENT`) — `bearer` это
  вывод из формы эндпоинтов, а не факт из документа.

# Часть 4. Порядок, в котором это делать

1. **Письмо в Viva** — одним сообщением: API client_id/client_secret + 7
   вопросов по VPN + формат номера + способ передачи токена. Это самый
   длинный по времени пункт, начинать с него.
2. **Письмо Contabo** — найти письмо с root-доступом.
3. Пока Viva отвечает: выполнить `bootstrap/00-audit.sh` на VPS (только
   чтение) и прислать вывод — из него становятся известны реальный public IP
   и то, стоит ли VPS за NAT.
4. Создать шаблон и sender name в кабинете Viva.
5. Получить ответ Viva → заполнить `viva.conf.template` → поднять туннель.
6. Развернуть gateway, выпустить сертификат, задать
   `SMS_VIVA_GATEWAY_SECRET`.
7. Внести SMS-переменные в **staging**, проверить живой OTP.
8. Только после этого — production, по чеклисту
   `docs/RAILWAY_PRODUCTION_RUNBOOK_RU.md` §F.

Параллельно, не дожидаясь Viva: п. 5–10 из таблицы 3.1 (домены, Sentry,
webhook, Expo, секреты, планы БД) — они ни от чего не зависят.
