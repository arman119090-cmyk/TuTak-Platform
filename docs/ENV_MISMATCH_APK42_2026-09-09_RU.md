# Куда на самом деле обращается APK42, и что это значит

**Дата:** 9 сентября 2026. **Ничего не переключено и не развёрнуто.**
Production для проверок не использовался: ни одного HTTP-запроса к
production-хостам я не отправлял.

---

## 1. Какой API зашит в APK42 (`3d8707a`)

Прочитано из самого файла APK, `assets/app.config`:

```
apiBaseUrl : https://tutak-staging-api.onrender.com/v1
appEnv     : preview
diagnostics: true
useMocks   : false
```

**Это Render staging. Не Railway.**

Подмены на лету нет. `resolveApiBaseUrl` переписывает адрес **только** если он
loopback (`localhost`, `127.0.0.1`, `::1`) — это сделано для запуска с Metro на
компьютере. `tutak-staging-api.onrender.com` под это правило не подпадает и
возвращается нетронутым.

**Адрес API зашивается на этапе сборки.** Сменить его в установленном
приложении нельзя — только пересобрать APK с другим `API_BASE_URL`.

Косвенное подтверждение с другой стороны: четыре запроса OTP 9 сентября
(10:15:58, 10:17:28, 10:18:03, 14:30:46 UTC) пришли **именно на Render
staging** и видны в его журнале. То есть телефон и этот сервер действительно
разговаривали.

## 2. Роль Render staging: действующий тестовый сервер, который планировали выводить

Оба утверждения верны одновременно, и в этом всё дело.

**Действующий — доказано:** сервис `tutak-staging-api` запущен, отвечает на
`/health`, принял четыре запроса регистрации сегодня, живой деплой
`dep-daddj80ae00c73dqknag` от 4 сентября.

**Планировался к выводу — записано в самом коде.** Коммит `f63b34f`, который
сейчас и работает на этом сервисе:

> «With Railway as the primary platform it is simply wrong… the hostnames of
> the provider being retired»
> «Render is transitional and not primary»

То есть Render staging — **живое тестовое окружение переходного периода**. Не
брошенное: сегодняшние проверки шли через него.

## 3. Есть ли staging на Railway — **NOT VERIFIED**, но в репозитории его нет

| файл | что описывает |

| `railway.json`, `railway.admin.json`, `railway.partner.json` | сборка трёх сервисов, **production** |
| `docs/RAILWAY_PRODUCTION_RUNBOOK_RU.md` | production |

**Ни одного упоминания Railway staging нет.** `APP_ENV=staging` встречается в
Railway-документах ровно один раз — как временный обход production-проверок, и
там же написано, что так делать не следует.

Последнее, что зафиксировано в репозитории о состоянии Railway (3–4 сентября):

> «Статус: production **не задеплоен**. Ничего в Railway не создавалось»
> «Railway readiness: **NOT READY**»

**Проверить текущее состояние Railway отсюда я не могу**: доступа к Railway в
этой сессии нет, а DNS ничего не доказывает — я проверил, у `*.up.railway.app`
**wildcard**: заведомо несуществующее имя `definitely-not-a-real-service-…
.up.railway.app` тоже резолвится. HTTP-запросы к production-хостам я не
отправлял намеренно.

## 4. Расхождение — в чём оно

Вы говорите: основной сервер на Railway. Репозиторий говорит: на 4 сентября в
Railway ничего не создано, а Render — переходное окружение. Оба могут быть
правдой, если Railway production подняли уже после 4 сентября: этого я увидеть
не могу.

**Но одно установлено твёрдо и от Railway не зависит:**

> Приложение, которым вы тестируете, обращается к Render staging.
> Ни один из ваших запросов 9 сентября на Railway не приходил.

Отсюда три следствия:

1. **Разбор недоставки SMS верен — но верен про Render staging.** Транспорт
   выбирается из переменных окружения **каждого окружения отдельно**. На
   Railway настройки другие, и вывод «карьер не настроен» туда автоматически
   не переносится.
2. **Этап A, если развернуть его на Render, починит наблюдаемость там, где вы
   сейчас тестируете** — и нигде больше.
3. **Опасность, о которой вы сами предупредили:** если переключить
   диагностическую сборку на Railway, а там только production — это будет
   тестирование на production. Делать так нельзя, и я этого не предлагаю.

Выводы по клавиатуре расхождение не затрагивает: `collapsable={false}` —
клиентская правка, к серверу отношения не имеет.

## 5. Что предлагаю — три варианта, решение за вами

### Вариант 1 — Render staging остаётся тестовым (проще всего)

Если тестируем и дальше через APK42, действие остаётся прежним: развернуть
`deploy/staging-api-5c28b95` на `tutak-staging-api`. Ничего пересобирать не
надо, APK уже смотрит туда. Этап B потом — там же.

**Это рекомендуемый вариант**, пока на Railway нет отдельного staging.

### Вариант 2 — на Railway есть staging

Тогда мне нужен от вас его адрес API (`https://…/v1`), и порядок такой:

1. Развернуть ту же ветку на Railway staging (а не на Render).
2. **Пересобрать диагностический APK** с `API_BASE_URL` этого адреса —
   сменить адрес в установленном приложении невозможно.
3. Проверки этапа A выполнить уже там.

Render staging при этом можно оставить как есть или вывести — отдельным
решением.

### Вариант 3 — на Railway только production

Тогда диагностическую сборку туда **не направляем**. Выбор: либо оставить
тестирование на Render staging (вариант 1), либо сначала создать на Railway
отдельный staging-сервис, и только потом вариант 2.

Если удобнее — дайте доступ к Railway (токен в защищённые настройки, не в

## 7. Отдельно: маленькая правка, которая снимет этот вопрос навсегда

Сейчас узнать, к какому серверу обращается сборка, можно только распаковав
APK. Предлагаю добавить адрес API в шапку диагностического экспорта — рядом с
коммитом и `runId`:

```
commit dd459df · run QUISEI · api tutak-staging-api.onrender.com · SCF=off RR=on
```

Одна строка, попадёт в следующую сборку. Хост без пути и без параметров —
секретов там нет. Сейчас не делаю: это изменение кода, а вы просили ничего не
трогать до вашего решения.
