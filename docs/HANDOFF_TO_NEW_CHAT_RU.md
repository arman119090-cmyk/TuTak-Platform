# 1. Что уже сделано

## 1.1 Дефект клавиатуры на Android — устранён

Поле теряло фокус через 25–58 мс после его получения; клавиатура закрывалась.
Причина установлена нативной трассировкой: Fabric переносил сфокусированный
`ReactEditText` между родителями, потому что коробка поля переходила из
«плоского» состояния в стековый контекст, когда на фокусе появлялся
`shadowColor`.

Исправление: **постоянный `collapsable={false}`** на внутренней обёртке
`TextField`. Подтверждено на устройстве в сборке APK41 (прогоны `SS06VF`,
`0HX8CM`): при включённом свойстве отсоединений нет, при выключенном
возвращаются. Эксперименты CF, SCF и elevation закрыты — **не повторять**.

Важно: успех `collapsable={false}` **не доказывает вину именно `shadowColor`** —
проп закрепляет весь признак `FormsStackingContext`.

## 1.2 Ошибка отправки больше не обвиняет реферальное поле

На экране регистрации одно состояние ошибки отдавалось последнему полю шага —
реферальному коду. При этом реферальный код в запросе отправки вообще не
участвует, а API на неизвестный код отвечает молчаливым no-op. Разведено на три
слота: `formError` (баннер), `codeError` (поле OTP), `referralError` (только
если код ошибки API начинается с `REFERRAL`).

## 1.3 Наблюдаемость OTP и снятие персональных данных

Раньше три разных исхода выглядели одинаково: запрос не дошёл, номера нет в
базе, карьер отказал — везде `success: true` и ни строки в журнале. Теперь на
каждый запрос пишется одна строка:

```
otp register: skipped-number-already-registered | code-handed-to-carrier |
              carrier-refused | refused-number-rate-limit |
              refused-address-rate-limit | failed-before-send
otp login:    skipped-no-eligible-account | (те же остальные)
```

Плюс при старте печатается фактический транспорт:
`[SMS] SMS transport: viva | unavailable | console`. Убрана ложная строка
баннера «SMS codes are written to this log». Номер телефона в журнале
маскируется.

Ответ клиенту не менялся: защита от перебора аккаунтов сохранена, различие
живёт только в журнале сервера.

# 5. Переменные окружения

## 5.1 Первый деплой — вставить целиком (Raw Editor)

```
NODE_ENV=production
APP_ENV=staging
DEMO_MODE=true
PORT=4000
DATABASE_URL=${{Postgres.DATABASE_URL}}
REDIS_URL=${{Redis.REDIS_URL}}
QUEUE_PREFIX=tutak-test
CORS_ORIGINS=https://${{RAILWAY_PUBLIC_DOMAIN}}
MEDIA_PUBLIC_BASE_URL=https://${{RAILWAY_PUBLIC_DOMAIN}}
MEDIA_STORAGE_DRIVER=local
SMS_GLOBAL_MAX_PER_HOUR=50
SMS_GLOBAL_MAX_PER_DAY=200
SEED_BASELINE=true
```

Плюс три секрета — вводит владелец, в чат не выводить:
`JWT_ACCESS_SECRET` (≥32 символов), `JWT_REFRESH_SECRET` (≥32, **другой**),
`SEED_ADMIN_PASSWORD` (≥12).

## 5.2 Почему `APP_ENV=staging`, а не `production`

При `APP_ENV=production` модуль хранилища требует `MEDIA_STORAGE_DRIVER=s3` и
падает на старте с `local`; `DEMO_MODE` от этой проверки **не освобождает** —
в коде оговорено отдельно. Строгий production потребовал бы бакета и пяти
`MEDIA_STORAGE_S3_*` ради того, что сейчас не проверяется.

Что при `APP_ENV=staging` + `NODE_ENV=production` **сохраняется**:

* строгая проверка JWT-секретов — привязана к `NODE_ENV`, не к `APP_ENV`;
* коды не пишутся в журнал — `isPublicDeployment` покрывает и staging;
* реальные списания невозможны — боевого адаптера эквайринга в коде нет вовсе,
  есть только `SandboxPspAdapter`;
* это объявлено вслух — `DEMO_MODE=true` даёт `{"status":"ok","demoMode":true}`
  в `/health` и строку в журнале при старте;
* лимиты не отключены: 5 кодов на номер в час, 15 попыток, глобальный бюджет.

Отпускается только проверка долговечности медиа (берём `local` сознательно:
логотипы и аватары пропадут при передеплое) и проверка CORS на localhost
(приложение нативное).

## 5.3 Задавать нельзя

| переменная | почему |
|---|---|
| `DEMO_PASSWORD` | откроет публичный `POST /auth/demo-session` — вход без кода. Без неё маршрут отвечает 404 |
| `DEMO_SEED` | насыплет в базу выдуманных партнёров, клиентов и платежи |

## После включения Viva

Один запрос кода **только на согласованный номер владельца**. Успешный тест
8 сентября шёл с другой машины и **не доказывает**, что Viva примет исходящий
адрес Railway. Читать журнал по таблице:

| в журнале | что значит | что дальше |
|---|---|---|
| `carrier-refused` + сеть/таймаут | до Viva не достучались | адрес Railway не в списке разрешённых → шлюз |
| `carrier-refused` + отказ авторизации | связь есть, ключи не приняты | сверить учётные данные |
| `carrier-refused` + `RC != 0` | отказ Viva по существу | шаблон, отправитель, формат номера |
| `code-handed-to-carrier`, СМС нет | приняли, не доставили | вопрос к Viva с `transact_unique_id` |
| `code-handed-to-carrier`, СМС пришла | **работает** | вводим код |

## Критерий завершения

Приложение обращается к Railway, **владелец получил реальную СМС**, код
подтвердил регистрацию или вход, основные сценарии проверены. HTTP 200,
`success: true` и появление экрана OTP по отдельности завершением **не
считаются**.

Отдельно и позже: **ведущий ноль в OTP** — код уходит строкой цифр
(`'012345'`), тестом закреплено, живой доставкой не подтверждено. Закрывается
только настоящей СМС с кодом, начинающимся с нуля. Пока это открытый риск
примерно одного входа из десяти.

# 7. Откат

| что | как |
|---|---|
| Отменить первый запуск | **остановить или удалить сервис `tutak-api`**. Rollback недоступен: предыдущего деплоя нет |
| Выключить отправку | снять **весь** набор Viva, не только `SMS_DRIVER`. Проверено: снятие одного `SMS_DRIVER` при заданном `VIVA_API_BASE_URL` выбирает `HttpSmsProvider` — он пойдёт без подписи, будет отклонён, но отрапортует `SMS transport: http`, то есть будет выглядеть рабочим |
| Postgres, Redis, тома, данные | **не трогать ни при каком откате** |

Миграции откатом не отменяются. Данные сейчас не удаляем: отдельную очистку
тестовых данных подготовим перед запуском для пользователей.
