## 1. Что за дефект

На Android поле ввода **теряет фокус через 25–58 мс после того, как его
получило**. Команды снять фокус со стороны JavaScript при этом нет.

Внешние проявления зависят от числа полей на экране:

* **одно поле** («Вход по коду») — фокус снят, возвращать некому, клавиатура
  закрывается или открывается уже впустую;
* **два поля** (вход по паролю, регистрация) — фокус снят, Android отдаёт его
  следующему фокусируемому, тот теряет так же, и так до затухания. Внешне это
  выглядит как «пинг-понг между полями, заканчивающийся на первом».

Одна причина, два проявления. Практический итог: **во второе поле попасть
невозможно, форма входа неработоспособна.**

Воспроизводится на **Samsung и Xiaomi** одинаково.

## 2. Что доказано

| Утверждение | Чем доказано |
|---|---|
| JS не вызывает команд снятия фокуса | Перехвачены `focusTextInput`, `blurTextInput`, `focusField`, `blurField`, `Keyboard.dismiss`. Ни одной строки `REQ blur` перед аномальными переходами. Инструмент подтверждает свою работоспособность строкой `trace focus-commands armed` |
| Ничего не пересоздаётся на уровне React | Постоянные native-теги (`t=4178` во всех восьми попытках), отсутствие `mount`/`unmount` во время сбоя |
| Окно не сжимается под клавиатуру | `win` и `scr` не менялись ни разу |
| Триггер — само событие смены фокуса | В журнале сборки 34 единственная удачная попытка — та, где `REQ focus` **не породил события фокуса** (поле уже было в фокусе). Все попытки с настоящим событием фокуса его теряли |
| Клавиатура приходит **после** потери фокуса | `focus` → `blur` (+47 мс) → `kbShow … on=none of=1` (+233 мс) → `kbHide`. В одной попытке `kbShow` не было вовсе |
| Приложение само закрывало себе клавиатуру | `REQ blur phone` дважды в журнале сборки 32 — это `ScrollView` React Native при `keyboardShouldPersistTaps="handled"`. **Исправлено на `always`, подтверждено на устройстве** (сборка 33: ни одного `REQ blur`, ни одного `kbHide`) |

## 4. Границы доказательств — соблюдать строго

Это не формальность: на нарушении этих границ уже трижды делались неверные
выводы.

1. **Отсутствие `REQ` исключает только команды, которые оборачивает
   инструмент.** Косвенное влияние JS через пропсы или вёрстку — не исключено.
2. **Постоянный native-тег исключает замену view другой**, но **не**
   отсоединение и возврат той же.
3. **Порядок JS-событий ≠ доказанная последовательность действий Android и
   IME.** `kbShow` — это `keyboardDidShow`, поздняя точка; работа IME
   начинается раньше.
4. **`focus → scroll → blur` — корреляция, не причина.**
5. **Отсутствие `onScroll` не исключает `scrollToChild`:** он прокручивает
   только при ненулевой дельте (`ReactScrollView.java`), а вызывается на
   каждом фокусе.
6. **`mount App #n` означает монтирование React-компонента `Root`**, и ничего
   больше. `unmount App @1` + `mount App #2 @2` при том же run id = дерево
   React пересобрано, JS-контекст уцелел. Совместимо с пересозданием Activity,
   **но не доказывает его**.
7. **Один run id с разными `started`** = один JS-контекст, между экспортами
   нажимали CLEAR. Проверено в коде: `RUN_ID` вычисляется раз на контекст,
   `resetEvents` переписывает `startedAt`.
8. **Модель телефона и версия Android из размеров окна не выводятся.**

## 5. Что за инструмент существует

Диагностическая сборка показывает внизу экрана чёрную панель с журналом.
Кнопки слева направо: **SENTRY · SCF · RR · EXPORT · CLEAR**.
Заголовок: `<sha> · <run id> · SCF=off RR=on · win …`

Журнал пишет:

| Строка | Что означает |
|---|---|
| `touch <поле>` / `pressIn` / `press` | касание, приём нажатия, подтверждение |
| `REQ focus <поле> src=…` | **программный** запрос фокуса из JS |
| `focus <поле> kbd=… t=<tag>` | native сообщил о получении фокуса |
| `blur <поле> t=<tag>` | native сообщил о потере |
| `kbShow h=… on=<поле> kbd=…` / `kbHide on=…` | клавиатура, и какое поле считает себя сфокусированным |
| `mount/unmount <имя> #n @id` | монтирование, счётчик и экземпляр |
| `win WxH scr WxH` | размеры окна и экрана |
| `layout <поле> h=…` | вёрстка поля |
| `scroll y=<от>→<до> ×N` | серия прокруток, датированная началом |
| `exp scrollsChildToFocus=…` / `exp focusRerender=…` | переключение ветви эксперимента |
| `appState …` | фон/передний план |

Журнал защищён от вытеснения: при переполнении расходуются **только** строки
прокрутки.

Ничего введённого не пишется: поля названы ASCII-идентификаторами, view —
классом и числовым id.

## 7. Что сделано в последнем раунде

### 7.1. Эксперимент SCF закрыт

Контролируемое сравнение с одним изменяемым параметром, переключатель внутри
одной сборки (обе ветви — один бинарник, один запуск, один телефон).

Результат: 8 попыток, 8 сбоев, в обеих ветвях и при возврате. **Числа попыток
в ветвях разные — статистических выводов не делать.** Достаточный вывод: не
устраняет.

Это **не** исключает `ScrollView` целиком: отключён один проп,
`requestChildFocus` продолжает вызываться.

### 7.2. Добавлена ветвь RR — ждёт проверки

`RR=off` отключает `setFocused` в `TextField`, то есть перерисовку поля при
смене фокуса. В этой ветви пропадает рамка фокуса — приемлемо для опыта,
непригодно для релиза.

**Критерий:** одинаковый сбой при `RR on/off` означает, что отключение
`setFocused` не устраняет проблему. Это **не исключает** другие перерисовки,
изменения props/layout и влияние самой диагностической панели.

### 7.3. Подготовлена native-инструментация (не собрана)

Локальный Expo-модуль `apps/mobile/modules/focus-trace`, три наблюдателя:

| Наблюдатель | Что даёт | Ограничение |
|---|---|---|
| `OnGlobalFocusChangeListener` | Прежняя и новая view, стек **уведомления** | Android доставляет колбэк из своей обработки: если смена отложена, инициатора на стеке нет |
| `OnWindowFocusChangeListener` | Потеряло ли фокус всё окно | API 28+ |
| `OnAttachStateChangeListener` | Отсоединение/присоединение сфокусированной view | Только за текущей |

**Явно не покрыто:** записи `inputType`, `keyListener`, `focusable` в
`ReactEditText` — у них нет точки наблюдения, нужен подкласс или хук в
view-manager.

Доставка — **pull, не push**: native буферизует с момента старта, JS забирает
накопленное. Ничего до готовности JS не теряется. Время —
`SystemClock.uptimeMillis()` (монотонное) плюс wall clock.

Выполнимость проверена: `@expo/config-plugins` даёт `withMainActivity`,
`ReactApplication.reactHost` в RN 0.86.2 присутствует, каталог `android/`
генерируется EAS и коммитить его не нужно.
