# Отчёт: race condition через маршруты, versioned contribution rules, решения владельца

Дата: 15.09.2026
Ветка: `claude/money-audit`
База: `eb5ee4d` (предыдущий отчёт по пяти замечаниям)

---

## 1. Само задание

Продолжение money-audit. **НЕ MERGE, НЕ DEPLOY.**

Решения владельца, которые надо было реализовать:

1. **HAZE/FUEL.** Не округлять 10 AMD/L до процентов и не ослаблять
   глобальную BPS-сетку. Добавить versioned commercial contribution rule:
   `PERCENT_BPS | FIXED_PER_UNIT | HYBRID`. Для HAZE целевая модель —
   `FIXED_PER_UNIT` 10 AMD/L. Purchase snapshot должен хранить rule/version +
   quantity/unit/unitPrice/gross. Старых процентных партнёров не ломать.
2. **PSP REFUND.** Не делать штатный manual bank refund и не заменять refund
   бонусами. До подтверждённого Idram refund/reversal API PSP refund остаётся
   feature-gated. Provider interface подготовить, endpoint не выдумывать.
3. **RECONCILIATION.** Разрешение `REQUIRES_RECONCILIATION` — maker/checker,
   только finance/admin authority. Партнёр может сообщить о проблеме, но не
   подтверждать факт движения денег. `money-moved` / `money-did-not-move`
   должны иметь evidence/audit и двух разных actors.
4. **PSP TIMEOUT.** Никогда автоматически не превращать timeout/EXPIRED в
   FAILED. Время создаёт alerts/escalation; безопасное освобождение возможно
   только после authoritative provider result или подтверждённой manual
   reconciliation.

**Но сначала** — закрыть найденную race condition: A = `TUTAK_PSP` intent
создан, но `PspPaymentAttempt` ещё нет; затем B = `DIRECT_PARTNER` создаётся
и подтверждается; после этого `beginAttempt(A)` запускает Idram, и клиент
платит дважды. Причина: `assertNoUnresolvedPayment` смотрит на
`PspPaymentAttempt`, а уникальный индекс в БД защищал только
`TUTAK_PSP`/`AWAITING` и не `DIRECT`. Сделать инвариант: один customer +
partner не может иметь двух одновременно незавершённых логических покупок
независимо от маршрута; предпочтительно DB-level + серверная проверка; не
блокировать нормальные новые покупки после окончательного завершения
предыдущей.

Обязательные тесты перечислены в задании (шесть штук) — все написаны.

## 2. Что сделано

### 2.0. Race condition (сделано первым, как и просили)

Дыра была в том, что **обе** защиты, написанные для первой гонки, смотрели на
*попытки оплаты*, а опасный момент — это покупка, у которой попытки **ещё
нет**.

- Миграция `20260915150000_one_live_purchase_per_customer_partner`:
  старый индекс `purchase_intents_one_live_psp_checkout` **удалён** и заменён
  на маршрут-независимый:
  ```sql
  CREATE UNIQUE INDEX purchase_intents_one_live_per_customer_partner
    ON purchase_intents ("customerId", "partnerId")
    WHERE status = 'AWAITING_CONFIRMATION';
  ```
- `assertNoUnresolvedPayment` теперь делает **две** разные проверки:
  (а) есть ли живая покупка у этой пары независимо от маршрута;
  (б) есть ли неразрешённая попытка PSP на любой покупке этой пары.
  Ни одна не поглощает другую: (а) не видит EXPIRED-покупку с зависшей
  попыткой, (б) не видит покупку без попытки.
- `isLivePurchaseCollision` переводит нарушение индекса (гонка двух create)
  в то же самое сообщение, что и серверная проверка, вместо сырой ошибки
  Prisma.

Все шесть затребованных тестов + три дополнительных:

| Тест | Результат |
|---|---|
| PSP intent есть, попытки нет → DIRECT create падает | ✓ |
| DIRECT intent есть → PSP create падает | ✓ |
| два concurrent create разных маршрутов → ровно один побеждает | ✓ |
| после CONFIRMED / REJECTED / CANCELLED можно новую | ✓ (3 теста) |
| EXPIRED + неразрешённая PSP-попытка продолжает блокировать | ✓ |
| authoritative FAILED освобождает безопасно | ✓ |
| резерв бонусов проигравшего не застревает | ✓ |
| у другого бизнеса ничего не блокируется | ✓ |

### 2.1. HAZE / versioned contribution rules

- `ContributionRuleKind`: `PERCENT_BPS | FIXED_PER_UNIT | HYBRID`.
- `PartnerContributionRule` — версионируемая, **неизменяемая** строка на
  партнёра: `version`, `kind`, `percentBps?`, `fixedPerUnit?`, `unit?`,
  `effectiveFrom`/`effectiveUntil`, `liveKey`. Уникальные
  `(partnerId, version)` и `(partnerId, liveKey)`.
- `PurchaseIntent` получил снимок: `contributionRuleId`,
  `contributionRuleVersion`, `contributionRuleKind`. Поля
  `quantity`/`quantityUnit`/`unitPrice` уже были и теперь заполняются через
  DTO.
- Миграция `20260915160000_partner_contribution_rules`: 5 CHECK-ограничений
  (форма соответствует виду, адекватность чисел, версия ≥ 1, окно
  упорядочено, `liveKey` отслеживает окно) и 2 триггера: правило нельзя
  переписать или удалить (можно только закрыть окно), и снимок на покупке
  обязан совпадать с правилом, которое она называет — включая единицу
  измерения.
- `contribution-rule.ts` — **одна функция**, считающая долю TuTak. Это и есть
  выполнение требования «без дублирования ledger economics»: весь денежный
  контур зависит ровно от одного числа `pool`, и новый вид ценообразования —
  это ветка в этой функции и больше нигде. В `settlePurchase` изменилась
  ровно одна строка.
- `PartnerContributionRuleService.open()` — открывает следующую версию,
  закрывая предыдущую в одной транзакции; номер версии выделяется попыткой
  (как код подтверждения), потому что read-then-insert имеет окно гонки.

**HAZE доказан точно, все три случая:**

| Случай | pool | PARTNER_PAYABLE |
|---|---|---|
| DIRECT без бонуса | 500,00 | −500,00 |
| DIRECT + 1 000 бонуса | 500,00 | +500,00 |
| PSP + 1 000 бонуса | 500,00 | **+14 500,00** |

Не 499,50 и не 525,00 — ровно 500, потому что 50 × 10 считается как
50 × 10, а не как процент.

### 2.2. PSP refund — feature-gated отказ

- Флаг `PSP_REFUNDS_ENABLED`, выключен.
- `PurchaseIntentRefundService.assertRefundableRoute` отказывает в возврате
  по маршруту `TUTAK_PSP`, пока не выполнены **оба** условия: флаг включён
  **и** `PspAdapter.capabilities.refund === true`. Флаг не может создать API,
  а API не должен сработать оттого, что переменная окружения уехала.
- Сообщение прямо говорит не возвращать руками и не бонусами, а эскалировать
  в finance.
- `DIRECT_PARTNER` возвраты не тронуты — тест это проверяет.
- Новый `PspAdapterModule` — адаптер отдельно от `PspModule`, иначе импорт
  из `PurchaseIntentsModule` был бы циклом (`PspModule` импортирует
  `PurchaseIntentsModule`).

### 2.3. Reconciliation maker/checker

- Enum'ы `ReconciliationSource` (`FINANCE` / `PARTNER_REPORT`) и
  `ReconciliationOutcome` (`MONEY_MOVED` / `MONEY_DID_NOT_MOVE`).
- Девять новых колонок на `PartnerSettlement`: кто сообщил и когда, что
  предложено и на каком основании (`reconciliationEvidence`), кто предложил,
  кто подтвердил.
- Метод `resolveReconciliation` **удалён** и заменён двухфазным:
  `proposeReconciliationOutcome` (ничего не двигает) →
  `confirmReconciliationOutcome` (двигает).
- `reportTransferProblem` — партнёр сообщает о проблеме; после этого он
  заблокирован и от предложения, и от подтверждения.
- Миграция `20260915170000_reconciliation_maker_checker`: 5 CHECK —
  предложение неполно без evidence; подтверждение невозможно без
  предложения; **checker ≠ maker**; сообщивший партнёр не может быть ни тем,
  ни другим; статус `REQUIRES_RECONCILIATION` обязан называть источник.

### 2.4. PSP timeout никогда не разрешает

- `PspResolutionBasis`: `PROVIDER_CALLBACK | PROVIDER_STATUS_QUERY |
  MANUAL_RECONCILIATION`. `TIMEOUT` намеренно отсутствует — для «мы подождали»
  в эту колонку нечего написать.
- Миграция `20260915180000_psp_timeout_never_resolves`: 3 CHECK + триггер.
  `FAILED` без `resolutionBasis` невозможен; `MANUAL_RECONCILIATION` требует
  двух разных людей и evidence; статус и эскалацию нельзя изменить одной
  записью.
- `PspAttemptAgeingService` + sweep `psp.escalate-stale-attempts` (каждые 10
  минут): переводит зависшую живую попытку в `EXPIRED` (что **не** разрешение
  — `EXPIRED` остаётся в небезопасном наборе) и эскалирует всё неразрешённое,
  повышая severity до `critical` после пятой эскалации. Статус `FAILED` не
  пишет никогда.
- `PspPaymentService.reconcileAttemptManually` — единственный ручной выход, и
  он требует двух разных людей и evidence.
- Метода «человек утверждает, что платёж прошёл» **нет и не будет**: приход
  денег подтверждает только проверенный callback провайдера. Тест проверяет,
  что и таблица такую форму отвергает.

## 4. Что НЕ сделано, что не получилось, и мои ошибки

### 4.1. Не сделано

- **Контроллеров по-прежнему нет.** Ни `PartnerContributionRuleService`, ни
  `PartnerSettlementService`, ни `PspPaymentService` не выставлены по HTTP.
  Прав доступа тоже нет: решение №3 говорит «только finance/admin
  authority», и я реализовал **два разных человека** и **запрет для
  партнёра-заявителя**, но **не** проверку роли/permission — её негде
  проверять, пока нет гварда на контроллере. Это прямой недобор по
  формулировке задания, и он осознанный: гвард без эндпоинта не
  тестируется.
- **UI не тронут.** Ни выбора маршрута, ни экрана терминов партнёра, ни
  кнопок reconciliation, ни ввода литров на кассе. `quantity/unit/unitPrice`
  принимаются API, но клиента, который их пошлёт, не существует.
- **`PROVIDER_STATUS_QUERY` не реализован** — только объявлен как основание.
  Idram-адаптер объявляет `statusQuery: false`, метода нет.
- **Миграция существующих партнёров на rule-строки не делалась.** Все
  партнёры сейчас без правила и считаются по `negotiatedRateBps`, как
  раньше. Чтобы HAZE заработал, кто-то должен открыть ему версию 1 — и
  сделать это некому, потому что эндпоинта нет (см. выше).
- **Эскалация идёт только в alert-канал.** Никакой очереди задач для
  finance, никакого экрана «неразрешённые платежи».

### 4.2. Что осталось непроверенным (UNVERIFIED)

- **Idram по-прежнему ни разу не работал с реальным провайдером.**
  Не изменилось с прошлого отчёта.
- **Миграции на production-данных не проверялись.** Проверено только
  применение на пустой БД. Опасные места, которые я **не** проверял на
  реальных данных:
  - `DROP INDEX purchase_intents_one_live_psp_checkout` и создание нового —
    если в production сейчас есть клиент с двумя одновременными
    `AWAITING_CONFIRMATION` покупками у одного партнёра, **создание индекса
    упадёт**. Это вероятнее, чем кажется: старый индекс DIRECT не
    ограничивал.
  - `partner_settlements_reconciliation_has_source` — упадёт, если есть
    строки в `REQUIRES_RECONCILIATION` без источника. На production их, скорее
    всего, нет (движок не использовался), но я это не проверял.
- **Поведение sweep'а под нагрузкой.** `escalateStaleAttempts` читает и
  пишет по одной строке в цикле; на тысячах зависших попыток это будет
  медленно. Не оптимизировал сознательно — сейчас таких строк ноль.
- **Порог `LIVE_ATTEMPT_TIMEOUT_MS = 30 минут` выбран мной, не согласован.**
  Это решение о том, когда живой счёт объявляется протухшим, и оно
  коммерческое, а не техническое.
- **Параллелизм открытия версий правил проверен слабо.** Тест
  `lets exactly one of two concurrent version opens win` утверждает только
  что живое правило одно и версии не дублируются — он **не** утверждает, что
  ровно одна попытка побеждает, потому что вторая может легально
  выиграть после ретрая. Это честно, но слабее, чем аналогичный тест для
  покупок.

### 4.3. Мои ошибки по ходу работы

- **Своей же миграцией сломал четыре собственных теста и не заметил.**
  Триггер `psp_attempt_timeout_never_resolves` требует `resolutionBasis` при
  переходе в `FAILED`, а четыре теста в `psp-payment.int-spec.ts`,
  написанные раньше в этот же день, ставили `FAILED` напрямую без основания.
  После добавления миграции я прогнал только новый набор
  `psp-timeout-and-refund` и не перепрогнал `psp-payment` — падение нашлось
  только на полном прогоне. Исправление оказалось содержательным: эти тесты
  моделируют именно «провайдер authoritative сказал нет», так что
  `PROVIDER_CALLBACK` — это то, что они всегда и имели в виду.
- **Забыл добавить новую зависимость sweep'а в `sweeps.int-spec.ts`.**
  Добавил `pspAgeing` в `SweepDependencies`, поправил `alerting.int-spec.ts`
  (на который указал компилятор) и пропустил второй стенд, собирающий тот же
  бандл вручную — там поле не обязательно по типам, потому что объект
  строится через `useValue`. Тест `reaches the real handler for every
  scheduled job` упал с `Cannot read properties of undefined`.
- **Сломал загрузку `PspModule`**, вынеся адаптер в отдельный модуль: оставил
  `PSP_ADAPTER` в `exports`, хотя провайдер там больше не объявлен. Nest
  отказался стартовать, **45 тестов** в двух suite упали разом. Исправление —
  экспортировать сам `PspAdapterModule`.
- **Запустил второй прогон тестов поверх идущего полного прогона.** Обе
  используют одну БД и делают TRUNCATE между тестами; получил 8 «падений»,
  которых не было, и потратил время на их разбор, прежде чем понял, что
  сам их и создал. В `jest.config.js` про это написано прямым текстом
  (`maxWorkers: 1`, «один воркер делает TRUNCATE поверх открытой транзакции
  другого»), и я это читал в начале сессии.
- **Неправильно диагностировал «накопление процессов» и убил здоровый
  прогон.** `pgrep -f jest` считал мои же команды-опросчики, содержащие слово
  jest, за процессы jest; счётчик рос, я решил, что прогоны накапливаются, и
  убил работающий. Плюс `pgrep -f "npx jest ..."` в цикле ожидания находил
  сам себя и никогда не завершался — несколько таких сторожей висели впустую.


- **Сломал загрузку `PspModule`**, вынеся адаптер в отдельный модуль: оставил
  `PSP_ADAPTER` в `exports`, хотя провайдер там больше не объявлен. Nest
  отказался стартовать, **45 тестов** в двух suite упали разом. Исправление —
  экспортировать сам `PspAdapterModule`. Ошибка ровно того сорта, который
  ловится первым же запуском, и я её туда и отправил.
- **Первый вариант матчера `isLivePurchaseCollision` не сработал.** Я искал
  в `meta.target` имя индекса, а Prisma вернула список колонок
  (`customerId,partnerId`). Инвариант при этом **держался** — тест упал не на
  «оба create прошли», а на тексте ошибки. То есть защита работала, а
  сообщение пользователю было сырой ошибкой Prisma.
- **`RAISE` с `%%` в plpgsql.** Написал `'purchase % %% snapshot'`, получил
  `too many parameters specified for RAISE` — миграция не применилась вообще.
- **Забыл `prisma generate` после правки схемы** — получил пять ошибок
  типов на несуществующих полях и полминуты искал их в коде, а не в
  сгенерированном клиенте. Второй раз за сессию.
- **Пере-усложнил первый заход на `resolveReconciliation`.** Сначала написал
  вариант, где оба actor'а передаются одним вызовом. Это формально «два
  разных actor'а», но фактически один человек, вводящий два id. Переделал на
  двухфазный propose/confirm — то есть ту же форму, что уже есть у
  `markReady`/`approve` в этом же файле. Надо было посмотреть на соседний
  метод прежде, чем изобретать.
- **Контейнерный PostgreSQL потерял роль `tutak`** посреди работы (данные
  кластера сбросились). Восстановил роль и базы вручную. Не моя ошибка, но
  стоила времени и стоит упоминания: тестовая БД в этой среде не переживает
  перезапуск.
- **Дисковый I/O контейнера деградировал** до того, что полный прогон
  (11 минут в начале сессии) перестал завершаться за час: `pg_stat_activity`
  показывал `TRUNCATE` в ожидании `DataFileImmediateSync`. Места на диске
  было 25 ГБ, база — 21 МБ, то есть дело не в переполнении. Обошёл двумя
  способами: `fsync=off`/`synchronous_commit=off` на тестовом кластере (он
  одноразовый, и это стандартная настройка для тестовой БД — на
  корректность транзакций и ограничений не влияет, только на живучесть при
  падении машины) и прогон шестью шардами вместо одного. После этого шард
  проходит за 60–90 секунд.

## 5. Вопросы владельцу

1. **Кто открывает партнёру версию терминов?** Сейчас это только сервисный
   метод. Нужен ли maker/checker и на терминах тоже (сейчас — один человек),
   или достаточно аудита? Я специально не стал изобретать процесс.
2. **Порог «живой счёт протух» — 30 минут.** Моё число. Сколько должно быть?
