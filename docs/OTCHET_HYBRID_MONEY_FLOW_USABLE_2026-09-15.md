### §1. Долговечный inbox для callback'ов

Не увеличением пула. `PspCallbackInbox` + `PspCallbackInboxService` +
`PspCallbackWorkerService` + sweep каждые 5 секунд.

Механика скопирована у существующего outbox — `FOR UPDATE SKIP LOCKED`,
аренда, backoff с потолком, dead-letter с алертом, — но **не сам outbox**:
его `publish` намеренно требует транзакцию-источник («outbox-строка,
записанная вне породившей её транзакции, — это очередь с лишними шагами»), а
у входящего callback'а транзакции-источника нет. Эта причина верна и именно
поэтому переиспользовать его нельзя.

`dedupeKey` = `провайдер:вид:счёт:транзакция` — идентичность события у самого
провайдера, поэтому повтор сталкивается с той строкой, повтором которой он
является. Сериализация по счёту — отдельная узкая блокировка в воркере.

### §2. Реальный HTTP-контур Idram

- **Контракт handoff починен по-настоящему.** Поля формы Idram считались и
  терялись: `beginAttempt` их наружу не отдавал, и документированный поток
  нельзя было выполнить вообще. Введён типизированный `ProviderHandoff`
  (`REDIRECT` | `FORM_POST`), одинаковый для обоих видов провайдеров.
- **Precheck** — отвечает по протоколу (`OK`/`NO`), проверяет счёт, продавца,
  сумму и допустимость покупки, **ничего не проводит**.
- **Final callback** — checksum, продавец, счёт, сумма, id транзакции, сырое
  свидетельство, inbox, идемпотентный расчёт.
- **Статус для клиента** — доменная модель из наших же записей:
  `NOT_STARTED / WAITING_PROVIDER / PROCESSING / SUCCEEDED /
  REQUIRES_RECONCILIATION / FAILED`. SUCCESS_URL не является источником
  истины ни в одной точке.

Ничего не выдумано: refund, void, status query, settlement feed, fee API
по-прежнему объявлены отсутствующими.

### §3. Аутентифицированный actor

### §17. Причины падения CI #735 и корневая причина гонки

**Причин оказалось четыре, они выстроились цепочкой, и ни одна из первых
двух не была той, что предполагалась в задании.** Каждая следующая пряталась
за предыдущей: job останавливается на первом красном шаге, поэтому всё, что
за ним, выглядит несуществующим.

*Lint.* Ошибка не в `psp-callback-inbox.service.ts`, а в
`apps/partner/src/app/(dashboard)/purchase-intents/page.tsx:153` —
компонент `AwaitingProvider` принимал проп `intent` и не использовал его.
Это следствие моей же правки прошлой сессии: я вынес `LineItem` из ветки с
кнопкой, и последнее обращение к `intent` из компонента ушло. Проп удалён,
а не переименован в `_intent`: компоненту он действительно не нужен.
`npx eslint .` по всему дереву — ноль проблем.

*Integration.* Тест
`settles the purchase exactly once no matter how often the callback is
delivered` получал 0 `psp.payment.captured` вместо 1. **Это не дефект
машины состояний и не двойной расчёт — это ноль расчётов.**

**Корневая причина.** Транзакция расчёта брала соединения из пула *снаружи
самой себя*. Внутри открытой `this.prisma.$transaction(...)` шли вызовы
через `this.prisma`, а не через `tx`:

| Место | Что читало мимо транзакции |
|---|---|
| `psp-payment.service.ts` | `ledger.accountFor` ×2 |
| `purchase-intents.service.ts` | `findByIdOrThrow` |
| `settlePurchase` | `contributionFor` |
| `settlePurchase` | `referralService.resolveReferralChain` (до 3 запросов) |
| `postContributionLedger` | `accountFor` ×3 + по одному на партнёра-реферера |
| `postRedemptionCompensation` | `accountFor` ×2 |

Пять одновременных подтверждений открывают пять транзакций и занимают все
пять соединений пула. Каждая затем просит шестое, которого не существует.
Никто не отпускает своё соединение, потому что каждый ждёт следующего —
взаимная блокировка на пуле, а не на строках. Через пять секунд срабатывает
дефолтный таймаут интерактивной транзакции Prisma, и все пять умирают:

```
Transaction API error: Transaction already closed: ...
The timeout for this transaction was 5000 ms, however 5128 ms passed
since the start of the transaction.
```

**Как доказано, а не предположено.** Локально тест проходил (на этой машине
4 CPU → пул Prisma по умолчанию 9). Я воспроизвёл падение, закрепив пул на
размере CI: `TEST_DATABASE_URL=...&connection_limit=5`. Получил ровно то же
`Expected: 1, Received: 0` за 5745 мс. Затем временной пробой напечатал
причину отказа каждого из пяти вызовов — все пять оказались тем самым
таймаутом. Только после этого я трогал код.

**Исправление — два пункта.**

1. *Ни один запрос внутри денежной транзакции больше не берёт соединение
   снаружи.* `accountFor` теперь принимает `tx` — **единообразно**, и это
   важно. В коде стоял комментарий, запрещавший передавать `tx`, потому что
   раньше это вызывало самоблокировку. Диагноз был наполовину верен:
   блокировку вызывало не `tx`, а **смешение** — `postContributionLedger`
   искал счёт внутри транзакции, а соседний `postRedemptionCompensation` тот
   же счёт снаружи, не видел несозафиксированную строку и вставал в очередь
   за самим собой. Сделать оба tx-less прятало проблему; сделать оба
   транзакционными её убирает. `resolveReferralChain`, `findByIdOrThrow` и
   `contributionFor` получили необязательный клиент и в PSP-пути читают на
   транзакции вызывающего — это заодно и корректнее: цепочка привязки
   читается в том же снимке, в котором по ней платят.

2. *Строка попытки блокируется до тяжёлой работы.* `SELECT ... FOR UPDATE`
   по `psp_payment_attempts` в начале транзакции. Раньше все N проделывали
   весь расчёт — проводки, бонусные лоты, реферальные доли — и N-1 узнавали
   на последнем операторе, что попытку забрал кто-то другой, и выбрасывали
   всю работу. Это не только расточительно: N транзакций, держащих замки на
   одном кошельке, счетах и покупке в произвольном порядке, — это заготовка
   для дедлока. Теперь конкуренция сведена к одной строке. Условный `claim`
   в конце **оставлен**: он сторожит `resolutionBasis`, который блокировка
   не закрывает — ручная реконсиляция могла ответить между захватом и
   claim'ом.

**Атомарный инвариант не тронут.** PSP capture, канонический расчёт покупки,
бонусы/рефералы/contribution и `SUCCEEDED` по-прежнему коммитятся вместе или
никак: всё это одна `$transaction`, и `settleFromProviderConfirmation`
по-прежнему получает `tx` вызывающего.

**Тесты добавлены, ни один не ослаблен и не удалён.**

- `answers every duplicate caller — one settles, the rest replay, none fails`
  — проверяет **исход каждого из пяти вызывающих**, а не только итоговый
  счётчик: ровно один `alreadySettled: false`, четыре `alreadySettled: true`,
  ноль отказов, один и тот же `attemptId`. Прежний тест не отличал «один
  расчитал, четыре сделали replay» от «один расчитал, четыре умерли» — и в
  #735 умерли все пять, что он поймал лишь по случайности арифметики.
  Проверено, что новый тест **падает на старом коде**: я отложил правки
  исходников через `git stash`, оставив только тест, и получил красное.
- `settles once when 50 duplicates are drained by concurrent workers` —
  требование 6 задания, и отдельно от прямого вызова сервиса: 50 дубликатов
  через реальный HTTP → одна строка inbox → **четыре воркера разгружают
  одновременно** → `processed` в сумме 1, `failed` 0, по одной проводке
  `psp.payment.captured`, `partner.contribution` и
  `partner.bonus_redemption_compensation`, покупка `CONFIRMED`, строка inbox
  `PROCESSED`.

Тест `settles the purchase exactly once...` оставлен ровно как был.

**Результат на воспроизведённых условиях CI:** 5745 мс и 0 расчётов → 357 мс
и 1 расчёт.

*Третья причина, которая пряталась за первой.* После исправления lint'а
прогон #736 дошёл до шага `Typecheck` — и упал там. В #735 этот шаг вообще не

недоделка прошлой сессии: я расширил общий DTO и обновил api, partner и admin,

Исправлено по существу, а не приведением типов: три литерала в

экрана — так же, с тем же обоснованием в комментарии. `turbo run typecheck`

*Четвёртая причина, которая пряталась за третьей.* Прогон #738 дошёл до шага

### §18. Пополнение баланса клиента закрыто флагом

Хранимый баланс, который клиент пополняет заранее, — это приём вкладов.
Кто вправе его держать — лицензированный эмитент или TuTak на своём
мерчант-счёте — вопрос юридический, а не технический, и он открыт.

`CUSTOMER_PREPAID_TOPUP_ENABLED` по умолчанию выключен. При выключенном
флаге `CustomerBalanceController` **не регистрируется вовсе**: `/balance/me`,
`/balance/topup` и `/balance/topup/webhook` отвечают `404`, а не отказом,
который подтверждал бы наличие функции. Сервис проверяет флаг **отдельно**,
в `initiateTopUp` и `confirmTopUpWebhook` — чтобы внутренний вызов не смог
начислить реальные деньги в обход HTTP; EV-роуминг уже держит ссылку на этот
сервис, так что поверхность шире, чем один контроллер.

**Закрыто именно начисление.** `getBalance` и `collectFromBalance` остаются
доступны, и это осознанно: EV-роуминг тратит баланс через
`collectFromBalance`, а клиент, у которого баланс уже есть, должен видеть его
и мочь потратить. Запереть чужие деньги — не безопасное направление.

EV-код не удалён вслепую: он не тронут вообще. Idram к этому контуру не
подключён — адаптер остаётся `NoopBankTopUpAdapter`, и тест это утверждает
явно, а не подразумевает.

Новый набор `customer-balance-disabled.int-spec.ts` (8 тестов) проверяет
именно состояние по умолчанию: три маршрута дают 404, сервис отказывает на
начисление и на вебхук, чтение и трата работают, банк — no-op. Переменная в
нём **явно удаляется** перед сборкой приложения: тест, который проходит лишь
потому, что раннер случайно не выставил переменную, ничего не доказывает.
Два существующих набора (`customer-balance`, `ev-roaming-financial-accounting`)
включают флаг явно и восстанавливают прежнее значение.

### §19. Экран расчётов для партнёра (закрыт) и мобильный экран (заблокирован)

**Сделано: экран расчётов для партнёра.** API существовал с прошлой сессии,
экрана не было — партнёр не мог увидеть ни начисленного, ни переведённого.
Теперь на одной странице: что накапливается сейчас (до того, как кто-либо
составил расчёт), и список выписок с референсом перевода. Только чтение:
получатель платежа, который может поправить собственную Net Position, не
получатель. Единственное действие — сообщить о проблеме, и оно намеренно
ничего не утверждает о движении денег.

Две формулировки выбраны против интуиции и обе проверены тестами. `FAILED`
показан жёлтым и подписан «перевод не прошёл, деньги по-прежнему
причитаются»: отказ банка не меняет долга, записи остаются закреплёнными,
перевод повторяется против той же суммы — красный цвет сообщал бы партнёру,
что деньги потеряны. Непроклассифицированные виды проводок выводятся
списком, а не выбрасываются: без этой строки три цифры выше были бы тихо
неполными. 8 тестов, partner 88/13.

**Собственная ошибка в этом же экране, найденная через час после пуша.** Я
написал в клиенте поля `deductionsAmount`, `netAmount` и `transferReference`,
а модель называет их `deductionAmount`, `netPayableAmount` и
`bankTransferReference`. Строки приходят из `PartnerSettlementService.list()`
напрямую, без слоя отображения, так что партнёр увидел бы `NaN` вместо
чистой суммы к выплате — на экране, который существует ровно затем, чтобы
показать сумму к выплате.

Восемь тестов при этом были зелёными, и это главный вывод. Фикстура
повторяла мои же выдуманные имена, то есть проверяла согласие клиента с
самим собой. Фикстура, которая согласна с клиентом, а не с сервером, не
доказывает ничего — я писал ровно эту фразу в комментарии к чужой фикстуре
тремя днями раньше и повторил ошибку сам. Исправлено, имена сверены со
схемой, в клиенте оставлен комментарий о том, откуда они берутся.

Настоящее лекарство — общие типы в `@tutak/shared-types` для расчётов, как
у purchase-intent: тогда несовпадение ловил бы `tsc`, а не партнёр. Дашборд
сейчас типизирует их у себя, потому что второго потребителя не было; теперь
он появится (админский экран), и вынос типов стоит сделать вместе с ним.

**Не сделано: мобильный экран оплаты — и причина техническая, а не «не дошли
руки».** Документированный handoff Idram — это `FORM_POST`. Выполнить POST
формы из мобильного приложения нечем: в `apps/mobile` нет ни
`react-native-webview`, ни `expo-web-browser`, ни `expo-linking`, а
`Linking.openURL` умеет только GET. Добавление зависимости трогает lockfile
и вендорную копию `demo/`, которую CI пересобирает и сравнивает, — начинать
это на остатке лимита значило бы оставить ветку в полусобранном состоянии.

Я предпочёл не выкатывать экран, который доходит до кнопки «Оплатить» и
упирается в тупик. Это **вопрос владельцу**, а не просто задача: какую
зависимость ставить (`react-native-webview` — стандартный выбор) и
согласны ли вы, что `demo/` вырастет на неё.

### Админский экран расчётов

Составление, готовность, одобрение вторым человеком, отметка о переводе.
Правило **видно**, а не только применяется: Approve недоступен тому, кто
составил, и рядом написано почему. Админ, узнающий это из 409, выучивает,
что приложение непредсказуемо; админ, который видит причину, выучивает, как
устроен контроль. Когда maker неизвестен (старая строка), кнопка остаётся:
угадать запрет и заблокировать работу, которую сервис разрешил бы, хуже,
чем дать серверу ответить.

Чего на экране нет: `PAID` неизменяем; у `REQUIRES_RECONCILIATION` нет
кнопки статуса вообще, потому что «деньги прошли» — утверждение о мире, и
один админ не должен уметь его сделать; это propose/confirm двумя людьми.
`FAILED`, наоборот, сохраняет действия: отказ банка не меняет долга.
7 тестов, admin 87/13.

### Мобильная оплата

Добавлен `react-native-webview`. Решение принял сам: выбор библиотеки —
техническое решение, а ваша инструкция спрашивать только при настоящем
business/legal/provider вопросе. Версия закреплена ровно на `13.16.1`, как
требует SDK 57, — это поймал собственный guard репозитория, когда я поставил
диапазон `^14.0.1`.

Правило, которому подчинено всё на экране: **то, где оказался браузер, не
доказывает ничего.** Страница успеха провайдера — это страница; на неё
попадает и тот, кто бросил оплату, и не попадает тот, кто заплатил. Поэтому
`onNavigationStateChange` ничего не решает, статус берётся только из
`GET /psp/purchases/:id/status`, и кнопки «я оплатил» не существует: клиенту
нечего сообщить, чему мы вправе поверить. На `REQUIRES_RECONCILIATION` нет
«попробовать ещё раз» — так платят дважды за один кофе.

Поля формы подставляются дословно и в том же порядке: провайдер проверяет
контрольную сумму именно по ним, и клиент, «улучшивший» формат суммы, ломает
подпись. Значения экранируются. 11 тестов, mobile 530/64.

Вход в экран — на экране статуса покупки, и только после одобрения продавцом:
до `merchantApprovedAt` платить нечего, сервер откажет. Пока одобрения нет,
написано именно это, а не «ждём кассира».

### Перевод партнёров на contribution-rule — почему не сделан

`ACTIVE`-правило обязано называть человека, который его одобрил
(`partner_contribution_rules_in_force_was_approved`). У миграции такого
человека нет, и вписать его значило бы отмыть ровно тот maker/checker, ради
которого ограничение существует. Партнёр переходит на явное правило, когда
двое его туда переводят через `propose`/`approve` — механизм уже есть.

Вместо миграции — доказательство того, что миграция должна была обеспечить:
unit-спека на `contributionForPurchase`, **которой раньше не было вовсе**,
показывает, что партнёр без правила считается байт-в-байт как партнёр с
эквивалентным `PERCENT_BPS`, на пяти ставках включая неделящиеся. Отсутствие
правила — не второсортное состояние, и мигрировать его незачем.

Заодно спека закрывает функцию, от которой зависит весь денежный контур и у
которой была только косвенная интеграционная проверка: HAZE 50 л × 10 = 500,
округление вниз на четырёх знаках, гибрид округляется один раз в конце, литры
к киловатт-часам не применяются.

### P1-9. Ротация ключа JWT

Смена `JWT_ACCESS_SECRET` отвергала все выданные токены разом: каждый
вошедший получал 401 посреди действия. **Эта цена и есть причина, по которой
утёкший секрет не меняют неделями,** а неменяемый утёкший секрет — настоящая
опасность. Теперь `JWT_ACCESS_SECRET_PREVIOUS` принимается при проверке и
никогда не подписывает; новый секрет подписывает с момента выката, старые
токены доживают свои пятнадцать минут, потом переменная убирается.

Реализовано через `secretOrKeyProvider`, а не вторую стратегию Passport:
вторую пришлось бы регистрировать из `process.env` на этапе вычисления
метаданных модуля, то есть решать вопрос конфигурации там, где конфигурации
ещё нет, и это невозможно протестировать. 5 тестов по реальному HTTP, включая
то, что чужой ключ по-прежнему отвергается и что просроченный токен остаётся
просроченным: окно ротации, продлевающее сессии, было бы ошибкой хуже той,
которую оно чинит.

**Побочная находка, и неприятная.** `JWT_REFRESH_SECRET` не используется
нигде: refresh-токены непрозрачные и хранятся хешами в `refresh_tokens`.
При этом `DEPLOYMENT.md` утверждал, что его смена разлогинивает все сессии.
Это неправда — она не делает ничего. Тот, кто ротировал его, считая, что
рвёт сессии, ошибался насчёт того, что сделал, и это хуже, чем не ротировать
вовсе. Документ исправлен.

### P2-3. Выгрузки для бухгалтерии

CSV по проводкам и по оплаченным расчётам. Читается реестр и ничего больше:
удобная свёртка по `transactions` была бы вторым набором чисел, и в день
расхождения кто-то выяснял бы, какой из двух — позиция компании.

Период полуоткрытый `[from, until)`. Включающая правая граница — классический
источник задвоения или пропуска суток, а полуоткрытые периоды стыкуются
точно; тест это и проверяет, складывая два соседних периода обратно в один.

Отдельно — **защита от формул**. Значение, начинающееся с `=`, `+`, `-`, `@`,
таба или CR, Excel и его аналоги выполняют. Партнёр, назвавшийся
`=HYPERLINK("http://evil","Click")`, — это код, исполняемый на машине
бухгалтера, то есть человека, менее всех способного заметить подвох. Поля
экранируются ведущей кавычкой, отрицательная сумма остаётся читаемой и со
знаком. 8 интеграционных тестов + 13 unit.

### P1-12. Хранение в браузере — уведомление, а не баннер согласия

И это вывод, а не уклонение. Панели хранят ровно два предмета: идентификатор
устройства, которым сессия привязывается к браузеру, и выбранную тему. Оба
строго необходимы для услуги, о которой человек попросил, войдя, — то самое
исключение, вокруг которого написаны правила о согласии.

Спрашивать согласие там, где оно не требуется, — не лишняя осторожность.
Это учит людей закрывать такие окна не читая, и тогда настоящий opt-in на
аналитику, когда она появится, закроют быстрее всех. Поэтому уведомление
информирует и не изображает выбор, который ничего не меняет; в тестах прямо
закреплено, что кнопки «отклонить» нет. Когда появится аналитика, менять надо
не это уведомление, а место загрузки SDK, где и должен стоять выключенный по
умолчанию гейт.

### P1-5. Нагрузочные сценарии

Два сценария k6 на реальные горячие пути: покупка (самая дорогая операция —
одна транзакция с проводками, бонусами, отложенными лотами и реферальными
долями) и «партнёры рядом» (самое частое чтение). `BASE_URL` без значения по
умолчанию намеренно: забытый дефолт `localhost` однажды окажется проброшенным
туннелем. Токены передаются, а не подписываются — секрет в нагрузочном
скрипте это секрет в репозитории. Порог отказов на денежном пути ноль, а не
«меньше 1%»: один процент — это один покупатель, стоящий у кассы, и для него
это не процент.

Скрипты **линтуются**, а не добавлены в игнор: объявлены глобали k6.

### Попутно

HTTP-стенд получил опциональные auth-guard'ы. Их не было вовсе — проверить,
чего стоит токен, было нечем, и это ограничение стенда было описано в его же
комментарии как данность.

### Чего я не трогал и почему

Остальные ❌ в дорожной карте — **эксплуатационные, а не кодовые**: включить

## 6c. УЗИ: что я не доделал (19.09.2026)

Проверено сканированием кода, а не по памяти. Отсортировано по тому,
насколько это мешает пользоваться системой.

### Дыры «API есть, пользователя нет»

Общая форма у всех одна, и она моя: я строил серверную часть, писал в
докблоках, кому она нужна, и не доводил до человека, который должен ею
пользоваться.

1. **Выгрузки для бухгалтерии недостижимы из интерфейса.** `grep accounting`
   по `apps/admin/src` — **ноль** совпадений. Я написал в докблоке контроллера
   «файлы, которые открывает бухгалтер», и не дал бухгалтеру кнопки: без
   `curl` с токеном выгрузку получить нельзя. Сделано вчера, замечено сегодня.

2. **Админский экран расчётов не умеет создать расчёт.**
   `settlementAdminApi.draft` — **ноль** использований. Экран показывает и
   двигает по статусам существующие расчёты, но составить новый нельзя, то
   есть цикл не замкнут: расчётам неоткуда взяться, кроме как вызовом API
   напрямую.

3. **Из `REQUIRES_RECONCILIATION` экран не выводит.** На самом экране я
   написал «resolved by two-person reconciliation» — и этой резолюции не
   сделал: `proposeReconciliation` и `confirmReconciliation` имеют **ноль**
   использований. Расчёт может войти в состояние, из которого интерфейс не
   выпускает. Это хуже, чем отсутствие экрана: текст обещает механизм,
   которого нет.

4. **Партнёр видит число, но не его разбор.** `settlementApi.statement`
   (детализация одной выписки) — **ноль** использований на странице. В
   докблоке API написано, что итемизация и есть то, что делает выписку
   «answerable rather than a number to be argued with». Я оставил партнёру
   ровно то число, с которым можно только спорить.

5. **`unsettled` в админке не используется.** Админ не видит, что накопилось
   у партнёра, перед тем как решать, составлять ли расчёт.

6. **`StorageNotice` принимает `privacyUrl` и нигде его не получает.** Проп
   есть, ссылки на политику в уведомлении нет ни в одной панели.

## 7a. Следующей сессии — с чего начинать

Записано потому, что следующая сессия начнётся с пустым контекстом, и
восстанавливать это рассуждением дороже, чем прочитать.

**Три факта, которые не видны из кода и стоили по несколько часов каждый.**

1. *Локальный зелёный прогон интеграционных тестов ничего не доказывает про
   CI.* Пул Prisma по умолчанию — `CPU × 2 + 1`, на этой машине 9, на раннере
   меньше. Гонки, связанные с соединениями, проявляются только на маленьком
   пуле. Прогонять так:
   `TEST_DATABASE_URL='...?schema=public&connection_limit=5' npx jest --selectProjects integration`.
2. *Внутри денежной транзакции нельзя обращаться к `this.prisma`.* Это берёт
   второе соединение из того же пула и при N одновременных вызовах вешает
   все N до таймаута. Правило: либо всё через `tx`, либо ничего — смешение
   даёт самоблокировку (подробно в §17).
3. *Падения в одном job'е маскируют друг друга.* Перед пушем гонять
   `eslint .`, `turbo run typecheck`, `turbo run build`
   (с `NEXT_PUBLIC_API_BASE_URL`), `scripts/build-demo-app.sh` — по всему
   дереву, а не по тронутому пакету.

**Оставшееся, по возрастанию стоимости.**

|---|---|---|
| Мобильный экран оплаты (§7) | **сделано 18.09** | — |
| Админский экран расчётов (§6-7) | **сделано 18.09** | — |
