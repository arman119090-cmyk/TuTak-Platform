# План запроса ленты движений партнёра

Дата: 22.09.2026. Ветка `partner-settlement-transparency`, PR #69.

Экран «Взаиморасчёты» отдаёт ленту движений страницами по keyset-курсору
`(postedAt, id)`. Ниже — фактические планы PostgreSQL на синтетическом
наборе, а не оценка «на глаз».

## Как измерялось

Отдельная база `tutak_explain`, схема развёрнута штатным
`prisma migrate deploy` (все миграции ветки). В неё засеяно:

| | строк |
|---|---|
| `ledger_transactions` | 400 020 |
| `ledger_postings` | 800 040 |
| постинги счёта «крупный партнёр» (`acct-under-test`) | 200 000 |
| постинги счёта «новый партнёр» (`acct-sparse`) | 20 |

Даты разбросаны случайно по двум годам, поэтому порядок `(postedAt, id)`
не совпадает с порядком вставки. Каждая транзакция — сбалансированная
пара проводок, как того требует триггер `assert_ledger_transaction_balances`.
Продакшен-данные не использовались и не генерировались сотнями тысяч
строк в рабочей базе: база создана под эту проверку и удаляется после неё.

## Индексы, которыми располагает запрос

```
ledger_postings("accountId", id)
ledger_postings("transactionId")
ledger_transactions("postedAt")
ledger_transactions("sourceType", "sourceId")
```

Составного индекса, который покрывал бы сортировку `t."postedAt" DESC,
p."id" DESC`, нет и быть не может: два столбца сортировки лежат в разных
таблицах.

## Что показали планы

### 1. Первая страница крупного партнёра — 2.9 мс

```
Limit (actual time=1.581..2.821 rows=51)
  Incremental Sort  Sort Key: t."postedAt" DESC, p.id DESC
                    Presorted Key: t."postedAt"
    Nested Loop Left Join (actual rows=52)
      Index Scan Backward using "ledger_transactions_postedAt_idx"  (actual rows=99)
      Index Scan using "ledger_postings_transactionId_idx"          (loops=99)
Execution Time: 2.895 ms
```

Планировщик идёт по индексу `postedAt` назад и добирает проводки по
`transactionId`. Полной сортировки 200 000 строк нет — `Incremental Sort`
досортировывает только группы с одинаковым `postedAt`. Это ровно то
поведение, ради которого keyset и делался.

### 2. Первая страница нового партнёра (20 проводок из 800 040) — 0.09 мс

```
Limit (actual time=0.069..0.071 rows=20)
  Sort  Sort Key: t."postedAt" DESC, p.id DESC   (Memory: 26kB)
    Nested Loop
      Index Scan using "ledger_postings_accountId_id_idx"  (actual rows=20)
      Index Scan using ledger_transactions_pkey            (loops=20)
Execution Time: 0.091 ms
```

На разреженном счёте планировщик сам переключается на другой план — идёт
от `accountId` и сортирует маленький результат. Обе формы выборки
обслуживаются имеющимися индексами; добавлять ничего не нужно.

### 3. Глубокая страница по курсору — растёт линейно с глубиной

| курсор на строке | примерно страница | время |
|---|---|---|
| 500 | 10 | 12 мс |
| 5 000 | 99 | 59 мс |
| 20 000 | 393 | 205 мс |
| 50 000 | 981 | 496 мс |
| 150 000 | 2 942 | 1 656 мс |

Причина видна в плане: условие `(t."postedAt", p."id") < (…)` применяется
как фильтр при обратном проходе по индексу `postedAt`, а не как seek —
seek невозможен, потому что вторая половина ключа лежит в другой таблице.
На строке 150 000 проход отбрасывает 299 860 транзакций, прежде чем дойти
до курсора.

Это деградация, но не узкое место пилота:

* до сотой страницы (≈5 000 строк) запрос укладывается в 59 мс;
* до тысячной страницы — в полсекунды;
* глубина, на которой становится больно, недостижима перелистыванием
  руками: 2 942 нажатия «дальше».

Главное — у экрана есть фильтр периода, и он снимает проблему полностью.
Тот же участок истории с фильтром за март 2025 года:

```
Limit (actual time=1.620..2.534 rows=51)
  Index Scan Backward using "ledger_transactions_postedAt_idx" (actual rows=99)
Execution Time: 2.610 ms
```

2.6 мс вместо 1 656 мс: обратный проход останавливается на границе
периода. Партнёр, который хочет старые строки, выбирает период, а не
листает тысячу страниц.

### 4. Итоги выборки — считаются по всей выборке, без курсора, 116 мс

```
Finalize Aggregate (actual time=111.587..116.295)
  Parallel Hash Join
    Parallel Seq Scan on ledger_postings  (actual rows=66667 loops=3)
    Parallel Seq Scan on ledger_transactions (actual rows=133340 loops=3)
Execution Time: 116.387 ms
```

Это худший случай, а не типичный: в синтетическом наборе один счёт
владеет четвертью всех проводок, и при такой избирательности
последовательный проход дешевле индексного — планировщик прав. На
разреженном счёте тот же запрос идёт по `ledger_postings_accountId_id_idx`
и выполняется за 0.2 мс. На реальной площадке доля одного партнёра во
всех проводках — малая, то есть рабочая форма именно вторая.

Убирание трёх джойнов из этого запроса (при пустых фильтрах они ничего не
добавляют — связи 1:1) снижает его со 116 мс до 59 мс, но не меняет
характер плана: это всё тот же последовательный проход. Поэтому правка
не сделана: она выигрывает половину времени только в той форме данных,
которой на площадке не будет, и добавляет второй вариант запроса, который
должен оставаться согласованным с первым. Итоги выборки и строки страницы
намеренно строятся из одного и того же `activityWhere`, чтобы не могли
разойтись.

## Вывод

Проверенного узкого места нет, ничего не меняется. Если оно появится,
известно и где, и что делать:

* **признак** — партнёр в пилоте жалуется на задержку ленты, или у одного
  партнёра больше ~50 000 проводок и он действительно листает вглубь;
* **исправление** — денормализовать `postedAt` в `ledger_postings` и
  добавить индекс `("accountId", "postedAt" DESC, "id" DESC)`; тогда
  keyset становится настоящим seek, и глубина страницы перестаёт влиять
  на время. Это изменение схемы с обратной засыпкой, и делать его до
  доказанной нужды — платить миграцией за проблему, которой нет.
