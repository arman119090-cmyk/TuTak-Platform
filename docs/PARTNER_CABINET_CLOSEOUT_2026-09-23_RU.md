* те же 13 пунктов, что в боковой панели, тот же выход из системы, тот же
  переключатель темы и языка;

* закрытие при переходе — по изменению пути, а не по обработчику клика:
  ссылку рисует приложение своим роутером, оболочка клика не видит, а панель,

### 1.3. Приглашение сотрудника целиком через интерфейс

Настоящих SMS не отправлялось: API поднят с консольным транспортом
(`SMS transport: budgeted:console`), каждое сообщение пишется в журнал и
никуда не уходит. Поэтому **эта проверка ничего не говорит о реальной
доставке через Viva** — она говорит, что панель, эндпоинты и база
согласованы между собой.

Прогон (Chromium, панель на 3101, API на 4000), 13 шагов из 13:

```
PASS  владелец вошёл в панель
PASS  экран сотрудников открыт, карточка приглашений на месте
PASS  приглашение создано и видно в таблице со статусом «Ожидает»
PASS  код ушёл на приглашённый номер через тестовый транспорт
PASS  токен не показан в панели ни разу
PASS  повторная отправка выдала новый код, отличный от первого
PASS  отменённое приглашение показано как «Отменено» и без кнопок
PASS  приглашённый завёл учётную запись по своему номеру
PASS  старый код после повторной отправки не принимается (HTTP 400)
PASS  приглашение принято действующим кодом (HTTP 201, EMP-010)
PASS  повторное принятие тем же кодом отклонено (HTTP 400)
PASS  в таблице приглашений статус стал «Принято»
PASS  приглашённый появился в списке сотрудников с тем самым кодом EMP
```

Половина владельца пройдена целиком через экраны. Принятие приглашения —
через API, и вот почему это честная граница, а не обход: **экрана принятия
приглашения не существует**. Маршрут `POST /partner-invitations/accept`
требует сессию того, кто доказал владение приглашённым номером, а никакого
интерфейса к нему ни в панели, ни в мобильном приложении нет. В прогоне
приглашённый регистрируется настоящим путём — OTP на свой номер через тот же
консольный транспорт — и затем принимает. Это дыра в продукте, а не в
проверке; записана в остатках.

### 1.4. Светлая тема и крупный текст — измерением, а не на глаз

Перелив по горизонтали измерялся как `scrollWidth − clientWidth` корневого
элемента. Десять проверок, во всех — **0 px**:

| Тема | Ширина | Масштаб | Экраны | Перелив |
| --- | --- | --- | --- | --- |
| светлая | 1280 | 100% | взаиморасчёты, сотрудники, филиалы | 0 px |
| светлая | 390 | 100% | взаиморасчёты, сотрудники, филиалы | 0 px |
| светлая | 390 | 150% | сотрудники, филиалы | 0 px |
| светлая | 390 | 200% | сотрудники, филиалы | 0 px |

Тёмная тема прогнана тем же скриптом — тоже 0 px во всех десяти.

Таблицы при этом шире экрана (на 390px при 200% таблица филиалов шире
области на 857px) — и это правильно: они прокручиваются внутри своей
обёртки `overflow-x-auto`, а страница целиком не едет. Именно это различие и
измерялось.

Скриншоты: `docs/screenshots/partner-light-large-text-2026-09-22/`.

**Найдено по ходу и не исправлено — нужно решение владельца.** Контраст
подписей `text-faint` (12px) ниже порога WCAG AA (4.5:1 для мелкого текста):

| Тема | Цвет текста | Фон | Контраст |
| --- | --- | --- | --- |
| светлая | `#98A2B3` | `#F8F9FB` | **2.44 : 1** |
| тёмная | `#636366` | `#0A0A0F` | **3.30 : 1** |

Замерено точечно, с печатью обоих цветов, а не грубым обходом страницы:
первый, грубый вариант замера выдал 1:1 на заголовке, то есть был неверен
сам. Под это правило попадает, например, строка «Всего = ещё не в расчёте +
в неоплаченных расчётах» — та самая, которая объясняет владельцу
арифметику его долга.

Исправление — один шаг по той же шкале нейтральных: `#667085` в светлой
(4.72:1) и `#8E8E93` в тёмной (6.06:1). Я этого не сделал: `--tutak-text-tertiary`
— общий токен, он меняет внешний вид каждого экрана в обеих панелях, а
задание прямо просит не устраивать редизайн. Решение за владельцем.

даже если поле переименуют.

**Ошибка по ходу, которую стоит записать.** Первая версия этого теста
проверяла и `poolAmount` как значение — и упала на собственном вкладе
партнёра. Пул и есть вклад партнёра, ровно то, что партнёр вправе видеть;
скрывать надо деление пула: остаток TuTak, зелёную и отложенную доли. Если
бы я «починил» код под тот тест, партнёр перестал бы видеть, за что с него
удержали. Тест исправлен, код — нет.

## 6. Ошибки, допущенные по ходу этой части работы

1. **Тест, который чуть не сломал правильный код.** Проверка коммерческой
   тайны сначала считала `poolAmount` секретом и упала на собственном вкладе
   партнёра. Разобрался до того, как «чинить» код, — но если бы не разобрался,
   партнёр перестал бы видеть, за что с него удержали.
2. **Грубый замер контраста дал заведомо неверный ответ.** Обход всей
   страницы выдал 1:1 на заголовках. Я не стал выдавать эти числа за факт и
   перемерил точечно с печатью обоих цветов; в отчёт попали только
   перемеренные.
3. **Ложные «PASS» в первой версии прогона приглашения.** Шаги «старый код
   не принимается» и «повторное принятие отклонено» проходили, пока сам
   вызов возвращал 401 из-за отсутствия сессии: отказ по любой причине
   засчитывался как отказ по нужной. Исправлено — 401 теперь считается
   провалом проверки, а не успехом.
4. **Перезагрузка страницы в прогоне выбрасывала из панели**, и я сначала
