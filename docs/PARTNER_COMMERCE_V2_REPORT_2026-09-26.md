================================================================
E. ORDER STATE MACHINE (operationalStatus)
================================================================
DRAFT ─«Подтвердить заказ»→ SUBMITTED ─«Увидел»→ SEEN ─«В наличии»→
STOCK_CONFIRMED ─«Передан»→ HANDED_OVER ─«Получил заказ»→ RECEIVED
─(все внешние части подтверждены, нет открытого спора)→ COMPLETED
SUBMITTED|SEEN ─«Нет в наличии»→ OUT_OF_STOCK ─(sourcing принят клиентом
  или партнёр всё-таки нашёл)→ STOCK_CONFIRMED
DRAFT ─24 ч→ EXPIRED
DRAFT|SUBMITTED|SEEN|STOCK_CONFIRMED|OUT_OF_STOCK ─отмена→ CANCELLED
«Получил заказ» доступен из STOCK_CONFIRMED и HANDED_OVER. После передачи
отмена запрещена — это уже возврат. Отдельные измерения:
sourcingStatus NONE→REQUIRED→SEARCHING→AWAITING_CUSTOMER→RESOLVED|FAILED;
disputeStatus NONE→OPEN→RESOLVED_CUSTOMER|RESOLVED_PARTNER|RESOLVED_SPLIT.
Каждый переход — условный UPDATE по исходному состоянию в той же
транзакции, что и движение денег: у гонки ровно один победитель.

================================================================
F. PAYMENT STATE MACHINE
================================================================
Заказ: UNFUNDED ─подтверждение→ RESERVED (электронные части в escrow)
─внешние подтверждены→ FUNDED ─завершение→ SETTLED ─возврат→
PARTIALLY_REFUNDED | REFUNDED. Отмена → REFUNDED, либо REFUND_PENDING,
пока партнёр не подтвердит возврат уже подтверждённой наличной части.
Часть оплаты: DISCOUNT/TUTAK_MONEY: PENDING→CAPTURED→SETTLED|RETURNED;
EXTERNAL: PENDING→CONFIRMED→CORRECTED (только до передачи) |
RETURN_PENDING→RETURNED.

================================================================
G. OFFLINE QR
================================================================
Существующий flow сохранён. Добавлено: необязательная часть «деньгами
TuTak» (скидка и деньги раздельно, лимит партнёра — только на скидку);

требуют смены (с rollout). Проверено: сценарии A и B.

================================================================
H. ONLINE ORDER
================================================================
Сайт партнёра создаёт заказ server-to-server (x-api-key, идемпотентно по
externalOrderId) → клиент видит заказ, оба баланса, лимит скидки и
предоплату → «Подтвердить заказ» (идемпотентно, перехват ссылки другим
клиентом запрещён) → партнёр: Увидел → В наличии/Нет → Передан →
подтверждение наличных на смене → клиент «Получил заказ» (с повторным
подтверждением) → завершение. Отмена клиентом до передачи — полный возврат
без штрафов. Sourcing: задача сотруднику TuTak; любой найденный вариант
(даже тот же товар по той же цене) — только с согласия клиента; дешевле —
разница возвращается; дороже — клиент доплачивает выбранным способом;
«не найден» — отмена с возвратом. allowExternalSourcing=false — сразу
отмена с возвратом.

================================================================
I. SPLIT PAYMENT
================================================================
discount + tutakMoney + external = total (проверяет сервис и CHECK в БД).
Скидка — через бонусный движок; деньги — через CUSTOMER_PREPAID_BALANCE;
внешняя часть в леджер TuTak не попадает никогда. Комиссия всегда с полного
total.

================================================================
J. RESERVE
================================================================
Настоящий резерв: отдельный счёт PARTNER_ORDER_ESCROW в существующем
леджере. Каждое движение — отдельная проводка со ссылкой из части оплаты.
Двойной выпуск и «выпуск × возврат» исключены условным захватом статуса.
По таймеру деньги партнёру не уходят никогда (24 ч напоминание, 48 ч ручная
проверка, дальше решение человека).

================================================================
K. PARTNER BALANCE
================================================================
PARTNER_PAYABLE: + электронная часть при завершении, − комиссия (pool) на
весь total — взаимозачёт в одном счёте, наличные партнёру не
зачисляются. Кабинет показывает: к выплате партнёру / долг партнёра перед
TuTak / в резерве (ещё не получено клиентами) / заморожено спорами /
наличные к подтверждению / выписки. Кнопки «вывести» нет.

================================================================
L. SETTLEMENT
================================================================
Период у каждого партнёра (DAILY/WEEKLY/BIWEEKLY/MONTHLY; существующие =
BIWEEKLY). В конце периода выписка строится из проводок: строка = проводка,
closing = opening + Σ строк, одна проводка — максимум в одной выписке.
Два воркера → одна выписка. Проверка «пора рассчитаться» (бывшие 14 дней)
теперь по периоду партнёра. Деньги двигают только существующие
Payout/PartnerCollection. На копии данных «как в production» выписки
совпали с балансом леджера до копейки.

================================================================
M. COMMISSION
================================================================
База — Partner.bonusAccrualRateBps. Переопределения по serviceType и/или
category; приоритет: serviceType+category → serviceType → category → база.
Одна ставка на заказ, снимок при создании. Euro Import: сайт передаёт
только услугу (например, $2000 в AMD) с serviceType, машина вне базы.
Little Joe 15% — настройка, не код. Ставки вне 0.5–20% не принимаются.

================================================================
N. COMMISSION DISTRIBUTION
================================================================
Код settlePurchase вынесен без изменений в CommissionDistributionService
(зелёный, продвижение чёрных лотов, новый чёрный лот, рефералка L1/L2/L3,
contribution-проводка). QR-регрессия прошла без изменений. Онлайн-заказ
вызывает тот же сервис при завершении. Снимок распределения хранится в
заказе; сумма долей = pool проверяется тестами.

================================================================
O. SHIFTS
================================================================
Смена = филиал + рабочий день + сотрудник. Несколько сотрудников в филиале
одновременно; одна открытая смена на сотрудника; начало смены закрывает
только незакрытые смены прошлого рабочего дня этого филиала; ежечасный
sweep добивает остальное; деактивация сотрудника закрывает его смену в той
же транзакции. Проверка смены блокирует строку смены в транзакции действия.
Rollout: существующим партнёрам 14 дней (действие без смены работает и
пишется в AuditLog как withoutShift, кассир видит баннер); новым — сразу;
дату можно только приблизить.

================================================================
P. SLA
================================================================
От submittedAt: 5 мин без «Увидел» → алерт (один); 30 мин без решения по
наличию → critical, повтор каждые 5 мин; «Взял в работу» останавливает
повторы, заказ остаётся в очереди. Через AlertsService.fire и BullMQ-sweep.
Клиент видит только нейтральные статусы.

================================================================
Q. SOURCING
================================================================
Очередь в админке: заказ, партнёр, клиент, фото, название, SKU, OEM,
количество, цена, уже обеспечено через TuTak, время ожидания. Кнопки:
найден точный / найден аналог (с отличиями и источником) / не найден.
«Взял в работу» и «партнёр всё-таки нашёл» — гонка с одним победителем.

================================================================
R. RETURNS
================================================================
Только после завершения (до — это отмена). Полный и частичный, доля
r = сумма/total, через накопительный «водяной знак» (повторные частичные
возвраты не могут развернуть больше оригинала). Разворачиваются связанными
проводками: распределение ×r по снимку, скидка ×r (восстановление клиенту),
деньги ×r (на баланс клиента), внешняя часть ×r — возвращает партнёр и
подтверждает на смене. Если часть распределения уже потрачена — возврат
целиком откатывается и уходит в MANUAL_REVIEW: деньги не двигаются, TuTak
ничего не покрывает, отрицательных балансов нет (до ответа на Q8/Q9).

================================================================
S. DISPUTES
================================================================
Клиент — спор по заказу после передачи; партнёр — спор по оплате после
передачи. До расчёта: чистый кредит партнёра по заказу (пропорционально
спорной сумме) переводится PARTNER_PAYABLE → PARTNER_DISPUTE_HOLD, выплата
его не видит. После расчёта: ничего не замораживается; решение в пользу
клиента идёт как возврат, PARTNER_PAYABLE может стать положительным — долг
партнёра, попадает в следующую выписку. Решает только админ с
ORDER_DISPUTE_RESOLVE, один открытый спор на заказ, два админа → одно
решение, всё в AuditLog.

================================================================
T. SECURITY
================================================================
RBAC и scope: партнёр A не видит B; сотрудник филиала — только свои филиалы
(и заказы без филиала); клиент — только свои заказы, чужую ссылку оплаты не
может ни открыть, ни подтвердить, ни отменить. Партнёр не может: ставить
PAID на электронную часть (такого эндпоинта нет), менять комиссию, период,
дату смен, выводить баланс. Сайт партнёра — только по API-ключу (хэш,
timing-safe), браузер секрет не видит, цены приходят только server-to-server.
Идемпотентность: создание заказа, подтверждение, наличные, получение,
возврат, частичный возврат, решение спора, выписка, доплата, top-up callback.
AuditLog: все шаги заказа, смены, исправления наличных с причиной, решения
админа.

================================================================
U. CONCURRENCY (реальный параллелизм на PostgreSQL)
================================================================
Проверено тестами: получил × отмена; получил × возврат; в наличии × нет в
наличии; sourcing «взял» × «в наличии»; два админа по одному спору; двойное
подтверждение наличных; двойной top-up callback (IDRAM, когда подключим);
двойное «Подтвердить заказ»; возврат × выписка; спор × выписка; деактивация
× подтверждение; закрытие смены × подтверждение; два воркера выписок;
повтор частичного возврата; повтор принятия доплаты.

Не подключено / не сделано:
- IDRAM: пополнение возвращает «не подключено»; после пополнения нужен
  адаптер с возвратом в тот же checkout.
- Удешевление, которое можно вернуть только из уже полученных партнёром
  наличных, уходит в ручную проверку (правило не придумывал).
- Напоминание 24 ч / проверка 48 ч считаются от «Передан»; если партнёр не
  нажал «Передан», таймеры не стартуют (заказ виден в очереди с временем).
- Новых fraud-сигналов (§63) не добавлял; работает существующая защита от
  self-dealing, идемпотентность и проверки прав. Аналитика партнёров (§56) —
  только сохранённые метки времени, без дашбордов.
- Уведомления партнёру пишутся во входящие сотрудников, но в веб-кабинете
  партнёра нет экрана уведомлений (существующий пробел).
- В кабинете партнёра роль PARTNER_MANAGER не определяется как основная
  (существующая особенность authStore) — менеджер не видит панель смены.
- Экран настроек коммерции в админке принимает UUID партнёра (без выбора
  из списка).
