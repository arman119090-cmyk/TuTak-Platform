# Требования к провайдеру пополнения предоплаченного баланса

Дата: 20.09.2026. Контекст: гибридная платёжная модель
(`docs/PARTNER_HYBRID_PAYMENTS_PILOT_RU.md`), компонент «prepaid».

Этот документ — то, что нужно **получить от провайдера** (банк, PSP, Idram или
другой), прежде чем к `BankTopUpAdapter` можно будет подключить реальную
реализацию. Ничего из перечисленного здесь не выдумано и не предполагается:
пока провайдер не дал ответ письменно, соответствующий пункт считается
BLOCKED BY PSP.

## Что уже есть в коде (и что провайдер должен лечь в это)

| Место | Что делает | Что ждёт от провайдера |
|---|---|---|
| `BankTopUpAdapter.initiateTopUp` | открывает пополнение на нашей стороне (`BalanceTopUp` PENDING) и передаёт провайдеру `idempotencyKey` | ответ `INITIATED {providerReference, redirectUrl?}` или `DECLINED {declineReason}`; идемпотентность по нашему ключу на **его** стороне |
| `BankTopUpAdapter.verifyTopUpWebhook` | проверяет подпись входящего уведомления и трактует исход | подписанное уведомление с `providerReference` и однозначным исходом `COMPLETED / DECLINED / FAILED` |
| `CustomerBalanceService.confirmTopUpWebhook` | зачисляет **только** по проверенному `COMPLETED`, ровно один раз (условный `updateMany` PENDING/UNRESOLVED → COMPLETED) | повторные и параллельные доставки допустимы — они no-op |
| `balance.escalate-stale-topups` (sweep) | через 30 мин без ответа переводит PENDING → UNRESOLVED и алертит каждый час | **не** трактует таймаут как отказ |
| `GET /balance/topup/:id` | статус пополнения клиенту | — |

## Обязательные ответы провайдера

1. **Авторитетный источник результата.** Что является финальным словом:
   webhook, ответ синхронного API, выписка? Если webhook — что делать при его
   потере: есть ли API запроса статуса по `providerReference`? Без такого API
   состояние UNRESOLVED может закрываться только вручную по выписке.
2. **Подпись уведомлений.** Алгоритм (HMAC-SHA256 по сырому телу? RSA?),
   какие поля входят, как передаётся секрет, ротация. Сейчас в API нет
   захвата сырого тела запроса — если подпись считается по байтам, это
   отдельная работа при написании адаптера (см. комментарий в интерфейсе).
3. **Идемпотентность инициации.** Принимает ли провайдер наш ключ; что
   возвращает при повторе (тот же `providerReference` или ошибку).
4. **Семантика статусов.** Точный список статусов и какие из них финальны.
   Отдельно: бывает ли «оплачено, но позже отменено провайдером» (chargeback,
   reversal) — тогда нужен путь списания с баланса, которого сейчас нет.
5. **Тайминги.** Максимальная задержка уведомления; после какого срока
   провайдер сам считает операцию неуспешной. От этого зависят
   `CUSTOMER_PREPAID_TOPUP_STALE_AFTER_MS` / `..._ESCALATE_EVERY_MS`.
6. **Суммы и валюта.** Минимум/максимум пополнения, валюта, комиссии — кто
   их платит и как они отражаются (нетто/брутто). Сейчас зачисляется ровно
   `amount`, комиссия не моделируется.
7. **Сверка.** Формат выписки/реестра операций для ежедневной сверки
   `PSP_RECEIVABLE` против фактического поступления
   (`ReconciliationService.reconcile`).
8. **Возвраты пополнений.** Может ли клиент вернуть пополнение (не покупку)
   и как это проходит через провайдера. Сейчас — нет такого пути.
9. **Sandbox.** Тестовый контур, тестовые карты/кошельки, отдельные ключи.
   Реальные деньги в разработке не используются.
10. **Договор и лицензия.** Кто юридически держит средства клиента — см.
    `docs/PREPAID_BALANCE_LEGAL_QUESTIONS_RU.md`. Пока нет ответа, флаг
    `CUSTOMER_PREPAID_TOPUP_ENABLED` в production не включается.

## Что провайдеру делать не нужно

- Знать о бонусах, партнёрах, расчётах — он видит только «клиент X пополняет
  баланс на Y».
- Участвовать в покупке. Idram как платёжный провайдер покупки
  (`TUTAK_PSP`) и провайдер пополнения — разные роли; одно и то же
  подключение для обеих ролей — отдельное решение владельца, не техническое.

## Порядок подключения (после получения ответов)

1. Класс `XxxBankTopUpAdapter implements BankTopUpAdapter` + конфиг в
   `AppConfig` (без секретов в git).
2. `CustomerBalanceModule`: `useClass` на новый адаптер.
3. Интеграционные тесты адаптера с записанными (не живыми) ответами
   провайдера; существующий `customer-balance.int-spec.ts` остаётся
   контрактом сервиса.
4. Sandbox: полный цикл initiate → redirect → webhook → COMPLETED; повторный
   webhook; DECLINED; потерянный webhook → UNRESOLVED → поздний webhook.
5. Только после этого — обсуждение включения флага в production.
