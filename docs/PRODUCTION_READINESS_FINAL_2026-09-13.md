## RATE LIMITING — закрыто, с доказательством

Было: `Request rate limiting is STOOD DOWN` при каждом старте. Лимиты по одному
источнику не работали; глобальный бюджет SMS был единственным, что стояло между
циклом `curl` и счётом за сообщения.

Угадывать `CLIENT_IP_TRUSTED_HOPS` нельзя: значение на единицу больше нужного
превращает `req.ip` в то, что написал сам атакующий. Документация Railway про
`X-Forwarded-For` молчит вообще. Поэтому я сделал измеритель.

**Как измерено.** Запрос с одной записью в `X-Forwarded-For` и той же записью,
названной в `X-TuTak-Proxy-Probe`, — процесс точно знает, какую запись написал
вызывающий. Отправлено с раннера GitHub, через настоящий edge Railway.

Результат (дословно из лога production):

```
X-Forwarded-For entries: 2; probe marker position from right: 0;
X-Real-IP present: true; X-Real-IP position from right: 2.
The marker did not survive: this edge replaces X-Forwarded-For rather than
appending to it, so every entry is infrastructure-written.
CLIENT_IP_TRUSTED_HOPS=2.
```

**Повторено на маршрутизируемом адресе** (`8.8.8.8` вместо документационного
`203.0.113.7`) — результат посимвольно тот же. Это была не формальность: прокси
иногда вычищают именно зарезервированные диапазоны, и тогда «безопасное» чтение
оказалось бы ложным. Свойство, которое держится на одном классе адресов, — не
свойство.

**Вывод:** edge Railway **заменяет** `X-Forwarded-For`, а не дополняет его. Ни
одна запись в заголовке не контролируется вызывающим. `X-Real-IP` стоит на
позиции 2 справа и согласуется с арифметикой.

**Включено:** `CLIENT_IP_STRATEGY=xff-depth`, `CLIENT_IP_TRUSTED_HOPS=2`.

Подтверждение из живого лога после передеплоя:

```
Client IP resolved from X-Forwarded-For, trusting 2 hop(s) from the right.
```

Строки `STOOD DOWN` в логе больше нет. Лимиты по источнику работают: OTP-запросы,
проверка кода, регистрация, вход и сброс пароля снова считаются на каждого
вызывающего отдельно, а не в один общий счётчик.

## PRODUCTION CONFIG AUDIT — найдено и исправлено

**Главная находка: боевой деплой был помечен `APP_ENV=staging`.**

Это ровно та ошибка, о которой предупреждает комментарий в `app-environment.ts`:
развёртывание, доступное из интернета, названо `staging`, и каждая проверка вида
«в production так нельзя» молча к нему не применялась. Не применялись:

* требование `MEDIA_STORAGE_DRIVER=s3` (локальный диск не переживает передеплой —
  строки в базе пережили бы байты, на которые указывают);
* требование настоящего оператора SMS;
* требование настроенного push;
* требование явного `REDIS_URL`;
* **отказ загружаться, если `CORS_ORIGINS` содержит `localhost`** — а это значит,
  что страница на чьём-то ноутбуке была бы доверенной с куками против боевого API;
* **отказ загружаться, если `MEDIA_PUBLIC_BASE_URL` указывает на localhost.**

Как обнаружено: при старте не появлялось предупреждение `AlertsModule`, которое
печатается только при `appEnv === 'production'`. Значит, метка была другой.

**Исправлено:** `APP_ENV=production`. Сервис поднялся, деплой SUCCESS.

Это и есть аудит конфигурации — не чтение значений, а доказательство делом: если
бы хоть одна из шести проверок не прошла, процесс отказался бы стартовать и назвал
бы переменную. Он стартовал. Значит:

| Проверка | Результат |
|---|---|
| `CORS_ORIGINS` без `localhost`/`127.0.0.1`/`::1`/`0.0.0.0` | пройдена |
| `MEDIA_PUBLIC_BASE_URL` задан и не loopback | пройдена |
| `MEDIA_STORAGE_DRIVER=s3` + все пять S3-переменных | пройдена |
| Настоящий оператор SMS (не заглушка) | пройдена, `SMS transport: budgeted:viva` |
| `PUSH_ENABLED=true` | пройдена |
| Явный `REDIS_URL` | пройдена |
| `DATABASE_URL` задан, оба JWT-секрета ≥ 32 символов | пройдена |
| `APP_ENV` — валидное значение | пройдена |

Дополнительно: `CARD_PAYMENTS_ENABLED` не задан, поэтому legacy-модуль платежей не
импортируется и маршрутов `/payments`, `/refunds` в production просто нет.
`DEMO_SEED` не задан — демо-данных в боевой базе нет. `SEED_BASELINE=true`

Из ранее внесённого (в этой же сессии): `DEMO_MODE` переведён `true → false`,
`PUSH_ENABLED=true`, `PUSH_ENDPOINT` прописан явно.

## MAP

Провайдер выбран — **MapTiler**. Всё, что можно было сделать без аккаунта, сделано:

* сборка передаёт провайдера на машину, которая собирает APK;
* адрес плиток и строка копирайта **подставляются автоматически**, если задан
  ключ, — настройка сведена к одному секрету вместо трёх значений, которые надо
  скопировать без опечатки;
* приложение представляется провайдеру (`User-Agent`/`Referer`) — этого требует
  политика любого провайдера;
* копирайт рисуется на самой карте.

**И главное — поставлен блок.** `app.config.js` теперь **отказывается собирать**
профили `preview`, `staging`, `production` без `MAP_TILE_URL_TEMPLATE`. Это
добавлено после реального случая: APK #47 собрался, был выложен и описан как
готовый, и только распаковка бинарника показала, что карта внутри на
openstreetmap.org. Такая ошибка ничем себя не выдаёт — приложение работает до дня,
когда OSM его заблокирует, и тогда серый прямоугольник получают сразу все.

Плюс: если плитки не грузятся (нет сети, отозван ключ, исчерпана квота), карта
теперь **говорит об этом**, а не показывает пустой прямоугольник, неотличимый от
района без партнёров. Порог — половина экрана, чтобы одна потерянная плитка не
поднимала ложную тревогу.

**Доказательство, что APK больше не на fallback, будет только после ключа** —
сейчас сборка установочного профиля просто откажется стартовать. Это и есть
доказательство того, что молча уехать на fallback больше нельзя.

## HEALTH / READINESS

Модель проверена и признана правильной для Railway, менять не стал:

* `/health` — только «процесс жив». Намеренно ничего не щупает: сбой базы не
  должен приводить к убийству процесса, который сам бы восстановился.
* `/health/ready` — щупает Postgres, Redis и объектное хранилище **параллельно**.
  Из ротации выводят только первые два: без них ни один запрос не выполнится.
  Хранилище — нет, и это осознанная асимметрия: без него не грузится логотип, а
  покупки, начисления, реферальные выплаты и возвраты проходят полностью; ронять
  на нём готовность значило бы вывести все реплики и остановить кассу из-за
  картинки.
* Railway использует именно `/health/ready` как healthcheck — то есть плохая
  реплика в трафик не попадёт.
* Нагрузки эндпоинт не создаёт: `SELECT 1`, `PING` и чтение заведомо
  несуществующего ключа.

## REQUIRES ARMAN

Только то, что физически требует твоего аккаунта или твоих прав.

**1. Ключ MapTiler — блокирует финальный APK.**
maptiler.com → зарегистрироваться (бесплатный тариф, 100 000 плиток в месяц) →
**Account → API keys** → скопировать ключ → GitHub → **Settings → Secrets and
variables → Actions → Secrets → New repository secret**, имя ровно
`MAP_TILE_API_KEY`, значение — ключ → **Add secret**.
Ключ вводится прямо в GitHub; присылать его мне не нужно.
После этого финальный APK — один запуск workflow «Build Android APK».

**2. Бэкапы Postgres — сейчас их нет.**
Railway → проект TuTak → сервис **Postgres** → вкладка **Backups** → включить
**Daily** (хранится 6 дней) и **Weekly** (месяц). Там же кнопка **Enable PITR** —
включи и её: она даёт откат на любую минуту за ~4 недели, а не на сутки назад.
Мои инструменты этого не умеют, CLI Railway здесь нет и токена к нему тоже.

**3. Wait for CI — по одному переключателю на сервис.**
Railway → сервис → вкладка **Source** → включить **Wait for CI** (Check Suites).
Повторить для `tutak-api`, `tutak-admin`, `tutak-partner`. Сейчас слияние в `main`
уезжает в production, даже если CI красный.

**4. Ветка по умолчанию.**
GitHub → **Settings → General → Default branch** → переключить на `main`.
Сейчас это старая ветка, и любой, кто откроет репозиторий, начнёт не с того кода,
что в production.

**5. Защита `main`.**
GitHub → **Settings → Branches → Add branch protection rule**:
* Branch name pattern: `main`
* ✅ Require status checks to pass before merging → добавить **ровно эти две**:
  `Lint, test and build` и `Build the container images`
* ✅ Require a pull request before merging, **Required approvals: 0** (чтобы
  владелец не заблокировал сам себя)
* «Do not allow bypassing the above settings» — **оставить выключенным**: это и
  есть аварийный выход для владельца
* «Require branches to be up to date» — **не включать**: на одном разработчике это
  только заставит перегонять CI после каждого изменения базы

**6. Sentry.** sentry.io → создать проекты и взять DSN. Куда класть:
`SENTRY_DSN` на `tutak-api`; `NEXT_PUBLIC_SENTRY_DSN` на `tutak-admin` и
`tutak-partner` (там же уже есть `NEXT_PUBLIC_SENTRY_ENVIRONMENT`); для мобильного —
`SENTRY_DSN` в секреты GitHub. Пока DSN нет, падение в production не увидит никто.

**7. `ALERT_WEBHOOK_URL`.** Любой входящий webhook (Slack, Telegram-бот, Discord) →
переменная на `tutak-api`. Без него расхождения сверки и упавшие фоновые задачи
остаются только в логе.

**8. Пройти 13 шагов на телефоне** — `docs/PHONE_CHECKLIST_RU.md`.

**9. Решение, а не задача: репозиторий публичный.** Утечки нет (см. выше), но
бизнес-логика, экономика рефералов и схема базы видны всем. Если так задумано —
делать ничего не нужно.

**NOT READY FOR PRODUCTION.**

   сборки (пункт 1).

и больше ни во что.

webhook для алертов платформа работает вслепую — сбой увидит первым клиент, а не вы.
