# QarBerg на staging: первый партнёр, прогон и ожидаемые числа

Первый партнёр TuTak — QarBerg, продажа щебня, две точки в Ереване. Этот
документ — то, что вводится в систему, в каком порядке, и какие числа должны
получиться. Числа посчитаны по коду, а не по памяти: ссылки на места, где
каждое из них берётся, стоят рядом.

Документ описывает **staging** — репетицию. Ни одного реального платежа здесь
не происходит, эквайера нет, база на free-плане живёт 30 дней. Для пилота
(п. 10 плана запуска) всё это заводится заново на платной инфраструктуре.

## 1. Карточка партнёра

| Поле | Значение | Откуда ограничение |
|---|---|---|
| `legalName` | QarBerg | 2–200 символов |
| `displayName` | QarBerg | 2–100, это видит клиент |
| `taxId` | ваш ИНН | 5–30; на staging допустим тестовый |
| `category` | `construction` | свободная строка 2–50. **Не** `fuel` — топливная логика филиалов не включается |
| `bonusAccrualRateBps` | **1000** (10%) | сетка 0,5%: кратно 50, от 50 до 2000 (`is-commission-rate-bps.validator.ts`) |
| `ownerUserId` | id владельца | существующий пользователь, создаётся до партнёра |
| `sellsGas` / `sellsPetrol` | не указывать | имеют смысл только при `category = fuel` |
| `maxBonusPaymentPercent` | 100 (по умолчанию) | сколько процентов чека клиент может закрыть бонусами |

Партнёр, созданный админом, активен сразу: `POST /v1/partners` заводит
`PartnerMembership`, выдаёт владельцу роль `PARTNER_OWNER` в области этого
партнёра и создаёт партнёрский реферальный код.

## 2. Три аккаунта, и почему именно три

| Кто | Откуда берётся | Зачем |
|---|---|---|
| Администратор платформы | сид `SEED_BASELINE`, телефон `+37400000000` | создаёт партнёра |
| Владелец QarBerg | обычная регистрация | владеет партнёром и подтверждает покупки |
| Клиент | обычная регистрация | покупает |

Клиент обязан быть **третьим лицом**. Покупка аккаунтом, аффилированным с
партнёром (владелец или сотрудник), отклоняется намеренно —
`purchase-intents.service.ts:269`, защита от самообслуживания. Своим же
аккаунтом владельца купить у себя и получить бонус не выйдет, и это не
поломка.

Отдельный кассир для первого прогона не нужен: `PARTNER_OWNER` уже держит
`PURCHASE_INTENT_CONFIRM` (`scripts/role-permissions.ts`). Кассиров заводят
позже, когда нужно разграничить, кто именно подтвердил.

## 3. Порядок действий

1. **Админ** входит в админ-панель (`+37400000000`, пароль — сгенерированный
   Render `SEED_ADMIN_PASSWORD`), меняет пароль: аккаунт создан с
   `mustChangePassword`.
2. **Выключить `SEED_BASELINE`** в переменных сервиса API — он своё отработал
   (`docs/RENDER_STAGING_RU.md` §7).
3. **Владелец QarBerg** регистрируется как обычный пользователь. Код
   подтверждения в staging **не приходит по SMS**: оператора связи нет,
   `ConsoleSmsProvider` пишет код в лог. Смотреть: Render → сервис API →
   Logs → строка `[not actually sent] to=… body=…`.
4. **Админ создаёт партнёра** по карточке из §1, `ownerUserId` — id владельца.
5. **Владелец** входит в партнёрскую панель:
   - «Локации» → добавить два филиала;
   - «QR» → коды появляются сами, по одному на активный филиал (статические,
     без срока действия, кодируют `partnerId:branchId`). Ничего «выпускать»
     не нужно — распечатать или показать с экрана;
   - «Профиль» → описание и витрина (`Щебень`, `7000`).
6. **Клиент** регистрируется (код — там же, в логах), сканирует QR нужного
   филиала, вводит сумму **7000**, бонусами не платит.
7. **Владелец** → «Покупки» → подтверждает.

## 4. Что должно получиться: покупка № 1

Чек 7000, ставка 10%, реферера нет, бонусы не тратились.

| Величина | Сумма | Кому |
|---|---|---|
| Пул: 7000 × 10% | **700** | обязательство QarBerg перед платформой |
| Зелёный бонус, 20% пула | **140** | клиенту, доступен сразу |
| Отложенный бонус, 30% пула | **210** | клиенту, в заблокированный лот |
| Доля TuTak, остаток | **350** | доход платформы |

Пул считается от **полной** суммы чека и по ставке, снятой снимком в момент
покупки (`purchase-intents.service.ts:470`) — поэтому изменение ставки позже
не переписывает уже совершённые покупки.

Доли реферера (10% + 5% + 5%) при отсутствии цепочки никому не
перераспределяются: доля TuTak — остаток, поэтому она и вбирает
незадействованные уровни (`referral.service.ts:288` и далее).

**Проводки** (админка → Леджер):

```
PARTNER_PAYABLE (QarBerg)   дебет   700
BONUS_LIABILITY             кредит  350   (140 зелёных + 210 отложенных)
PLATFORM_REVENUE            кредит  350
```

Сходится: 700 = 350 + 350. Если сошлось — расчётный контур работает.

---

## 5. Покупка № 2: проверка скидки

Скидку на первой покупке проверить нечем — у клиента ещё нет бонусов. Она
проверяется на второй.

Тот же чек 7000, при оплате указать бонусами **140**:

- клиент платит 6860 деньгами и 140 бонусами;
- пул снова считается от полных 7000 → снова **700**;
- в партнёрских расчётах за день (партнёрская панель → «Доходы») появляются
  две величины: `discountGiven` = 140 — это TuTak должен QarBerg за
  предоставленную скидку, и `commissionOwed` = 700 — это QarBerg должен
  TuTak комиссии. Нетто = 140 − 700 = **−560** в пользу платформы.

Это и есть «отражение в расчётах» из плана запуска.

## 6. Что выглядит как ошибка, но ею не является

- **210 отложенных не разблокируются.** Лот открывается при обороте 54 000
  драмов за 3 месяца (`DEFERRED_BONUS_REQUIRED_TURNOVER`,
  `DEFERRED_BONUS_WINDOW_MONTHS`). С одной покупки — нет.
- **Коды подтверждения не приходят по SMS.** В staging их печатает в лог
  `ConsoleSmsProvider`; в production так не получится — там боот-гард не даст
  стартовать без оператора связи.
- **Владелец не может купить у себя.** Защита от самообслуживания, см. §2.
- **Панели просыпаются 30–50 секунд.** Free-план Render засыпает после ~15
  минут простоя.
- **Стеки ошибок в Sentry — по минифицированному бандлу.** Загрузка source
  maps выключена намеренно, отдельной задачей
  (`docs/SENTRY_SOURCEMAPS_FUTURE_RU.md`).

---

## 7. Чего этот прогон не проверяет

- реальные деньги: эквайера нет, PSP по умолчанию выключен;
- выплаты партнёру: `Payout` требует отдельного сценария с двойным контролем;
- отложенный бонус и реферальные цепочки: нужен оборот и второй клиент;
- поведение под нагрузкой и на нескольких инстансах.

Всё это — предмет пилота (п. 10 плана), а не первой репетиции.
