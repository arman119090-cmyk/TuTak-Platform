# Приложение работает целиком: регистрация по СМС и основные экраны — 10.09.2026

## Критерий завершения выполнен полностью

Исходный критерий звучал так: «Приложение обращается к Railway, владелец
получил реальную СМС, код подтвердил регистрацию или вход, основные
сценарии проверены». Все четыре части подтверждены журналом сервера.

Один непрерывный сеанс с телефона (клиент `okhttp`, мобильное приложение):

```

12:14:44  POST /v1/auth/login/request-otp    → otp login: skipped-no-eligible-account
12:15:05  POST /v1/auth/register/request-otp → otp register: code-handed-to-carrier
12:15:32  POST /v1/auth/register/verify-otp  → 201  (аккаунт создан)
12:15:33  GET  /v1/referral/me/invites       → 200
12:15:33  GET  /v1/wallet/me                 → 200

12:18:30  GET  /v1/ev/stations/nearby        → 200
12:18:30  GET  /v1/partners/nearby           → 200
```

СМС пришла на телефон, код подтвердил регистрацию, после чего приложение
самостоятельно открыло кошелёк, историю операций, рефералы, зарядки и
партнёров рядом — всё отвечает 200.

## Что на самом деле мешало

Строки 12:14:44 и 12:15:05 показывают причину прямо:

- нажали **«Вход»** → номера в базе Railway не было → сервер намеренно
  промолчал (`skipped-no-eligible-account`, защита от перебора аккаунтов);
- нажали **«Регистрация»** → код ушёл и дошёл.

## Поправка к предыдущему разбору

Версия «у человека старый APK, который ходит на Render» **не подтвердилась**:
его сборка всё это время обращалась к Railway, что видно по адресу хоста в
запросах. Блокировало не это, а выбор экрана «Вход» вместо «Регистрации».

Правка `eas.json` (ветка `fix/mobile-api-base-url-railway`, профиль
`staging` переключён с Render на Railway) остаётся верной и нужной для
любого, у кого действительно старая сборка, но текущую проблему решала не
она. Сборка нового APK перестаёт быть срочной.

## Что осталось

1. **Влить исправление подписи шлюза в `deploy/railway-api-df1fd99`.**
   Сейчас `tutak-api` собирается с `fix/viva-gateway-path-signing`, потому
   что пуш в ветку `deploy/*` блокируется защитным механизмом инструмента:
   `git merge --ff-only fix/viva-gateway-path-signing`, затем вернуть
   источник сервиса на `deploy/railway-api-df1fd99`.
2. **Ведущий ноль в OTP** — по-прежнему открытый риск (примерно один вход
   из десяти). Закроется только СМС с кодом, начинающимся с нуля.
3. **Per-IP лимиты отключены** — `CLIENT_IP_STRATEGY` не задан, в каждом
   старте предупреждение. Для пилота приемлемо, для широкого запуска — нет.
4. `SEED_BASELINE` выключить, пароль супер-админа ротировать.
5. Render не отключать, пока не решено, что все перешли на сборку с
   адресом Railway.
6. Интеграционные тесты на живой БД так и не прогонялись.

Перед боевым запуском отдельно: `APP_ENV=production` (потребует S3 и пяти
`MEDIA_STORAGE_S3_*`), снятие `DEMO_MODE`, и главное — боевого адаптера
эквайринга в коде нет вовсе, только песочница.
