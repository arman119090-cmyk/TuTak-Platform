## 1. Публичный домен — создавать явно, на автоматизм не полагаться

**Замечание верное, и последствие хуже, чем «переменная будет пустой».**

Проверено по коду. Если домена нет, `MEDIA_PUBLIC_BASE_URL` получит значение
вида `https://` — и защита **не сработает**:

```ts
export function isLoopbackOrigin(origin: string): boolean {
  const trimmed = origin.trim();
  if (!trimmed) return false;
  try { return LOOPBACK_HOST.test(new URL(trimmed).hostname); }
  catch { return false; }        // ← "https://" сюда и попадает
}
```

`new URL('https://')` бросает исключение, функция возвращает `false`, и
`assertProductionMediaPublicBaseUrl` пропускает значение. Приложение
**стартует молча с нерабочим адресом медиа** — ровно тот класс отказа, ради
которого эта проверка и написана, только зашедший с другой стороны. То же с
`CORS_ORIGINS`: `https://` не localhost, значит проверка его пропустит.

Отложенный патч содержал `serviceDomains: "Generated on Deploy"` — но патч мы
отменяем, а у сервиса, созданного заново, домена может не быть вовсе.

**Исправление порядка:** домен создаётся и проверяется **до** того, как
задаются `MEDIA_PUBLIC_BASE_URL` и `CORS_ORIGINS`, и до первого деплоя с
`APP_ENV=production`. Проверка — глазами: в переменных сервиса
`RAILWAY_PUBLIC_DOMAIN` должен иметь непустое значение вида
`<что-то>.up.railway.app`. Если пусто — переменные не задаём и деплой не
запускаем.

Порядок в разделе «Действия в панели» ниже это учитывает.

## 3. Первый запуск: Rollback невозможен, миграции проверить до применения

**Замечание верное.** Предыдущего деплоя у нового сервиса нет, откатываться
некуда. Кнопка Rollback появится только со второго деплоя.

**Отмена первого запуска = остановка нового сервиса.** В панели Railway:
сервис `tutak-api` → Settings → Remove service (или Pause, если нужно
сохранить настройки). Postgres, Redis, их тома и их переменные при этом
не трогаются.

### Миграции

`docker-entrypoint.sh` выполняет `prisma migrate deploy` до старта приложения.
В репозитории **52 миграции**.

**Одна из них содержит удаление данных** —
`20260806150000_harden_money_invariants`:

```
DROP INDEX IF EXISTS "transactions_idempotencyKey_key";
DELETE FROM "transactions" a …            (дубликаты по ключу идемпотентности)
DELETE FROM "bonus_ledger_entries" …
DELETE FROM "bonus_ledger_entries" WHERE "amount" < 0;
DROP CONSTRAINT IF EXISTS "transactions_amounts_non_negative" …
```

Это миграция-починка: она приводит данные к инвариантам, удаляя строки, которые
им противоречат. **На пустой базе это ничего не делает. На непустой — делает.**
Отсутствие пользователей само по себе безопасности не гарантирует, и я это
утверждать не буду.

**Ожидание:** база пуста. API на Railway не запускался ни разу, значит
`prisma migrate deploy` там не выполнялся, значит нет ни схемы, ни таблицы
`_prisma_migrations`. Это **вывод, а не измерение**: доступа к базе из этой
сессии нет.

**Проверка до первого деплоя — одна команда, выполняете вы.** В панели
Railway: сервис `Postgres` → вкладка данных / query:

```sql
SELECT migration_name, finished_at
FROM   _prisma_migrations
ORDER  BY finished_at;
```

* Ошибка «relation does not exist» → база чистая, все 52 миграции пойдут с
  нуля, удалять нечего. **Запускаем.**
* Таблица есть и в ней строки → база не чистая. **Останавливаемся**, я
  сверяю список применённых с репозиторием и говорю, что именно сделает
  `migrate deploy`, до того как он это сделает.

## 4. Проверка SMS — сначала связь и авторизация, только потом доставка

**Номер.** Реальная отправка — **только на согласованный номер владельца**.
Никаких других номеров, включая мои тестовые: с живым транспортом каждый
запрос стоит денег и уходит на чей-то телефон.

**Успешный тест 8 сентября ничего не доказывает про Railway.** Он выполнялся
вручную, с другой машины и с другого адреса. Примет ли Viva исходящий адрес
Railway — **не проверялось никогда**.

**Порядок проверки, от связи к доставке.** Провайдер авторизуется не при
старте, а при первой отправке, поэтому первый же запрос кода на ваш номер и
есть проверка связи. Различить стадии позволяет журнал — он для этого и
переделан:

| что в журнале | что это значит | что дальше |
| --- | --- | --- |
| `otp register: carrier-refused` + ошибка сети/таймаут | **до Viva не достучались** | почти наверняка адрес Railway не в списке разрешённых → шлюз |
| `carrier-refused` + отказ авторизации | связь есть, **ключи или логин не приняты** | сверяем учётные данные, шлюз не нужен |
| `carrier-refused` + `RC != 0` | связь и авторизация есть, **отказ Viva по существу** | шаблон, отправитель или формат номера |
| `code-handed-to-carrier`, СМС не пришла | Viva приняла, но не доставила | вопрос к Viva с `transact_unique_id` |
| `code-handed-to-carrier`, СМС пришла | **связь, авторизация и доставка работают** | вводим код |

**Шлюз Contabo — запасной путь, а не отменённый.** Конфигурация, ключ HMAC и
совместимость подписи проверены и остаются в силе. Если первая же строка
таблицы окажется нашим случаем — переставляем `VIVA_API_BASE_URL` на адрес
шлюза, заполняем `SMS_VIVA_GATEWAY_SECRET`, и туннель становится обязательным.
Прямой путь выбран первым потому, что он дешевле в проверке, а не потому, что
шлюз больше не нужен.

**Ведущий ноль в OTP** остаётся отдельным открытым вопросом: закрывается только
настоящей доставкой кода, начинающегося с нуля.

(pending / staged changes, патч на **70 изменений** от 3 сентября) →
**Discard**.

