## 2. Старый патч применять нельзя — и вот почему конкретно

Патч `e0b2070b…`, 70 изменений, лежит с 3 сентября. Я разобрал его по составу.
**18 из 70 изменений — это удаление переменных у живых Postgres и Redis:**

```
Postgres: DATABASE_URL, PGDATA, PGDATABASE, PGHOST, PGPASSWORD, PGPORT,
          PGUSER, POSTGRES_DB, POSTGRES_PASSWORD, POSTGRES_USER,
          RAILWAY_DEPLOYMENT_DRAINING_SECONDS, SSL_CERT_DAYS   → removed
Redis:    REDISHOST, REDISPASSWORD, REDISPORT, REDISUSER,
          REDIS_PASSWORD, REDIS_URL                            → removed
```

Это переменные, которыми шаблоны Railway настраивают сами базы. Применение
патча снимет их с работающих сервисов. Данные удалять не просил никто, но
следующий перезапуск Postgres без `POSTGRES_PASSWORD` и `PGDATA` — это не то,
что стоит выяснять на живой базе.

Кроме того патч создал бы **три** сервиса (API, admin, partner) и бакет. Нам
сейчас нужен один — API.

**Предлагаю: патч отменить (Discard), а API создать отдельно с явным набором
переменных.** Так ни одна переменная живых Postgres и Redis не трогается.

## 4. Примерные расходы и допущения расчёта

Тарифы Railway на сегодня (из их документации): **RAM $10 / ГБ / месяц,
CPU $20 / vCPU / месяц, исходящий трафик $0.05 / ГБ, том $0.15 / ГБ / месяц.**
Считается по фактическому потреблению, посекундно. Подписка — отдельно
(Hobby $5/мес с включёнными $5 потребления, Pro $20/мес с включёнными $20).

**Новые расходы — только от сервиса API:**

| допущение | расчёт | в месяц |
| --- | --- | --- |
| RAM в среднем 0.5 ГБ, работает круглосуточно | 0.5 × $10 | **$5.00** |
| CPU в среднем 0.1 vCPU (тестовая нагрузка, не боевая) | 0.1 × $20 | **$2.00** |
| Исходящий трафик до 1 ГБ | 1 × $0.05 | **$0.05** |
| | **итого новых** | **≈ $7 / месяц** |

**Допущения, на которых держится расчёт, и что их сдвинет:**

* Считаю круглосуточную работу. Если сервис останавливать между проверками,
  выйдет пропорционально меньше — оплата посекундная.
* 0.5 ГБ — оценка для Node/NestJS с Prisma в покое. Реальное потребление
  увидим на метриках после первого дня; если окажется 1 ГБ, строка RAM
  удвоится до $10.
* Сборка образа тоже расходует ресурсы; при редких деплоях это единицы центов.
* **Postgres и Redis уже работают и уже стоят денег** — с 1 сентября. Их тома
  по 5 ГБ каждый дают 10 × $0.15 = **$1.50/мес**, и это не новый расход, а
  текущий. В сумму выше не включаю.
* Если подписка Hobby и общее потребление уложится в $5 — доплаты не будет
  вовсе. Тариф вашего аккаунта я не вижу.

## 5. Изменения настроек

Значения секретов вводятся вами в панели Railway. В чат, в документы и в git
они не попадают. Ниже — имена и **указание**, чем заполнять.

### 5.1 Окружение и режим

| переменная | значение | зачем |
| --- | --- | --- |
| `NODE_ENV` | `production` | включает строгую проверку JWT-секретов |
| `APP_ENV` | `production` | включает **все** production-проверки на старте |
| `DEMO_MODE` | `true` | разрешает песочный эквайринг и объявляет это в журнале и в `/health` |
| `DEMO_PASSWORD` | **не задавать** | см. 5.5 — иначе откроется вход без кода |
| `DEMO_SEED` | **не задавать** | иначе в базу попадут выдуманные партнёры, клиенты и платежи |

### 5.2 База, Redis, очереди

| переменная | значение |
| --- | --- |
| `DATABASE_URL` | ссылка `${{Postgres.DATABASE_URL}}` — не строкой, а ссылкой |
| `REDIS_URL` | ссылка `${{Redis.REDIS_URL}}` |
| `QUEUE_PREFIX` | `tutak-test` |
| `DATABASE_CONNECTION_LIMIT`, `DATABASE_POOL_TIMEOUT` | по умолчанию, можно не задавать |

Ссылки, а не скопированные строки: скопированная строка молча устареет при
ротации пароля базы.

### 5.3 Авторизация — **не ослабляется**

| переменная | значение |
| --- | --- |
| `JWT_ACCESS_SECRET` | случайное, ≥ 32 символов |
| `JWT_REFRESH_SECRET` | случайное, ≥ 32 символов, **другое** |

При `NODE_ENV=production` приложение отказывается стартовать, если секреты
совпадают, выглядят как заглушка или имеют низкую энтропию. Эти проверки
остаются включёнными.

### 5.4 Адреса и хранилище

| переменная | значение |
| --- | --- |
| `CORS_ORIGINS` | `https://${{RAILWAY_PUBLIC_DOMAIN}}` |
| `MEDIA_PUBLIC_BASE_URL` | `https://${{RAILWAY_PUBLIC_DOMAIN}}` |
| `MEDIA_STORAGE_DRIVER` | `local` |

`RAILWAY_PUBLIC_DOMAIN` Railway подставляет сама и обновляет при каждом
деплое. Это снимает известную проблему «адрес нужен до того, как он появится»:
при `APP_ENV=production` приложение отказывается стартовать, если
`MEDIA_PUBLIC_BASE_URL` указывает на localhost, а по умолчанию он именно
такой.

### 5.5 Реальные списания — исключены, и это не настройка, а свойство кода

В кодовой базе **нет ни одного боевого адаптера эквайринга.** Единственный
существующий — `SandboxPspAdapter`. При `APP_ENV=production` без `DEMO_MODE`
приложение **не стартует вообще**:

> `PaymentsModule: no production PSP adapter is configured. Refusing to boot
> with the sandbox adapter in production.`

`DEMO_MODE=true` разрешает песочный адаптер и одновременно объявляет это: в
журнале при старте и в ответе `/health` (`{"status":"ok","demoMode":true}`).
То есть «денег не списывается» будет не обещанием, а строкой, которую можно
показать.

**Единственное, что `DEMO_MODE` ослабляет в авторизации** — открывает
публичный маршрут `POST /auth/demo-session`, вход под фиксированной учётной
записью без кода. Он требует **двух** переменных: без `DEMO_PASSWORD` маршрут
возвращает 404. Поэтому `DEMO_PASSWORD` не задаём — и защита не ослаблена.

Проверка после запуска: `POST /v1/auth/demo-session` должен вернуть **404**.

### 5.6 Прокси и ограничения запросов

| переменная | значение | почему |
| --- | --- | --- |
| `TRUST_PROXY` | **не задавать** | вместе с `CLIENT_IP_STRATEGY` даёт отказ на старте |
| `CLIENT_IP_STRATEGY` | **не задавать на первом запуске** | число хопов `X-Forwarded-For` надо **измерить** на живом сервисе, а не угадать: завышенное значение выбирает адрес, который подставил вызывающий |
| `SMS_GLOBAL_MAX_PER_HOUR` | `50` | тестовому окружению столько не нужно, а ошибка в конфигурации не должна стоить счёта |
| `SMS_GLOBAL_MAX_PER_DAY` | `200` | то же |

Ограничения **не отключаются**. Лимит на аккаунт (5 кодов на номер в час,
15 попыток проверки) и глобальный бюджет действуют. Пер-IP лимиты пока стоят
down — это состояние по умолчанию, выбранное безопасным; включим отдельным
шагом после измерения хопов.

### 5.7 Первичное наполнение

| переменная | значение |
| --- | --- |
| `SEED_BASELINE` | `true` |
| `SEED_ADMIN_PASSWORD` | не менее 12 символов |

`seed-baseline` создаёт роли, права и супер-администратора. Ни клиентов, ни
платежей он не создаёт и безопасен при каждом перезапуске.

### 5.8 Необязательное

`SENTRY_DSN`, `ALERT_WEBHOOK_URL`, `PUSH_ENABLED`, `PUSH_ACCESS_TOKEN`,
`SWEEPS_ENABLED`, `PAYOUT_DUAL_CONTROL` — можно не задавать на первом запуске.

## 7. Порядок миграций и развёртывания

Миграции запускает сам образ: `docker-entrypoint.sh` выполняет
`prisma migrate deploy` **до** старта приложения. Отдельного шага не нужно.
`migrate deploy` применяет только неприменённые миграции и ничего не
пересоздаёт.

**Запуск в два шага — чтобы у каждого была одна причина отказа.**

### Шаг 1 — платформа поднимается, СМС ещё нет

1. Отменить (Discard) отложенный патч в панели Railway.
2. Создать сервис из репозитория `arman119090-cmyk/TuTak-Platform`, ветка
   `deploy/railway-api-df1fd99`.
3. Задать переменные из разделов 5.1–5.7. **Переменные Viva пока не задавать.**
4. Дождаться сборки и старта.

Ожидаемое состояние: приложение поднялось, миграции применены, роли созданы,
в журнале строка

```
[SMS] SMS transport: unavailable — every verification and password-reset code will be REFUSED…
```

Это нормально для шага 1: `DEMO_MODE=true` пропускает production-проверку
карьера, и транспорт остаётся отказным — но теперь он об этом **пишет**.

### Шаг 2 — включаем отправку

5. Добавить переменные Viva из раздела 6.
6. Дождаться перезапуска. В журнале должно стать `[SMS] SMS transport: viva`.
7. Запросить код на ваш номер и проверить доставку.

## 9. Откат

| что | как |
| --- | --- |
| Выключить отправку | снять **весь** набор Viva из раздела 6, не только `SMS_DRIVER`. Проверено: снятие одного `SMS_DRIVER` при заданном `VIVA_API_BASE_URL` выбирает `HttpSmsProvider` — он пойдёт без подписи, будет отклонён, но отрапортует `SMS transport: http`, то есть будет выглядеть рабочим |
| Откатить код | Deployments → предыдущий деплой → Rollback |
| Убрать всё созданное | удалить **только** сервис `tutak-api`. Postgres, Redis и их тома не трогаются: они существовали до этого запуска |

**Данные не удаляем** — ни сейчас, ни при откате. Отдельную очистку тестовых
данных с сохранением нужных настроек подготовим перед запуском для
пользователей, как вы и сказали.

Миграции откатом не отменяются: `migrate deploy` их применил, и снимать их
никакой откат кода не будет. Для тестовой базы без пользователей это
безопасно; отмечаю, чтобы это не было сюрпризом.
