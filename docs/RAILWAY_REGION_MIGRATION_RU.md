# Railway: регион production и переезд ближе к Армении

Дата: 19.09.2026. Статус: **SAFE TO MOVE AFTER PILOT** (обоснование ниже).

## Как есть

| Ресурс | Регион | Примечание |
|---|---|---|
| `tutak-api`, `tutak-admin`, `tutak-partner` | `sfo` (US West, Сан-Франциско) | 1 реплика каждый |
| Postgres (volume 5 GB) | `sfo` | образ `postgres-ssl:18` |
| Redis (volume 5 GB) | `sfo` | образ `redis:8.2` |
| Bucket `tutak-media` | `sjc` (San Jose) | объектное хранилище (S3-совместимое) |

Пользователи и партнёры — в Армении. Ближайший регион Railway —
`europe-west4` (Амстердам).

## Оценка задержки

Прямых измерений с армянского телефона у нас нет (из этой среды
`*.up.railway.app` закрыт прокси; GitHub-runner стоит в США и не
репрезентативен). Оценка по географии и типичным RTT:

| Маршрут | RTT (оценка) |
|---|---|
| Ереван → Амстердам | 60–90 мс |
| Ереван → Сан-Франциско | 180–230 мс |

Каждый экран приложения делает 1–3 запроса; разница между регионами —
порядка **+120–150 мс на запрос**, то есть 0,2–0,5 с на экран. Для
ограниченного пилота это заметно, но не мешает: ни один флоу не завязан
на десятки последовательных запросов; QR-покупка — 2 запроса.

Измерить точно можно одной командой с телефона/ноутбука в Армении:
`curl -o /dev/null -s -w '%{time_connect} %{time_starttransfer}\n' https://tutak-api-production.up.railway.app/health`
(повторить 5 раз, взять медиану). Если `time_starttransfer` стабильно
> 0,4 с — довод за переезд усиливается.

## Что означает переезд (по документации Railway)

1. **Сервисы (api/admin/partner)** — смена региона в Settings → Region и
   redeploy. Без данных, без простоя сверх обычного деплоя. Домены
   `*.up.railway.app` не меняются.
2. **Volumes (Postgres, Redis)** — том привязан к региону. Перенос:
   создать новый volume/сервис в целевом регионе → восстановить данные
   (pg_dump/pg_restore или volume backup → restore) → переключить
   `DATABASE_URL`/`REDIS_URL` → удалить старый. Это **простой на время
   восстановления** (минуты для текущего объёма) и **риск потерять
   записи**, сделанные между dump и переключением, если не остановить
   API на время переноса.
3. **Bucket `tutak-media`** — регион задаётся при создании; перенос =
   новый bucket + копирование объектов + смена `MEDIA_STORAGE_S3_*` и
   `MEDIA_PUBLIC_BASE_URL`. Ссылки на медиа в БД — относительные ключи,
   поэтому копирование без переименования достаточно (проверить перед
   переносом).
4. Redis у нас — кэш/очереди/OTP-счётчики: при переносе допустимо
   начать с пустого; активные OTP и rate-limit окна сбросятся.

## Почему не сейчас

- Переезд Postgres — это та самая операция «restore в новую базу»,
  которую по плану пилота ещё нужно **отрепетировать** (PR #58,
  `scripts/verify-restored-db.sh`). Делать её впервые на production ради
  120 мс — неверный порядок: сначала доказать restore, потом
  использовать его для переезда.
- Wait for CI, branch protection, alert-канал ещё не включены; любой
  инфраструктурный шаг сейчас — без страховки.
- Латентность 0,2–0,5 с на экран не блокирует пилот.

## Рекомендация

**SAFE TO MOVE AFTER PILOT.** Порядок, когда придёт время:

1. Замерить RTT из Армении (команда выше) — зафиксировать цифры.
2. Отрепетировать backup → restore → verify на новой базе (уже нужно
   для пилота).
3. Окно 30 минут: остановить API (или включить read-only), dump →
   restore в `europe-west4`, переключить переменные, redeploy, проверить
   `/health/ready`, `pilot-verify.sql`, imbalance 0.
4. Bucket — копирование заранее, переключение в том же окне.
5. Старые ресурсы держать 7 дней, потом удалить.

Никакой автоматической миграции регионов этот документ не запускает.
