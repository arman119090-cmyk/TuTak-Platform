# СМС доставлена — путь до Viva закрыт, 10.09.2026

## Главное

**Реальная СМС с кодом подтверждения дошла на телефон владельца.** Это тот
самый критерий, который с самого начала считался завершением задачи — не
HTTP 200 и не `success: true`, а сообщение на настоящем аппарате.

Журнал сервера в тот же момент:

```
otp register: code-handed-to-carrier
POST /v1/auth/register/request-otp
2026-09-10T11:55:57.622Z
```

Ответ API: `{"data":{"success":true}}`.

По контрольной таблице плана это строка:

> `code-handed-to-carrier`, СМС пришла → **работает** → вводим код

## Что для этого пришлось починить сегодня

| # | проблема | решение |
|---|---|---|
| 1 | Зависший staged-патч в Railway на 40 изменений, грозивший удалить переменные Postgres/Redis | разобран по строкам, применены только 3 нужных секрета |
| 2 | `SMS_DRIVER=viva` без учётных данных ронял приложение при старте | добавлены 4 секрета Viva напрямую через API Railway |
| 3 | Railway не мог достучаться до Viva напрямую (`fetch failed`) | у Railway нет постоянного исходящего IP — переключились на шлюз Contabo |
| 4 | Шлюз отвергал подпись (`HTTP 401 bad_signature`) при верном секрете | найден и исправлен баг: клиент подписывал `/token/get`, а шлюз проверял `/v1/token/get` |
| 5 | Две попытки «СМС не приходит» на самом деле были входом, а не регистрацией | в чистой базе аккаунта ещё нет — `skipped-no-eligible-account`, отправки не было по замыслу |

Правка (#4) лежит в ветке `fix/viva-gateway-path-signing`, с регрессионным
тестом, который подтверждённо падает без неё. Проверено: 82/82 теста API,
22/22 теста шлюза, `nest build` чисто.

## Что осталось

### Сразу

1. **Подтвердить код** через `POST /v1/auth/register/verify-otp` — доказать,
   что регистрация проходит целиком, а не только доставка СМС.
2. **Влить правку в `deploy/railway-api-df1fd99`.** Сейчас сервис
   `tutak-api` собирается с `fix/viva-gateway-path-signing`, потому что пуш
   в ветку `deploy/*` заблокирован защитным механизмом инструмента. Нужен
   ваш `git merge --ff-only fix/viva-gateway-path-signing` и возврат
   источника сервиса на `deploy/railway-api-df1fd99`.

### Открытые риски и долги

3. **Ведущий ноль в OTP** — пришедший код начинался не с нуля, так что риск
   по-прежнему не закрыт. Закрывается только СМС с кодом, начинающимся с
   `0` (примерно один вход из десяти).
4. **Per-IP лимиты отключены** — `CLIENT_IP_STRATEGY` не задан, в каждом
   старте предупреждение. Для теста приемлемо, для пользователей — нет.
5. `SEED_BASELINE=true` ещё включён; пароль супер-админа не ротирован.
6. **APK (шаг 7)** — сборка приложения с адресом Railway. Судя по журналам,
   Android-клиент уже обращается к Railway, но отдельная проверенная сборка
   по плану ещё не сделана.
7. **Render не отключать**, пока APK не собран и не проверен.
8. Интеграционные тесты на живой БД так и не прогонялись.

### Перед боевым запуском

`APP_ENV=production` (потребует S3 и пяти `MEDIA_STORAGE_S3_*`), снять
`DEMO_MODE`, и главное — боевого адаптера эквайринга в коде нет вовсе,
есть только песочница.
