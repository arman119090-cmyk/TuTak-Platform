Проверено всё три: **приглашение друга, начисление бонусов покупателю и
начисление бонусов пригласившему — работают.** Проверка сделана не на

## 1. Чем именно проверено

### 1.1 Полный интеграционный набор — впервые запущен

В каждом отчёте до сегодняшнего дня стояла строка «интеграционные тесты на
живой БД не прогонялись». Она закрыта.

```
Test Suites: 79 passed, 79 total
Tests:       1075 passed, 1075 total
Time:        250 s
```

Условия прогона: настоящая PostgreSQL 16.13, настоящий Redis, все 51
миграция применены, база создана с нуля. На чистой базе дополнительно
проверяется ограничение `bonus_ledger_delta_matches_direction` — то самое,
которое в рабочей базе стоит «непроверенным» из-за старых строк. Оно прошло:
значит ни один путь кода в нынешнем виде не может записать проводку, чьи
дельты противоречат её направлению.

Из этих 79 наборов прямо к вашему вопросу относятся два:

| набор | что доказывает | тестов |
|---|---|---|
| `bonus-engine.int-spec.ts` | начисление, резерв, списание, сгорание, откат — включая гонки и запрет отрицательного баланса | 46 |
| `referral-abuse.int-spec.ts` | награда обеим сторонам после порога, запрет самоприглашения, защита от двойной выплаты, лимит слотов | 13 |

### 1.2 Новый набор — путь приглашения целиком

Обнаружился пробел. Старые тесты доказывали *правила* реферальной программы,
но вызывали `advanceChallengeProgress` напрямую. В жизни этот метод никто по
имени не вызывает: транзакция при завершении пишет строку в outbox,
`ReferralListener` подписан на этот тип события, а фоновая задача outbox
разгребает. Эта цепочка не была покрыта нигде. Сломай её опечаткой в имени
события — все тесты по-прежнему зелёные, а награды в проде не выплачиваются
и никто об этом не узнаёт.

Написан набор `apps/api/test/referral-journey.int-spec.ts`, который начинается
с настоящей регистрации по СМС-коду с реферальным кодом и заканчивается
двумя кошельками, не вызывая по имени ни одного реферального метода:

```
✓ привязывает друга к пригласившему при регистрации и показывает его в списке
✓ платит покупателю его собственный бонус по ставке партнёра
✓ доводит завершённую покупку до реферального челленджа только через outbox
✓ награждает пригласившего и друга после перехода порога
✓ не награждает того, чей друг зарегистрировался без кода
```

**Проверка самой проверки.** Я переименовал событие в слушателе на заведомо
неверное и прогнал набор заново: упали ровно те два теста, которые зависят от
доставки через outbox, остальные три остались зелёными. То есть набор
действительно ловит обрыв этой цепочки, а не проходит «сам по себе».

## 2. Как это устроено — с числами

### 2.1 Приглашение друга

Пригласивший берёт свой код на экране «Моя сеть» (`GET /v1/referral/me/code`)
и делится им. Друг вводит код **при регистрации** — поле «реферальный код»
есть на экране регистрации в приложении.

Связь создаётся один раз и навсегда: у записи приглашения уникальный ключ по
приглашённому, изменить её задним числом нельзя. Тогда же открывается «слот»
реферального челленджа. Самоприглашение отсекается, и — на случай подделки
записи в базе — отсекается ещё раз при выплате.

### 2.2 Бонусы покупателю

Основной путь в приложении: покупатель сканирует QR партнёра, вводит сумму,
сотрудник партнёра подтверждает в своём кабинете. Дальше считается пул:

```
пул = сумма покупки × ставка партнёра (снимок на момент покупки)
```

и делится на шесть частей — доли заданы в базисных пунктах и в сумме всегда
дают ровно пул:

| кому | доля | когда доступно |
|---|---|---|
| покупателю, «зелёный» бонус | 20 % | сразу |
| покупателю, отложенный | 30 % | после накопления оборота |
| пригласившему, 1-й уровень | 10 % | сразу |
| 2-й уровень | 5 % | сразу |
| 3-й уровень | 5 % | сразу |
| TuTak | 30 % | остаток |

Уровень, которого нет (человека никто не приглашал), не оставляет свою долю
неоплаченной и не раздаёт её другим уровням — она уходит в долю TuTak,
которая считается остатком. Поэтому шесть частей сходятся до копейки при
любой сумме.

Начислять может только **подтверждённый номер**: тратить и платить открыто
всем, зарабатывать — нет. Это защита от заработка на выдуманных аккаунтах.

Обычная покупка сначала попадает в «ожидание» на **48 часов**, срок жизни
бонуса — **12 месяцев**. Реферальная доля кладётся сразу, без ожидания:
покупку, за которую она платится, уже проверили.

### 2.3 Награда за приглашение

Отдельно от постоянной доли работает разовая награда:

| параметр | значение |
|---|---|
| порог | **10 000 ֏** накопительно по покупкам друга |
| награда | **1 000 бонусов** каждой стороне |
| лимит | **3** оплаченных приглашения на человека |

Порог накопительный: 4 000 + 6 000 засчитываются так же, как одна покупка на
10 000. Награду платит TuTak из своей выручки — партнёр за неё не платит, из
пула она не берётся; это видно проводкой по счёту выручки.

Покупка без партнёра в челленджe не засчитывается вовсе — это ровно форма
накрутки «сам себе выставил QR, сам оплатил».

## 3. Чего не хватает, чтобы это заработало у живых людей

Код готов и проверен. Не хватает данных.

**В базе Railway нет ни одного партнёра.** Без партнёра:

* нечего сканировать — покупка не создаётся;
* ставка начисления берётся у партнёра, значит пул равен нулю;
* челлендж не двигается: покупка без партнёра намеренно не засчитывается.

То есть сегодня зарегистрироваться по приглашению **можно** (связь создастся,
друг появится в списке), а получить бонусы **не за что** — покупок нет.

Это единственное, что отделяет проверенный механизм от работающего.
Заводятся партнёры в админке, которая теперь поднята (см. ниже).

Отдельно: сама оплата бонусами **не требует эквайринга** — покупатель платит
партнёру как обычно, а приложение только считает и списывает бонусы. Ставка
партнёра и договорная ставка задаются в админке при заведении партнёра.

## 4. Найдено и исправлено: почему не поднимались админка и кабинет

Оба сервиса падали при старте с ошибкой:

```
Error code: P1012
error: Environment variable not found: DATABASE_URL.
  -->  prisma/schema.prisma:16
```

Prisma внутри контейнера админки — это и есть подсказка: запускался не тот
образ. Причина — корневой `railway.json`. Railway применяет его **ко всем
сервисам, которые собираются из этого репозитория**, и он перекрывает
настройки самих сервисов. В файле было прописано `apps/api/Dockerfile`,
поэтому админка и партнёрский кабинет собирали образ API и падали на его
старте. Их собственный `dockerfilePath` был задан правильно и просто не
читался.

Исправление: настройки сборки перенесены в сами сервисы, корневой
`railway.json` удалён (коммит `3060a53`, ветка `fix/viva-gateway-path-signing`).
Файлы `railway.admin.json` и `railway.partner.json` удалены тоже — Railway их
никогда не читал.

Результат:

| сервис | состояние | адрес |
|---|---|---|
| `tutak-api` | SUCCESS, слушает 4000 | `tutak-api-production.up.railway.app` |
| `tutak-admin` | SUCCESS, Next.js готов | `tutak-admin-production.up.railway.app` |
| `tutak-partner` | SUCCESS | `tutak-partner-production.up.railway.app` |

API перезапустился чисто, `SweepsModule` инициализирован — значит фоновая
разгрузка outbox в проде работает, и та самая цепочка до реферальной награды
замкнута не только в тестах.

`CORS_ORIGINS` у API выставлен на оба адреса дашбордов, `NEXT_PUBLIC_API_BASE_URL`
у обоих дашбордов указывает на API Railway.
