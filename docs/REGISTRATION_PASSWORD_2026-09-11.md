## 1. Что было неправильно

Не «не хватало экрана». Ломались три вещи сразу.

1. **Аккаунт создавался с паролем, которого никто никогда не видел.** Не
   пустым и не сентинелом — настоящим argon2-хешем от 32 случайных байт.
   Проверить его не может ни один ввод.
2. **Пользователя тут же впускали внутрь**, а при следующем запуске
   приложения встречал экран входа, просящий пароль, которого не существует.
   Единственная дорога обратно в собственный аккаунт — ещё одна СМС.
3. **Каждый такой аккаунт потом приходилось как-то отличать** от нормального.
   Ровно поэтому в этой правке появился отдельный скрипт-отчёт — он
   существует только из-за строки `randomBytes(32)`.

Тест на это был, и он закреплял поведение как правильное:
«makes the account passwordless: a random-guess password login fails cleanly».
Про код он был прав, про продукт — нет; он перевёрнут вместе с кодом.

## 2. Какой flow теперь

```
этап 1   телефон  (+ реферальный код, необязательно)
           → POST /v1/auth/register/request-otp
этап 2   6-значный код из СМС
           → никуда не отправляется; форма просто переходит дальше
этап 3   пароль + повтор пароля
           → POST /v1/auth/register/verify-otp
              { phone, code, password, locale, referralCode, deviceId, deviceName }
           → аккаунт создан → выданы access/refresh → вход
```

**Почему код не проверяется на этапе 2.** Отдельного «проверь код» не
существует и не должно: код одноразовый, а эндпоинт, отвечающий «валиден ли
он», не тратя его, — это бесплатный оракул для перебора. Поэтому код несётся
дальше и судится один раз — тем же запросом, что создаёт аккаунт.

**Цена этого решения и чем она оплачена.** Неверный код обнаруживается уже
после ввода пароля. Форма возвращается на этап 2 с отмеченным полем — и
**сохраняет уже набранный пароль**. Исправление одной цифры стоит одного поля,
а не трёх.

**Про предложенный вами альтернативный вариант** (OTP → короткоживущий
registration token → установка пароля → создание аккаунта). Он убирает этот
сюрприз и добавляет второй тип учётных данных: выпуск, область действия, срок
жизни, отзыв, хранение, тесты — и новую поверхность атаки, которой сейчас нет.
Для потока длиной в двадцать секунд это не окупается. **Минимальный вариант
выбран сознательно**, и сюрприз оплачен сохранением пароля, а не проигнорирован.

**СМС на неверном пароле не тратится.** Пароль проверяет глобальный
`ValidationPipe` — до обработчика. Слишком короткий пароль отклоняется, код
остаётся нетронутым.

## 4. Как теперь создаётся `passwordHash`

```ts
const passwordHash = await argon2.hash(dto.password);
```

Открытый текст живёт ровно столько, сколько длится вызов: приходит в DTO,
хешируется, и больше нигде не появляется — ни в колонке, ни в аудит-записи, ни
в строке лога. Тест `is never stored in the clear, anywhere on the row`
проверяет, что хеш начинается с `$argon2` и что сериализованная строка
пользователя не содержит пароля. Тест
`is what the stored hash verifies against` вызывает `argon2.verify` — именно он
отличил бы случайный пароль от пользовательского, и именно он падал бы на
старом коде.

## 5. Что с session после OTP

**Ничего.** Ввод кода переводит форму на следующий этап и не делает запроса.
`setSession` вызывается в одном месте — после успешного ответа на
`verify-otp`, то есть когда аккаунт уже существует. Закреплено тестом
`does not create a session when the code alone has been entered`: после ввода
кода `verifyRegistrationOtp` не вызван ни разу и `setSession` не вызван ни разу.

## 6. Существующие OTP-only пользователи

Вы просили исследовать и не делать опасную миграцию. **Миграции нет, ни одна
строка не изменена.** Ниже ответы на пять ваших вопросов.

### 6.1 Как точно определить — можно, двумя признаками сразу

**Признак 1.** `AuditLog`: `action = USER_LOGIN`, `entityType = 'User'`,
`metadata.via = 'register_otp'`. Запись делается в том же запросе, который
создал аккаунт. Парольный путь пишет `via: 'register'` — то есть пути
*различимы*, а не просто считаемы.

Ключевая проверка: **`RetentionService` аудит-лог не трогает.** Он чистит
уведомления, сессии, истёкшие QR, записи идемпотентности и обработанные
события outbox — `audit_logs` в нём нет. Маркер не истекает.

**Признак 2.** `passwordChangedAt IS NULL`. Первый признак говорит, как аккаунт
*начинался*, а не где он сейчас. Кто с тех пор воспользовался «забыли пароль»,
пароль знает — `PasswordService` проставляет эту колонку. Без второго признака
отчёт называл бы людей, у которых всё в порядке.

**Третье свойство замыкает набор:** аккаунты, создаваемые теперь, проставляют
`passwordChangedAt` при создании. Новая регистрация не может попасть в это
множество, даже если аудит-запись каким-то образом окажется со старым маркером.

**Вывод: точное определение возможно.** Скрипт `report-otp-only-users.ts`
печатает количество и идентификаторы. Номера телефонов он намеренно не
печатает — на этой платформе номер и есть идентификатор клиента, а список
номеров в терминале это клиентская база.

Запуск на Railway:
```
node dist/scripts/report-otp-only-users.js
```

### 6.2 Можно ли использовать `mustChangePassword` — нет, и вот почему

Механизм существует и работает (`PasswordRotationGuard`), но он **рассчитан на
того, кто свой текущий пароль знает**. Поставить его этим людям — значит
запереть их: гвард пропускает только `change-password` и `logout`, а
`ChangePasswordDto` требует `currentPassword`, которого у них нет.

Формально тупик не вечный: `password-reset/request` и `password-reset/confirm`
помечены `@Public()`, сессия для них не нужна, так что выйти можно. Но это
тупик внутри приложения, из которого выход — снаружи приложения. Это худший из
возможных UX для человека, который ничего не сделал неправильно.

**Если всё же решите заставлять** — единственная безопасная форма: путь
установки первого пароля, принимающий **свежий OTP вместо текущего пароля**.
Это ровно то, что уже делает сброс пароля (см. 6.4).

### 6.3 Как дать им задать свой пароль без знания текущего

**Уже можно, ничего дописывать не нужно.** «Забыли пароль» на экране входа:

```
phone → password-reset/request → код по СМС → password-reset/confirm { newPassword }
```

Владение номером доказывается свежим кодом. Захвата аккаунта нет: код уходит
на тот же номер. Обхода OTP нет: OTP и есть условие.

### 6.4 Заставлять ли после следующего OTP-входа

**Моя рекомендация — нет.** Причины:

* они не сломаны: вход по СМС работает, «забыли пароль» работает;
* их единицы (скрипт скажет точно) — это тестовые аккаунты периода запуска;
* любое принуждение требует нового пути установки пароля (6.2), то есть
  второй парольной системы ради нескольких человек.

Дешевле и честнее: сказать этим людям «нажмите „Забыли пароль“ и задайте
пароль» — или, если это тестовые номера, удалить аккаунты и зарегистрировать
заново по новому потоку.

**Это ваше решение, а не моё.** Если хотите принуждение — скажите, и я сделаю
его через OTP-путь, а не через `mustChangePassword`.

### 6.5 Без захвата аккаунта и без обхода OTP

Всё вышеописанное держится на одном: **пароль меняется только тем, кто получил
свежий код на этот номер**. Ни один из предложенных путей не позволяет задать
пароль, не приняв СМС. `mustChangePassword` сам по себе ничего не ослабляет и
ничего не решает — он лишь закрывает приложение.

### 6.6 Переиспользование сброса пароля для первичной установки

**Да, и это уже сделано — тем, что ничего не сделано.** Сброс пароля имеет
ровно те семантики, которые нужны первичной установке: докажи владение
номером свежим кодом, задай новый пароль, `passwordChangedAt` проставляется.

Разница между «сбросом» и «первичной установкой» здесь только в словах на
кнопке. Заводить вторую парольную систему ради этой разницы было бы хуже:
две системы, которые можно рассогласовать, вместо одной проверенной.

### Набор по пункту 22 — чем именно закреплена стратегия «ничего не трогаем»

Решение оставить legacy-пользователей в покое защитимо ровно пока верны три
вещи. До этого набора не проверялась ни одна.

| тест | что держит |
|---|---|
| `can still sign in by SMS` | они не заперты: вход по коду работает |
| `can set a password without knowing the random one, and then use it` | сброс пароля даёт им пароль, и он потом работает на обычном входе |
| `is not carrying mustChangePassword` | ничто не закрывает вокруг них приложение |
| `finds the legacy account` | критерий их находит |
| `does not name an account registered the new way` | новая регистрация несёт **тот же** маркер `via: 'register_otp'` — отсекает только вторая половина критерия |
| `does not name a password-registered account at all` | у парольной регистрации `passwordChangedAt` тоже null — отсекает только первая половина |
| `stops naming a legacy account once its owner has set a password` | множество самоочищается, без чьего-либо вмешательства |
| `does not name a deleted account` | у удалённого нечего терять |

Два средних теста — причина, по которой критерий состоит из двух половин, а не
из одной. **Проверено обрывом:** если убрать половину про `passwordChangedAt`,
падают ровно эти два, остальные шесть остаются зелёными.

Сам критерий переехал из скрипта в `modules/users/otp-only-accounts.ts`:
запрос, спрятанный в скрипте, — это запрос, который ничем не проверяется, а
ошибиться в нём можно в обе стороны. Слишком широкий — отчёт называет людей, у
которых всё хорошо; слишком узкий — будущая миграция кого-то молча пропустит.
