## 1. Что исправлено

### CI: две падавшие юнит-проверки (и настоящая дыра за ними)

Падали `apps/api/src/modules/auth/otp-code-consumption.spec.ts` —
«counts a wrong attempt against the challenge» и «burns the challenge once the
attempts run out».

**Причина.** Мок `update` возвращал `{}`, а сервис читает возвращённую строку
(`bumped.attempts`, `bumped.consumedAt`), чтобы решить, гасить ли challenge.
Против `{}` обе величины — `undefined`, ветка гашения не выполнялась никогда,
а тест «доказывал» гашение, разглядывая аргументы вызова, эффекта которого он
не видел. Проверки при этом ожидали `attempts: 1` / `attempts: 5`, тогда как
код пишет `data: { attempts: { increment: 1 } }`.

**Что сделано.** Мок заменён на смоделированную строку: `{ increment: n }`
увеличивает счётчик, условный `updateMany` соблюдает своё условие и
возвращает честный `count`. Утверждения теперь о состоянии строки, а не о форме
аргумента Prisma. Небезопасный `read + 1` не возвращён, проверки блокировки не
удалены. Одно утверждение об аргументе оставлено намеренно —
`data: { attempts: { increment: 1 } }`: именно эта запись и есть свойство
безопасности (считает база, а не процесс), и её написание проверяется отдельно.
Было 9 тестов, стало 11.

**Найдена и закрыта настоящая уязвимость.** Отдельная проверка гонок на живом
PostgreSQL (`apps/api/test/otp-consumption-races.int-spec.ts`, 7 тестов)
показала: `findFirst` фильтровал по `consumedAt` и `expiresAt`, но не по
`attempts`. Лимит в 5 попыток держался одной записью — превысил, и следующий
оператор ставит `consumedAt`. Это два оператора, между ними есть зазор:
процесс, остановленный посередине, или незаписавшееся гашение оставляли
исчерпанный challenge выбираемым, и он продолжал принимать догадки, пока его не
остановит часовой бюджет номера — 15 вместо 5, втрое больше задуманного.
Тест зафиксировал 6 попыток на мёртвой строке до исправления.

Исправление в `apps/api/src/modules/auth/auth-otp.service.ts` — одна строка в
условии выборки:

```ts
attempts: { lt: MAX_ATTEMPTS },
```

Исчерпанный challenge теперь невидим независимо от того, легло гашение или нет.
Само гашение оставлено: оно делает состояние видимым в строке, а не выводимым
из счёта.

Проверено «от красного» в обе стороны: убрать гашение — падает тест гашения;
заменить на `challenge.attempts + 1` — падает тест подсчёта.

Пять сценариев из задания покрыты на PostgreSQL: параллельные неверные
попытки; верный код одновременно с последней разрешённой неверной; повторное
использование; истечение срока во время обработки; остановка процесса между
инкрементом и установкой `consumedAt`.

## 2. Проверка связного сценария и прав

`apps/api/test/partner-application-lifecycle.int-spec.ts` — 10 тестов на живой
базе, вся цепочка: пользователь подаёт заявку → админ её видит → одобряет или
отклоняет → кабинет партнёра получает корректный статус и доступ.

Что зафиксировано отдельно:

- **Самоодобрение закрыто.** `PARTNER_OWNER` действительно держит
  `PARTNER_MANAGE` (это утверждается тестом, а не предполагается), и всё равно
  `approvePartner` отвечает ему 403. Иначе заявитель одобрял бы себя сам.
- **Изоляция арендаторов.** Владелец не читает филиалы, транзакции и аналитику
  чужого партнёра — 403.
- **Владелец не может снизить собственный кешбэк.** После
  `updateCommercialSettings` `bonusAccrualRateBps` остаётся 1000: иначе это
  приманка — подать заявку на 10 %, получить позицию в выдаче и маркер, затем
  опустить до 0,5 % и остаться на месте.
- Партнёр в статусе `PENDING_APPROVAL` не участвует в денежных операциях —
  `findActiveOrThrow` закрывает все денежные пути.

Кабинет партнёра — отдельное работающее веб-приложение с разделами, а не одна
форма заявки.

**Номер сборки — важная оговорка.** «#51» в заголовке релиза — это номер
прогона workflow (предыдущий APK был прогоном #50), а **не** `versionCode`
Android. Внутри APK:

| | новый (production-apk #51) | предыдущий (preview #50) |
|---|---|---|
| package | `am.tutak.app` | `am.tutak.app` |
| versionCode | 1 | 1 |
| versionName | 0.1.0 | 0.1.0 |
| сертификат подписи (SHA-256) | `AA:9B:27:2A:…:12:34` | тот же байт в байт |

`autoIncrement` в `eas.json` включён только на профиле `production` (App
Bundle), поэтому `production-apk` берёт текущий удалённый `versionCode` и не
увеличивает его. Android отказывает только при **строго меньшем**
`versionCode`; при равном установка поверх проходит. Пакет и сертификат
совпадают, значит **новый APK встаёт обновлением поверх установленного, без
удаления и без потери данных** — это проверено извлечением подписи из обоих
файлов, а не выведено из настроек.

## 6. Короткая проверка на телефоне

1. Открыть ссылку релиза, нажать `tutak.apk`, разрешить установку из этого
   источника. Приложение должно встать **поверх** прежнего, без удаления.
2. Войти по номеру и SMS-коду. Ввести три неверных кода подряд — отказ
   одинаковый; после пятого код гасится и шестая попытка бессмысленна.
3. При регистрации ввести имя; затем изменить имя в профиле — оно должно
   сохраниться.
4. На экранах входа и регистрации нажать «глаз» у пароля — символы
   показываются и скрываются.
5. Открыть карту: тайлы должны прорисоваться, внизу — надпись
   «© MapTiler © OpenStreetMap». Серый прямоугольник означал бы, что ключ
   не работает.
6. Открыть список партнёров рядом — отсортированы по кешбэку внутри радиуса,
   у щедрых есть маркер.
7. «Стать партнёром» → заполнить заявку (налоговый номер можно не указывать) →
   отправить → увидеть экран результата.
8. В админ-панели (браузер) открыть раздел заявок, найти свою, одобрить.
9. Войти в кабинет партнёра тем же пользователем — статус изменился, разделы
   доступны.
10. Кошелёк: баланс и история операций открываются, медиа подгружаются.

1. **`ALERT_WEBHOOK_URL` не задан.** API сообщает об этом сам при старте:
   «Set it before taking real money». Пока он пуст, тревоги никуда не уходят.
   Задаётся переменной в панели Railway.
2. **Sentry DSN не задан** ни в API, ни в мобильном приложении (`sentryDsn`
   в APK пуст). Ошибки у пользователей никто не увидит.
3. **Резервные копии Railway / PITR и проверенное восстановление.** Наличие
   бэкапа без единожды выполненного восстановления — предположение, а не
   бэкап.
4. **Старый ключ MapTiler не отозван** в https://cloud.maptiler.com/account/keys/.
5. **Защита веток не настроена**, и ветка по умолчанию в репозитории —
   `claude/tutak-loyalty-mvp-e485jm`, а не `main`. Из-за этого, в частности,
   кнопка «Run workflow» показывает только те workflow, которые есть в ветке
   по умолчанию.
6. **Обе панели только на английском** — локализации интерфейса нет.
7. **Реальный SMS-канал.** Коды уходят через настроенного провайдера; сквозной
