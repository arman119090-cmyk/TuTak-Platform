# TuTak — Release Candidate, 13.09.2026

Ветка: `release/rc-1`. Десять веток сведены в одно дерево и проверены
**вместе**, а не по отдельности. Всё, что помечено проверенным, проверено
командами, вывод которых я видел.

## READY — что реально готово

- **Единое дерево.** 36 коммитов, 109 файлов, +8428/−524 относительно `main`.
- **Покупка целиком:** QR филиала с выданным сервером токеном → `PurchaseIntent`
  → 4-значный код для кассы → подтверждение/отклонение сотрудником →
  списание бонусов → начисление → реферальные L1/L2/L3 → отложенные лоты →
  история и двойная бухгалтерия.
- **Отмена клиентом** неподтверждённой покупки, с освобождением резерва.
- **Возвраты с двойным контролем:** кассир просит, владелец/управляющий
  решает; прямой возврат владельца оставляет ту же запись и не может обойти
  висящую заявку.
- **Экран возвратов у партнёра** — раньше интерфейса не было вообще.
- **Карта:** идентификация клиента провайдеру плиток, сменный провайдер,
  реальная геолокация, маркер себя, возврат к себе.
- **Идентичность персонала:** кто подтвердил, кто отклонил, кто вернул;
  отключение доступа действует со следующего запроса.
- **Границы сессии** (старый PR #30) — в дереве и с зелёными тестами.
- **Durable object storage** — создан и работает (см. PRODUCTION INFRA).

## FIXED — настоящие проблемы, найденные и исправленные

### Найдены только интеграцией (каждый PR по отдельности был зелёным)

1. **Три места ломались о типы после слияния.** `PurchaseIntentDto` за три
   разные ветки получил четыре обязательных поля (`confirmationCode`,
   `refundedAmount`, `rejectedByUserId`, `cancelledAt`); фикстура экрана
   возвратов партнёра, фикстура экрана статуса в мобильном и запасной литерал
   оффлайн-адаптера перестали соответствовать. Починены фикстуры, а не
   ослаблены типы.
2. **Интеграционная спека покупок могла потерять половину тестов.** Два блока
   `describe` были вставлены в один якорь, область конфликта git их перекрыла,
   и механическое снятие маркеров съело хвост одного блока. Файл пересобран
   детерминированно из двух версий веток: 64 теста, оба блока целы.
3. **Спека health переставала компилироваться** после расширения readiness:
   конструировала контроллер с тремя аргументами и сверяла точную форму
   `checks`. Приведена к новому контракту, а не ослаблена.

### Найдены анализом, а не тестами

4. **Прямой возврат владельца был обходом двойного контроля.** Он ничего не
   оставлял там, где видны все остальные возвраты, и позволял ответить на
   неудобную заявку кассира тихим собственным возвратом. Теперь пишет ту же
   запись (владелец на обеих ролях, явно) и **отказывает**, пока по покупке
   висит нерешённая заявка.
5. **Media storage терял файлы при каждом редеплое.** У `tutak-api` не
   смонтирован том — всё, что писалось на локальный диск, исчезало, а строки
   `MediaAsset` в базе переживали байты. Исправлено настоящим бакетом.
6. **Readiness не знал про хранилище.** Теперь знает — и сознательно **не**
   валит готовность на нём (обоснование ниже).
7. **Healthcheck Railway смотрел на liveness.** Деплой, который не видит базу
   или Redis, мог заменить собой работающий. Переключён на `/health/ready`.

## PRODUCTION INFRA

- **Object storage: создан и работает.** Railway Bucket `tutak-media`,
  подключён к `tutak-api` **ссылками на переменные**, а не копированием
  ключей — ни один секрет не прошёл через чат, документы или git. Доказано
  логом деплоя: `Using S3-compatible object storage (bucket
  tutak-media-hsholrmurza-x)` и `TuTak API listening on port 4000`.
  Бакет приватный; API и так отдаёт медиа по подписанным URL.
- **Postgres 18 и Redis 8.2** — с томами, живые.
- **Readiness** `/health/ready`: база, Redis, хранилище. База и Redis валят
  готовность; хранилище — нет, и это осознанно: без бакета не грузится
  логотип, а покупки, начисления, рефералы и возвраты идут. Уронить readiness
  на этом — вывести все реплики из ротации и остановить кассу из-за картинки.
  Сбой хранилища пишется в лог отдельной строкой, на неё вешается алерт.
- **Healthcheck Railway** переключён на `/health/ready`.
- **Миграции** применяются на старте (`prisma migrate deploy`), четыре новые —
  только добавление колонок, значений enum и одной таблицы; ни одна не
  переписывает данные.
- **Резервное копирование:** процедура доказана в CI («Backup and restore
  rehearsal»); расписание бэкапов Railway — в панели, см. REQUIRES ARMAN.
- **Release gating:** Railway деплоит с `main` и **не ждёт CI**
  (`checkSuites: false`). Через API это не переключается — см. REQUIRES ARMAN.

### Короткий smoke-чеклист для телефона (то, что нельзя проверить без устройства)

1. Установить APK, открыть карту → появляется запрос геолокации.
2. Разрешить → появляется своя точка, список сортируется от неё.
3. Отказать → карта показывает центр Еревана и честную подпись.
4. Плитки карты прорисовываются (если серые — это провайдер, см. ниже).
5. Регистрация: номер → SMS-код → свой пароль → вход.
6. Покупка: сканировать QR филиала → сумма → **4 цифры на экране**.
7. Кассир видит покупку в очереди по этим цифрам, подтверждает.
8. Баллы списались и начислились; история показывает покупку.
9. Кассир просит возврат → владелец одобряет → баллы вернулись.

## REQUIRES ARMAN — по одному конкретному действию

1. **Провайдер плиток карты.** Задать в окружении сборки
   `MAP_TILE_URL_TEMPLATE` и `MAP_TILE_API_KEY` (например MapTiler). Больше
   ничего менять не нужно.
2. **Railway → tutak-api → Settings → Source → включить «Wait for CI».**
   Сейчас деплой уходит на любой push в `main` независимо от тестов.
3. **GitHub → Settings → Branches:** сделать `main` default и включить защиту
   с обязательной проверкой CI.
4. **Railway → tutak-api → Variables → `SEED_ADMIN_PASSWORD`:** сменить пароль
   супер-админа, войти, сменить его в интерфейсе, затем снять `SEED_BASELINE`.
5. **Railway → Postgres → Backups:** проверить, что расписание включено.
6. **Sentry DSN и вебхук алертов** — задать переменные, если нужна телеметрия.
7. **Один запуск APK по чеклисту выше.**

## REMAINING BEFORE LAUNCH — только настоящие блокеры

1. Провайдер плиток (п. 1 выше) — без него карта коммерчески непригодна.
2. Ротация пароля супер-админа (п. 4) — пока она не сделана, админ-панель
   заблокирована `PasswordRotationGuard`.
3. Прогон чеклиста на живом телефоне (п. 7).

Всё остальное из списка — не блокеры: система работает и без них.

## FINAL VERDICT

**READY FOR PILOT.**

Не «READY FOR PRODUCTION» — и причина ровно одна, техническая: карта сейчас
стоит на плитках openstreetmap.org, чья политика использования прямо просит
приложения с реальным трафиком уйти к своему провайдеру. Код к этому готов и
переключается двумя переменными; пока они не заданы, коммерческий запуск
опирался бы на инфраструктуру, не предназначенную для него.

Для пилота в одном-двух филиалах этого достаточно: деньги, бонусы, рефералы,
возвраты и права доступа доказаны тестами на интегрированной системе, а не
по отдельным веткам.
