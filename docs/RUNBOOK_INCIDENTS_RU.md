# Runbook оператора TuTak — инциденты и спорные ситуации

Дата: 19.09.2026. Для человека, который дежурит по production. Каждый
раздел: симптом → что проверить → чего не делать → безопасное действие →
когда эскалировать. «Эскалировать» = владелец платформы (Arman) плюс, где
указано, второй человек с нужным правом.

Инструменты: Admin-панель (`/admin`), Railway (логи, переменные,
Backups), Partner-панель для проверки глазами партнёра, канал алертов.
Все действия с деньгами делаются через Admin/API, **никогда** прямыми
UPDATE в базе: триггеры и CHECK-констрейнты откажут, а если не откажут —
ledger разойдётся.

Общие запреты:
- не менять статусы покупок/попыток/расчётов в БД руками;
- не удалять строки из `ledger_*`, `psp_callback_inbox`, `outbox_events`;
- не включать `TUTAK_PSP_ENABLED`, `PSP_REFUNDS_ENABLED`,
  `CUSTOMER_PREPAID_TOPUP_ENABLED`, `DEMO_MODE`;
- не запускать `restore.sh --force-into` на production.

## 1. Спорная DIRECT-покупка («я не покупал» / «сумма не та»)

- **Симптом:** клиент или партнёр оспаривает покупку.
- **Проверить:** Admin → Payments/Purchases → покупка: статус, кто
  подтвердил (`confirmedByUserId`), время, сумма, ветка; Audit logs по
  кассиру; Partner-панель → транзакции того же периода.
- **Нельзя:** менять сумму или статус подтверждённой покупки (экономика
  заморожена триггером после подтверждения — это не обойти и не надо).
- **Действие:** если покупка ошибочна — возврат (раздел 4), не «отмена».
  Если верна — показать клиенту время и кассира.
- **Эскалировать:** если кассир подтверждал покупки без клиента (мошенничество)
  — владелец + отключение кассира (Admin → Users → деактивировать).

## 2. Ошибочный cashback

- **Симптом:** клиент говорит, что баллов больше/меньше, чем должно.
- **Проверить:** покупка → `bonus_lots` типа `ACCRUAL_PURCHASE` по ней;
  правило партнёра (`contribution rule`) на момент покупки — оно
  зафиксировано в покупке (`contributionRuleVersion`), текущее правило
  **не** влияет на прошлые покупки; `maxBonusPaymentPercent` партнёра.
- **Нельзя:** править `bonus_lots` руками; менять правило «задним числом»
  (оно и не применится).
- **Действие:** если ставка была неверна в правиле — корректировка через
  Admin → Bonus → Manual adjustment (`POST /wallet/admin/adjust`, право
  `WALLET_WRITE`, лимит `BONUS_MANUAL_ADJUSTMENT_MAX` = 1 000 000 по
  умолчанию, причина обязательна, пишется в audit как
  `BONUS_MANUAL_ADJUSTMENT`); затем исправить правило вперёд (proposal →
  approve вторым человеком).
- **Эскалировать:** расхождение больше одной покупки или у нескольких
  клиентов — стоп, владелец: это дефект правила или кода.

## 3. Ошибочный referral

- **Симптом:** реферер не получил награду или получил лишнюю.
- **Проверить:** `referral_invites` (кто кого привёл, `refereeUserId`
  уникален — второго реферера у клиента быть не может), покупка
  подтверждена ли, `bonus_lots` типа `ACCRUAL_REFERRAL` у реферера;
  self-referral не начисляется намеренно.
- **Нельзя:** создавать invite задним числом — награда начисляется в
  момент подтверждения покупки и не пересчитывается.
- **Действие:** только ручная корректировка через Admin → Bonus с причиной,
  после проверки, что правило действительно предполагало награду.
- **Эскалировать:** подозрение на фермы аккаунтов (много рефералов с
  одного устройства/номера-паттерна) — владелец; Admin → Fraud signals.

## 4. Возврат

- **Симптом:** клиент вернул товар/услугу партнёру.
- **Проверить:** покупка `CONFIRMED`; сколько уже возвращено
  (`refundedAmount`); маршрут — DIRECT (для PSP возврат сейчас невозможен и
  отказывается кодом).
- **Нельзя:** возвращать «баллами вместо денег»; делать возврат в БД.
- **Действие:** кассир создаёт refund request → владелец/менеджер партнёра
  одобряет (тот же человек одобрить не может); либо прямой refund
  владельцем партнёра. Платформа откатывает бонусы, реферальные и
  партнёрскую долю автоматически; деньги клиенту возвращает **партнёр** у
  кассы.
- **Эскалировать:** покупка старше периода расчёта и расчёт партнёру уже
  оплачен — владелец: возврат породит `deduction` в следующем расчёте,
  нужно предупредить партнёра.

## 5. Потерянный телефон

- **Симптом:** клиент потерял телефон с приложением.
- **Что реально умеет система (проверено по коду 19.09.2026):**
  - «выйти со всех устройств» кнопки в Admin **нет**;
  - refresh-сессии клиента отзываются автоматически при **смене пароля**
    (`POST /auth/change-password`) и при **сбросе пароля по SMS**
    (`POST /auth/password-reset/request` → `confirm`), а также при
    **деактивации** (Admin → Users → Deactivate: refresh отклоняется для
    неактивного аккаунта);
  - **деактивация действует мгновенно**: каждый запрос заново читает
    `isActive` (`UsersService.buildRequestUserClaims` → 401 «Account is no
    longer active»); после смены/сброса пароля чужой телефон теряет доступ
    в момент истечения access-токена — максимум через 15 минут.
- **Нельзя:** удалять аккаунт по телефонному звонку без верификации;
  просить клиента «назвать последние покупки» как подтверждение личности
  — это не верификация, а утечка.
- **Действие:** клиент на новом телефоне (та же SIM, номер восстановлен у
  оператора) делает **«Забыли пароль» → SMS-код → новый пароль**: это
  само отзывает все старые сессии. Если клиент не может — оператор
  **Deactivate** в Admin → Users (это блокирует и старый телефон, и
  самого клиента) и **Reactivate** после того, как клиент готов сбросить
  пароль. Каждая деактивация пишется в audit log (`ACCOUNT_LOCKED`).
- **Эскалировать:** номер тоже потерян — раздел 6.

## 6. Смена номера / утраченная SIM

- **Симптом:** клиент сменил номер или потерял SIM без восстановления.
- **Что реально умеет система:** **смены номера телефона нет** — ни в
  приложении (`verify-phone/*` подтверждает *текущий* номер, а не меняет
  его), ни в Admin (`PATCH users/:id` с полем `phone` не существует).
  Номер — идентификатор аккаунта.
- **Нельзя:** менять `phone` в базе руками (уникальный индекс, история
  OTP, audit — всё завязано на номер); «переносить баллы» ручным
  начислением без записи причины; верифицировать личность по имени и
  покупкам.
- **Действие в пилоте:** клиент регистрирует **новый аккаунт** на новом
  номере. Баллы со старого аккаунта в пилоте **не переносятся**: у
  оператора нет способа доказать, что звонящий — владелец старого
  номера. Старый аккаунт клиент может удалить сам, если помнит пароль
  (`DELETE /users/me` с паролем; 30 дней grace, потом анонимизация), либо
  Admin → Deactivate по решению владельца.
- **Если владелец решает перенести баллы** (не рекомендовано в пилоте):
  Admin → Bonus → Manual adjustment (право `WALLET_WRITE`, лимит
  `BONUS_MANUAL_ADJUSTMENT_MAX`, причина обязательна, пишется в audit):
  debit со старого кошелька, credit на новый — две записи, обе с одной
  причиной вида «перенос по решению владельца, тикет N». Решение
  принимает владелец лично, не оператор.
- **Эскалировать:** всегда владелец.

## 7. Партнёр говорит, что расчёт неверный

- **Симптом:** партнёр оспаривает выписку.
- **Проверить:** Partner-панель → Settlements → «Из чего состоит» (строки:
  дата, вид проводки, сумма); Admin → Settlements → detail; период и
  правило.
- **Нельзя:** править сумму расчёта; «доплачивать» вне расчёта.
- **Действие:** партнёр нажимает «Сообщить о проблеме» на выписке
  (`report-problem`) → расчёт переходит в `REQUIRES_RECONCILIATION` →
  два человека (propose → confirm) фиксируют исход. Если ошибка в наших
  строках — корректирующая проводка через Admin, следующий расчёт её
  учтёт.
- **Эскалировать:** любой случай, где расчёт уже `PAID` — владелец.

## 8. Зависшая PSP-оплата (когда Idram включат)

- **Симптом:** алерт `psp.attempt-unresolved` или клиент говорит «деньги
  списали, покупка не подтверждена».
- **Проверить:** Admin → Payments → unresolved attempts; inbox по счёту;
  кабинет Idram — есть ли платёж по `EDP_BILL_NO`.
- **Нельзя:** отмечать попытку FAILED «потому что давно»; подтверждать
  покупку руками; просить клиента заплатить ещё раз.
- **Действие:** если в кабинете Idram платёж есть — два человека с
  `PSP_RECONCILE`: propose → confirm с ссылкой на выписку; покупка
  подтвердится. Если платежа нет — то же, с исходом «не оплачено», клиент
  может платить снова.
- **Эскалировать:** любой случай — минимум два человека по конструкции;
  владелец в курсе каждого.

## 9. Ledger imbalance

- **Симптом:** алерт `reconciliation.drift`, `tutak_ledger_imbalance_amd ≠ 0`
  или Admin → Ledger показывает рассинхрон.
- **Проверить:** Admin → Reconciliation → последний прогон и findings;
  выплаты партнёрам, попавшим в findings, уже заблокированы автоматически.
- **Нельзя:** править балансы; запускать выплаты «вручную, чтобы не ждать».
- **Действие:** ничего не менять; собрать findings, время первого
  расхождения, последние деплои.
- **Эскалировать:** немедленно владелец + инженер. Это либо баг, либо
  ручное вмешательство в БД.

## 10. Dead-letter (inbox или outbox)

- **Симптом:** алерт `psp.callback-dead-letter:*` или `outbox.dead-letter`.
- **Проверить:** Admin → Payments → dead-lettered callbacks (`lastError`);
  Railway логи по времени; Sentry (когда включат).
- **Нельзя:** удалять строку; менять её статус в БД (обработанные строки
  защищены триггером неизменяемости — UPDATE откажет).
- **Что реально есть:** маршрута «повторить DEAD-строку» в API/Admin
  **нет**. DEAD означает 10 неудачных попыток; повтор — только инженер
  кодом (миграция/скрипт, который создаёт *новую* строку inbox с тем же
  payload), после того как причина из `lastError` устранена.
- **В пилоте:** `TUTAK_PSP_ENABLED` выключен, callback-inbox пуст по
  построению; outbox-обработчики (`payment.captured`,
  `roaming.margin.ledger_post`, `ev.contribution.ledger_post`,
  `transaction.completed`) работают; `outbox.dead-letter` в пилоте = баг
  кода, не «внешняя причина».
- **Эскалировать:** всегда инженер; клиент, чьи деньги в этой строке,
  ждёт — приоритет выше всего остального.

## 11. Недоступен API

- **Симптом:** приложение и панели не открываются; Railway показывает
  crashed/restarting; healthcheck `/health/ready` красный.
- **Проверить:** Railway → tutak-api → Deployments → логи последнего
  деплоя (миграция? переменные?); `/health/ready` → какая зависимость
  `error`; Postgres/Redis online?
- **Нельзя:** нажимать «Redeploy» много раз подряд; менять переменные
  наугад; откатывать миграции.
- **Действие:** если упал после деплоя — Railway → предыдущий успешный
  деплой → **Rollback** (миграции аддитивны, старый код работает с новой
  схемой). Если зависимость — разделы 12/13. Restart policy ALWAYS
  поднимет контейнер сама, когда зависимость вернётся.
- **Эскалировать:** дольше 10 минут или после rollback не поднялся —
  инженер.

## 11a. Красный CI на `main` (после включения Wait for CI)

- **Симптом:** merge в `main`, деплой в Railway висит WAITING, затем
  SKIPPED; production на старом коммите.
- **Что это значит:** так и должно быть — плохой коммит не доехал.
  Production остаётся на последнем SUCCESS. Ручной cancel не нужен.
- **Действие:** починить в новом PR → merge → у нового коммита свой run и
  свой deployment. Не нажимать «Deploy latest commit» вручную для красного
  коммита — это обходит защиту.
- **Если CI «cancelled»** (следующий push отменил предыдущий run): деплой
  отменённого коммита пропускается; ждать деплой следующего коммита.
- **Если WAITING дольше 2 часов:** Railway пропустит деплой; проверить, не
  завис ли workflow (Actions), перезапустить его — или merge fix.

## 12. Недоступен Postgres

- **Симптом:** `/health/ready` → `database: error`; алерт
  `readiness.database.unreachable`; API 503.
- **Проверить:** Railway → Postgres → статус, метрики (диск тома 5 ГБ —
  заполнен?), логи.
- **Нельзя:** удалять/пересоздавать сервис Postgres; менять `DATABASE_URL`;
  запускать restore поверх.
- **Действие:** Railway → Postgres → Restart. Если диск полон — увеличить
  том. Если данные повреждены — **PITR restore в новый сервис** (Backups →
  Restore to this moment), проверить данные, затем переключить
  `DATABASE_URL` на новый сервис.
- **Эскалировать:** любая потеря данных или restore — владелец + инженер до
  переключения.

## 13. Недоступен Redis

- **Симптом:** `/health/ready` → `redis: error`; алерт
  `readiness.redis.unreachable`; sweeps не идут (heartbeat).
- **Проверить:** Railway → Redis → статус, память.
- **Нельзя:** менять `REDIS_URL` на чужой Redis; удалять сервис.
- **Действие:** Railway → Redis → Restart. Потеря данных Redis безопасна:
  расписание sweeps пересоздаётся heartbeat'ом, подавление алертов и
  rate-limit'ы сбрасываются (возможны повторные страницы — это ожидаемо).
- **Эскалировать:** не поднимается за 10 минут — инженер.

## 14. Восстановление доступа — что оператор может обещать клиенту

Таблица честных ответов (по коду на 19.09.2026):

| Ситуация | Возможно? | Как |
|---|---|---|
| Забыл пароль, SIM на руках | да | приложение → «Забыли пароль» → SMS → новый пароль; все старые сессии отозваны |
| Потерял телефон, SIM восстановил | да | то же |
| Потерял телефон и SIM, номер не восстановить | **нет** | новый аккаунт на новом номере; баллы не переносятся (§6) |
| Сменил номер, старая SIM ещё работает | частично | войти со старой SIM, **потратить** баллы; смены номера в продукте нет |
| «Верните доступ по имени и списку покупок» | **нет, никогда** | это не верификация; отказ фиксируется |
| Удалить аккаунт | да, сам клиент | Настройки → удалить (пароль обязателен); 30 дней grace, потом анонимизация; доступ прекращается сразу |
| Оператор «выкинул» чужой телефон | да | Admin → Users → Deactivate, затем Reactivate после сброса пароля клиентом |

## Проверка канала алертов на production (без копирования секретов)

```bash
railway login                                  # один раз, на ноутбуке
railway ssh -p 901cf202-7c6a-4403-8853-56c36d684a53 -s tutak-api -e production -- node dist/scripts/alert-verify.js
```

Команда выполняется **внутри** production-контейнера API с его переменными
(`ALERT_WEBHOOK_URL` / `ALERT_TELEGRAM_*`, `REDIS_URL`): ничего не копируется
на ноутбук. Ожидание: `Sent through the webhook|telegram|webhook+telegram
channel (accepted at …)` и сообщение «TuTak alert channel test» в канале.
`exit 1` с текстом «no receiver accepted» — канал настроен, но приёмник
отказал (проверить URL / бот в группе / chat id). Скриншот сообщения —
в `docs/PILOT_GATES_2026-09-19.md`.

## Кто дежурит

Пока не назначен человек и канал `ALERT_WEBHOOK_URL`, этот runbook — текст
без адресата. Минимум для пилота: один человек с доступом в Railway и
Admin, читающий канал алертов, и второй с правами `PSP_RECONCILE` /
`CONTRIBUTION_RULE_APPROVE` для двухчеловечных действий.
