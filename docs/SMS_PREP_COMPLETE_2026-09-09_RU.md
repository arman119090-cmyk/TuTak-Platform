## 1. Совместимость: наблюдаемость OTP + Viva

**Этап B содержит этап A байт в байт** — проверено диффом по всем файлам
этапа A между `d23946e` и `df1fd99`: пусто.

**Найдено и исправлено: две записи результата терялись или уходили не туда.**

| путь | было | стало |
| --- | --- | --- |
| Лимит по адресу (`consume` бросает до всего остального) | **ни одной строки**, запрос кончался 429 в тишине — ровно то состояние, из-за которого вечер тестов оказался нечитаем | `otp <flow>: refused-address-rate-limit`, исключение пробрасывается неизменным |
| Лимит по номеру (5 кодов в час) | писалось `carrier-refused` — указывает на чужую систему | `otp <flow>: refused-number-rate-limit` |
| Прочий сбой до отправки (например, БД) | тоже `carrier-refused` | `failed-before-send` |

Классификация точна по построению: `requestCode` сам проглатывает отказ
карьера и отвечает `delivered: false`, поэтому всё, что из него **вылетает**,
случилось **до** отправки.

Полный набор исходов, по одной строке на запрос, ни один путь не молчит:

```
otp register: skipped-number-already-registered
otp register: code-handed-to-carrier
otp register: carrier-refused
otp register: refused-number-rate-limit
otp register: refused-address-rate-limit
otp register: failed-before-send
otp login:    skipped-no-eligible-account
otp login:    code-handed-to-carrier
otp login:    carrier-refused
otp login:    refused-number-rate-limit
otp login:    refused-address-rate-limit
otp login:    failed-before-send
```

Совместимость с Viva: при живом транспорте `RC != 0` и HTTP-отказ приводят к
отклонению из провайдера → `delivered: false` → `carrier-refused`. Успех →
`code-handed-to-carrier`. Ничего в цепочке не переопределяется.

## 5. Инструкция на вечер: что посмотреть в Railway

Ничего не менять — только посмотреть и записать.

### Шаг 1. Что вообще есть

В проекте TuTak на Railway выписать список сервисов и окружений (environments).
Для каждого сервиса API — какое у него окружение и какой публичный домен.

**Ключевой вопрос: существует ли окружение, отличное от production.**
Если все сервисы в одном окружении — значит staging на Railway нет, и
диагностическую сборку туда направлять нельзя.

### Шаг 2. Какие переменные там заданы (имена, не значения)

Достаточно выписать **имена** — значения не нужны и в переписку не идут:

```
APP_ENV                 ожидается staging (не production) для тестового
NODE_ENV
DATABASE_URL            задан / не задан
REDIS_URL               задан / не задан
CORS_ORIGINS            задан / не задан
MEDIA_PUBLIC_BASE_URL   задан / не задан
SMS_DRIVER              ← главный: задан ли, и какое значение
SMS_ENDPOINT            задан / не задан
VIVA_API_BASE_URL       задан / не задан
DEMO_MODE               задан / не задан
```

Из них **значения** нужны только для двух: `APP_ENV` и `SMS_DRIVER` — они не
секретны и решают, какой транспорт выберется.

### Шаг 3. Проверка соединения — три команды, ничего не меняют

```
1. curl -si https://<адрес-тестового-api>/health | head -20
2. в журнале сервиса найти строку при старте:   SMS transport: …
3. в журнале найти строку:                      APP_ENV / Bootstrap
```

Пункт 2 появится только **после** деплоя этапа A. Сейчас его там не будет — и
это само по себе ответ: значит на Railway работает код без наблюдаемости.

### Шаг 4. Порядок деплоя, когда адрес известен

1. Прислать мне адрес API тестового окружения.
2. Развернуть на нём этап A — коммит `d23946e`, ветка
   `deploy/staging-api-d23946e`.
3. Проверить: фактический SHA, `/health`, строка `SMS transport: …`.
4. **Пересобрать диагностический APK** с `API_BASE_URL` этого адреса — адрес
   зашивается при сборке, в установленном приложении не меняется. В шапке
   экспорта появится новый хост, по нему и будет видно, что сборка та.
5. Этап B — отдельным разрешением, после этого.

### Шаг 5. Полный откат

| что откатывать | как |
| --- | --- |
| Деплой этапа A на Railway | Deployments → предыдущий деплой → Redeploy/Rollback. Миграций в `d23946e` нет, БД не затрагивается |
| Переменные (если этап B) | снять **весь** набор Viva, не только `SMS_DRIVER`. Проверено: снятие одного `SMS_DRIVER` при заданном `VIVA_API_BASE_URL` выбирает `HttpSmsProvider` — он пойдёт без подписи HMAC, будет отклонён и при этом отрапортует `SMS transport: http`, то есть будет выглядеть рабочим |
