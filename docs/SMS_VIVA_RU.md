# SMS через Viva Business Hub — подключение

Интеграция реализована в коде. Чтобы она заработала, нужны реальные
credentials от Viva и один зарегистрированный шаблон. Ниже — что именно
сделано, что нужно от вас и как проверить.

Источник: integration document (4 страницы), присланный владельцем 2026-09-02.
Базовый адрес: `https://businesshubapi.viva.am/api/v1`.

---

## 1. Что делает Viva не так, как обычный шлюз

**Viva не принимает текст сообщения.** Отправка называет *шаблон*, заранее
зарегистрированный в профиле Viva (Templates/Text), и передаёт значения его
тегов. Формулировка живёт на стороне Viva и из нашего кода не задаётся.

Это главное архитектурное отличие. Наш прежний `HttpSmsProvider` отправлял
готовый текст — с Viva так нельзя. Поэтому:

* в порт `SmsMessage` добавлено поле `templateParams` — переменная часть
  сообщения (у нас всегда один элемент: шестизначный код);
* `body` остался и по-прежнему содержит полный текст — его использует
  обычный HTTP-шлюз и консольный транспорт в разработке;
* `VivaSmsProvider` **отказывается** отправлять сообщение без
  `templateParams`, вместо того чтобы молча отправить пустой шаблон.

Второе отличие: endpoint отправки — *батч*, получатели являются ключами
`params_data` (до 200 за вызов). Мы отправляем по одному получателю на вызов:
все три места отправки в коде доставляют код одному человеку, и объединять
чужие входы в один запрос незачем.

Третье: номера. Пример Viva — `93600600`, то есть 8 цифр **без** кода страны.
Мы храним `+374XXXXXXXX`. **Это единственный пример и никакого правила в
документе нет**, поэтому формат сделан обязательной настройкой
(`SMS_VIVA_NUMBER_FORMAT`) без значения по умолчанию: API не стартует, пока
формат не назван явно. Ошибка здесь невидима — номер в непонятной Viva форме
принимается в батч и просто никогда не доставляется, а единственный симптом:
клиент говорит, что код не пришёл.

## 2. Что реализовано

| Файл | Что |
|---|---|
| `apps/api/src/infrastructure/sms/viva-sms.provider.ts` | Провайдер: `token/get`, `token/refresh`-семантика, `transact/send/batch`, нормализация номера |
| `apps/api/src/infrastructure/sms/viva-sms.provider.spec.ts` | 18 тестов на формат запроса |
| `sms-provider.interface.ts` | `SmsMessage` с `templateParams` |
| `sms-transport.ts` | Выбор по `SMS_DRIVER=viva` + `missingVivaSettings` |
| `configuration.ts`, `.env.example` | Переменные |

Поведение, заложенное намеренно:

* **Токен кэшируется** и переиспользуется между отправками. Одна
  аутентификация на «пачку» одновременных отправок — иначе первый всплеск
  после рестарта шлёт по `token/get` на каждую отправку, а это ровно тот
  эндпоинт, который обычно лимитируют.
* **401 → один refresh, одна повторная попытка.** Второй 401 — это проблема
  учётных данных, а не протухший токен; цикл на нём превратил бы каждую
  отправку в два неудачных запроса.
* **Текст ошибки Viva не доходит до вызывающего** — он может называть аккаунт
  и шаблон. Пишется в лог, наружу уходит generic «временно недоступно».
* **Неполная конфигурация — отказ при старте, во всех окружениях**, с
  перечислением всех недостающих переменных сразу.

## 3. Чего в документе нет — и как это изолировано

Документ описывает четыре формы запроса и **больше ничего**. Ни одно
предположение не спрятано в коде: каждое вынесено в настройку или в
защищённый парсер.

| Чего нет | Что сделано |
|---|---|
| **Как предъявляется access token** | `SMS_VIVA_TOKEN_PLACEMENT`: `bearer` (по умолчанию) / `header:<Name>` / `body:<field>` / `query:<param>`. `bearer` — **вывод** из формы пары `token/get`+`token/refresh`, а не факт. Официального источника Viva Armenia по `businesshubapi.viva.am` найти не удалось; `developer.viva.com` — это Viva.com (Viva Wallet), **другая компания**, и про этот хост там ничего нет. Если первый живой вызов вернёт 401 при верных credentials — меняется переменная, а не код. |
| **Формат номера** | `SMS_VIVA_NUMBER_FORMAT`, обязателен, без значения по умолчанию. |
| **Формат ответов** | Ничего не читается без проверки типа. `readTransactionId` заглядывает максимум на один уровень в `data` и возвращает `null` на любой другой форме. Принятая по HTTP-статусу отправка считается отправленной. |
| **Время жизни токена** | Не выдумано. Кэш до первого 401. |
| **Коды ошибок** | В лог попадает только короткий идентификатор из поля, названного как код. |

### `/token/refresh` реализован

При 401 порядок такой, без циклов:

1. если есть `refresh_token` → `POST /token/refresh` (client_id, client_secret,
   refresh_token — как в документе);
2. если refresh не сработал или его нет → один полный `POST /token/get`;
3. **одна** повторная отправка.

Второй 401 — это проблема credentials или способа передачи токена, а не
протухший токен; повтор только удвоил бы отказы. Если refresh вернул новый
access, но не вернул новый refresh — старый refresh сохраняется: он
единственный, и выбрасывать его незачем.

### Что попадает в лог

Только: `HTTP <status>`, безопасный код ошибки, transaction id.

**Никогда:** тело ответа, текст сообщения, OTP, номер телефона, токены,
credentials. `safeProviderErrorCode` пропускает лишь значение вида
`^[A-Za-z0-9_.-]{1,64}$` из поля, названного как код — предложение не
проходит, даже если лежит в поле `code`. Это покрыто тестами, которые
проверяют, что в логе нет ни кода, ни номера, ни пароля.

## 4. Что нужно от вас

Из личного кабинета Viva:

1. **`client_id`** и **`client_secret`** — выдаёт Viva.
2. **Username и пароль партнёра** (в примере Viva username — это e-mail).
3. **Sender name** — зарегистрировать в разделе **Templates/Sender name**.
4. **Шаблон** — зарегистрировать в разделе **Templates/Text**. Он должен
   содержать **ровно один тег**, в который подставится код. Например:

   > `TuTak: Ваш код подтверждения {code}`
   > `TuTak: Ձեր հաստատման կոդը {code}`

   Точное имя тега задаёте вы в кабинете Viva; наш код передаёт значения
   позиционно, массивом из одного элемента.

**Важно:** один шаблон используется для всех трёх сценариев — вход по OTP,
подтверждение телефона и сброс пароля. Формулировка должна подходить всем
трём («код подтверждения», а не «код для входа»). Если Viva позволит и
понадобится разделить — скажите, добавлю второй шаблон для сброса пароля.

5. **Спросить у Viva формат номера получателя.** Один вопрос: писать
   `93600600`, `37493600600` или `+37493600600`? Без ответа API не стартует —
   намеренно.

## 5. Переменные

```
SMS_DRIVER=viva
SMS_ENDPOINT=https://businesshubapi.viva.am/api/v1
SMS_USERNAME=<username партнёра>
SMS_TOKEN=<пароль партнёра>            # секрет
SMS_SENDER=<Sender name из кабинета>
SMS_VIVA_CLIENT_ID=<client_id>
SMS_VIVA_CLIENT_SECRET=<client_secret> # секрет
SMS_VIVA_TEMPLATE_NAME=<имя шаблона>
SMS_VIVA_NUMBER_FORMAT=<national | msisdn | e164>   # спросить у Viva
SMS_VIVA_TOKEN_PLACEMENT=bearer                     # менять, если 401
SMS_GLOBAL_MAX_PER_HOUR=<из контракта>
SMS_GLOBAL_MAX_PER_DAY=<из контракта>
```

`SMS_AUTH_SCHEME` и `SMS_ENCODING` при `SMS_DRIVER=viva` не используются.

`SMS_VIVA_SEND_UTF=1` — армянский не помещается в GSM-7, а код внутри
нечитаемого сообщения бесполезен. Выключать только если Viva скажет иначе.

Глобальные лимиты — единственное, что ограничивает **счёт от оператора**, а не
охват одного атакующего. Взять числа из контракта.

## 6. Порядок проверки

Проверять **на staging**, не в production.

1. Задать переменные на `tutak-staging-api` (Render) и дождаться редеплоя.
2. В логах старта — не должно быть `SMS_DRIVER=viva but ... not set`.
3. Запросить код на **реальный номер** через приложение.
4. Смотреть в логи API. В логе будет только статус и безопасный код —
   ни номера, ни OTP, ни credentials там нет и не будет:
   * `Viva refused the credentials (HTTP 401...)` → неверные
     client_id / client_secret / логин / пароль.
   * `Viva rejected the message (HTTP 401...)` **дважды подряд** → скорее
     всего неверен способ передачи токена. Попробуйте
     `SMS_VIVA_TOKEN_PLACEMENT=body:access_token`, затем
     `header:X-Access-Token`. Код менять не нужно.
   * `Viva rejected the message (HTTP 422/400, code=...)` → чаще всего имя
     шаблона или sender name не совпадает с кабинетом. Код в логе —
     единственное, что Viva сообщила; полный текст ошибки намеренно не пишется.
   * SMS не пришла, но ошибок нет → почти наверняка `SMS_VIVA_NUMBER_FORMAT`.
     Перебрать `national` / `msisdn` / `e164`.
5. Кода нет ни в логах, ни в ответе API — это намеренно. Единственный способ
   проверить доставку — реальный телефон.

## 7. Что это НЕ включает

* **Production не трогали.** Ни одна production-переменная не задана, ни один
  деплой не выполнен.
* **Credentials не выдуманы.** В документе Viva приведены усечённые примеры
  (`qGejMFojqVuj...`, `password132`, `user@viva.am`) — это плейсхолдеры, и в
  репозиторий не попало ни одного значения.
* **Production guards не ослаблены.** Без `SMS_ENDPOINT` API в
  `APP_ENV=production` по-прежнему не стартует.
* **`/transact/show/progress` не реализован.** Мы отправляем по одному
  получателю и опираемся на HTTP-статус; опрос прогресса имеет смысл для
  батчей и может быть добавлен, если понадобится отчётность по доставке.
