## 2. Что сделано: PR #37 — двойной контроль (бэкенд)

Ветка `feat/refund-dual-control`, база `main`.

- Новая таблица `purchase_intent_refund_requests` и статус
  `PENDING / APPROVED / REJECTED`. Отдельная запись, а не статус на
  возврате: строка в таблице возвратов означает «деньги и бонусы уже
  двинулись», и ничего неодобренного там появляться не должно.
- Кассир (`PARTNER_STAFF`) создаёт заявку — **финансового эффекта нет
  никакого**. Владелец или управляющий одобряет либо отклоняет.
- **Тот, кто попросил, никогда не может сам одобрить** — проверка в
  сервисе, а не только в контроллере, поэтому роль тут не лазейка.
- Прямой возврат `POST /purchase-intents/:id/refund` теперь только
  владельцу/управляющему (был доступен любому персоналу). Оставлен для
  случая, который заявка не покрывает: владелец, которому некого просить.
- Частичный уникальный индекс: **одна нерешённая заявка на покупку**. Две
  одновременные заявки были бы написаны против остатка, который каждая из
  них вот-вот изменит.

### Два дефекта, которые нашли тесты, написанные вместе с кодом

**1. Двойной возврат.** Первая версия полагалась на ключ идемпотентности
`refund-request:<id>`. Но `PurchaseIntentRefund` уникален по
`(actorId, idempotencyKey)`, а scope идемпотентности — `...:<actorId>`,
то есть **на актора**. Владелец и управляющий, нажавшие одновременно, не
сталкивались ни с чем: клиенту возвращали дважды, 3000 превращались в 6000.

Исправление: решение **захватывается в базе** условным
`UPDATE ... WHERE status = 'PENDING'` до вызова движка, и движок всегда
вызывается с актором, **записанным в строке**, а не с тем, кто вызывает
сейчас. Захват может выиграть ровно один; любая последующая попытка —
ретрай, второй одобряющий, перезапуск после падения — использует того же
актора и тот же ключ, то есть читает уже проведённый возврат.

Порядок сознательный: если движок бросил ошибку, ничего не проведено и
захват отпускается обратно в `PENDING`; если процесс умер после коммита
движка, но до записи `refundId`, следующий вызов `approve()` дописывает
её и получает существующий возврат, а не второй.

**2. Охрана «одна заявка» не узнавала собственное нарушение** — сверяла
имя индекса, а Prisma вернула имя поля. Тот же класс ошибки, что и с
кодом покупки в PR #36; теперь распознаются обе формы.

### Ещё одно, пойманное проверкой дрейфа

Prisma по умолчанию ставит `SetNull` для необязательных связей, а миграция
объявляла `Restrict` для всех шести внешних ключей — схема и миграция
расходились на трёх нулевых. Разрешил **в пользу миграции**: эта строка —
запись о том, кто просил вернуть деньги и кто согласился; тихо обнулить
филиал или того, кто решил, значит стереть ровно ту часть, которая делает
её доказательством.

**Проверено:** 14 новых интеграционных тестов, зелёные три прогона подряд;
полный интеграционный набор **1107/1107 (82 набора)**; дрейфа нет на базе,
пересобранной только из миграций ветки; CI на `ee06a50` зелёный.

## 3. Что сделано: PR #38 — экран возвратов в партнёрской панели

Ветка `feat/refund-queue-ui`, база — ветка PR #37 (он ещё не влит).

Интерфейса возврата у партнёра не было вообще (`grep -rln -i refund
apps/partner/src` — пусто). Экран написан для двух разных людей:

- **кассир** видит завершённые продажи, выбирает ту, которую возвращают, и
  пишет причину; пустая сумма означает «всё, что ещё можно вернуть»;
- **владелец/управляющий** видит, что ждёт решения, с достаточным
  количеством данных в одной строке: сколько, почему, кто попросил, по
  какой продаже — и одобряет либо отказывает с пояснением.

Какая половина активна, решает `isPartnerApprover` — и **только для того,
что рисовать**: сервер откажет в любом случае, так что смысл в том, чтобы
не показывать кассиру кнопку, которая может ответить только 403.

### Три находки, не связанные с возвратами

1. **`PARTNER_ROLES` не включал `PARTNER_MANAGER`** — пользователь только с
   этой ролью не получал partnerId, и **весь дашборд** для него был пустым.
2. **В общем enum `Role` не было `PARTNER_MANAGER`** — ни один клиент не мог
   назвать роль, которую сервер выдаёт и проверяет.
3. **`PurchaseIntentDto` не отдавал `refundedAmount`** — нельзя было
   показать, сколько уже вернули, не запрашивая список возвратов по каждой
   строке.

Заодно эндпоинты заявок теперь отвечают DTO, а не сырыми строками Prisma:
деньги строкой (число в JSON не удержит 18,4 без вранья), даты — ISO.

**Проверено:** партнёрский набор **68/68** (6 новых), интеграционные по
затронутым файлам **63/63**, API unit **580/580**, админка **60/60**,
мобильный **416/416**, `eslint` и `pnpm -r typecheck` чистые, `demo/`
перегенерирован.
