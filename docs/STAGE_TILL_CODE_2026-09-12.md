## 2. Что найдено в заготовке и что я сделал иначе

Подход заготовки в основе правильный, и я его сохранил: колонка
`CHAR(4)`, уникальность обеспечивает база, а не приложение, повтор на
`P2002`, освобождение кода после терминального состояния.

**Изменил одно существенное решение.** Заготовка ставила два индекса:
уникальность по (филиал, код) и отдельно по (партнёр, код) для интентов
без филиала. Это оставляет дыру: кассир, назначенный на два филиала одной
сети, может ввести код, который прямо сейчас занят живой покупкой в
**каждом** из них, и поиск обязан выбирать между двумя строками. Сделал
один индекс — по (партнёр, код) среди `AWAITING_CONFIRMATION`. Двусмысленность
становится невозможной по построению, а 10 000 кодов — заведомо больше, чем
одна сеть может держать в ожидании внутри трёхминутного окна.

Второе: заготовка выдавала код, но не давала кассиру **никакого** способа
им воспользоваться — ни поиска, ни отображения. Добавил и то, и другое.

## 3. Что сделано: PR #36

Ветка `feat/purchase-intent-confirmation-code`, база `main`, PR
[#36](https://github.com/arman119090-cmyk/TuTak-Platform/pull/36).

- **Колонка** `confirmationCode CHAR(4)` + частичный уникальный индекс
  по активным интентам одной сети. У старых строк — `NULL`, и все места
  чтения трактуют это как «кода нет».
- **Выдача кода — «попыткой», а не «просмотром»**: случайное значение из
  CSPRNG, вставка, и при нарушении уникальности — новая попытка (до 12).
  Сначала прочитать занятые и выбрать свободный — это check-then-act: два
  клиента в один момент получили бы одинаковые цифры. Здесь аллокатором
  является сам индекс: держать код можно только владея строкой.
- **`CHAR(4)`, а не число**: 0042 и 42 — разные коды для человека,
  который читает их вслух, а целочисленная колонка ведущие нули не
  сохранит.
- **Почему это не «второй пароль»**: код — средство сопоставления. Поиск
  по нему требует аутентификации сотрудника, области партнёра и области
  филиала — ровно как очередь. Сам по себе код не даёт ничего.
- **`GET /purchase-intents/by-code`** — та же проверка прав, что у
  очереди, ищет только среди ожидающих, проверяет формат (`^\d{4}$`) до
  запроса в базу, и отказывает по филиалу на найденной строке. Объявлен
  **до** `@Get(':id')`, иначе параметр маршрута его перехватит.
- **Мобильное приложение**: на экране ожидания код показан крупно, с
  разрядкой и с доступным описанием по цифрам; ID покупки остался ниже и
  мелко — он нужен поддержке, а не очереди.
- **Партнёрская панель**: колонка кода в очереди плюс поле сужения по
  цифрам. Сужение **локальное**, а не через новый эндпоинт, и это
  осознанно: очередь уже содержит ровно те ожидающие покупки, которые
  этому кассиру разрешено видеть (сервер фильтрует по партнёру и филиалу),
  поэтому запрос к серверу добавил бы задержку, но не возможности.
  Эндпоинт — путь для клиента, который очередь не держит.

**Проверено локально:** интеграционный набор `purchase-intents` — **59/59**

артефакта нет вовсе.
