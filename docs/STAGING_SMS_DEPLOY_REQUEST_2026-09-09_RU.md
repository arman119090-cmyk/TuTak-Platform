### Сценарий A — регистрация, ~19:24, красная ошибка

**Запроса в этом времени на сервере нет.** Зато есть другое: в 15:23:52 UTC

приложения — **15 секунд** (`httpClient.ts:41`).

Точка отказа этого сценария: **запрос не дошёл до API, клиент отвалился по
таймауту, пока бесплатный сервис Render просыпался.** Красная ошибка —
клиентская, а не ответ API. Это **другая** причина, чем у запросов 1–4.

### Сценарий B — вход по коду, ~19:29, ошибки нет, СМС нет

**Записи на сервере нет, и это может значить две разные вещи.** Вывод по
регистрации сюда не переносится.

Причина неопределённости — в коде `AuthService.requestLoginOtp`:

```ts
const user = await this.usersService.findByPhone(dto.phone);
if (user && user.isActive && !user.deletedAt) {
  await this.authOtpService.requestCode(dto.phone, AuthOtpPurpose.LOGIN)…
}
return { success: true };
```

Если аккаунта с таким номером нет, метод **не делает ничего**: ни попытки
отправки, ни единой строки в журнале — и возвращает успех. Это защита от
перебора номеров, и она работает как задумано.

Два объяснения, оба совместимы с наблюдаемым:

1. **Запрос дошёл, аккаунта нет.** Регистрация ни разу не завершилась (СМС не
   приходили), поэтому номер не зарегистрирован. Тогда «нет ошибки, нет СМС» —
   штатное поведение, и никакого сбоя входа не существует.
2. **Запрос не дошёл**, как в сценарии A.

**Пробел обозначаю прямо: различить эти два случая по имеющимся данным
нельзя.** Различит первый же запрос после деплоя — новая строка
`SMS transport: …` при старте плюс, при живом транспорте, попытка отправки в
журнале. Просить владельца повторять попытки сейчас не нужно и я не прошу.

## 1.2 Реферальное поле перестало обвиняться зря — `57ea026`

Причина: одно состояние ошибки отдавалось тому полю, которое на шаге стоит
последним, а последним на первом шаге стоит **реферальный код**.

Это было не «почти правильно», а неправильно всегда:

- `handleSendCode` отправляет **только номер** — реферального кода в этом
  запросе нет вовсе;
- API вообще не умеет отвечать ошибкой на реферальный код:
  `ReferralService.createAttribution` на неизвестном коде делает
  `if (!code) return` — молчаливый no-op.

Стало три слота:

| слот | где показывается | когда заполняется |
| --- | --- | --- |
| `formError` | баннер с ролью `alert` над кнопкой | всё, что не вина одного поля |
| `codeError` | поле OTP | API отверг код |
| `referralError` | реферальное поле | **только** если код ошибки API начинается с `REFERRAL` |

Сегодня `referralError` не заполняется никогда — и это ровно то, что требуется:
правило записано исполняемым кодом, а не комментарием, и тот, кто когда-нибудь
введёт такой ответ API, получит подсветку поля даром.

Сбой транспорта (таймаут) отправляется в баннер отдельной веткой: если запрос
не дошёл, ничего из введённого не оценивалось, и помечать поле — значит винить
человека за сеть. При таймауте 15 с и засыпающем staging это не редкий путь, а
поведение первого же запроса после простоя.

Защита от перебора не тронута: наличие номера не раскрывается, OTP клиенту не
возвращается, ответ API не менялся.

## 1.3 Баннер, DEMO_MODE, доверенные прокси — `1e7f735`

**Баннер врал.** Строка `SMS codes are written to this log, not delivered.`
перестала быть правдой, когда консольный транспорт убрали из публичных
развёртываний: `DEMO_MODE` этого больше не даёт нигде. Тот, кто шёл искать код
в журнале по подсказке баннера, не находил ничего.

Теперь при каждом старте печатается **фактический** транспорт, прочитанный из
контейнера (то есть то, что реально собрано, а не пересчитанное из
переменных):

```
[SMS] SMS transport: viva
[SMS] SMS transport: unavailable — every verification and password-reset code will be REFUSED…   ← level: error
[SMS] SMS transport: console — codes are written to this log and not delivered. Local development only.   ← level: warn
```

Ложная строка из баннера убрана.

**DEMO_MODE.** Выставлен на staging **вручную в панели Render**, вопреки
`render.yaml`, первая строка которого гласит «This blueprint is staging only: no
DEMO_MODE». Он не влияет на выбор SMS-транспорта (проверено кодом: `demoMode`
участвует только в ветке production). Он влияет на платежи — песочный эквайер.
**Решение о нём — ваше**, я его не менял и в запрос на деплой не включаю.

**Доверенные прокси и лимиты — ничего не отключено и отключать не предлагаю.**
Сейчас `CLIENT_IP_STRATEGY` и `TRUST_PROXY` не заданы, поэтому per-IP лимиты OTP
**стоят down** — это состояние по умолчанию, выбранное безопасным: лучше снять
лимит, чем свалить всех вызывающих в одно ведро, где один клиент запирает
остальных. Действующими остаются лимит на аккаунт (5 кодов на номер в час) и
глобальный бюджет (500/час, 5000/сутки). Чтобы восстановить per-IP лимиты,
нужно **измерить** число хопов X-Forwarded-For на живом сервисе и выставить
`CLIENT_IP_STRATEGY=xff-depth` с `CLIENT_IP_TRUSTED_HOPS`; измерение без
работающего деплоя недостоверно, поэтому это отдельный шаг **после**, а не
внутри этого запроса.

## 2.3 Совместимость подготовленных доработок со шлюзом

Сверено построчно, а не по описанию:

| участок | клиент (`viva-sms.provider.ts`) | шлюз (`viva-gateway.mjs`) | вердикт |
| --- | --- | --- | --- |
| Заголовки | `X-TuTak-Timestamp/Nonce/Signature` | `x-tutak-timestamp/nonce/signature` | совпадают (HTTP-заголовки регистронезависимы) |
| Строка подписи | `[ts, nonce, METHOD, path, sha256hex(body)].join('\n')` | идентично | **байт в байт** |
| Алгоритм | HMAC-SHA256, hex | HMAC-SHA256, hex, сравнение с постоянным временем | совпадает |
| Метка времени | секунды | окно + кэш nonce от повторов | совпадает |
| Пути | 4 endpoint'а | `ALLOWED_PATHS`, остальное — 404 | совпадает |
| Upstream | — | `businesshubapi.viva.am` жёстко, `/api` | подмена хоста невозможна |

Прочее, что просили проверить, покрыто тестами самой ветки:

- **обязательные переменные** — `missingVivaSettings`, падение на старте с
  именем недостающей;
- **шаблон** — `VIVA_OTP_TEMPLATE_NAME`, без значения по умолчанию;
- **формат номера** — `national` / `msisdn` / `e164`, без значения по
  умолчанию **намеренно**: документ Viva показывает один пример и не
  формулирует правила, а номер в непонятной Viva форме принимается в пакет и
  не доставляется — отказ без симптомов;
- **обработка ответа Viva** — `safeProviderErrorCode`, `readTransactionId`
  (идентификатор сообщения), `applyAccessToken` (место токена);
- **OTP с ведущим нулём** — тест «keeps a leading zero by sending the code as
  digits rather than a number»: `012345` уходит строкой, а не числом `12345`;
- **параллельные отправки** и **невозможность реальной отправки из тестов**.

# 3. ТРЕБОВАНИЯ ДОСТУПА ПО УЧАСТКАМ МАРШРУТА

Предположение «Viva видит исходящий IP Render» **неверно, и на нём ничего не
строится**. Маршрут задуман именно так, чтобы этого не требовалось:

```
Render staging  ──HTTPS + HMAC──►  Contabo VPS  ──IPsec/IKEv2──►  Viva
 (адрес плавает)                  217.76.49.94                  217.76.0.20
```

| участок | чем доказывается право доступа | состояние |
| --- | --- | --- |
| Render → шлюз | **Подпись HMAC** в заголовках. Секрет не передаётся. Именно поэтому здесь не bearer-токен: на платформе без постоянного исходящего адреса нет сетевой идентичности, на которую можно опереться | код готов с обеих сторон, подписи совместимы |
| Шлюз → Viva | **IP-адрес VPS** `217.76.49.94`, зафиксированный в форме Viva, плюс сам туннель. Адрес Render Viva не видит и видеть не должен | конфиг готов, туннель не поднят |
| Туннель | PSK + крипто-параметры из подписанной формы | параметры подтверждены, **PSK на сервер не введён** |
| Viva API | `client_id` / `client_secret` Business Hub | **не выданы** |

**Вывод по пункту 3 задания: маршрут спроектирован и подготовлен, но не может
быть завершён отсюда.** Три оставшихся действия физически недоступны этой
сессии, и ни одно из них не про телефон владельца.
