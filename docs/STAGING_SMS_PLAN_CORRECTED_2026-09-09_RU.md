**Откат «снять только `SMS_DRIVER`» неверен.** Прогнал реальный
`selectSmsTransport` с полным набором переменных этапа B:

```
B.  этап B как настроен                        -> viva
R1. снять только SMS_DRIVER                    -> http     ← ошибка
R2. снять SMS_DRIVER + VIVA_API_BASE_URL       -> unavailable
```

бюджет. Правильный откат — **R3**, минимально допустимый — **R2**.

## 3. Что неизвестно из-за доступа — **NOT VERIFIED**

Ни одно из этого я не утверждаю ни в одну сторону.

| вопрос | почему NOT VERIFIED |
| --- | --- |
| Введён ли PSK на VPS | нет консоли: SSH (22) закрыт политикой egress сессии, учётных данных нет |
| Поднят ли туннель IPsec | то же |
| Запущен ли gateway на VPS | TCP 443 на `217.76.49.94` принимает соединение — и это всё. HTTP-запрос отсюда не проходит: прокси сессии отвечает 403 на CONNECT к голому IP. Открытый порт не доказывает, что за ним gateway |
| Принимает ли Viva исходящий адрес Render | обращения не было; меряется только с самого сервиса |
| Дошли ли запросы 19:24 / 19:29 до Render | **у сервиса нет request-логов вообще**: `list_log_label_values(type)` возвращает только `app`. Приложение пишет, лишь когда что-то делает |

**Холодный старт как причина красной ошибки на регистрации — гипотеза, не
установленная причина.** В её пользу: в 19:23:52 сервис холодно стартовал и был
готов к 19:24:17 (25 с только на Nest), а таймаут HTTP-клиента приложения —
15 с. Против: подтвердить конкретный запрос нечем, request-логов нет. Различить
«запрос дошёл до Render, но не до приложения» и «запрос не ушёл с телефона»
сейчас невозможно.

**Вход по коду 19:29 — два живых объяснения, выбрать нельзя.**
`AuthService.requestLoginOtp` при номере без активного аккаунта не делает
ничего, не пишет ни строки и отвечает успехом — это защита от перебора, и она
работает штатно. Поэтому «нет ошибки, нет СМС, нет записи» одинаково подходит
и под «аккаунта нет» (регистрация ни разу не завершилась), и под «запрос не
дошёл». Вывод по регистрации сюда не переношу.

**Это и чинит этап A.** После него каждый запрос пишет строку с requestId,
маршрутом и техническим результатом: `skipped-no-eligible-account`,
`skipped-number-already-registered`, `code-handed-to-carrier`,
`carrier-refused`. Без номера, кода и секретов; ответ клиенту не меняется, так
что оракулом наличия аккаунта это не становится.

## 5. Безопасный вариант деплоя и отката

### Последствия merge — проверено, шире одного сервиса

На ветке `claude/tutak-loyalty-mvp-e485jm` c `autoDeploy: commit` висят **три**
сервиса: `tutak-staging-api`, `tutak-staging-admin`, `tutak-staging-partner`.
Merge пересоберёт и перезапустит все три, включая два, которых правка не
касается. Плюс `ci.yml` (push в любую ветку). `docker-publish.yml` не
сработает — он только на `main` и теги.

### Поэтому: деплой без merge

**Развернуть ветку `claude/staging-sms-observability-20260909` на одном
сервисе**, не сливая её в базовую:

1. Render → `tutak-staging-api` → Settings → Build & Deploy → **Branch** →
   `claude/staging-sms-observability-20260909` → Save.
2. Дождаться автодеплоя (или Manual Deploy → Deploy latest commit).

Затрагивается ровно один сервис. Базовая ветка не меняется, admin и partner не
трогаются, ничего не пересобирается лишний раз.

**Состав этапа A — один коммит `5c28b95` над живым `f63b34f`.** Провайдер Viva
в него **не входит**: он не нужен, пока реальная отправка не включена, и
переносить его заранее — лишний риск без выгоды. Он ждёт в ветке этапа B.

Что входит и зачем именно сейчас:

| изменение | зачем до подключения отправки |
| --- | --- |
| Строка `SMS transport: …` при старте | сегодня живой транспорт не виден нигде; без этого проверять этап B нечем |
| Правка лживого баннера | он утверждает, что коды пишутся в журнал, — это неправда и уводит в сторону ровно на этой задаче |
| Строка результата на каждый запрос OTP | единственное, что различит «запроса не было» и «аккаунта нет» |
| Маскирование номера в журнале | сейчас staging пишет полные номера телефонов; это стоит выкатить само по себе |

**Настройки менять не нужно ни одной.** Транспорт останется `unavailable` — но
теперь об этом будет написано.

**Откат этапа A:** вернуть Branch на `claude/tutak-loyalty-mvp-e485jm` и
нажать Manual Deploy; либо Deploys → на `dep-daddj80ae00c73dqknag`
(коммит `f63b34f`) → Rollback. Миграций БД нет, откат чистый.

### Этап B — отдельным разрешением

Сначала попробовать **прямой путь**, тот самый, которым прошёл живой тест: он
не требует ни туннеля, ни VPS.

```
SMS_DRIVER=viva
VIVA_API_BASE_URL=https://businesshubapi.viva.am/api/v1
VIVA_CLIENT_ID, VIVA_CLIENT_SECRET, VIVA_USERNAME, VIVA_PASSWORD   ← уже есть
VIVA_SENDER_NAME=Tu-Tak
VIVA_OTP_TEMPLATE_NAME=Tu-Tak2
SMS_VIVA_NUMBER_FORMAT=national
SMS_VIVA_GATEWAY_SECRET                                            ← пусто
```

Единственное неизвестное — примет ли Viva исходящий адрес Render. Проверяется
одним запросом кода и стоит ничего. Если откажет по адресу — тогда и только
тогда нужен шлюз: `VIVA_API_BASE_URL` переставляется на адрес шлюза и
заполняется `SMS_VIVA_GATEWAY_SECRET`, а пункты 2–3 раздела 4 становятся
обязательными.

Ветка этапа B — `claude/staging-sms-viva-20260909` (5 коммитов над `f63b34f`,
включая этап A).

**Важно:** при любой незаданной переменной из списка приложение **не
стартует** и назовёт недостающую. Заводить все разом, одним сохранением.

**Откат этапа B — R3:** снять **весь** набор переменных выше, не только
`SMS_DRIVER`, и перезапустить. Проверено: транспорт вернётся в `unavailable`,
приложение стартует, вход по паролю продолжит работать. Снятие одного
`SMS_DRIVER` даёт `http` и **не является откатом**.
