### H3. Обрыв базы 19.09 17:31–17:33 UTC и «навсегда упавшие» фоновые задачи

Факт: сервис `Postgres` (production) получил новый деплой `e8b6faaf` в
17:31:48 UTC 19.09 (образ `postgres-ssl:18`, причина `deploy`). API в
17:32:50 потерял соединение (`Error in PostgreSQL connection: Closed`,
`Can't reach database server at postgres.railway.internal:5432`), к
17:33:05 связь вернулась. За эти секунды `SweepsProcessor` пометил две
задачи как `failed permanently after 0 attempt(s)` и «stopped retrying».

Две проблемы:

1. Политика повторов: «0 попыток → навсегда» при недоступной БД. Задачи
   `psp.process-callbacks` и `outbox.drain` сейчас не критичны (деньги
   выключены), но та же логика обслужит начисления и сверки. Нужно
   проверить в admin-метриках, что sweep-ы возобновились после 17:33
   (`SweepsHeartbeatService` пишет liveness), и поменять политику:
   недоступность БД — это retry с backoff, а не терминальная ошибка.
2. Почему production Postgres переразвернулся в 17:31: это время
   репетиции restore (рядом создан `Postgres-restored-20260919-1733` в
   17:35). Restore не должен трогать production. Вероятная причина —
   подключение bucket `Postgres-PITR` или изменение конфигурации сервиса
   из панели Railway. Владельцу проверить в Railway → Postgres →
   Deployments → `e8b6faaf` → причину. Пока не выяснено, повторных
   репетиций restore не делать.

Данных в production после обрыва не потеряно (0 покупок, 0 партнёров),
но с реальными данными такой рестарт — инцидент.
