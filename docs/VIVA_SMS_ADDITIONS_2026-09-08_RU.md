## 2. Конфликт `VIVA_*` и `SMS_*` — приоритет и отказ загрузиться

**Приоритет: `VIVA_*` выигрывает.** Это имена, которые владелец реально
заводит в Railway; `SMS_*` оставлены запасными, потому что их уже несут
`docs/RAILWAY_ENV_CONTRACT_RU.md` и staging-сервис на Render, а
переименование, тихо обесточивающее живой сервис, обнаруживается клиентом,
который не смог войти.

**Но если обе переменные заданы и значения различаются — процесс не
стартует.** `VIVA_SENDER_NAME=Tu-Tak` рядом с забытым `SMS_SENDER=TuTak` — это
не «предпочтение», которое надо разрешить: одно из двух значений оператор
считает настроенным, и молчаливый выбор любого из них означает, что часть
развёртываний отправляет SMS под именем, которого никто не выбирал. Ошибка
называет обе переменные и не содержит ни одного из значений — они могут быть
секретами.

Реализация: `oneOf(preferred, fallback, default)` в
`apps/api/src/config/configuration.ts`, применён к семи парам:

| Основное имя | Запасное |
|---|---|
| `VIVA_API_BASE_URL` | `SMS_ENDPOINT` |
| `VIVA_USERNAME` | `SMS_USERNAME` |
| `VIVA_PASSWORD` | `SMS_TOKEN` |
| `VIVA_SENDER_NAME` | `SMS_SENDER` |
| `VIVA_CLIENT_ID` | `SMS_VIVA_CLIENT_ID` |
| `VIVA_CLIENT_SECRET` | `SMS_VIVA_CLIENT_SECRET` |
| `VIVA_OTP_TEMPLATE_NAME` | `SMS_VIVA_TEMPLATE_NAME` |

Тесты (`apps/api/src/config/configuration.spec.ts`, 5 новых): берётся
`VIVA_*`, когда задан только он; читается `SMS_*`, когда развёртывание
настроено по-старому; совпадающие значения принимаются; расходящиеся значения
роняют загрузку с обоими именами в сообщении; в тексте ошибки нет ни одного из
двух значений.

## 3. OTP с ведущим нулём — **БЛОКЕР реального OTP-flow**

Живой тест владельца выполнен кодом `123456` и этот случай показать не мог.
Генератор `common/utils/crypto.ts:22` использует `padStart(6, '0')`, то есть
`012345` — реальный код платформы, **примерно каждый десятый**.

Шаблон `Tu-Tak2` подтверждён с числовым тегом `<n>`. Числа `012345` в JSON не
существует: отправка числом даёт `12345`. Клиент вводит то, что получил, и
получает отказ, который выглядит как его собственная опечатка и в логах не
отличим ни от чего.

Код отправляет такой параметр **строкой цифр**, а не числом (`vivaTemplateParam`).
**Живой доставкой строковый вариант не подтверждён.** Пока шаг 6
staging-инструкции не пройден, это фиксируется как **блокер реального
OTP-flow**, а не как закрытый риск.

Три решения, выбор за владельцем:

1. **Проверить на staging** (изменений в коде не требуется): запрашивать код,
   пока не придёт начинающийся с `0`, и убедиться, что он пришёл
   шестизначным и принимается формой.
2. **Попросить Viva перевести шаблон на строковый тег** — тогда ведущий ноль
   гарантирован контрактом, а не наблюдением.
3. **Исключить ведущий ноль в генераторе** — одна строка. Энтропия 10⁶ →
   9·10⁵ (≈0,15 бита); при пяти попытках и действующих rate limit это
   несущественно.

Вариант 3 **не выполнен**: это правка security-пути, а задание прямо
запрещает менять генерацию и проверку OTP без отдельного согласования.
Дополнять введённый пользователем код нулями код тоже не делает.

## 4. `RC` и то, что осталось неподтверждённым

`RC` проверяется в трёх местах: отправка, `/token/refresh`, `/token/get`.
HTTP 200 с `RC != 0` считается отказом; отсутствие `RC` отказом не считается.

Явно помечено как **НЕ ПОДТВЕРЖДЕНО** (в коде — комментарием, в
`docs/SMS_VIVA_RU.md` — отдельной таблицей):

| Пункт | Что делает код |
|---|---|
| Состав тела `POST /token/refresh` | Отправляются `client_id`, `client_secret`, `refresh_token`; пароль не отправляется. Отказ refresh не считается ошибкой — выполняется полный `token/get` |
| Время жизни access-токена | Никакой срок **не выдуман**: расписания обновления нет, обновление запускает только реальный 401 |
| Ротация refresh-токена | Если ответ не принёс нового refresh-токена, остаётся прежний. Ничего не предполагается о том, погашен ли он |
| Существуют ли успешные ответы с `RC != 0` | Такой ответ считается отказом. Первые живые отправки покажут |

Ни одно из этих значений не придумано и не зашито.

## 5. Один общий refresh, поздний 401 и ограничение при нескольких экземплярах

**Внутри процесса.** У кэшированной пары токенов есть номер поколения.
Отправка запоминает, каким именно токеном она воспользовалась, и при 401
сообщает это поколение обновлению. Отсюда три свойства:

* одна аутентификация на всплеск одновременных отправок;
* один общий `token/refresh` на все отправки, промахнувшиеся по одному и тому
  же токену — второй параллельный refresh, если Viva ротирует токены,
  предъявил бы уже погашенный;
* **поздний 401 о паре, которая уже заменена, обновление не запускает** — он
  получает текущую пару без сетевого вызова. Иначе поздняя жалоба на давно
  мёртвый токен выбрасывала бы рабочую пару, и следующие отправки получали бы
  отказ по-настоящему.

Concurrency-тесты (`viva-sms.provider.spec.ts`, describe «Viva under
concurrent sends», 6 тестов, маршрутизация ответов по эндпоинту, а не по
порядку вызовов):

| Тест | Что доказывает |
|---|---|
| authenticates once for a burst | 3 одновременные отправки → один `token/get` |
| refreshes once when several sends are rejected | 2 отказа по одному токену → один `token/refresh`, две повторные отправки |
| does not renew again for an already-replaced token | «поздний» 401 после завершившегося обновления → сетевых вызовов обновления **не добавляет** |
| shares one full re-authentication | refresh отвергнут → один общий `token/get`, не по одному на отправку |
| does not resend a message whose result is unknown | таймаут → ровно одна отправка |
| keeps a token that a send only found expired | следующая отправка использует новую пару |

Проверено, что тесты действительно ловят регрессию: при снятой проверке
поколения падает тест позднего 401; при снятом объединении — тесты общего
refresh и общей повторной аутентификации.

**Ограничение при нескольких экземплярах backend.** Всё вышеперечисленное
действует в пределах одного процесса. При нескольких репликам (Railway/Render
scale, blue-green, отдельный воркер) каждый экземпляр держит свою пару и
обновляет её независимо:

* число вызовов `token/get` и `token/refresh` растёт линейно по числу
  экземпляров — если Viva лимитирует эти эндпоинты, лимит достигается быстрее;
* если Viva ротирует refresh-токены (не подтверждено), обновление в одном
  экземпляре может погасить токен другого; тот получит отказ refresh и
  выполнит полный `token/get` — деградация, не поломка;
* общий кэш токенов в Redis намеренно не сделан: он превращает отказ Redis в
  отказ входа в систему. Это правка на случай, если Viva окажется
  чувствительна к числу аутентификаций, а не сейчас.

## 6. Повторные отправки и таймаут как неопределённый результат

Слоя очередей и ретраев вокруг отправки SMS в проекте нет: `AuthOtpService`,
`PhoneVerificationService` и `PasswordService` вызывают провайдер напрямую, вне
BullMQ. Проверено поиском по всем очередям и processor-ам.

Единственный повтор внутри провайдера — **один** после HTTP 401, то есть после
явного «токен не годится».

**Таймаут, обрыв соединения и нечитаемый ответ трактуются как неопределённый
исход и не повторяются.** Сообщение могло уйти: Viva могла принять батч и
отправить SMS до того, как оборвался ответ. Идемпотентного ключа в этом API
нет, поэтому автоматический повтор мог бы означать вторую SMS клиенту и вторую
строку в счёте. Отправка объявляется неудачной, клиент запрашивает код заново —
единственный путь, который не может привести к двойной оплате. Закреплено
тестом «does not resend a message whose result is unknown».

## 7. Маршрут: шлюз/VPN сохранён, прямым адресом не подменён

`infra/viva-gateway/README.md` описывает согласованную схему production:

`SMS_VIVA_GATEWAY_SECRET`; ни один заголовок аутентификации шлюза не тронут.

Ручной тест владельца выполнялся напрямую и этой схемы не отменяет — адрес
шлюза прямым адресом Viva на основании ручного теста **не подменён**.

**Правило для production:** если трафик идёт через шлюз, `VIVA_API_BASE_URL`
указывает **на шлюз**, а `SMS_VIVA_GATEWAY_SECRET` заполнен. Прямой адрес Viva
оставлен умолчанием только потому, что именно он подтверждён доставкой.

**Доступность Viva из среды разработки проверить не удалось:** исходящие
соединения этой среды идут через прокси, который отвечает `403` на
`CONNECT businesshubapi.viva.am:443`. Ни одного живого запроса к Viva из этой
работы не выполнено — ни к Viva напрямую, ни через шлюз.

## 8. Тесты не могут отправить настоящую SMS; в отчёте нет чувствительных данных

**Структурная гарантия.** `selectSmsTransport` при `NODE_ENV === 'test'`
возвращает `ConsoleSmsProvider` даже при полностью корректной конфигурации
Viva. «Учётных данных, вероятно, нет» — не гарантия: разработчик со
staging-окружением в шелле или CI-джоб, унаследовавший его, — это ровно тот
путь, которым тестовый прогон начинает писать реальным клиентам.

Guard стоит **после** проверок конфигурации, а не до них: ошибка в переменных
обязана падать в CI — именно там проверяется поведение при старте. Подменяется
транспорт, а не валидация. Закреплено двумя тестами: «hands back the console
transport under the test runner, credentials and all» и «still refuses a broken
Viva configuration under the test runner».

**Номер телефона больше не пишется в лог.** Найдено при выполнении этого
пункта: `auth-otp.service.ts:61` писал `Could not deliver OTP to +374…` при
любой неудаче доставки. На платформе, где номер и есть идентификатор аккаунта,
лог неудачных доставок — это список клиентов, а с подключённым живым
оператором эта строка перестала быть гипотетической: сбой у оператора пишет её
на каждую попытку входа. Добавлен `common/utils/phone-mask.ts`
(`+374******00` — хватает, чтобы связать две записи в одном инциденте, и не
хватает, чтобы восстановить номер). Тесты: `phone-mask.spec.ts` и
`auth-otp-logging.spec.ts` (лог не содержит ни номера, ни кода; вызывающему
по-прежнему отвечают одинаково — anti-enumeration не ослаблен).

Провайдер Viva не пишет в лог ни номер, ни код, ни пароль, ни client_secret,
ни access/refresh токены — только HTTP-статус, `RC` и короткий безопасный код
ошибки. Закреплено тестом «never logs a secret, a token, a code or a number».

**В этом отчёте и в коммитах нет** номеров, OTP-кодов, credentials и полных
ответов Viva. Ни один секрет не попал в git, тестовые fixtures или логи.

**Staging E2E** (полная инструкция — `docs/VIVA_SMS_INTEGRATION_2026-09-08_RU.md` §7):
номер выбирается явно, заранее, из числа принадлежащих владельцу; результат
теста фиксируется как «пришло/не пришло, шестизначный/нет», без записи самого
номера, кода, credentials и полных ответов Viva.
