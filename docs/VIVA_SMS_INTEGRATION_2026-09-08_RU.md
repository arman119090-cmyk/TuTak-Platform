## 2. Архитектура интеграции

Ничего параллельного не создано. Схема осталась прежней:

```
AuthOtpService / PhoneVerificationService / PasswordService
        │  send({ to, body, templateParams: [code] })
        ▼
   SMS_PROVIDER (порт)
        ▼
   BudgetedSmsProvider   ← глобальные лимиты SMS, общие для всех транспортов
        ▼
   selectSmsTransport()  ← решает по конфигурации, кто повезёт
        ├── viva     → VivaSmsProvider   (только при SMS_DRIVER=viva)
        ├── http     → HttpSmsProvider
        ├── публичное развёртывание без оператора → UnavailableSmsProvider
        └── dev/test → ConsoleSmsProvider
```

Три вызывающих места уже передавали `templateParams: [code]` — Viva не принимает
готовый текст, только имя шаблона и значения тегов. Поэтому подключение свелось
к исправлению провайдера, а не к правке потока: ни один rate limit, ни
anti-enumeration, ни логика проверки кода, ни защита регистрации не тронуты.

Внутри провайдера: один кэшированный access-токен на процесс, единственный
in-flight `token/get` (чтобы всплеск входов не устроил штурм эндпоинта
аутентификации), при 401 — один `token/refresh` и одна повторная отправка,
дальше отказ.

## 3. Переменные окружения

```
SMS_DRIVER=viva
VIVA_API_BASE_URL=https://businesshubapi.viva.am/api/v1
VIVA_CLIENT_ID=<из кабинета Viva>
VIVA_CLIENT_SECRET=<секрет>
VIVA_USERNAME=<логин партнёра>
VIVA_PASSWORD=<секрет>
VIVA_SENDER_NAME=Tu-Tak
VIVA_OTP_TEMPLATE_NAME=Tu-Tak2
```

Необязательные, уже с верными умолчаниями: `SMS_VIVA_NUMBER_FORMAT=national`,
`SMS_VIVA_SEND_UTF` (выкл.), `SMS_VIVA_TOKEN_PLACEMENT=bearer`,
`SMS_VIVA_GATEWAY_SECRET` (пусто = без Contabo-шлюза).

Старые имена (`SMS_ENDPOINT`, `SMS_USERNAME`, `SMS_TOKEN`, `SMS_SENDER`,
`SMS_VIVA_*`) продолжают работать как запасные: переименование, которое тихо
обесточивает уже настроенный сервис, обнаруживается клиентом, который не смог
войти.

## 5. Найденные проблемы и риски

### Р-1 (высокий, устранён в коде, но требует проверки) — OTP с ведущим нулём

Код генерируется через `padStart(6, '0')` (`common/utils/crypto.ts:22`), то есть
`012345` — реальный код этой платформы. В JSON нет числа `012345`: отправка
числом даёт `12345`. Клиент вводит то, что ему пришло, и получает отказ —
**примерно каждый десятый вход**, и выглядит это как опечатка пользователя.
Ваш ручной тест использовал `123456` и показать этого не мог.

Сделано: код уходит числом, когда это ничего не теряет, и строкой цифр, когда
ведущий ноль есть. **Строковый вариант живой доставкой не подтверждён** — это
шаг 6 инструкции ниже. Если Viva его не примет, альтернатива — одна строка в
генераторе, чтобы ведущий ноль не возникал (энтропия 10⁶ → 9×10⁵, ≈0,15 бита,
при лимитах и блокировке после пяти попыток это несущественно). Но это правка
security-пути, и решение ваше, а не моё.

### Р-2 (средний) — тело `/token/get` не подтверждено

Отправляется `scopes: ['transact']` — так написано в документе Viva. Вы
сообщили scope, но не форму поля. Если Viva ответит ошибкой про scope, это
правка в одну строку.

### Р-3 (средний) — `RC` теперь решает

Ответ с HTTP 200 и `RC != 0` считается отказом. Это правильно, но если у Viva
есть успешные ответы с ненулевым `RC` (например, «принято частично»), они
теперь будут считаться неудачей. Первые живые отправки покажут.

### Р-4 (низкий) — Contabo-шлюз не задействован

`VIVA_API_BASE_URL` указывает прямо на Viva. Подпись HMAC для шлюза в коде
осталась и включается заполнением `SMS_VIVA_GATEWAY_SECRET`. Если Viva требует
site-to-site VPN для production-трафика, прямой путь может работать сейчас и
перестать позже — это вопрос к Viva, не к коду.

### Р-5 (низкий) — четыре падения в `production-boot`

Не связаны с этой работой: касаются медиа-хранилища и PSP, воспроизводятся
идентично на чистом дереве на этой машине и зелёные на CI.

## 7. Инструкция для staging end-to-end теста

Выполнять **на staging**, не в production.

1. В переменных сервиса staging задать все восемь переменных из §3.
   `VIVA_CLIENT_SECRET` и `VIVA_PASSWORD` вводить прямо в дашборд — они не
   должны появиться ни в git, ни в переписке.
2. Дождаться редеплоя. В логах старта **не должно** быть строки
   `SMS_DRIVER=viva but ... is not set` — если она есть, в ней названа
   недостающая переменная.
3. В приложении запросить код на **реальный номер** через обычную регистрацию
   или вход по OTP.
4. Проверить, что SMS пришла и код в ней совпадает с тем, что принимает форма.
5. Посмотреть логи API. Там будет только статус, `RC` и безопасный код ошибки:
   * `Viva refused the credentials (HTTP 401…)` → неверные client_id /
     client_secret / логин / пароль;
   * `Viva rejected the message (HTTP 401…)` дважды подряд → способ передачи
     токена; попробовать `SMS_VIVA_TOKEN_PLACEMENT=body:access_token`, код
     менять не нужно;
   * `Viva rejected the message (HTTP 422…, RC=…)` → имя шаблона или sender
     name не совпадает с кабинетом;
   * `RC=…` при HTTP 200 → Viva отказала, сообщение не ушло;
   * SMS не пришла, ошибок нет → формат номера; проверить
     `SMS_VIVA_NUMBER_FORMAT`.
6. **Отдельно — проверка ведущего нуля (Р-1).** Повторять запрос кода до тех
   пор, пока не придёт код, начинающийся с `0` (в среднем один раз из десяти),
   и убедиться, что он пришёл **шестизначным** и принимается формой. Это
   единственная непроверенная часть контракта. Если такой код не приходит или
   приходит пятизначным — сообщите, закрою правкой генератора по вашему
   решению.
7. Проверить второй сценарий, использующий тот же транспорт: подтверждение
   телефона или сброс пароля.

## 8. Что требуется до production deploy

**Обязательно:**

1. Пройти staging-тест выше целиком, включая шаг 6.
2. Завести те же переменные в production отдельно от staging. Секреты
   production не должны совпадать со staging.
3. Решить вопрос Contabo-шлюза (Р-4): нужен ли Viva трафик изнутри туннеля.
   Если да — `VIVA_API_BASE_URL` меняется на адрес шлюза и добавляется
   `SMS_VIVA_GATEWAY_SECRET`.
4. Проверить `SMS_GLOBAL_MAX_PER_HOUR` и `SMS_GLOBAL_MAX_PER_DAY` против
   реального контракта с Viva — это единственное, что ограничивает счёт от
   оператора, а не охват одного атакующего.
5. Измерить `CLIENT_IP_TRUSTED_HOPS` на живом развёртывании и включить
   `CLIENT_IP_STRATEGY=xff-depth`: сейчас лимиты OTP по IP выключены, и с
   работающим SMS это перестаёт быть безобидным — счёт оплачиваете вы.
