# Готовность к запуску: три независимых объёма

Заменяет двухступенчатую схему READY-A / READY-B из
`READINESS_CHECKLIST_2026-09-21_RU.md`. Причина замены: та схема складывала в
один объём «оплата покупки через Idram», «предоплаченный баланс» и «POS», и из
неё следовало, что без предоплаченного баланса и POS денег через TuTak быть не
может. В коде это не так, и юридически это три разных вопроса.

---

## 0. Три объёма и одна отдельная возможность

| Объём | Что это | Что включает | Нужен ли предоплаченный баланс |
| --- | --- | --- | --- |
| **A. DIRECT_PARTNER** | Клиент платит партнёру напрямую (касса, его терминал). TuTak считает бонусы и взаиморасчёты | ничего из денежных флагов | Нет |
| **B. Оплата конкретной покупки через Idram** | Клиент платит за эту покупку внутри TuTak; деньги собирает провайдер, TuTak рассчитывается с партнёром | `TUTAK_PSP_ENABLED=true` | **Нет** |
| **C. Stored value / предварительное пополнение** | Клиент держит баланс в TuTak и тратит его | `CUSTOMER_PREPAID_TOPUP_ENABLED` (пополнение) и/или `CUSTOMER_PREPAID_PURCHASE_ENABLED` (трата) | Это и есть C |
| **POS** — отдельная интеграционная возможность, не условие A/B/C | Касса партнёра открывает покупку через M2M API, клиент забирает её по динамическому QR | `PARTNER_POS_PURCHASES_ENABLED=true` | Нет |

**B не требует C — это свойство кода, а не намерение.** Флаги разделены и
проверяются в разных местах:

- `purchase-funding.service.ts`: маршрут `TUTAK_PSP` отклоняется только по
  `features.tutakPspEnabled` (код проблемы `PROVIDER_DISABLED`);
- трата баланса отклоняется отдельно по `customerPrepaidPurchaseEnabled`
  (`PREPAID_DISABLED`), и при выключенном флаге квота показывает баланс как
  «недоступен», а не как ноль;
- пополнение — третий флаг (`customerPrepaidTopUpEnabled`), и его докблок
  прямо говорит, что «принимать депозиты, которые некому потратить» —
  состояние, в котором платформа быть не должна.

Иначе говоря: покупку можно оплатить через Idram, не заводя в TuTak ни одного
пользовательского кошелька с деньгами.

**Законность B не следует из наличия merchant API.** Наличие у провайдера
технической возможности собрать платёж и право TuTak собирать платёж в пользу
партнёра — разные вещи (marketplace-сбор, кто является получателем средств,
чей это оборот, чей фискальный документ). Это вопрос из
`05_OWNER_ACTIONS_RU.md`, а не вывод из документации API.

## 2. Объём A — DIRECT_PARTNER

Код в production (`369eda1`) уже это умеет; кандидат добавляет правдивые
экраны, тёмную тему, код приложения и исправления D01–D18 + D02/D05.

Нужно сверх §1: договор с партнёром пилота, параметры (ставка вклада,
потолок бонуса), обучение кассира, поддержка. Денежные флаги остаются
выключенными: `TUTAK_PSP_ENABLED`, `PSP_REFUNDS_ENABLED`,
`CUSTOMER_PREPAID_TOPUP_ENABLED`, `CUSTOMER_PREPAID_PURCHASE_ENABLED`,
`PARTNER_POS_PURCHASES_ENABLED`.

Блокирует: §1 п. 1, 4, 6, 7, 8.

## 3. Объём B — оплата покупки через Idram

Сверх §1 и §2:

| № | Пункт | Состояние |
| --- | --- | --- |
| B1 | Юридическая модель сбора средств в пользу партнёра, письменно | 🟡 владелец сообщил устно 22.09: **работаем как маркетплейс** — TuTak площадка-посредник, партнёр остаётся продавцом. Письменного подтверждения и ответа «чей фискальный чек» нет. См. `PREPAID_BALANCE_LEGAL_QUESTIONS_RU.md` |
| B2 | Договор с Idram + письменные ответы: checksum, `EDP_TRANS_ID`, повтор callback, запрос статуса, refund API, комиссия, сроки оплаты bill | 🔴 владелец ↔ Idram |
| B3 | Sandbox на staging: оплата, повтор callback, два callback с одним `EDP_TRANS_ID`, callback после cancel/timeout, EXPIRED → UNRESOLVED, refund | 🔴 ждёт B2 |
| B4 | Production-креды в Railway, таймауты `PSP_STALE_AFTER_MS`/`PSP_ESCALATE_EVERY_MS` по ответам Idram | 🔴 владелец |
| B5 | Первый реальный платёж под контролем: малая сумма, два человека сверяют ledger с кабинетом Idram | 🔴 |
| B6 | **D01 не должен уехать в production со старым кодом**: на `main` `psp.payment.captured` не входит в settleable-список, и включение `TUTAK_PSP_ENABLED` там означает, что захваты провайдера не попадут ни в один settlement | 🔴 снимается выкаткой кандидата |

B не требует ни одного пункта из §4 (C) и ни одного из §5 (POS).

## 4. Объём C — stored value

Отдельное юридическое и продуктовое решение, а не следующий технический шаг.
Вопросы: чем является баланс (предоплата услуг, электронные деньги, депозит),
кто хранит средства, как они возвращаются при закрытии аккаунта, какие
ограничения по суммам и идентификации. Пока нет письменного ответа,
`CUSTOMER_PREPAID_TOPUP_ENABLED` и `CUSTOMER_PREPAID_PURCHASE_ENABLED`
остаются выключенными. Код гибридной модели (`gross = bonus + prepaid +
external`) готов и проверен на PostgreSQL, но это именно код за флагом.

Документы по теме: `PREPAID_BALANCE_LEGAL_QUESTIONS_RU.md`,
`PREPAID_PSP_PROVIDER_REQUIREMENTS_RU.md`.

---

## 5. POS — отдельная возможность

`PartnerCheckout` (M2M API под `x-api-key`, одноразовый непрозрачный токен,
идемпотентность, ограничение ключа веткой и интеграцией — D11/D17) готов и
проверен интеграционными тестами. Нужен реальный интегратор и его тест на
sandbox. **Не является условием ни A, ни B, ни C** и включается своим флагом.

---

## 6. Вне объёма текущего запуска

Магазины приложений (Google Play / App Store), Google Pay, live EV roaming.
Ни один из них не входит в A/B/C и не блокирует пилот: APK раздаётся ссылкой,
оплата картой в приложении не используется, EV-роуминг выключен.
