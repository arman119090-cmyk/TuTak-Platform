## Сначала — три коротких действия, от которых зависит остальное

### 1. Проверить, использовался ли путь D01 в production (5 минут, read-only)

Вопрос: были ли на production захваты провайдера, которые не попали ни в один
settlement. Один запрос к production-БД, только чтение:

```sql
SELECT count(*) AS captures,
       min("postedAt") AS first_seen,
       max("postedAt") AS last_seen
  FROM ledger_transactions
 WHERE kind = 'psp.payment.captured';
```

- `0` — путь никогда не исполнялся, тема закрыта; D01 остаётся дефектом кода,
  который уедет исправленным вместе с кандидатом.
- `> 0` — напишите мне число и даты: нужно сверить эти суммы с тем, что
  партнёрам уже заплатили, до любого merge.

Почему не сделал я: чтение production-БД выходит за разрешённый список
read-only проверок в этом задании.

### 2. Подтвердить канал алертов (gate 4)

Обе переменные (`ALERT_TELEGRAM_BOT_TOKEN`, `ALERT_TELEGRAM_CHAT_ID`) заданы
на `tutak-api`, редеплоя не было. Доставка ни разу не подтверждена, и из моей
среды подтвердить её нельзя: egress-прокси отвечает 403 на CONNECT к
`api.telegram.org`. Три способа, любой на выбор:

- **С машины владельца** (быстрее всего): в репозитории
  `ALERT_TELEGRAM_BOT_TOKEN=… ALERT_TELEGRAM_CHAT_ID=5986297803 pnpm --filter
  @tutak/api alert:verify` → в Telegram должно прийти «TuTak alert channel
  test».
- **С GitHub Actions runner**: добавьте эти два значения в Secrets
  репозитория и скажите — я добавлю workflow с ручным запуском, который
  выполнит тот же `alert:verify`. Кода для этого пока нет: без секретов его
  нечем запускать.
- **С сервиса Railway** — требует деплоя кандидата (в `369eda1` канала
  Telegram нет вовсе).

До подтверждения: durable outbox (D05) гарантирует, что алерт дождётся канала
в базе. Он не гарантирует, что кто-то смотрит.

### 3. Открыть `/metrics` (`METRICS_TOKEN`)

Сейчас 403, переменной нет среди 38 имён сервиса. Без неё не видно ни
dead-letter, ни очереди недоставленных алертов, ни глубины sweep-очередей.
Действие: сгенерировать случайный токен, добавить `METRICS_TOKEN` в Railway,
сказать мне — проверю, что эндпоинт отвечает и что токен не попадает в логи.

production-bucket. Альтернатива — вы прогоняете сами по

## Решения, которые не мои

### 9. Правило возвратов

Строгая Model C (STAFF никогда не возвращает сам, любой возврат — через
второго менеджера) или исключение для solo-партнёра, где владелец и кассир —
один человек. Код сейчас реализует Model C.

Отдельно: DIRECT-возврат «Approved» означает «проводка сделана», а не «деньги
отданы из кассы». Нужно ваше слово, считается ли это завершённым возвратом
для клиента.

### 10. Юридическая модель сбора средств (объём B)

Кто является получателем средств при оплате покупки через Idram, чей это
оборот, чей фискальный документ, допустим ли marketplace-сбор. Наличие
merchant API у провайдера этого вопроса не решает.

### 11. Письменные подтверждения Idram (объём B)

checksum, `EDP_TRANS_ID`, повтор callback, запрос статуса, refund API,
комиссия за транзакцию, сроки оплаты bill. Список вопросов —
`IDRAM_ACTIVATION_CHECKLIST.md`; без ответов таймауты PSP останутся нашими
догадками.

### 12. Stored value (объём C)

Чем является баланс клиента юридически, кто хранит средства, как они
возвращаются при закрытии аккаунта, лимиты и идентификация. До письменного
ответа оба флага остаются выключенными.

### 13. Комиссии, взаимозачёт, отрицательная позиция, документы

Ставка вклада партнёра пилота, потолок бонуса, что происходит при
отрицательной позиции (партнёр должен TuTak), какие документы сопровождают
settlement.

### 14. Договоры и параметры пилотных партнёров

Кто участвует, на каких условиях, с какого дня.

### 15. Получатель алертов и ответственный за инциденты

Кто читает Telegram-канал, кто дежурит, за какое время реагирует. Технически
канал будет работать после п. 2; без человека это по-прежнему тишина.

### 16. Ежедневная сверка: назначить человека

Инструкция написана (`DAILY_RECONCILIATION_RU.md`). Нужен ответственный и
5 рабочих дней подряд с подписанным результатом.

### 17. Границы пилота и поддержка

Сколько партнёров, сколько клиентов, часы поддержки, что делаем при
расхождении.

### 18. Физическая приёмка APK

`06_DEVICE_ACCEPTANCE_RU.md`. Это подтверждает человек с телефоном в руках;
jest не подтверждает.
