# Нагрузочные сценарии

Запускаются [k6](https://k6.io). Бинарник один, без зависимостей, в CI не
ставится и в репозиторий не кладётся:

```bash
k6 run load/purchase-flow.js -e BASE_URL=https://staging.example/v1
```

## Чего эти сценарии НЕ делают

**Не запускаются против production.** Каждый из них создаёт покупки и
двигает бонусы — на боевой базе это настоящие записи в реестре, которые
потом придётся разбирать вручную. Сценарии требуют `BASE_URL`, у них нет
значения по умолчанию, и это сделано нарочно: забытый дефолт `localhost`
однажды окажется проброшенным туннелем.

**Не измеряют «сколько выдержит система».** Они измеряют, где именно она
перестаёт выдерживать, и это разные вопросы. Число RPS без указания, что
именно упёрлось — пул соединений, CPU, блокировка строки — не помогает
принять ни одного решения.

## Почему пороги такие

`http_req_failed` = 0 для денежных путей, а не «меньше 1%». Один процент
отказов на подтверждении покупки — это один покупатель из ста, стоящий у
кассы с непринятой оплатой; для него это не процент, а полный отказ.

`p(95) < 800ms` на чтениях и `p(95) < 1500ms` на записи: записи проходят
через транзакцию с проводками в реестре, и требовать от них скорости чтения
значит требовать не того.

## Что смотреть после прогона

Не только сводку k6. Одновременно — `pg_stat_activity` на базе: число
активных соединений и ожидающих блокировок. Известное узкое место контура —
пул соединений Prisma, и оно видно там, а не в отчёте генератора нагрузки
(см. §17 отчёта о денежном контуре: пять одновременных подтверждений
занимали все пять соединений и умирали на таймауте транзакции).
